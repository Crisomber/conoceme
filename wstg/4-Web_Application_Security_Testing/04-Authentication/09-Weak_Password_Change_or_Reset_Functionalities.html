Funcionalidades débiles de cambio o restablecimiento de contraseña

ID
WSTG-ATHN-09

Resumen

Para cualquier aplicación que requiera que el usuario se autentique con una contraseña, debe existir un mecanismo mediante el cual el usuario pueda recuperar el acceso a su cuenta si olvida su contraseña. Aunque a veces esto puede ser un proceso manual que implica contactar al propietario del sitio web o a un equipo de soporte, con frecuencia se permite a los usuarios realizar un restablecimiento de contraseña de autoservicio y recuperar el acceso a su cuenta proporcionando alguna otra evidencia de su identidad.

Dado que esta funcionalidad ofrece una vía directa para comprometer la cuenta del usuario, es fundamental que se implemente de forma segura.

Objetivos de la prueba

  • Determinar si la funcionalidad de cambio y restablecimiento de contraseña permite que se comprometan cuentas.

Cómo probar

Recopilación de información

El primer paso es reunir información sobre qué mecanismos existen para permitir al usuario restablecer su contraseña en la aplicación. Si hay múltiples interfaces en el mismo sitio (como una interfaz web, una aplicación móvil y una API), todas deben revisarse, por si ofrecen funcionalidad diferente.

Una vez establecido esto, determinar qué información se requiere para que un usuario inicie un restablecimiento de contraseña. Puede ser el nombre de usuario o la dirección de correo electrónico (ambos pueden obtenerse de información pública), pero también podría ser un ID de usuario generado internamente.

Consideraciones generales

Independientemente de los métodos específicos utilizados para restablecer contraseñas, hay una serie de áreas comunes que se deben considerar:

  • ¿El proceso de restablecimiento de contraseña es más débil que el proceso de autenticación?

    El proceso de restablecimiento de contraseña ofrece un mecanismo alternativo para acceder a la cuenta de un usuario y, por lo tanto, debería ser al menos tan seguro como el proceso de autenticación habitual. Sin embargo, puede ofrecer una vía más fácil para comprometer la cuenta, especialmente si utiliza factores de autenticación más débiles, como las preguntas de seguridad.

    Además, el proceso de restablecimiento de contraseña puede eludir el requisito de usar autenticación multifactor (MFA), lo que puede reducir sustancialmente la seguridad de la aplicación.

  • ¿Existe limitación de tasa (rate limiting) u otra protección contra ataques automatizados?

    Como con cualquier mecanismo de autenticación, el proceso de restablecimiento de contraseña debería contar con protección contra ataques automatizados o de fuerza bruta. Existen diversos métodos para lograrlo, como la limitación de tasa o el uso de CAPTCHA. Estos son especialmente importantes en funcionalidades que desencadenan acciones externas (como enviar un correo electrónico o un SMS), o cuando el usuario ingresa un token de restablecimiento de contraseña.

    También es posible protegerse contra ataques de fuerza bruta bloqueando la cuenta en el proceso de restablecimiento de contraseña tras cierto número de intentos consecutivos. Sin embargo, esto también podría impedir que un usuario legítimo pueda restablecer su contraseña y recuperar el acceso a su cuenta.

  • ¿Es vulnerable a ataques comunes?

    Además de las áreas específicas tratadas en esta guía, también es importante comprobar otras vulnerabilidades comunes como la Inyección SQL o el Cross-Site Scripting.

  • ¿El proceso de restablecimiento permite la enumeración de usuarios?

    Consulte la guía de Enumeración de cuentas para obtener más información.

Correo electrónico: envío de una nueva contraseña

En este modelo, al usuario se le envía una nueva contraseña por correo electrónico una vez que ha demostrado su identidad. Esto se considera menos seguro por dos razones principales:

  • La contraseña se envía al usuario sin cifrar.
  • La contraseña de la cuenta se cambia en el momento en que se realiza la solicitud, lo que en la práctica deja al usuario sin acceso a su cuenta hasta que reciba el correo. Mediante solicitudes repetidas, es posible impedir que un usuario pueda acceder a su cuenta.

Cuando se utiliza este enfoque, se deben revisar las siguientes áreas:

  • ¿Se obliga al usuario a cambiar la contraseña en el primer inicio de sesión?

    La nueva contraseña se envía por correo electrónico sin cifrar y puede permanecer en la bandeja de entrada del usuario indefinidamente si no elimina el correo. Por ello, se debe exigir al usuario que cambie la contraseña tan pronto como inicie sesión por primera vez.

  • ¿La contraseña se genera de forma segura?

    La contraseña debe generarse utilizando un generador de números pseudoaleatorios criptográficamente seguro (CSPRNG) y debe ser lo bastante larga para evitar la adivinación de contraseñas o los ataques de fuerza bruta. Para una experiencia segura y amigable para el usuario, debería generarse mediante un enfoque seguro de estilo frase de contraseña (es decir, combinando varias palabras), en lugar de una cadena de caracteres aleatorios.

  • ¿Se le envía al usuario su contraseña existente?

    En lugar de generar una nueva contraseña para el usuario, algunas aplicaciones le envían su contraseña existente. Este es un enfoque muy inseguro, ya que expone su contraseña actual por correo electrónico sin cifrar. Además, si el sitio es capaz de recuperar la contraseña existente, esto implica que las contraseñas se almacenan con cifrado reversible o (más probablemente) en texto plano sin cifrar, lo cual representa una grave debilidad de seguridad.

  • ¿Los correos se envían desde un dominio con protección contra suplantación?

    El dominio debería implementar SPF, DKIM y DMARC para evitar que los atacantes suplanten correos desde él, lo cual podría utilizarse como parte de un ataque de ingeniería social.

  • ¿Se considera que el correo electrónico es lo suficientemente seguro?

    Los correos electrónicos normalmente se envían sin cifrar y, en muchos casos, la cuenta de correo del usuario no estará protegida por MFA. También puede compartirse entre varias personas, en particular en un entorno corporativo.

    Hay que considerar si la funcionalidad de restablecimiento de contraseña basada en correo electrónico es apropiada, según el contexto de la aplicación que se está probando.

Correo electrónico: envío de un enlace

En este modelo, al usuario se le envía por correo electrónico un enlace que contiene un token. Luego puede hacer clic en este enlace y se le solicita ingresar una nueva contraseña en el sitio. Este es el enfoque más común para el restablecimiento de contraseña, pero es más complejo de implementar que el enfoque tratado anteriormente. Las áreas clave que se deben probar son:

  • ¿El enlace utiliza HTTPS?

    Si el token se envía por HTTP sin cifrar, un atacante podría interceptarlo.

  • ¿Se puede usar el enlace varias veces?

    Los enlaces deberían expirar después de utilizarse; de lo contrario, ofrecen una puerta trasera persistente a la cuenta.

  • ¿El enlace expira si no se utiliza?

    Los enlaces deberían tener un límite de tiempo. Cuánto tiempo es apropiado depende del sitio, pero rara vez debería ser más de una hora.

  • ¿El token es suficientemente largo y aleatorio?

    La seguridad del proceso depende por completo de que un atacante no pueda adivinar ni descubrir por fuerza bruta un token. Los tokens deben generarse con un generador de números pseudoaleatorios criptográficamente seguro (CSPRNG) y ser lo bastante largos como para que a un atacante le resulte impráctico adivinarlos o descubrirlos por fuerza bruta. Un mínimo de 128 bits (o 32 caracteres hexadecimales) es suficiente para hacer impráctico un ataque en línea de este tipo.

    Los tokens nunca deben generarse a partir de valores conocidos, como tomar el hash MD5 del correo electrónico del usuario con md5($email), ni utilizando GUID que pueden usar funciones PRNG inseguras o que, según el tipo, ni siquiera sean aleatorios.

    Los evaluadores también deben verificar cómo se almacenan en el servidor los tokens de restablecimiento de contraseña. Si los tokens de restablecimiento se almacenan en texto plano en la base de datos, un atacante que obtenga acceso a la base de datos podría reutilizarlos para restablecer las contraseñas de los usuarios. Una implementación más segura almacena una versión con hash del token y compara el hash durante la validación.

    Un enfoque alternativo a los tokens aleatorios es utilizar un token firmado criptográficamente, como un JWT. En este caso, deben realizarse las comprobaciones habituales de JWT (¿se verifica la firma?, ¿se puede usar el algoritmo "nONe"?, ¿se puede descubrir por fuerza bruta la clave HMAC?, etc.). Consulte la guía Testing JSON Web Tokens para obtener más información.

  • ¿El enlace contiene un ID de usuario?

    A veces el enlace de restablecimiento de contraseña puede incluir un ID de usuario además de un token, como reset.php?userid=1&token=123456. En este caso, podría ser posible modificar el parámetro userid para restablecer las contraseñas de otros usuarios.

  • ¿Se puede inyectar una cabecera host diferente?

    Si la aplicación confía en el valor de la cabecera Host y lo utiliza para generar el enlace de restablecimiento de contraseña, podría ser posible robar tokens inyectando una cabecera Host modificada en la petición. Consulte la guía Host Header Injection para obtener más información.

  • ¿El enlace está expuesto a terceros?

    Probar si el token de restablecimiento puede quedar expuesto a través de la cabecera HTTP Referer cuando la página de restablecimiento carga recursos de terceros.

    Cuando un enlace de restablecimiento de contraseña contiene el token en la URL, como https://example.com/reset?token=ABC123, el token puede incluirse en la cabecera HTTP Referer cuando la página carga recursos externos, como scripts de analítica, imágenes o JavaScript de dominios de terceros.

    Verificar si el token de restablecimiento se filtra a dominios externos inspeccionando las peticiones de red realizadas por la página de restablecimiento.

    1. Desencadenar una solicitud de restablecimiento de contraseña y abrir el enlace de restablecimiento.
    2. Inspeccionar las peticiones de red mediante las herramientas para desarrolladores del navegador o un proxy interceptor como Burp Suite o ZAP.
    3. Identificar las peticiones realizadas a dominios externos.
    4. Comprobar si la URL completa de restablecimiento, incluido el token, aparece en la cabecera Referer de estas peticiones.
    5. Comprobar si la página de restablecimiento establece una cabecera de respuesta Referrer-Policy apropiada.

    Si dominios de terceros reciben el token, un atacante que controle esos recursos puede capturarlo y restablecer la contraseña de la víctima.

  • ¿Los correos se envían desde un dominio con protección contra suplantación?

    El dominio debería implementar SPF, DKIM y DMARC para evitar que los atacantes suplanten correos desde él, lo cual podría utilizarse como parte de un ataque de ingeniería social.

  • ¿Se considera que el correo electrónico es lo suficientemente seguro?

    Los correos electrónicos normalmente se envían sin cifrar y, en muchos casos, la cuenta de correo del usuario no estará protegida por MFA. También puede compartirse entre varias personas, en particular en un entorno corporativo.

    Hay que considerar si la funcionalidad de restablecimiento de contraseña basada en correo electrónico es apropiada, según el contexto de la aplicación que se está probando.

Tokens enviados por SMS o llamada telefónica

En lugar de enviar un token por correo electrónico, un enfoque alternativo es enviarlo por SMS o mediante una llamada telefónica automatizada, que el usuario luego ingresará en la aplicación. Las áreas clave que se deben probar son:

  • ¿El token es suficientemente largo y aleatorio?

    Los tokens enviados de esta forma normalmente son más cortos, ya que están pensados para que el usuario los escriba manualmente, en lugar de estar incrustados en un enlace. Es bastante común que las aplicaciones utilicen seis dígitos numéricos, lo que solo ofrece ~20 bits de seguridad (viable para un ataque de fuerza bruta en línea), en lugar del token de correo electrónico, normalmente más largo.

    Esto hace mucho más importante que la funcionalidad de restablecimiento de contraseña esté protegida contra ataques de fuerza bruta.

  • ¿Se puede usar el token varias veces?

    Los tokens deben invalidarse después de utilizarse; de lo contrario, ofrecen una puerta trasera persistente a la cuenta.

  • ¿El token expira si no se utiliza?

    Como los tokens más cortos son más susceptibles a ataques de fuerza bruta, debería implementarse un tiempo de expiración más corto para limitar la ventana disponible para que un atacante lleve a cabo un ataque.

  • ¿Existen limitación de tasa y restricciones apropiadas?

    Enviar un SMS o desencadenar una llamada telefónica automatizada a un usuario es mucho más molesto que enviar un correo electrónico, y podría usarse para acosar a un usuario o incluso para llevar a cabo un ataque de denegación de servicio contra su teléfono. La aplicación debería implementar limitación de tasa para evitarlo.

    Además, los mensajes SMS y las llamadas telefónicas a menudo implican costos económicos para quien los envía. Si un atacante logra provocar el envío de una gran cantidad de mensajes, esto podría resultar en costos significativos para el operador del sitio web. Esto es especialmente cierto si se envían a números internacionales o de tarifa especial. Sin embargo, permitir números internacionales puede ser un requisito de la aplicación.

  • ¿Se considera que un SMS o una llamada telefónica es lo suficientemente seguro?

    Se han demostrado diversos ataques que permitirían a un atacante secuestrar efectivamente mensajes SMS, y existen opiniones contradictorias sobre si el SMS es lo bastante seguro para utilizarse como factor de autenticación.

    Normalmente es posible contestar una llamada telefónica automatizada con acceso físico a un dispositivo, sin necesidad de ningún tipo de PIN o huella digital para desbloquear el teléfono. En algunas circunstancias (como un entorno de oficina compartido), esto podría permitir a un atacante interno restablecer trivialmente la contraseña de otro usuario acercándose a su escritorio cuando este no se encuentra en la oficina.

    Hay que considerar si el SMS o las llamadas telefónicas automatizadas son apropiados, según el contexto de la aplicación que se está probando.

Preguntas de seguridad

En lugar de enviarle un enlace o una nueva contraseña, las preguntas de seguridad pueden utilizarse como mecanismo para autenticar al usuario. Esto se considera un enfoque débil y no debería utilizarse si existen mejores opciones.

Cambios autenticados de identidad y configuración

Si la aplicación admite la capacidad de modificar el identificador principal de una cuenta (como una dirección de correo electrónico o un número de teléfono) que se utiliza en las funcionalidades de cambio y restablecimiento de contraseña, se debería obligar al usuario a volver a autenticarse. Cuando el identificador principal utilizado en la funcionalidad de cambio de contraseña puede modificarse sin reautenticación, se permite eludir la reautenticación de la funcionalidad de cambio de contraseña. En general, cualquier cosa que afecte la seguridad de la cuenta (correo electrónico, MFA, configuración de respaldo, etc.) debería requerir reautenticación antes de poder modificarse.

Por ejemplo: una aplicación tiene un flujo de restablecimiento de contraseña que envía un enlace de restablecimiento a la dirección de correo electrónico de la cuenta. La aplicación también requiere reautenticación si se intenta cambiar la contraseña desde la perspectiva de un usuario autenticado. Si un atacante obtiene acceso a la cuenta (mediante una cookie robada, acceso físico al computador, etc.) y cambia la dirección de correo electrónico de la cuenta sin necesidad de reautenticarse, entonces el flujo de restablecimiento de contraseña puede utilizarse para cambiar la contraseña, eludiendo el flujo autenticado de cambio de contraseña.

Cambios de contraseña autenticados

Una vez que el usuario ha demostrado su identidad (ya sea mediante un enlace de restablecimiento de contraseña, un código de recuperación o iniciando sesión en la aplicación), debería poder cambiar su contraseña. Las áreas clave que se deben probar son:

  • Al establecer la contraseña, ¿se puede especificar el ID de usuario?

    Si el ID de usuario se incluye en la solicitud de restablecimiento de contraseña y no se valida, podría ser posible modificarlo y cambiar las contraseñas de otros usuarios.

  • ¿Se requiere que el usuario se reautentique?

    Si un usuario con sesión iniciada intenta cambiar su contraseña, se le debería pedir que se reautentique con su contraseña actual para protegerse contra un atacante que obtenga acceso temporal a una sesión desatendida. Si el usuario tiene MFA habilitado, normalmente se reautenticaría con este en lugar de con su contraseña.

  • ¿El formulario de cambio de contraseña es vulnerable a CSRF?

    Si no se requiere que el usuario se reautentique, podría ser posible llevar a cabo un ataque de CSRF contra el formulario de restablecimiento de contraseña, lo que permitiría comprometer su cuenta. Consulte la guía de Cross-Site Request Forgery para obtener más información.

  • ¿Se aplica una política de contraseñas robusta y eficaz?

    La política de contraseñas debería ser coherente en las funcionalidades de registro, cambio de contraseña y restablecimiento de contraseña. Consulte la guía de Métodos de autenticación débiles para obtener más información.

Corrección

Asegurarse de que:

  • Los flujos de cambio y restablecimiento de contraseña sean al menos tan robustos como la autenticación normal y no puedan eludir MFA.
  • Los tokens de restablecimiento tengan alta entropía, sean de un solo uso, de corta vida y se almacenen con hash; los enlaces de restablecimiento usen HTTPS y no se construyan a partir de una cabecera Host no confiable.
  • Las páginas de restablecimiento no filtren tokens a terceros mediante la cabecera Referer; establecer una Referrer-Policy apropiada y evitar recursos de terceros en esas páginas. Véase Other HTTP Security Header Misconfigurations.
  • Se apliquen limitación de tasa, reautenticación para los cambios sensibles de la cuenta, protección contra CSRF y una política de contraseñas coherente.
