Autenticación multifactor (MFA)

ID
WSTG-ATHN-11

Resumen

Muchas aplicaciones implementan la autenticación multifactor (MFA) como una capa adicional de seguridad para proteger el proceso de inicio de sesión. También se conoce como autenticación de dos factores (2FA) o verificación en dos pasos (2SV), aunque estrictamente no son lo mismo. MFA significa pedir al usuario que proporcione al menos dos factores de autenticación diferentes al iniciar sesión.

MFA añade complejidad adicional tanto a la funcionalidad de autenticación como a otras áreas relacionadas con la seguridad (como la gestión de credenciales y la recuperación de contraseñas), por lo que es crítico que se implemente de manera correcta y robusta.

Objetivos de la prueba

  • Identificar el tipo de MFA utilizado por la aplicación.
  • Determinar si la implementación de MFA es robusta y segura.
  • Intentar eludir la MFA.

Cómo probar

Tipos de MFA

MFA significa que se requieren al menos dos de los siguientes factores para autenticarse:

Factor Ejemplos
Algo que sabes Contraseñas, PIN y preguntas de seguridad.
Algo que tienes Tokens de hardware o software, certificados, correo electrónico*, SMS y llamadas telefónicas.
Algo que eres Huellas dactilares, reconocimiento facial, escaneo de iris, escaneo de la palma de la mano y factores de comportamiento.
Ubicación Rangos de IP de origen y geolocalización.

* El correo electrónico solo constituye realmente "algo que tienes" si la propia cuenta de correo está protegida con MFA. Por ello, debe considerarse más débil que otras alternativas como los certificados o TOTP, y puede no aceptarse como MFA según algunas definiciones.

Vale la pena señalar que exigir varios ejemplos de un único factor (como necesitar tanto una contraseña como un PIN) no constituye MFA, aunque puede ofrecer algunos beneficios de seguridad respecto de una simple contraseña y puede considerarse verificación en dos pasos (2SV).

Debido a la complejidad de implementar la biometría en un entorno basado en navegador, "Algo que eres" rara vez se utiliza en aplicaciones web, aunque se está comenzando a adoptar mediante estándares como WebAuthn. El segundo factor más común es "Algo que tienes".

Comprobar si hay elusiones de MFA

El primer paso para probar la MFA es identificar toda la funcionalidad de autenticación de la aplicación, que puede incluir:

  • La página principal de inicio de sesión.
  • Funcionalidad crítica para la seguridad (como deshabilitar la MFA o cambiar una contraseña).
  • Proveedores de inicio de sesión federado.
  • Endpoints de API (tanto de la interfaz web principal como de las aplicaciones móviles).
  • Protocolos alternativos (no HTTP).
  • Funcionalidad de prueba o depuración.

Deben revisarse todos los métodos de inicio de sesión para asegurar que la MFA se aplique de manera coherente. Si algunos métodos no requieren MFA, estos pueden ofrecer una forma sencilla de eludirla.

Si la autenticación se realiza en varios pasos, podría ser posible eludirla completando el primer paso del proceso de autenticación (ingresar el nombre de usuario y la contraseña) y luego forzando la navegación a la aplicación o realizando peticiones directas a la API sin completar la segunda etapa (ingresar el código de MFA).

Si la autenticación utiliza un proveedor OpenID Connect (OIDC) que permite flujos (o políticas) de autenticación personalizados, como Azure B2C, puede haber múltiples flujos definidos, algunos de los cuales pueden no requerir MFA. Por ejemplo, si la aplicación se autentica con un flujo llamado B2C_1_SignInWithMFA, se debe intentar manipularlo a B2C_1_SignIn, B2C_1_SignInWithoutMFA u otros valores similares.

En algunos casos, también puede haber elusiones de MFA implementadas intencionalmente, como no requerir MFA:

  • Desde direcciones IP específicas (que pueden ser falsificables mediante la cabecera HTTP X-Forwarded-For).
  • Cuando se establece una cabecera HTTP específica (como una cabecera no estándar como X-Debug).
  • Para una cuenta específica codificada de forma fija (hard-coded) (como una cuenta "root" o "breakglass").

Cuando una aplicación admite tanto inicios de sesión locales como federados, podría ser posible eludir la MFA si no hay una separación sólida entre estos dos tipos de cuentas. Por ejemplo, si un usuario registra una cuenta local y configura MFA para ella, pero no tiene MFA configurada en su cuenta del proveedor de inicio de sesión federado, un atacante podría volver a registrar (o vincular) una cuenta federada en la aplicación objetivo con la misma dirección de correo electrónico comprometiendo la cuenta del usuario en el proveedor de inicio de sesión federado.

Finalmente, si la MFA se implementa en un sistema diferente al de la aplicación principal (como en un proxy inverso, para proteger una aplicación heredada que no admite MFA de forma nativa), entonces podría ser posible eludirla conectándose directamente al servidor de aplicaciones del backend, como se explica en la guía sobre cómo mapear la arquitectura de la aplicación.

Comprobar la gestión de la MFA

La funcionalidad utilizada para gestionar la MFA desde dentro de la cuenta del usuario debe probarse en busca de vulnerabilidades, incluyendo:

  • ¿Se requiere que el usuario se reautentique para eliminar o cambiar la configuración de MFA?
  • ¿La funcionalidad de gestión de MFA es vulnerable a cross-site request forgery?
  • ¿Se puede modificar la configuración de MFA de otros usuarios mediante vulnerabilidades IDOR?

Comprobar las opciones de recuperación de la MFA

Muchas aplicaciones ofrecen a los usuarios una forma de recuperar el acceso a su cuenta si no pueden autenticarse con su segundo factor (por ejemplo, si han perdido su teléfono). Estos mecanismos a menudo pueden representar una debilidad significativa en la aplicación, ya que en la práctica permiten eludir el segundo factor de autenticación.

Códigos de recuperación

Algunas aplicaciones entregan al usuario una lista de códigos de recuperación o de respaldo cuando habilita la MFA, que pueden usarse para iniciar sesión. Estos deben comprobarse para asegurar que:

  • Sean lo suficientemente largos y complejos para protegerse contra ataques de fuerza bruta.
  • Se generen de forma segura.
  • Solo puedan usarse una vez.
  • Exista protección contra fuerza bruta (como el bloqueo de cuenta).
  • Se notifique al usuario (por correo electrónico, SMS, etc.) cuando se usa un código.

Consulte la sección "Backup Codes" de la Forgotten Password Cheat Sheet para más detalles.

Proceso de restablecimiento de la MFA

Si la aplicación implementa un proceso de restablecimiento de la MFA, este debe probarse de la misma manera que se prueba el proceso de restablecimiento de contraseña. Es importante que este proceso sea al menos tan robusto como la implementación de MFA de la aplicación.

Autenticación alternativa

Algunas aplicaciones permiten al usuario demostrar su identidad por otros medios, como el uso de preguntas de seguridad. Esto suele representar una debilidad significativa, ya que las preguntas de seguridad ofrecen un nivel de seguridad mucho menor que la MFA.

Contraseñas de un solo uso

La forma más común de MFA es la de las contraseñas de un solo uso (One-Time Passwords, OTP), que normalmente son códigos numéricos de seis dígitos (aunque pueden ser más largos o más cortos). Estos pueden ser generados tanto por el servidor como por el usuario (por ejemplo, con una aplicación de autenticación), o pueden generarse en el servidor y enviarse al usuario. Hay varias formas de proporcionar esta OTP al usuario, entre ellas:

Tipo Descripción
HMAC One-Time Password (HOTP) Genera un código basado en el HMAC de un secreto y un contador compartido.
Time-based One-Time Password (TOTP) Genera un código basado en el HMAC de un secreto y la hora actual.
Correo electrónico Envía un código por correo electrónico.
SMS Envía un código por SMS.
Teléfono Envía un código mediante una llamada de voz a un número de teléfono.

La OTP normalmente se ingresa después de que el usuario ha proporcionado su nombre de usuario y contraseña. Hay varias comprobaciones que se deben realizar, entre ellas:

  • ¿Se bloquea la cuenta tras múltiples intentos fallidos de MFA?
  • ¿Se bloquea la dirección IP del usuario tras múltiples intentos fallidos de MFA en diferentes cuentas?
  • ¿Se registran los intentos fallidos de MFA?
  • ¿Es el formulario vulnerable a ataques de inyección, incluida la inyección de comodines SQL?

Dependiendo del tipo de OTP utilizado, también hay otras comprobaciones específicas que se deben realizar:

  • ¿Cómo se envían las OTP al usuario (correo electrónico, SMS, teléfono, etc.)?
    • ¿Existe limitación de tasa para evitar que el spam por SMS/teléfono cause costos económicos?
  • ¿Qué tan robustas son las OTP (longitud y espacio de claves)?
  • ¿Durante cuánto tiempo son válidas las OTP?
  • ¿Son válidas varias OTP a la vez?
  • ¿Se pueden usar las OTP más de una vez?
  • ¿Las OTP están vinculadas a la cuenta de usuario correcta o es posible autenticarse con ellas en otras cuentas?

HOTP y TOTP

Los códigos HOTP y TOTP se basan en un secreto compartido entre el servidor y el usuario. En el caso de los códigos TOTP, normalmente se entrega al usuario en forma de código QR que escanea con una aplicación de autenticación (aunque también puede entregarse como un secreto de texto para que lo ingrese manualmente).

Cuando el secreto se genera en el servidor, debe comprobarse que sea suficientemente largo y complejo (RFC 4226 recomienda al menos 160 bits) y que se genere mediante una función aleatoria segura.

Cuando el secreto puede ser proporcionado por el usuario, se debe imponer una longitud mínima adecuada y comprobar la entrada frente a los ataques de inyección habituales.

Los códigos TOTP normalmente son válidos durante 30 segundos, pero algunas aplicaciones optan por aceptar varios códigos (como el anterior, el actual y el siguiente) para lidiar con las diferencias entre la hora del sistema en el servidor y en el dispositivo del usuario. Algunas aplicaciones pueden permitir múltiples códigos a ambos lados del actual, lo que puede facilitar a un atacante adivinar o descubrir el código por fuerza bruta. Códigos válidos Tasa de éxito tras 1 hora Tasa de éxito tras 4 horas Tasa de éxito tras 12 horas Tasa de éxito tras 24 horas

Correo electrónico, SMS y teléfono

Cuando los códigos son generados por el servidor y enviados al cliente, se deben considerar las siguientes áreas:

  • ¿El mecanismo de transporte (correo electrónico, SMS o voz) es lo suficientemente seguro para la aplicación?
  • ¿Los códigos son suficientemente largos y complejos?
  • ¿Los códigos se generan mediante una función aleatoria segura?
  • ¿Durante cuánto tiempo son válidos los códigos?
  • ¿Son válidos varios códigos a la vez o la generación de un nuevo código invalida el anterior?
    • ¿Podría usarse esto para bloquear el acceso a una cuenta solicitando códigos repetidamente?
  • ¿Existe suficiente limitación de tasa para evitar que un atacante solicite grandes cantidades de códigos?
    • Grandes cantidades de códigos enviados por correo pueden hacer que el servidor sea bloqueado por enviar spam.
    • Grandes cantidades de SMS o llamadas de voz pueden costar dinero o utilizarse para acosar a un usuario.

Aplicaciones móviles y notificaciones push

Un enfoque alternativo a los códigos OTP es enviar una notificación push al teléfono móvil del usuario, que este puede aprobar o denegar. Este método es menos común, ya que requiere que el usuario instale un autenticador específico de la aplicación.

Evaluar adecuadamente la seguridad de esto requiere ampliar el alcance de las pruebas para cubrir tanto la aplicación móvil como cualquier API o servicio de apoyo que utilice; lo que significa que a menudo quedaría fuera del alcance de una prueba tradicional de aplicaciones web. Sin embargo, hay un par de comprobaciones sencillas que se pueden realizar sin probar la aplicación móvil, entre ellas:

  • ¿La notificación proporciona suficiente contexto (direcciones IP, ubicación, etc.) para que el usuario tome una decisión informada sobre si aprobarla o denegarla?
  • ¿Existe algún tipo de mecanismo de desafío y respuesta (como mostrar un código en el sitio que el usuario deba ingresar en la aplicación, a menudo llamado "number matching" o "number challenge")?
  • ¿Existe alguna limitación de tasa o mecanismo para evitar que se inunde al usuario con notificaciones con la esperanza de que acepte una a ciegas?

Filtrado por dirección IP y ubicación

Uno de los factores que a veces se utilizan con la MFA es la ubicación ("algún lugar donde estás"), aunque es discutible si esto constituye un factor de autenticación propiamente dicho. En el contexto de una aplicación web, esto normalmente significa restringir el acceso a direcciones IP específicas o no solicitar un segundo factor al usuario siempre que se conecte desde una dirección IP de confianza específica. Un escenario común sería autenticar a los usuarios solo con su contraseña cuando se conectan desde los rangos de IP de la oficina, pero exigir un código OTP cuando se conectan desde otro lugar.

Dependiendo de la implementación, podría ser posible que un usuario falsifique una dirección IP de confianza estableciendo la cabecera X-Forwarded-For, lo que podría permitirle eludir esta comprobación. Considérese también que, si la aplicación no sanea correctamente el contenido de esta cabecera, también podría ser posible llevar a cabo aquí ataques como la Inyección SQL. Si la aplicación admite IPv6, esto también debe comprobarse para asegurar que se apliquen las restricciones apropiadas a esas conexiones.

Además, deben revisarse las direcciones IP de confianza para asegurar que no presenten debilidades, como cuando incluyen:

  • Direcciones IP a las que podrían acceder usuarios no confiables (como las redes inalámbricas de invitados en una oficina).
  • Direcciones IP asignadas dinámicamente que podrían cambiar.
  • Rangos de redes públicas donde un atacante podría alojar su propio sistema (como Azure o AWS).

Certificados y tarjetas inteligentes

Transport Layer Security (TLS) se utiliza comúnmente para cifrar el tráfico entre el cliente y el servidor y para ofrecer un mecanismo con el que el cliente confirma la identidad del servidor (comparando el Common Name (CN) o el Subject Alternative Name (SAN) del certificado con el dominio solicitado). Sin embargo, también puede ofrecer un mecanismo para que el servidor confirme la identidad del cliente, conocido como autenticación con certificado de cliente o TLS mutuo (mTLS). Una discusión completa de la autenticación con certificado de cliente queda fuera del alcance de esta guía, pero el principio clave es que el usuario presenta un certificado digital (almacenado en su equipo o en una tarjeta inteligente), que el servidor valida.

El primer paso al probar es determinar si la aplicación objetivo restringe las Autoridades de Certificación (CA) en las que se confía para emitir certificados. Esta información puede obtenerse con diversas herramientas o examinando manualmente el handshake de TLS. La forma más sencilla es usar s_client de OpenSSL:

$ openssl s_client -connect example:443
[...]
Acceptable client certificate CA names
C = US, ST = Example, L = Example, O = Example Org, CN = Example Org Root Certificate Authority
Client Certificate Types: RSA sign, DSA sign, ECDSA sign

Si no hay restricciones, podría ser posible autenticarse usando un certificado de una CA diferente. Si hay restricciones pero están mal implementadas, podría ser posible crear una CA local con el nombre correcto ("Example Org Root Certificate Authority" en el ejemplo anterior) y usar esta nueva CA para firmar certificados de cliente.

Si se puede obtener un certificado válido, también debe verificarse que el certificado solo pueda utilizarse para el usuario al que fue emitido (es decir, que no se pueda usar un certificado emitido a Alice para autenticarse en la cuenta de Bob). Además, deben comprobarse los certificados para asegurar que no hayan expirado ni sido revocados.

Casos de prueba relacionados

  • Mecanismo de bloqueo débil
  • Funcionalidades débiles de cambio o restablecimiento de contraseña

Corrección

Asegurarse de que:

  • La MFA esté implementada para todas las cuentas y funcionalidades relevantes de las aplicaciones.
  • Los métodos de MFA admitidos sean apropiados para la aplicación.
  • Los mecanismos utilizados para implementar la MFA estén adecuadamente protegidos y resguardados contra ataques de fuerza bruta.
  • Exista auditoría y registro apropiados para toda la actividad relacionada con la MFA.

Consulte la OWASP Multi-Factor Authentication Cheat Sheet para más recomendaciones.
