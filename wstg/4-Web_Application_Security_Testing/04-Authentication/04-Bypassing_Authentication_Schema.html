Elusión del esquema de autenticación

ID
WSTG-ATHN-04

Resumen

En seguridad informática, la autenticación es el proceso de intentar verificar la identidad digital del emisor de una comunicación. Un ejemplo común de este proceso es el inicio de sesión. Probar el esquema de autenticación significa entender cómo funciona el proceso de autenticación y usar esa información para eludir el mecanismo de autenticación.

Aunque la mayoría de las aplicaciones requieren autenticación para acceder a información privada o ejecutar tareas, no todos los métodos de autenticación son capaces de ofrecer una seguridad adecuada. La negligencia, la ignorancia o la simple subestimación de las amenazas de seguridad suelen dar como resultado esquemas de autenticación que se pueden eludir simplemente saltándose la página de inicio de sesión y llamando directamente a una página interna que se supone solo debería ser accesible después de haber realizado la autenticación.

Además, a menudo es posible eludir las medidas de autenticación manipulando las peticiones y engañando a la aplicación para que piense que el usuario ya está autenticado. Esto puede lograrse modificando el parámetro de la URL, manipulando el formulario o falsificando sesiones.

Los problemas relacionados con el esquema de autenticación pueden encontrarse en diferentes etapas del ciclo de vida de desarrollo de software (SDLC), como las fases de diseño, desarrollo e implementación:

  • En la fase de diseño, los errores pueden incluir una definición incorrecta de las secciones de la aplicación que se deben proteger, la decisión de no aplicar protocolos de cifrado robustos para asegurar la transmisión de las credenciales, y muchos más.
  • En la fase de desarrollo, los errores pueden incluir la implementación incorrecta de la funcionalidad de validación de entrada o no seguir las mejores prácticas de seguridad para el lenguaje específico.
  • En la fase de implementación (despliegue) de la aplicación, puede haber problemas durante la puesta en marcha (actividades de instalación y configuración) debido a la falta de las habilidades técnicas necesarias o a la falta de buena documentación.

Objetivos de la prueba

  • Asegurar que la autenticación se aplique en todos los servicios que la requieren.

Cómo probar

Existen varios métodos para eludir el esquema de autenticación utilizado por una aplicación web:

  • Modificación de parámetros
  • Predicción del ID de sesión
  • Inyección SQL

Modificación de parámetros

Otro problema relacionado con el diseño de la autenticación se da cuando la aplicación verifica un inicio de sesión exitoso con base en parámetros de valor fijo. Un usuario podría modificar estos parámetros para obtener acceso a las áreas protegidas sin proporcionar credenciales válidas. En el ejemplo siguiente, el parámetro "authenticated" se cambia a un valor de "yes", lo que permite al usuario obtener acceso. En este ejemplo, el parámetro está en la URL, pero también podría usarse un proxy para modificar el parámetro, especialmente cuando los parámetros se envían como elementos de formulario en una petición POST o cuando se almacenan en una cookie.

Predicción del ID de sesión

Muchas aplicaciones web gestionan la autenticación mediante identificadores de sesión (session IDs). Por lo tanto, si la generación del ID de sesión es predecible, un usuario malicioso podría encontrar un ID de sesión válido y obtener acceso no autorizado a la aplicación, suplantando a un usuario previamente autenticado.

Comparación laxa de PHP

Si un atacante ha logrado obtener el código fuente de la aplicación explotando una vulnerabilidad descubierta previamente (p. ej., directory traversal) o desde un repositorio web (aplicaciones de código abierto), podría ser posible realizar ataques refinados contra la implementación del proceso de autenticación.

En el siguiente ejemplo (PHPBB 2.0.12 - Vulnerabilidad de elusión de autenticación), en la línea 2 la función unserialize() analiza una cookie proporcionada por el usuario y establece valores dentro del arreglo $sessiondata. En la línea 7, el hash MD5 de la contraseña del usuario almacenado en la base de datos del backend ($auto_login_key) se compara con el proporcionado por el usuario ($sessiondata['autologinid']).

1. if (isset($HTTP_COOKIE_VARS[$cookiename . '_sid'])) {
2.     $sessiondata = isset($HTTP_COOKIE_VARS[$cookiename . '_data']) ? unserialize(stripslashes($HTTP_COOKIE_VARS[$cookiename . '_data'])) : array();
3.     $sessionmethod = SESSION_METHOD_COOKIE;
4. }
5. $auto_login_key = $userdata['user_password'];
6. // We have to login automagically
7. if( $sessiondata['autologinid'] == $auto_login_key )
8. {
9.     // autologinid matches password
10.     $login = 1;
11.     $enable_autologin = 1;
12. }

En PHP, una comparación entre un valor de cadena y un valor booleano true siempre es true (porque la cadena contiene un valor), por lo que al proporcionar la siguiente cadena a la función unserialize(), es posible eludir el control de autenticación e iniciar sesión como administrador, cuyo userid es 2:

a:2:{s:11:"autologinid";b:1;s:6:"userid";s:1:"2";}  // original value: a:2:{s:11:"autologinid";s:32:"8b8e9715d12e4ca12c4c3eb4865aaf6a";s:6:"userid";s:4:"1337";}

Desglosemos lo que hicimos en esta cadena:

  1. autologinid es ahora un booleano establecido en true: esto se logra reemplazando el valor MD5 del hash de la contraseña (s:32:"8b8e9715d12e4ca12c4c3eb4865aaf6a") por b:1
  2. userid ahora está establecido con el ID del administrador: esto se ve en la última parte de la cadena, donde reemplazamos nuestro ID de usuario normal (s:4:"1337") por s:1:"2"

Hashes mágicos de PHP

Un problema similar puede ocurrir en PHP cuando los hashes se comparan de forma laxa y terminan evaluándose como números.

PHP admite el uso de notación científica para los números, por lo que el número 2e4 se trata como "dos por diez elevado a la cuarta potencia", que equivale a 20,000. De manera similar, un número como 0e4 sería "cero por diez elevado a la cuarta potencia", que equivale a cero. Como cero multiplicado por cualquier cosa es cero, una comparación como 0e2 == 0e3 se evaluaría como verdadera, porque ambos lados equivalen a cero.

Esto puede ser explotable cuando se comparan dos hashes de contraseñas y ambos tienen la forma de una cadena de ceros, la letra "e" y luego una cadena de números. Considérese el siguiente código:

<?php
{
    if (md5('240610708') == md5('QLTHNDT')) {
        print("Passwords match");
    } else {
        print("Passwords are different");
    }                                                                           
}

Las dos contraseñas son claramente distintas, pero como ambas producen hashes que equivalen a cero en notación científica ("0e462097431906509019562988736854" y "0e405967825401955372549139051580" respectivamente), la comparación devolverá verdadero y el usuario iniciará sesión.

Para probar esto, primero hay que identificar el tipo de hash utilizado por la aplicación. Luego se puede establecer en una cuenta de usuario una contraseña que produzca este tipo de hash y después intentar iniciar sesión con una contraseña diferente que produzca un hash distinto que también se evalúe como cero. Las cadenas para varios hashes de contraseñas están disponibles en el repositorio de GitHub spaze/hashes.

Si esto tiene éxito, no solo implica que la aplicación compara los hashes de las contraseñas de forma insegura, sino también que no utiliza salt en las contraseñas y, muy probablemente, que emplea un algoritmo de hash heredado.

Funcionan contraseñas de la misma longitud

Ocasionalmente las aplicaciones permiten a los usuarios iniciar sesión ingresando cualquier contraseña que tenga la longitud correcta de la contraseña real. Este es un problema bastante inusual y sugiere fallas importantes en la forma en que se almacenan y procesan las contraseñas.

Una posible causa de este problema son los problemas de codificación de caracteres entre distintas partes de la aplicación, ya que los caracteres desconocidos o inválidos suelen representarse con un carácter ?, que algunos lenguajes como SQL tratan como un comodín de un solo carácter. Así, una comparación de una cadena como password y ???????? puede devolver verdadero si se interpretan los comodines, como en una comparación LIKE de SQL.

Nota: Esto también implica que las contraseñas se almacenan en texto plano o con cifrado reversible.

La prueba es sencilla: intentar iniciar sesión en una cuenta con una contraseña incorrecta, pero de la misma longitud que una válida.
