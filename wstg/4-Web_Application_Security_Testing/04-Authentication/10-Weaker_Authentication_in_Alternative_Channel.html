Autenticación más débil en un canal alternativo

ID
WSTG-ATHN-10

Resumen

Aunque los mecanismos de autenticación principales no incluyan ninguna vulnerabilidad, puede ser que existan vulnerabilidades en canales alternativos legítimos de autenticación de usuarios para las mismas cuentas de usuario. Se deben realizar pruebas para identificar los canales alternativos y, según el alcance de la prueba, identificar vulnerabilidades.

Los canales alternativos de interacción del usuario podrían utilizarse para eludir el canal principal o para exponer información que luego puede emplearse para ayudar en un ataque contra el canal principal. Algunos de estos canales pueden ser en sí mismos aplicaciones web independientes que usan distintos nombres de host o rutas. Por ejemplo:

  • Sitio web estándar
  • Sitio web optimizado para móviles o para un dispositivo específico
  • Sitio web optimizado para accesibilidad
  • Sitios web alternativos de otros países e idiomas
  • Sitios web paralelos que utilizan las mismas cuentas de usuario (p. ej., otro sitio web que ofrece una funcionalidad diferente de la misma organización, un sitio web de un socio con el que se comparten las cuentas de usuario)
  • Versiones de desarrollo, pruebas, UAT y staging del sitio web estándar

Pero también podrían ser otros tipos de aplicaciones o procesos de negocio:

  • Aplicación para dispositivos móviles
  • Aplicación de escritorio
  • Operadores de centros de llamadas
  • Sistemas de respuesta de voz interactiva o de menús telefónicos

Hay que tener presente que el enfoque de esta prueba está en los canales alternativos; algunas alternativas de autenticación pueden aparecer como contenido diferente entregado a través del mismo sitio web y casi con certeza estarían dentro del alcance de las pruebas. Estas no se tratan más aquí y deberían haberse identificado durante la recopilación de información y las pruebas de autenticación principal. Por ejemplo:

  • Mejora progresiva y degradación elegante que cambian la funcionalidad
  • Uso del sitio sin cookies
  • Uso del sitio sin JavaScript
  • Uso del sitio sin plugins, como los de Flash y Java

Incluso si el alcance de la prueba no permite probar los canales alternativos, su existencia debe documentarse. Estos pueden socavar el grado de garantía de los mecanismos de autenticación y pueden ser un precursor de pruebas adicionales.

Ejemplo

El sitio web principal es https://www.example.com y las funciones de autenticación siempre se realizan en páginas que usan TLS https://www.example.com/myaccount/.

Sin embargo, existe un sitio web independiente optimizado para móviles que no usa TLS en absoluto y tiene un mecanismo de recuperación de contraseña más débil https://m.example.com/myaccount/.

Objetivos de la prueba

  • Identificar los canales de autenticación alternativos.
  • Evaluar las medidas de seguridad utilizadas y si existe alguna elusión en los canales alternativos.

Cómo probar

Comprender el mecanismo principal

Probar por completo las funciones de autenticación principales del sitio web. Esto debería identificar cómo se emiten, crean o modifican las cuentas y cómo se recuperan, restablecen o cambian las contraseñas. Además, se debe conocer cualquier autenticación de privilegios elevados y las medidas de protección de la autenticación. Estos precursores son necesarios para poder comparar con cualquier canal alternativo.

Identificar otros canales

Se pueden encontrar otros canales utilizando los siguientes métodos:

  • Leer el contenido del sitio, especialmente la página de inicio, contacto, páginas de ayuda, artículos de soporte y preguntas frecuentes, términos y condiciones, avisos de privacidad, el archivo robots.txt y cualquier archivo sitemap.xml.
  • Buscar en los logs del proxy HTTP, registrados durante la recopilación de información y las pruebas previas, cadenas como "mobile", "Android", blackberry", "ipad", "iphone", "mobile app", "e-reader", "wireless", "auth", "sso", "single sign on" en las rutas de URL y en el contenido del cuerpo.
  • Usar motores de búsqueda para encontrar diferentes sitios web de la misma organización, o que usen el mismo nombre de dominio, que tengan contenido de página de inicio similar o que también tengan mecanismos de autenticación.

Para cada posible canal, confirmar si las cuentas de usuario se comparten entre ellos o si proporcionan acceso a la misma funcionalidad o a una similar.

Enumerar la funcionalidad de autenticación

Para cada canal alternativo en el que se compartan cuentas de usuario o funcionalidad, identificar si están disponibles todas las funciones de autenticación del canal principal y si existe algo adicional. Puede ser útil crear una tabla como la siguiente:

Principal Móvil Centro de llamadas Sitio web del socio
Registro Sí - -
Inicio de sesión Sí Sí Sí (SSO)
Cierre de sesión - - -
Restablecimiento de contraseña Sí Sí -
- Cambiar contraseña - -

En este ejemplo, el canal móvil tiene una función adicional, "cambiar contraseña", pero no ofrece "cerrar sesión". También es posible realizar un número limitado de tareas llamando al centro de llamadas. Los centros de llamadas pueden ser interesantes porque sus verificaciones de confirmación de identidad pueden ser más débiles que las del sitio web, lo que permite usar este canal para ayudar en un ataque contra la cuenta de un usuario.

Al enumerarlos, vale la pena tomar nota de cómo se gestiona la sesión, por si hay superposición entre algunos canales (p. ej., cookies con alcance al mismo nombre de dominio padre, sesiones concurrentes permitidas entre canales pero no en el mismo canal).

Revisar y probar

Los canales alternativos deben mencionarse en el informe de pruebas, incluso si se marcan como "solo informativo" o "fuera de alcance". En algunos casos el alcance de la prueba podría incluir el canal alternativo (p. ej., porque es solo otra ruta en el nombre de host objetivo) o podría añadirse al alcance tras conversar con los propietarios de todos los canales. Si las pruebas están permitidas y autorizadas, se deben realizar entonces todas las demás pruebas de autenticación de esta guía y compararlas con el canal principal.

Casos de prueba relacionados

Deben utilizarse los casos de prueba de todas las demás pruebas de autenticación.

Corrección

Asegurarse de que se aplique una política de autenticación coherente en todos los canales para que sean igualmente seguros.
