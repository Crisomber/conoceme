Mecanismo de bloqueo débil

ID
WSTG-ATHN-03

Resumen

Los mecanismos de bloqueo de cuentas se utilizan para mitigar los ataques de fuerza bruta. Algunos de los ataques que pueden frustrarse mediante un mecanismo de bloqueo son:

  • Adivinación de contraseñas o ataques de fuerza bruta.
  • Adivinación de preguntas de seguridad.
  • Adivinación de códigos OTP para la autenticación de dos factores (2FA/MFA).

Los mecanismos de bloqueo de cuentas requieren un equilibrio entre proteger las cuentas del acceso no autorizado y proteger a los usuarios de que se les niegue el acceso autorizado. Las cuentas normalmente se bloquean tras 3 a 5 intentos fallidos y solo pueden desbloquearse después de un periodo predeterminado, mediante un mecanismo de desbloqueo de autoservicio o por intervención de un administrador.

A pesar de lo fácil que es realizar ataques de fuerza bruta, el resultado de un ataque exitoso es peligroso, ya que el atacante tendrá acceso total a la cuenta del usuario y, con ello, a toda la funcionalidad y los servicios a los que esa cuenta tiene acceso.

Objetivos de la prueba

  • Evaluar la capacidad del mecanismo de bloqueo de cuentas para mitigar la adivinación de contraseñas por fuerza bruta.
  • Evaluar la resistencia del mecanismo de desbloqueo frente al desbloqueo no autorizado de cuentas.

Cómo probar

Credential stuffing y fuerza bruta distribuida

El credential stuffing utiliza pares de nombre de usuario y contraseña filtrados previamente en brechas de datos para obtener acceso no autorizado a las cuentas. La fuerza bruta distribuida y el password spraying envían muchos intentos de autenticación desde múltiples direcciones IP. Ambos pueden eludir los mecanismos de bloqueo que solo cuentan los fallos por IP.

Muchas aplicaciones bloquean cuentas basándose únicamente en intentos de inicio de sesión repetidos desde una sola dirección IP. Los atacantes evitan ese control repartiendo las peticiones entre botnets o proxies rotativos.

Verificar si la aplicación utiliza protecciones basadas en la cuenta, y no solo restricciones basadas en la IP, al manejar estos ataques.

  1. Obtener un conjunto controlado de cuentas de prueba y credenciales que se esté autorizado a utilizar. Para el credential stuffing, usar pares conocidos de nombre de usuario y contraseña. Para la fuerza bruta distribuida o el password spraying, usar una lista de contraseñas contra uno o más nombres de usuario de prueba.
  2. Enviar peticiones de autenticación con esas credenciales.
  3. Distribuir los intentos entre múltiples direcciones IP mediante proxies o puntos de salida de VPN.
  4. Observar si la aplicación aplica protecciones basadas en la cuenta o solo restricciones basadas en la IP.
  5. Monitorear las respuestas en busca de bloqueo de cuenta, desafíos CAPTCHA o limitación de tasa (rate limiting).

Ejemplo de petición de autenticación:

POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=user1@example.com&password=Password123

Ejemplo con ffuf para realizar fuzzing de contraseñas contra una única cuenta de prueba (fuerza bruta distribuida o password spraying cuando se combina con rotación de IP):

ffuf -w passwords.txt -X POST -d "username=test&password=FUZZ" -u https://example.com/login

Para el credential stuffing, se pueden procesar pares conocidos de nombre de usuario y contraseña con Burp Intruder, ZAP Fuzzer, Hydra o un script personalizado que envíe cada par y rote las IP de origen.

Mecanismo de bloqueo

Para probar la solidez de los mecanismos de bloqueo, se necesitará acceso a una cuenta que se esté dispuesto a bloquear o que se pueda permitir bloquear. Si solo se dispone de una cuenta con la que iniciar sesión en la aplicación web, se debe realizar esta prueba al final del plan de pruebas para evitar perder tiempo de prueba por quedar bloqueado.

Para evaluar la capacidad del mecanismo de bloqueo de cuentas para mitigar la adivinación de contraseñas por fuerza bruta, se debe intentar iniciar sesión con la contraseña incorrecta varias veces antes de utilizar la contraseña correcta, para verificar que la cuenta quedó bloqueada. Un ejemplo de prueba podría ser el siguiente:

  1. Intentar iniciar sesión con una contraseña incorrecta 3 veces.
  2. Iniciar sesión correctamente con la contraseña correcta, lo que demuestra que el mecanismo de bloqueo no se activa tras 3 intentos de autenticación incorrectos.
  3. Intentar iniciar sesión con una contraseña incorrecta 4 veces.
  4. Iniciar sesión correctamente con la contraseña correcta, lo que demuestra que el mecanismo de bloqueo no se activa tras 4 intentos de autenticación incorrectos.
  5. Intentar iniciar sesión con una contraseña incorrecta 5 veces.
  6. Intentar iniciar sesión con la contraseña correcta. La aplicación devuelve "Your account is locked out.", lo que confirma que la cuenta se bloquea tras 5 intentos de autenticación incorrectos.
  7. Intentar iniciar sesión con la contraseña correcta 5 minutos después. La aplicación devuelve "Your account is locked out.", lo que demuestra que el mecanismo de bloqueo no se desbloquea automáticamente después de 5 minutos.
  8. Intentar iniciar sesión con la contraseña correcta 10 minutos después. La aplicación devuelve "Your account is locked out.", lo que demuestra que el mecanismo de bloqueo no se desbloquea automáticamente después de 10 minutos.
  9. Iniciar sesión correctamente con la contraseña correcta 15 minutos después, lo que demuestra que el mecanismo de bloqueo se desbloquea automáticamente tras un periodo de 10 a 15 minutos.

Mecanismos de bloqueo singulares

Existen implementaciones más singulares de mecanismos de bloqueo que siguen siendo aceptables. Una de ellas es Cognito de AWS. Utiliza un algoritmo de escalamiento sencillo que mitiga los ataques de fuerza bruta sin permitir ataques de denegación de servicio a largo plazo contra el usuario afectado. Tras 5 intentos fallidos de inicio de sesión con una contraseña, el usuario queda bloqueado durante un segundo. La duración del bloqueo se duplica con cada intento fallido, con un máximo de 15 minutos. Los intentos de inicio de sesión realizados durante el periodo de bloqueo son excepciones denominadas Password attempts exceeded y, en la mayoría de las implementaciones, no se devuelven al usuario que inició el intento. Si no se le muestran al usuario, un evaluador podría pensar que no se utiliza ningún mecanismo de bloqueo, ya que 200 intentos rápidos de inicio de sesión generarían muchas de estas excepciones y muy pocos intentos fallidos legítimos.

La matemática detrás del mecanismo es: 2^(n-5), donde n es el número de intentos fallidos de inicio de sesión. El número resultante es la cantidad de segundos que el usuario permanece bloqueado. Para reiniciar a cero el conteo de bloqueo, el usuario debe iniciar sesión correctamente o esperar los 15 minutos.

Para probar esto con una herramienta de fuzzing, como Intruder de Burp Suite, se debe ir a "Resource Pool". Luego se establece el máximo de peticiones concurrentes en 1 y el retraso entre peticiones en 2 segundos. Se intenta la autenticación inválida 200 veces y, inmediatamente después de que termine la herramienta de fuzzing, se intenta usar las credenciales válidas 3 veces. Se esperan 2 minutos y se intenta iniciar sesión. Si el inicio de sesión es exitoso, es posible que se esté utilizando Cognito. Entonces se pueden realizar más pruebas para validar el uso de Cognito intentando elevar el tiempo de bloqueo, aunque puede ser más fácil validar esta información con el cliente.

Un CAPTCHA puede dificultar los ataques de fuerza bruta, pero tiene sus propias debilidades y no debe sustituir a un mecanismo de bloqueo. Un mecanismo CAPTCHA puede eludirse si se implementa incorrectamente. Entre las fallas de los CAPTCHA se encuentran:

  1. Un desafío fácil de vencer, como uno aritmético o con un conjunto limitado de preguntas.
  2. El CAPTCHA comprueba el código de respuesta HTTP en lugar de que la respuesta sea exitosa.
  3. La lógica del lado del servidor del CAPTCHA considera por defecto que se resolvió con éxito.
  4. El resultado del desafío CAPTCHA nunca se valida del lado del servidor.
  5. El campo o parámetro de entrada del CAPTCHA se procesa manualmente y se valida o escapa de forma incorrecta.
  6. Un único CAPTCHA resuelto puede reutilizarse varias veces.

Para evaluar la eficacia del CAPTCHA:

  1. Evaluar los desafíos CAPTCHA e intentar automatizar su resolución según su dificultad.
  2. Intentar enviar la petición sin resolver el CAPTCHA a través de los mecanismos normales de la interfaz de usuario.
  3. Intentar enviar la petición fallando intencionalmente el desafío CAPTCHA.
  4. Intentar enviar la petición sin resolver el CAPTCHA (suponiendo que el código del lado del cliente pueda pasar algunos valores predeterminados, etc.) mientras se usa un proxy de pruebas (petición enviada directamente al servidor).
  5. Intentar hacer fuzzing de los puntos de entrada de datos del CAPTCHA (si existen) con payloads de inyección comunes o secuencias de caracteres especiales.
  6. Comprobar si la solución del CAPTCHA podría ser el texto alternativo de las imágenes, los nombres de archivo o un valor en un campo oculto asociado.
  7. Intentar reenviar respuestas válidas conocidas previamente identificadas.
  8. Comprobar si borrar las cookies hace que se eluda el CAPTCHA (por ejemplo, si el CAPTCHA solo se muestra tras una cantidad de fallos).
  9. Si el CAPTCHA forma parte de un proceso de varios pasos, intentar acceder o completar un paso posterior al CAPTCHA (por ejemplo, si el CAPTCHA es el primer paso de un proceso de inicio de sesión, intentar enviar directamente el segundo paso [nombre de usuario y contraseña]).
  10. Comprobar si existen métodos alternativos en los que no se aplique el CAPTCHA, como un endpoint de API destinado a facilitar el acceso desde aplicaciones móviles.

Repetir este proceso para cada funcionalidad posible que pudiera requerir un mecanismo de bloqueo.

Mecanismo de desbloqueo

Para evaluar la resistencia del mecanismo de desbloqueo frente al desbloqueo no autorizado de cuentas, se debe iniciar el mecanismo de desbloqueo y buscar debilidades. Los mecanismos de desbloqueo típicos pueden involucrar preguntas secretas o un enlace de desbloqueo enviado por correo electrónico. El enlace de desbloqueo debe ser único y de un solo uso, para evitar que un atacante lo adivine o lo reutilice y realice ataques de fuerza bruta por lotes.

Hay que tener presente que un mecanismo de desbloqueo solo debe utilizarse para desbloquear cuentas. No es lo mismo que un mecanismo de recuperación de contraseña, aunque podría seguir las mismas prácticas de seguridad.

Corrección

Aplicar mecanismos de desbloqueo de cuentas según el nivel de riesgo. En orden de menor a mayor garantía:

  1. Bloqueo y desbloqueo basados en el tiempo.
  2. Desbloqueo de autoservicio (envía un correo de desbloqueo a la dirección de correo registrada).
  3. Desbloqueo manual por un administrador.
  4. Desbloqueo manual por un administrador con identificación positiva del usuario.

Factores a considerar al implementar un mecanismo de bloqueo de cuentas:

  1. ¿Cuál es el riesgo de adivinación de contraseñas por fuerza bruta contra la aplicación?
  2. ¿Es suficiente un CAPTCHA para mitigar este riesgo?
  3. ¿Se está utilizando un mecanismo de bloqueo del lado del cliente (p. ej., JavaScript)? (de ser así, se debe deshabilitar el código del lado del cliente para probar.)
  4. Número de intentos fallidos de inicio de sesión antes del bloqueo. Si el umbral de bloqueo es demasiado bajo, es posible que se bloquee con demasiada frecuencia a usuarios válidos. Si el umbral es demasiado alto, el atacante podrá hacer más intentos de fuerza bruta sobre la cuenta antes de que se bloquee. Según el propósito de la aplicación, un rango de 5 a 10 intentos fallidos es un umbral de bloqueo típico.
  5. ¿Cómo se desbloquearán las cuentas?
    1. Manualmente por un administrador: es el método de bloqueo más seguro, pero puede causar inconvenientes a los usuarios y consumir el "valioso" tiempo del administrador.
      1. El administrador también debe contar con un método de recuperación por si su cuenta se bloquea.
      2. Este mecanismo de desbloqueo puede dar lugar a un ataque de denegación de servicio si el objetivo del atacante es bloquear las cuentas de todos los usuarios de la aplicación web.
    2. Después de un periodo de tiempo: ¿cuál es la duración del bloqueo? ¿Es suficiente para la aplicación que se protege? Por ejemplo, una duración de bloqueo de 5 a 30 minutos puede ser un buen compromiso entre mitigar los ataques de fuerza bruta y molestar a los usuarios válidos.
    3. Mediante un mecanismo de autoservicio: como se indicó antes, este mecanismo de autoservicio debe ser lo bastante seguro para evitar que el atacante pueda desbloquear cuentas por sí mismo.
