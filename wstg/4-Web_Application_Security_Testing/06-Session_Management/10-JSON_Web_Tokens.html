JSON Web Tokens

ID
WSTG-SESS-10

Resumen

Los JSON Web Tokens (JWT) son tokens JSON firmados criptográficamente, destinados a compartir claims (afirmaciones) entre sistemas. Se utilizan con frecuencia como tokens de autenticación o de sesión, particularmente en APIs REST.

Los JWT son una fuente común de vulnerabilidades, tanto en la forma en que se implementan en las aplicaciones como en las bibliotecas subyacentes. Como se utilizan para la autenticación, una vulnerabilidad puede dar lugar fácilmente a un compromiso completo de la aplicación.

Objetivos de la prueba

  • Determinar si los JWT exponen información sensible.
  • Determinar si los JWT pueden ser manipulados o modificados.

Cómo probar

Visión general

Los JWT se componen de tres elementos:

  • La cabecera (header)
  • La carga útil (payload o cuerpo)
  • La firma (signature)

Cada componente está codificado en base64 y están separados por puntos (.). Hay que tener en cuenta que la codificación base64 utilizada en un JWT elimina los signos de igual (=), por lo que puede ser necesario volver a añadirlos para decodificar las secciones.

Analizar el contenido

Cabecera

La cabecera define el tipo de token (normalmente JWT) y el algoritmo utilizado para la firma. A continuación se muestra un ejemplo de cabecera decodificada:

{
  "alg": "HS256",
  "typ": "JWT"
}

Hay tres tipos principales de algoritmos que se utilizan para calcular las firmas:

Algoritmo Descripción
HSxxx HMAC usando una clave secreta y SHA-xxx.
RSxxx y PSxxx Firma de clave pública usando RSA.
ESxxx Firma de clave pública usando ECDSA.

También existe una amplia gama de otros algoritmos que pueden utilizarse para tokens cifrados (JWE), aunque son menos comunes.

Payload

El payload (carga útil) del JWT contiene los datos reales. A continuación se muestra un ejemplo de payload:

{
  "username": "administrator",
  "is_admin": true,
  "iat": 1516239022,
  "exp": 1516242622
}

El payload normalmente no está cifrado, por lo que hay que revisarlo para determinar si incluye datos sensibles o potencialmente inapropiados.

Este JWT incluye el nombre de usuario y el estado de administrador del usuario, así como dos claims estándar (iat y exp). Estos claims están definidos en la RFC 7519; en la tabla siguiente se ofrece un breve resumen de ellos:

Claim Nombre completo Descripción
iss Issuer (emisor) La identidad de la parte que emitió el token.
iat Issued At (emitido en) La marca de tiempo Unix de cuándo se emitió el token.
nbf Not Before (no antes de) La marca de tiempo Unix de la fecha más temprana en que se puede usar el token.
exp Expires (expira) La marca de tiempo Unix de cuándo expira el token.

Firma

La firma se calcula usando el algoritmo definido en la cabecera del JWT, y luego se codifica en base64 y se añade al token. Modificar cualquier parte del JWT debería invalidar la firma y hacer que el servidor rechace el token.

Para leer estas tres partes de un token, hay que decodificarlo con una herramienta de JWT. La pestaña JWT de Gori decodifica un token a medida que se pega y mantiene los claims editables para volver a firmarlos. gori run jwt imprime la misma decodificación:

$ gori run jwt "$TOKEN"
// header
{
  "typ": "JWT",
  "alg": "RS256"
}

// payload
{
  "data": {
    "id": 25,
    "email": "alice@wstg.test",
    "password": "646e613efcfc1317061b1df9340e3726",
    "role": "customer",
    // ... profile fields omitted
  },
  "bid": 6,
  "iat": 1789655485
}

// signature (not verified)
wcaY3SC6taMCJUH8F4CEcF2a1rUa8bjYetKAo3s8DO3yjt3D4GFmz2SyJR3151np…

Este token fue emitido por OWASP Juice Shop. Su payload contiene el rol del usuario y un hash de la contraseña. Dado que el payload no está cifrado, hay que tratar cada valor que contiene como legible por cualquiera que posea el token.

Revisar el uso

Además de ser criptográficamente seguro en sí mismo, el JWT también debe almacenarse y enviarse de forma segura. Esto debe incluir comprobaciones de que:

  • Siempre se envía a través de conexiones cifradas (HTTPS).
  • Si se almacena en una cookie, debe estar marcada con los atributos apropiados.

También se debe revisar la validez del JWT, con base en los claims iat, nbf y exp, para determinar que:

  • El JWT tiene una vida útil razonable para la aplicación.
  • La aplicación rechaza los tokens expirados.

Verificación de la firma

Una de las vulnerabilidades más graves que se encuentran con los JWT es cuando la aplicación no valida que la firma sea correcta. Esto suele ocurrir cuando un desarrollador usa una función como jwt.decode() de Node.js, que simplemente decodifica el cuerpo del JWT, en lugar de jwt.verify(), que verifica la firma antes de decodificar el JWT.

Esto se puede probar fácilmente modificando el cuerpo del JWT sin cambiar nada en la cabecera ni en la firma, y enviándolo en una petición para ver si la aplicación lo acepta.

La pestaña JWT de Gori también enumera payloads listos para enviar para las debilidades que se describen a continuación. gori run jwt --attacks imprime el mismo conjunto: variantes del algoritmo none, intentos de secretos débiles y payloads de inyección en la cabecera.

El algoritmo None

Además de los algoritmos basados en clave pública y HMAC, la especificación JWT también define un algoritmo de firma llamado none. Como su nombre indica, esto significa que el JWT no tiene firma, lo que permite modificarlo.

Esto se puede probar modificando el algoritmo de firma (alg) en la cabecera del JWT a none, como se muestra en el siguiente ejemplo:

{
        "alg": "none",
        "typ": "JWT"
}

Luego se vuelven a codificar en base64 la cabecera y el payload, y se elimina la firma (dejando el punto final). Usando la cabecera anterior y el payload indicado en la sección de payload, esto daría el siguiente JWT:

eyJhbGciOiAibm9uZSIsICJ0eXAiOiAiSldUIn0K.eyJ1c2VybmFtZSI6ImFkbWluaW5pc3RyYXRvciIsImlzX2FkbWluIjp0cnVlLCJpYXQiOjE1MTYyMzkwMjIsImV4cCI6MTUxNjI0MjYyMn0.

Algunas implementaciones intentan evitar esto bloqueando explícitamente el uso del algoritmo none. Si esto se hace sin distinguir entre mayúsculas y minúsculas, puede ser posible eludirlo especificando un algoritmo como NoNe.

Firmas psíquicas de ECDSA ("Psychic Signatures")

Se identificó una vulnerabilidad en las versiones 15 a 18 de Java en las que no se validaban correctamente las firmas ECDSA en algunas circunstancias (CVE-2022-21449, conocida como "psychic signatures"). Si se utiliza una de estas versiones vulnerables para procesar un JWT con el algoritmo ES256, esto puede usarse para eludir por completo la verificación de la firma manipulando el cuerpo y reemplazando luego la firma por el siguiente valor:

MAYCAQACAQA

Lo que da como resultado un JWT que se ve más o menos así:

eyJhbGciOiJFUzI1NiIsInR5cCI6IkpXVCJ9.eyJhZG1pbiI6InRydWUifQ.MAYCAQACAQA

Claves HMAC débiles

Si el JWT está firmado usando un algoritmo basado en HMAC (como HS256), la seguridad de la firma depende por completo de la fortaleza de la clave secreta utilizada en el HMAC.

Si la aplicación utiliza software comercial o de código abierto, el primer paso debe ser investigar el código y ver si existe una clave de firma HMAC predeterminada que se utilice.

Si no hay una predeterminada, puede ser posible adivinar o descifrar por fuerza bruta la clave. La forma más sencilla de hacerlo es usar el script crackjwt.py, que simplemente requiere el JWT y un archivo de diccionario.

Una opción más potente es convertir el JWT a un formato que pueda usar John the Ripper mediante el script jwt2john.py. Luego se puede usar John para llevar a cabo ataques mucho más avanzados contra la clave.

Si el JWT es grande, puede superar el tamaño máximo admitido por John. Esto se puede resolver aumentando el valor de la variable SALT_LIMBS en /src/hmacSHA256_fmt_plug.c (o el archivo equivalente para otros formatos HMAC) y recompilando John, como se explica en el siguiente GitHub issue.

Si se puede obtener esta clave, entonces es posible crear y firmar JWT arbitrarios, lo que normalmente da lugar a un compromiso completo de la aplicación.

Confusión entre HMAC y clave pública

Si la aplicación utiliza JWT con firmas basadas en clave pública, pero no comprueba que el algoritmo sea el correcto, esto se puede explotar potencialmente en un ataque de confusión de tipo de firma. Para que tenga éxito, deben cumplirse las siguientes condiciones:

  1. La aplicación debe esperar que el JWT esté firmado con un algoritmo basado en clave pública (es decir, RSxxx o ESxxx).
  2. La aplicación no debe comprobar qué algoritmo utiliza realmente el JWT para la firma.
  3. La clave pública utilizada para verificar el JWT debe estar disponible para el atacante.

Si se cumplen todas estas condiciones, un atacante puede usar la clave pública para firmar el JWT con un algoritmo basado en HMAC (como HS256). Por ejemplo, la biblioteca Node.js jsonwebtoken usa la misma función tanto para tokens basados en clave pública como en HMAC, como se muestra en el siguiente ejemplo:

// Verify a JWT signed using RS256
jwt.verify(token, publicKey);

// Verify a JWT signed using HS256
jwt.verify(token, secretKey);

Esto significa que si el JWT se firma usando publicKey como clave secreta para el algoritmo HS256, la firma se considerará válida.

Para explotar este problema, se debe obtener la clave pública. La forma más común en que esto puede ocurrir es si la aplicación reutiliza la misma clave tanto para firmar los JWT como para el certificado TLS. En este caso, la clave se puede descargar del servidor mediante un comando como el siguiente:

openssl s_client -connect example.org:443 | openssl x509 -pubkey -noout

Alternativamente, la clave puede estar disponible en un archivo público del sitio en una ubicación común como /.well-known/jwks.json.

Para probar esto, se modifica el contenido del JWT y luego se usa la clave pública obtenida previamente para firmar el JWT con el algoritmo HS256. Esto suele ser difícil de realizar durante las pruebas sin acceso al código fuente o a los detalles de la implementación, porque el formato de la clave debe ser idéntico al que usa el servidor, de modo que problemas como espacios vacíos o la codificación CRLF pueden hacer que las claves no coincidan.

Clave pública proporcionada por el atacante (JWK incrustado)

El estándar JSON Web Signature (JWS) (RFC 7515 §4.1.3) permite que la clave pública utilizada para verificar la firma se incruste directamente en la cabecera mediante el parámetro jwk. Si la biblioteca de verificación del lado del servidor acepta a ciegas esta clave incrustada sin comprobarla contra un almacén de confianza o una lista de permitidos de claves públicas conocidas, un atacante puede incrustar su propia clave pública y firmar tokens falsificados con la clave privada correspondiente.

Por ejemplo, un atacante puede incrustar su clave pública directamente en la cabecera:

{
  "alg": "RS256",
  "typ": "JWT",
  "jwk": {
    "kty": "RSA",
    "e": "AQAB",
    "use": "sig",
    "kid": "attacker-inline-key",
    "n": "u1SucjA342W..."
  }
}

Existen diversos scripts y extensiones que pueden utilizarse para generar e inyectar cabeceras jwk en línea, como jwt_tool o la JSON Web Tokens Burp Extension.

Manipulación del ID de clave (kid)

El parámetro de cabecera kid se utiliza normalmente para recuperar la clave necesaria para verificar la firma desde un sistema de archivos o una base de datos. Puede ser vulnerable a varios ataques de inyección.

Directory Traversal

Si la aplicación utiliza el parámetro kid para leer un archivo de clave del sistema de archivos, un atacante podría especificar una ruta a un archivo vacío conocido, como ../../../../dev/null (en Linux) o nul (en Windows).

Por ejemplo, un atacante puede modificar la cabecera para que apunte a un archivo vacío:

{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "../../../../../dev/null"
}

Dado que el contenido de /dev/null está vacío, el atacante puede firmar entonces el token malicioso usando una cadena vacía como clave secreta. Si el servidor es vulnerable, leerá el archivo vacío, usará la cadena vacía para verificar la firma y aceptará el token falsificado.

Inyección de comandos/SQL

Si el kid se pasa sin sanear a una consulta de base de datos o a un comando del sistema para recuperar la clave, puede ser vulnerable a Inyección SQL o a inyección de comandos.

Por ejemplo, un atacante puede inyectar un payload SQL en el parámetro kid para controlar la clave devuelta por la base de datos:

{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "invalid-key' UNION SELECT 'attacker-controlled-key'--"
}

Esto permite a un atacante obligar a la aplicación a usar una clave conocida (p. ej., "attacker-controlled-key") para la verificación, lo que le permite falsificar tokens válidos.

Inyección en las cabeceras JWKS URL (jku) y X.509 URL (x5u)

La especificación JSON Web Signature (JWS) (RFC 7515 §4.1.2, §4.1.5) admite parámetros de cabecera que apuntan a almacenes externos de claves públicas:

  • jku (JWK Set URL): Un URI que hace referencia a un recurso con un conjunto de claves públicas codificadas en JSON.
  • x5u (X.509 URL): Un URI que hace referencia a un recurso con un conjunto de certificados de clave pública X.509.

Si la biblioteca de verificación obtiene automáticamente las claves públicas del URI especificado en la cabecera sin imponer una lista de dominios permitidos estricta, un atacante puede apuntar jku/x5u a un servidor que controle, alojar allí su propia clave y firmar tokens falsificados con la clave privada correspondiente, que el servidor aceptará como válidos.

Procedimiento de prueba

  1. Generar un par de claves RSA en una máquina de pruebas.

  2. Alojar la clave pública correspondiente, con formato de JSON Web Key Set (JWKS), en un servidor público:

    {
  "keys": [
    {
      "kty": "RSA",
      "e": "AQAB",
      "use": "sig",
      "kid": "test-key-01",
      "alg": "RS256",
      "n": "u1SucjA342W..."
    }
  ]
}

  3. Modificar el payload del JWT objetivo con claims alterados (p. ej., modificando user_id o role).

  4. Actualizar la cabecera del JWT con el parámetro jku apuntando al endpoint JWKS alojado y con el kid correspondiente:

    {
  "alg": "RS256",
  "typ": "JWT",
  "jku": "https://attacker.example.com/.well-known/jwks.json",
  "kid": "test-key-01"
}

  5. Firmar el token falsificado con la clave privada y enviarlo en una petición autenticada.

  6. Si se bloquean los nombres de host externos directos, evaluar las elusiones del filtrado de URL:

    • Comprobar si existen vulnerabilidades de redirección abierta (open redirect) en dominios permitidos (p. ej., https://trusted.example.com/oauth/redirect?url=https://attacker.example.com/jwks.json).
    • Comprobar si hay discrepancias en el análisis de URL o fallos de normalización de rutas (p. ej., https://trusted.example.com@attacker.example.com/jwks.json).
    • Comprobar si el servidor intenta resolver la red interna (SSRF) cuando se apunta jku a loopback (http://127.0.0.1/) o a endpoints de metadatos de la nube (http://169.254.169.254/).

El parámetro x5u se puede probar de la misma manera: en lugar de alojar un documento JWKS, se aloja en la URL objetivo una cadena de certificados X.509 (codificada en PEM) firmada con una clave controlada por el atacante. Muchas bibliotecas extraen la clave pública del certificado hoja sin validar que la cadena sea de confianza o que termine en una CA raíz fijada (pinned), por lo que hay que comprobar si una cadena autofirmada o de otro modo no confiable sigue siendo aceptada.

Confusión de audiencia (aud) y emisor (iss) del token

En arquitecturas distribuidas de microservicios y multiinquilino, múltiples servicios distintos suelen compartir un proveedor de identidad (IdP) centralizado. Un fallo de autorización común ocurre cuando un servicio descendente valida la firma criptográfica del token contra el IdP, pero no comprueba que el token fue emitido explícitamente para ese servicio específico.

  • aud (Audience): Identifica los destinatarios a los que va dirigido el JWT (RFC 7519 §4.1.3).
  • iss (Issuer): Identifica a la entidad que emitió el JWT (RFC 7519 §4.1.1).

Si el Servicio B confía en la firma del IdP pero omite la validación de aud, un atacante con credenciales válidas en un Servicio A de bajo privilegio puede capturar su token y reproducirlo contra el Servicio B.

Procedimiento de prueba

  1. Autenticarse en una aplicación o inquilino (tenant) de bajo privilegio registrado bajo el proveedor de identidad de la organización objetivo.
  2. Interceptar y extraer el JWT válido emitido.
  3. Inspeccionar los claims del payload para identificar el aud objetivo (p. ej., aud: "client-portal") y el iss (p. ej., iss: "https://auth.example.com/").
  4. Reproducir el token sin modificar en una petición contra un servicio de alto privilegio, una API administrativa u otro inquilino (p. ej., https://internal-admin.example.com/api/v1/users).
  5. Si el servicio de alto privilegio acepta el token y realiza la acción, es vulnerable a la reproducción de tokens entre servicios (Cross-Service Token Replay) debido a la falta de validación de la audiencia.
  6. Probar la confusión de emisor por separado: si el IdP es multiinquilino o respalda varios entornos (p. ej., staging y producción) con un endpoint JWKS compartido, obtener un token emitido para un inquilino o aplicación diferente de menor confianza y reproducirlo contra el servicio objetivo. Que se acepte indica que iss no se valida o se valida con una comparación débil (como coincidencia de prefijo o subcadena) en lugar de una igualdad exacta de cadena con el emisor de confianza esperado.

Corrección

  • Utilizar una biblioteca segura y actualizada para manejar los JWT.
  • Asegurar que la firma es válida y que utiliza el algoritmo esperado.
  • No confiar en parámetros de cabecera no verificados como jku, x5u o jwk sin compararlos con una lista de permitidos estricta de dominios/URI.
  • Validar siempre los claims estándar: asegurar que exp está en el futuro, nbf está en el pasado, iss coincide con el servidor de autorización de confianza y aud coincide estrictamente con el identificador del servicio esperado.
  • Utilizar una clave HMAC fuerte o una clave privada única para firmar los tokens.
  • Asegurar que no se expone información sensible en el payload.
  • Asegurar que los JWT se almacenan y transmiten de forma segura.
  • Consulte la OWASP JSON Web Tokens Cheat Sheet.
