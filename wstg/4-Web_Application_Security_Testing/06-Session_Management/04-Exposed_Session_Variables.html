Variables de sesión expuestas

ID
WSTG-SESS-04

Resumen

Los tokens de sesión (cookie, SessionID, campo oculto), si quedan expuestos, normalmente permitirán a un atacante suplantar a una víctima y acceder a la aplicación de forma ilegítima. Es importante que estén protegidos de la escucha (eavesdropping) en todo momento, en particular mientras viajan entre el navegador del cliente y los servidores de la aplicación.

La información aquí presentada se refiere a cómo se aplica la seguridad del transporte a la transferencia de datos sensibles del ID de sesión, más que a los datos en general, y puede ser más estricta que las políticas de caché y transporte aplicadas a los datos servidos por el sitio.

Usando un proxy personal, es posible determinar lo siguiente sobre cada petición y respuesta:

  • Protocolo utilizado (p. ej., HTTP vs. HTTPS)
  • Cabeceras HTTP
  • Cuerpo del mensaje (p. ej., POST o contenido de la página)

Cada vez que se transmiten datos del ID de sesión entre el cliente y el servidor, se deben examinar el protocolo, la caché, las directivas de privacidad y el cuerpo. La seguridad del transporte aquí se refiere a los ID de sesión transmitidos en peticiones GET o POST, cuerpos de mensaje u otros medios sobre peticiones HTTP válidas.

Objetivos de la prueba

  • Asegurar que se implementa el cifrado adecuado.
  • Revisar la configuración de caché.
  • Evaluar la seguridad del canal y de los métodos.

Cómo probar

Vulnerabilidades de cifrado y reutilización de tokens de sesión

La protección contra la escucha suele proporcionarla el cifrado TLS, pero puede incorporar otros túneles o cifrados. Cabe señalar que el cifrado o el hash criptográfico del ID de sesión debe considerarse por separado del cifrado del transporte, ya que lo que se protege es el propio ID de sesión y no los datos que puedan estar representados por él.

Si un atacante pudiera presentar el ID de sesión a la aplicación para obtener acceso, entonces debe protegerse en tránsito para mitigar ese riesgo. Por lo tanto, se debe asegurar que el cifrado sea tanto el valor predeterminado como obligatorio para cualquier petición o respuesta en la que se transmita el ID de sesión, independientemente del mecanismo utilizado (p. ej., un campo de formulario oculto). Deben realizarse comprobaciones sencillas, como reemplazar https:// por http:// durante la interacción con la aplicación, junto con la modificación de los envíos de formularios, para determinar si se implementa una segregación adecuada entre los sitios seguros y no seguros.

Hay que tener presente que si el sitio también tiene un elemento en el que se rastrea al usuario con ID de sesión pero no hay seguridad (p. ej., anotar qué documentos públicos descarga un usuario registrado), es esencial que se utilice un ID de sesión diferente. Por lo tanto, se debe monitorear el ID de sesión a medida que el cliente cambia de los elementos seguros a los no seguros para asegurar que se utiliza uno distinto.

Cada vez que la autenticación sea exitosa, el usuario debe esperar recibir:

  • Un token de sesión diferente
  • Un token enviado por un canal cifrado cada vez que realice una petición HTTP

Vulnerabilidades de proxies y caché

Los proxies también deben considerarse al revisar la seguridad de la aplicación. En muchos casos, los clientes accederán a la aplicación a través de proxies corporativos, de ISP u otros, o de pasarelas que reconocen protocolos (p. ej., firewalls). El protocolo HTTP proporciona directivas para controlar el comportamiento de los proxies intermedios, y también debe evaluarse la correcta implementación de estas directivas.

En general, el ID de sesión nunca debe enviarse por un transporte sin cifrar y nunca debe almacenarse en caché. Se debe examinar la aplicación para asegurar que las comunicaciones cifradas son tanto el valor predeterminado como obligatorias para cualquier transferencia de ID de sesión. Además, siempre que se transmita el ID de sesión, deben existir directivas que impidan su almacenamiento en caché por parte de cachés intermedias e incluso locales.

La aplicación también debe configurarse para proteger los datos en las cachés tanto sobre HTTP/1.0 como sobre HTTP/1.1; la RFC 2616 analiza los controles apropiados en relación con HTTP. HTTP/1.1 proporciona varios mecanismos de control de caché. Cache-Control: no-cache indica que un proxy no debe reutilizar ningún dato. Aunque Cache-Control: Private parece una directiva adecuada, esto aún permite que un proxy no compartido almacene datos en caché. En el caso de cibercafés u otros sistemas compartidos, esto presenta un riesgo claro. Incluso con estaciones de trabajo de un solo usuario, el ID de sesión almacenado en caché puede quedar expuesto mediante el compromiso del sistema de archivos o cuando se utilizan almacenes de red. Las cachés HTTP/1.0 no reconocen la directiva Cache-Control: no-cache.

Las directivas Expires: 0 y Cache-Control: max-age=0 deben utilizarse para asegurar aún más que las cachés no expongan los datos. Se debe examinar cada petición/respuesta que transmita datos del ID de sesión para asegurar que se usan las directivas de caché apropiadas.

Vulnerabilidades de GET y POST

En general, no deben utilizarse peticiones GET, ya que el ID de sesión puede quedar expuesto en los logs de proxies o firewalls. También son mucho más fáciles de manipular que otros tipos de transporte, aunque debe tenerse en cuenta que casi cualquier mecanismo puede ser manipulado por el cliente con las herramientas adecuadas. Además, los ataques de Cross-site Scripting (XSS) se explotan con mayor facilidad enviando a la víctima un enlace especialmente construido. Esto es mucho menos probable si los datos se envían desde el cliente como POST.

Todo el código del lado del servidor que reciba datos de peticiones POST debe probarse para asegurar que no acepta los datos si se envían como GET. Por ejemplo, considérese la siguiente petición POST (https://owaspapp.com/login.asp) generada por una página de inicio de sesión.

POST /login.asp HTTP/1.1
Host: owaspapp.com
[...]
Cookie: ASPSESSIONIDABCDEFG=ASKLJDLKJRELKHJG
Content-Length: 51

Login=Username&password=Password&SessionID=12345678

Si login.asp está mal implementado, puede ser posible iniciar sesión usando la siguiente URL: https://owaspapp.com/login.asp?Login=Username&password=Password&SessionID=12345678

Los scripts del lado del servidor potencialmente inseguros pueden identificarse comprobando cada POST de esta manera.

Vulnerabilidades de transporte

Toda la interacción entre el cliente y la aplicación debe probarse al menos con los siguientes criterios.

  • ¿Cómo se transfieren los ID de sesión? p. ej., GET, POST, campo de formulario (incluidos los campos ocultos)
  • ¿Los ID de sesión se envían siempre por transporte cifrado de forma predeterminada?
  • ¿Es posible manipular la aplicación para que envíe ID de sesión sin cifrar? p. ej., ¿cambiando HTTPS a HTTP?
  • ¿Qué directivas de control de caché se aplican a las peticiones/respuestas que transmiten ID de sesión?
  • ¿Estas directivas están siempre presentes? Si no, ¿dónde están las excepciones?
  • ¿Se utilizan peticiones GET que incorporen el ID de sesión?
  • Si se utiliza POST, ¿se puede intercambiar por GET?
