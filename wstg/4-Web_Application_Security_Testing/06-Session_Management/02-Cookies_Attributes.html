Atributos de las cookies

ID
WSTG-SESS-02

Resumen

Las cookies web (en adelante, cookies) suelen ser un vector de ataque clave para los usuarios maliciosos (que normalmente atacan a otros usuarios), y la aplicación siempre debe ejercer la debida diligencia para protegerlas.

HTTP es un protocolo sin estado, lo que significa que no conserva ninguna referencia a las peticiones enviadas por el mismo usuario. Para resolver este problema se crearon las sesiones, que se añaden a las peticiones HTTP. Los navegadores, como se explica en pruebas del almacenamiento del navegador, contienen multitud de mecanismos de almacenamiento. En esa sección de la guía se analiza cada uno de ellos a fondo.

El mecanismo de almacenamiento de sesiones más utilizado en los navegadores es el almacenamiento de cookies. Las cookies pueden ser establecidas por el servidor, incluyendo una cabecera Set-Cookie en la respuesta HTTP, o mediante JavaScript. Las cookies pueden usarse por múltiples motivos, como:

  • gestión de sesiones
  • personalización
  • rastreo

Para proteger los datos de las cookies, la industria ha desarrollado medios que ayudan a blindarlas y limitar su superficie de ataque. Con el tiempo, las cookies se han convertido en un mecanismo de almacenamiento preferido para las aplicaciones web, ya que permiten gran flexibilidad de uso y protección.

Los medios para proteger las cookies son:

  • Atributos de las cookies
  • Prefijos de las cookies

Objetivos de la prueba

  • Asegurar que se establece la configuración de seguridad adecuada para las cookies.

Cómo probar

A continuación se describe cada atributo y prefijo. El evaluador debe validar que la aplicación los utiliza correctamente. Las cookies pueden revisarse mediante un proxy de interceptación o examinando el almacén de cookies (cookie jar) del navegador.

Atributos de las cookies

Atributo Secure

El atributo Secure indica al navegador que solo envíe la cookie si la petición se realiza a través de un canal seguro como HTTPS. Esto ayuda a proteger la cookie de ser transmitida en peticiones sin cifrar. Si se puede acceder a la aplicación tanto por HTTP como por HTTPS, un atacante podría redirigir al usuario para que envíe su cookie como parte de peticiones no protegidas.

Atributo HttpOnly

El atributo HttpOnly se utiliza para ayudar a prevenir ataques como la fuga de sesión, ya que no permite que la cookie sea accesible mediante un script del lado del cliente como JavaScript.

Esto no limita toda la superficie de ataque de los ataques XSS, ya que un atacante aún podría enviar peticiones en nombre del usuario, pero limita enormemente el alcance de los vectores de ataque XSS.

Atributo Domain

El atributo Domain se utiliza para comparar el dominio de la cookie con el dominio del servidor al que se dirige la petición HTTP. Si el dominio coincide o si es un subdominio, a continuación se comprobará el atributo path.

Solo los hosts que pertenecen al dominio especificado pueden establecer una cookie para ese dominio. Además, el atributo domain no puede ser un dominio de nivel superior (como .gov o .com) para evitar que los servidores establezcan cookies arbitrarias para otro dominio (como establecer una cookie para owasp.org). Si no se establece el atributo domain, se utiliza como valor predeterminado de domain el nombre de host del servidor que generó la cookie.

Por ejemplo, si una aplicación en app.mydomain.com establece una cookie sin atributo domain, la cookie se reenviaría en todas las peticiones posteriores a app.mydomain.com, pero no a sus subdominios (como hacker.app.mydomain.com) ni a otherapp.mydomain.com. (Sin embargo, las versiones antiguas de Edge/IE se comportan de forma diferente y sí envían estas cookies a los subdominios.) Si un desarrollador quisiera relajar esta restricción, podría establecer el atributo domain en mydomain.com. En este caso, la cookie se enviaría en todas las peticiones a app.mydomain.com y a los subdominios de mydomain.com, como hacker.app.mydomain.com, e incluso bank.mydomain.com. Si hubiera un servidor vulnerable en un subdominio (por ejemplo, otherapp.mydomain.com) y el atributo domain se hubiera establecido de forma demasiado laxa (por ejemplo, mydomain.com), el servidor vulnerable podría utilizarse para recolectar cookies (como tokens de sesión) en todo el alcance de mydomain.com.

Atributo Path

El atributo Path desempeña un papel importante al definir el alcance de las cookies junto con el domain. Además del dominio, se puede especificar la ruta de URL para la que es válida la cookie. Si el dominio y la ruta coinciden, la cookie se enviará en la petición. Al igual que con el atributo domain, si el atributo path se establece de forma demasiado laxa, podría dejar la aplicación vulnerable a ataques de otras aplicaciones en el mismo servidor. Por ejemplo, si el atributo path se estableciera en la raíz del servidor web /, las cookies de la aplicación se enviarían a todas las aplicaciones dentro del mismo dominio (si varias aplicaciones residen en el mismo servidor). Un par de ejemplos para múltiples aplicaciones en el mismo servidor:

  • path=/bank
  • path=/private
  • path=/docs
  • path=/docs/admin

Atributo Expires

El atributo Expires se utiliza para:

  • establecer cookies persistentes
  • limitar la vida útil si una sesión vive demasiado tiempo
  • eliminar una cookie de forma forzada estableciéndola en una fecha pasada

A diferencia de las cookies de sesión, las cookies persistentes serán utilizadas por el navegador hasta que la cookie expire. Una vez superada la fecha de expiración establecida, el navegador eliminará la cookie.

Atributo SameSite

El atributo SameSite puede utilizarse para indicar si una cookie debe enviarse junto con peticiones entre sitios (cross-site). Esta característica permite al servidor mitigar el riesgo de fuga de información entre sitios. En algunos casos, se utiliza también como estrategia de reducción de riesgo (o mecanismo de defensa en profundidad) para prevenir ataques de cross-site request forgery. Este atributo puede configurarse en tres modos diferentes:

  • Strict
  • Lax
  • None

SameSite compara sitios, no orígenes. Un sitio es el esquema y el dominio registrable, como https://mydomain.com, por lo que https://app.mydomain.com y https://otherapp.mydomain.com son el mismo sitio aunque sean orígenes distintos. SameSite no restringe las peticiones entre ellos. Si un atacante controla cualquier subdominio del mismo sitio, por ejemplo mediante XSS o una toma de control de subdominio, puede enviar a la aplicación peticiones que incluyan sus cookies, incluso las Strict. Al evaluar cuánta protección ofrece SameSite, hay que considerar todos los subdominios del sitio.

Valor Strict

El valor Strict es el uso más restrictivo de SameSite. El navegador envía la cookie solo en las peticiones que provienen del mismo sitio que la estableció, y nunca en peticiones entre sitios, incluidas las navegaciones de nivel superior, como seguir un enlace desde otro sitio. Este valor se recomienda especialmente para las acciones realizadas dentro del mismo sitio. Sin embargo, puede afectar la experiencia de navegación con algunos sistemas de gestión de sesiones. Cuando un usuario con sesión iniciada sigue un enlace a la aplicación desde otro sitio, como un cliente de correo web, el navegador no envía la cookie en esa primera petición, por lo que el usuario aparece como si hubiera cerrado sesión. La cookie se vuelve a enviar en la siguiente petición del mismo sitio, por ejemplo cuando el usuario sigue un enlace dentro de la aplicación.

Valor Lax

El valor Lax es menos restrictivo que Strict. Permite que la cookie se envíe en navegaciones de nivel superior entre sitios que usen un método HTTP "seguro" (en la práctica, GET), por ejemplo, cuando un usuario sigue un enlace desde otro sitio. No envía la cookie en peticiones de subrecursos entre sitios, como las desencadenadas por las etiquetas <img>, <script> o <iframe>, fetch() o XMLHttpRequest, y tampoco envía la cookie en navegaciones entre sitios que usen POST u otros métodos no seguros.

A partir de 2020, los navegadores basados en Chromium (Chrome, Edge, Opera) tratan cualquier cookie establecida sin un atributo SameSite explícito como SameSite=Lax de forma predeterminada. Firefox y Safari no aplican ese valor predeterminado. En esos navegadores, una cookie que omite SameSite sigue siendo elegible para enviarse en peticiones entre sitios, sujeta en cambio a sus propios controles de prevención de rastreo y de cookies de terceros (Enhanced Tracking Protection / Total Cookie Protection de Firefox, Intelligent Tracking Prevention de Safari). Obsérvese que omitir el atributo no es lo mismo que establecer SameSite=None, que es un valor explícito que además requiere el atributo Secure para ser aceptado. Esos controles de prevención de rastreo son mecanismos de privacidad y no sustituyen el establecimiento de SameSite, y se comportan de manera diferente a una restricción explícita SameSite=Lax. Los evaluadores no deben asumir que una cookie está protegida contra CSRF solo porque una petición entre sitios parezca bloqueada en Firefox o Safari: hay que verificar la cabecera Set-Cookie real en lugar de inferir la protección a partir del comportamiento observado del navegador.

Cuando un navegador basado en Chromium aplica Lax de forma predeterminada, usa una versión más permisiva de Lax: una cookie sin atributo SameSite se sigue enviando en peticiones POST de nivel superior entre sitios durante dos minutos después de establecerse. Las cookies que establecen explícitamente SameSite=Lax no tienen esta excepción. Esto significa que un POST entre sitios enviado poco después de que el usuario inicie sesión aún puede llevar una cookie de sesión que no tenga atributo SameSite.

Valor None

El valor None especifica que el navegador enviará la cookie en todos los contextos, incluidas las peticiones entre sitios (el comportamiento normal antes de la implementación de SameSite). Una cookie que establece SameSite=None también debe establecer el atributo Secure, p. ej. SameSite=None; Secure. Los navegadores basados en Chromium y Firefox rechazan una cookie SameSite=None sin Secure, de modo que la cookie no se almacena en absoluto. Safari no aplica este requisito (véase la tabla de compatibilidad de navegadores en MDN).

Prefijos de las cookies

Por diseño, las cookies no tienen la capacidad de garantizar la integridad y la confidencialidad de la información almacenada en ellas. Esas limitaciones hacen imposible que un servidor tenga confianza sobre cómo se establecieron los atributos de una cookie dada en el momento de su creación. Para dar a los servidores tales capacidades de forma retrocompatible, la industria ha introducido el concepto de Cookie Name Prefixes (prefijos en el nombre de la cookie) para facilitar el paso de dichos detalles incrustados como parte del nombre de la cookie.

Prefijo Host

El prefijo __Host- espera que las cookies cumplan las siguientes condiciones:

  1. La cookie debe establecerse con el atributo Secure.
  2. La cookie debe establecerse desde un URI considerado seguro por el agente de usuario.
  3. Se envía solo al host que estableció la cookie y NO DEBE incluir ningún atributo Domain.
  4. La cookie debe establecerse con el atributo Path con un valor de / para que se envíe con cada petición al host.

Por esta razón, la cookie Set-Cookie: __Host-SID=12345; Secure; Path=/ sería aceptada, mientras que cualquiera de las siguientes sería siempre rechazada: Set-Cookie: __Host-SID=12345 Set-Cookie: __Host-SID=12345; Secure Set-Cookie: __Host-SID=12345; Domain=site.example Set-Cookie: __Host-SID=12345; Domain=site.example; Path=/ Set-Cookie: __Host-SID=12345; Secure; Domain=site.example; Path=/

Prefijo Secure

El prefijo __Secure- es menos restrictivo y se puede introducir añadiendo al nombre de la cookie la cadena __Secure-, que distingue entre mayúsculas y minúsculas. Se esperaría que cualquier cookie que coincida con el prefijo __Secure- cumpla las siguientes condiciones:

  1. La cookie debe establecerse con el atributo Secure.
  2. La cookie debe establecerse desde un URI considerado seguro por el agente de usuario.

Buenas prácticas

Según las necesidades de la aplicación y cómo deba funcionar la cookie, deben aplicarse los atributos y prefijos. Cuanto más blindada esté la cookie, mejor.

Juntando todo esto, podemos definir la configuración de atributos de cookie más segura como: Set-Cookie: __Host-SID=<session token>; path=/; Secure; HttpOnly; SameSite=Strict.
