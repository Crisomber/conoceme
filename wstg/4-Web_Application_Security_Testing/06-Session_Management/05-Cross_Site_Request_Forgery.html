Cross Site Request Forgery

ID
WSTG-SESS-05

Resumen

Cross-Site Request Forgery (CSRF) es un ataque que obliga a un usuario final a ejecutar acciones no deseadas en una aplicación web en la que está autenticado actualmente. Con un poco de ayuda de ingeniería social (como enviar un enlace por correo electrónico o chat), un atacante puede obligar a los usuarios de una aplicación web a ejecutar acciones elegidas por el atacante. Un exploit CSRF exitoso puede comprometer los datos y las operaciones del usuario final cuando el objetivo es un usuario normal. Si el usuario final atacado es la cuenta de administrador, un ataque CSRF puede comprometer toda la aplicación web.

CSRF se basa en:

  1. El comportamiento del navegador web respecto al manejo de la información relacionada con la sesión, como las cookies y la información de autenticación HTTP.
  2. El conocimiento que tiene un atacante de URL, peticiones o funcionalidades válidas de la aplicación web.
  3. Una gestión de sesiones de la aplicación que se basa únicamente en información conocida por el navegador.
  4. La existencia de etiquetas HTML cuya presencia provoca el acceso inmediato a un recurso HTTP[S]; por ejemplo, la etiqueta de imagen img.

Los puntos 1, 2 y 3 son esenciales para que la vulnerabilidad esté presente, mientras que el punto 4 facilita la explotación real, pero no es estrictamente necesario.

  1. Los navegadores envían automáticamente la información utilizada para identificar una sesión de usuario. Supóngase que site es un sitio que aloja una aplicación web y que el usuario victim acaba de autenticarse en site. En respuesta, site envía a victim una cookie que identifica las peticiones enviadas por victim como pertenecientes a la sesión autenticada de victim. Una vez que el navegador recibe la cookie establecida por site, la enviará automáticamente junto con cualquier petición posterior dirigida a site.
  2. Si la aplicación no utiliza información relacionada con la sesión en las URL, entonces pueden identificarse las URL de la aplicación, sus parámetros y los valores legítimos. Esto puede lograrse mediante análisis de código o accediendo a la aplicación y tomando nota de los formularios y las URL incrustados en el HTML o JavaScript.
  3. "Conocida por el navegador" se refiere a información como cookies o información de autenticación basada en HTTP (como la autenticación Basic y no la autenticación basada en formularios), que es almacenada por el navegador y posteriormente está presente en cada petición dirigida a un área de la aplicación que solicita dicha autenticación. Las vulnerabilidades que se analizan a continuación se aplican a las aplicaciones que dependen completamente de este tipo de información para identificar una sesión de usuario.

Por simplicidad, considérense las URL accesibles mediante GET (aunque el análisis también se aplica a las peticiones POST). Si victim ya se ha autenticado, el envío de otra petición provoca que la cookie se envíe automáticamente con ella. La petición GET podría ser enviada por el usuario de varias maneras diferentes:

  • Usando la aplicación web
  • Escribiendo la URL directamente en el navegador
  • Siguiendo un enlace externo que apunta a la URL

Estas invocaciones son indistinguibles para la aplicación. En particular, la tercera puede ser bastante peligrosa. Existen varias técnicas y vulnerabilidades que pueden disfrazar las propiedades reales de un enlace. El enlace puede estar incrustado en un mensaje de correo electrónico, aparecer en un sitio malicioso al que se atrae al usuario, o aparecer en contenido alojado por un tercero (como otro sitio o un correo electrónico HTML) y apuntar a un recurso de la aplicación. Si el usuario hace clic en el enlace, dado que ya está autenticado por la aplicación web en site, el navegador emitirá una petición GET a la aplicación web, acompañada de la información de autenticación (la cookie con el ID de sesión). Esto da como resultado que se realice en la aplicación web una operación válida que el usuario no espera; por ejemplo, una transferencia de fondos en una aplicación de banca web.

Al utilizar una etiqueta como img, tal como se especifica en el punto 4 anterior, ni siquiera es necesario que el usuario siga un enlace particular. Supóngase que el atacante envía al usuario un correo electrónico que lo induce a visitar una URL que se refiere a una página que contiene el siguiente HTML (excesivamente simplificado).

<html>
    <body>
...
<img src="https://www.company.example/action" width="0" height="0">
...
    </body>
</html>

Cuando el navegador muestre esta página, intentará mostrar también la imagen especificada de dimensión cero (por lo tanto, invisible) de https://www.company.example. Esto da como resultado que se envíe automáticamente una petición a la aplicación web alojada en site. No importa que la URL de la imagen no se refiera a una imagen apropiada, ya que su presencia activará de todos modos la petición action especificada en el campo src. Esto ocurre siempre que la descarga de imágenes no esté deshabilitada en el navegador. La mayoría de los navegadores no tienen deshabilitada la descarga de imágenes, ya que eso dejaría inservibles la mayoría de las aplicaciones web.

El problema aquí es consecuencia de:

  • Etiquetas HTML en la página que provocan la ejecución automática de una petición HTTP (img es una de ellas).
  • El navegador no tiene forma de saber que el recurso referenciado por img no es una imagen legítima.
  • La carga de imágenes se produce independientemente de la ubicación de la supuesta fuente de la imagen, es decir, el formulario y la propia imagen no necesitan estar en el mismo host ni siquiera en el mismo dominio.

El hecho de que contenido HTML no relacionado con la aplicación web pueda hacer referencia a componentes de la aplicación, y el hecho de que el navegador componga automáticamente una petición válida hacia la aplicación, permite este tipo de ataque. No hay forma de prohibir este comportamiento a menos que se haga imposible que el atacante interactúe con la funcionalidad de la aplicación.

En entornos integrados de correo/navegador, simplemente mostrar un mensaje de correo electrónico que contenga la referencia a la imagen daría lugar a la ejecución de la petición a la aplicación web con la cookie asociada del navegador. Los mensajes de correo electrónico pueden hacer referencia a URL de imágenes aparentemente válidas como:

<img src="https://[attacker]/picture.gif" width="0" height="0">

En este ejemplo, [attacker] es un sitio controlado por el atacante. Mediante un mecanismo de redirección, el sitio malicioso puede usar https://[attacker]/picture.gif para dirigir a la víctima a https://[thirdparty]/action y activar la action.

Las cookies no son el único ejemplo involucrado en este tipo de vulnerabilidad. Las aplicaciones web cuya información de sesión es suministrada enteramente por el navegador también son vulnerables. Esto incluye las aplicaciones que dependen únicamente de mecanismos de autenticación HTTP, ya que la información de autenticación es conocida por el navegador y se envía automáticamente en cada petición. Esto no incluye la autenticación basada en formularios, que ocurre una sola vez y genera alguna forma de información relacionada con la sesión, normalmente una cookie.

Supongamos que la víctima ha iniciado sesión en una consola de administración web de un firewall. Para iniciar sesión, un usuario tiene que autenticarse y la información de sesión se almacena en una cookie.

Supongamos que la consola de administración web del firewall tiene una función que permite a un usuario autenticado eliminar una regla especificada por su ID numérico, o todas las reglas de la configuración si el usuario especifica * (una función peligrosa en la realidad, pero que hace el ejemplo más interesante). A continuación se muestra la página de eliminación. Supongamos que el formulario, por simplicidad, emite una petición GET. Para eliminar la regla número uno:

https://[target]/fwmgt/delete?rule=1

Para eliminar todas las reglas:

https://[target]/fwmgt/delete?rule=*

Este ejemplo es intencionalmente ingenuo, pero muestra de forma simplificada los peligros de CSRF.

Usando el formulario ilustrado en la figura anterior, introducir el valor * y hacer clic en el botón Delete enviará la siguiente petición GET:

https://www.company.example/fwmgt/delete?rule=*

Esto eliminaría todas las reglas del firewall.


Figura 4.6.5-3: Session Riding Firewall Management 2

El usuario también podría haber logrado los mismos resultados enviando manualmente la URL:

https://[target]/fwmgt/delete?rule=*

O siguiendo un enlace que apunte, directamente o mediante una redirección, a la URL anterior. O, nuevamente, accediendo a una página HTML con una etiqueta img incrustada que apunte a la misma URL.

En todos estos casos, si el usuario ha iniciado sesión actualmente en la aplicación de administración del firewall, la petición tendrá éxito y modificará la configuración del firewall. Se pueden imaginar ataques dirigidos a aplicaciones sensibles que realicen automáticamente pujas en subastas, transferencias de dinero, pedidos, cambios en la configuración de componentes de software críticos, etc.

Un aspecto interesante es que estas vulnerabilidades pueden explotarse detrás de un firewall; es decir, basta con que el enlace atacado sea alcanzable por la víctima y no directamente por el atacante. En particular, puede ser cualquier servidor web de una intranet; por ejemplo, en el escenario de administración de firewall mencionado antes, que es poco probable que esté expuesto a internet.

Las aplicaciones auto-vulnerables, es decir, las aplicaciones que se utilizan tanto como vector de ataque como objetivo (como las aplicaciones de correo web), empeoran las cosas. Dado que los usuarios han iniciado sesión cuando leen sus mensajes de correo electrónico, una aplicación vulnerable de este tipo puede permitir a los atacantes realizar acciones como eliminar mensajes o enviar mensajes que parecen provenir de la víctima.

Objetivos de la prueba

  • Determinar si es posible iniciar peticiones en nombre de un usuario que no han sido iniciadas por el usuario.

Cómo probar

Consideraciones sobre las cookies SameSite

Que las PoC anteriores funcionen depende del atributo SameSite de la cookie de sesión y del valor predeterminado del navegador. Consúltese esa sección para ver cómo SameSite=Lax trata las navegaciones de nivel superior frente a las peticiones de subrecursos.

En resumen: la PoC con la etiqueta img es una petición de subrecurso, y la PoC con el formulario de envío automático usa POST; ninguna cumple la excepción de Lax para navegaciones de nivel superior con un método seguro, por lo que en un navegador que usa Lax de forma predeterminada (navegadores basados en Chromium, desde 2020), la cookie de sesión no se adjuntará y la PoC tal como está escrita no se activará. Un formulario con method="GET" aún tendría éxito bajo Lax, ya que es una navegación GET de nivel superior. Obsérvese también que cuando Lax se aplica como valor predeterminado, los navegadores basados en Chromium aún envían la cookie en peticiones POST de nivel superior entre sitios durante dos minutos después de establecerse (véase Valor Lax), por lo que una PoC basada en POST disparada inmediatamente después de la autenticación aún puede tener éxito.

No se debe concluir que una aplicación está a salvo de CSRF solo porque una PoC no se activa en un navegador: hay que comprobar la cabecera Set-Cookie real de la cookie de sesión. Si la PoC del formulario de envío automático no se activa, se puede volver a probar en un navegador que no use Lax de forma predeterminada (p. ej., Firefox), porque el envío del formulario es una navegación de nivel superior. Repetir así la PoC de la etiqueta img no ayudará: la petición de la imagen es una petición de subrecurso de terceros y, por defecto, Firefox particiona y Safari bloquea las cookies de terceros, por lo que la cookie de sesión no se envía.

Gestión de sesiones

Audite la aplicación para determinar si su gestión de sesiones es vulnerable. Si la gestión de sesiones depende únicamente de valores del lado del cliente (información disponible para el navegador), entonces la aplicación es vulnerable. "Valores del lado del cliente" se refiere a cookies y credenciales de autenticación HTTP (autenticación Basic y otras formas de autenticación HTTP; no la autenticación basada en formularios, que es una autenticación a nivel de aplicación).

Los recursos accesibles mediante peticiones HTTP GET son fácilmente vulnerables, aunque las peticiones POST pueden automatizarse mediante JavaScript y también son vulnerables; por lo tanto, el uso de POST por sí solo no es suficiente para corregir la aparición de vulnerabilidades CSRF.

En el caso de POST, se puede utilizar el siguiente ejemplo.

  1. Crear una página HTML similar a la que se muestra a continuación
  2. Alojar el HTML en un sitio malicioso o de terceros
  3. Enviar el enlace de la página a la(s) víctima(s) e inducirlas a hacer clic en él.
<html>
<body onload='document.CSRF.submit()'>

<form action='https://targetWebsite/Authenticate.jsp' method='POST' name='CSRF'>
    <input type='hidden' name='name' value='Hacked'>
    <input type='hidden' name='password' value='Hacked'>
</form>

</body>
</html>

En el caso de aplicaciones web en las que los desarrolladores utilizan JSON para la comunicación del navegador al servidor, puede surgir un problema debido a que el formato JSON no tiene parámetros de consulta, los cuales son imprescindibles con los formularios de envío automático. Para eludir este caso, se puede usar un formulario de envío automático con payloads (cargas útiles) JSON que incluyan una entrada oculta para explotar CSRF. Habrá que cambiar el tipo de codificación (enctype) a text/plain para asegurar que el payload se entregue tal cual. El código del exploit se verá así:

<html>
 <body>
  <script>history.pushState('', '', '/')</script>
   <form action='https://victimsite.com' method='POST' enctype='text/plain'>
     <input type='hidden' name='{"name":"hacked","password":"hacked","padding":"'value='something"}' />
     <input type='submit' value='Submit request' />
   </form>
 </body>
</html>

La petición POST será la siguiente:

POST / HTTP/1.1
Host: victimsite.com
Content-Type: text/plain

{"name":"hacked","password":"hacked","padding":"=something"}

Cuando estos datos se envían como una petición POST, el servidor aceptará sin problema los campos name y password e ignorará el que tiene el nombre padding, ya que no lo necesita.
