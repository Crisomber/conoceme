Contaminación de prototipos (Prototype Pollution)

ID
WSTG-INJT-22

Resumen

JavaScript es un lenguaje basado en prototipos. Casi todos los objetos heredan de Object.prototype, y cualquier propiedad que no se encuentre directamente en un objeto se busca a través de la cadena de prototipos. La contaminación de prototipos (prototype pollution) ocurre cuando una aplicación usa entradas controladas por el atacante para establecer las claves de un objeto durante una mezcla (merge) recursiva, una clonación o una asignación basada en rutas, lo que permite al atacante llegar a Object.prototype a través de una clave especial como __proto__, constructor o prototype. Dado que ese prototipo es compartido por todos los objetos del entorno de ejecución, la propiedad inyectada se vuelve visible silenciosamente para partes no relacionadas de la aplicación.

Nota: esto no es lo mismo que HTTP Parameter Pollution; a pesar del nombre similar, las dos vulnerabilidades no están relacionadas.

La contaminación por sí sola rara vez causa daño directamente. Su impacto depende de un gadget: código existente que más tarde lee una propiedad que el atacante logró plantar y luego la usa de forma sensible. La misma causa raíz aparece en dos contextos:

  • Del lado del servidor (Node.js): dependiendo del gadget disponible, el impacto va desde la denegación de servicio y la elusión de la lógica de seguridad hasta la ejecución remota de código. Un ejemplo bien conocido es el RCE de Kibana, CVE-2019-7609.
  • Del lado del cliente (navegador): combinada con un gadget adecuado, comúnmente conduce a Cross-Site Scripting basado en DOM y puede usarse para eludir defensas del lado del cliente.

Objetivos de la prueba

  • Identificar las funciones y bibliotecas que mezclan, clonan o asignan de forma recursiva propiedades controladas por el usuario.
  • Determinar si la entrada del usuario puede alcanzar y modificar Object.prototype.
  • Identificar los gadgets que convierten la contaminación de prototipos en un impacto concreto.

Cómo probar

El siguiente ejemplo ilustra la causa raíz. Una mezcla recursiva ingenua copia cada clave de un objeto controlado por el atacante en un objeto destino:

function merge(target, source) {
    for (const key in source) {
        if (typeof source[key] === "object" && typeof target[key] === "object") {
            merge(target[key], source[key]);
        } else {
            target[key] = source[key];
        }
    }
    return target;
}

Si el objeto fuente se analiza a partir de una entrada del usuario como {"__proto__": {"polluted": "yes"}}, la asignación entra en __proto__ y escribe sobre Object.prototype. A partir de entonces, todos los objetos del entorno de ejecución heredan la propiedad plantada:

merge({}, JSON.parse('{"__proto__": {"polluted": "yes"}}'));
({}).polluted;   // "yes"  -> Object.prototype was polluted

Pruebas de caja negra

Identificar las fuentes

La contaminación de prototipos es alcanzable a través de cualquier entrada cuyas claves terminen como nombres de propiedades de un objeto. Se debe revisar la aplicación en busca de:

  • La cadena de consulta (query string) de la URL y el fragmento de la URL (hash), usando notación de corchetes o de puntos, p. ej., ?__proto__[key]=value o ?__proto__.key=value.
  • Cuerpos de petición JSON que se deserializan y luego se mezclan o clonan (los endpoints de configuración, perfil o ajustes son candidatos comunes).
  • Otras entradas estructuradas analizadas en objetos anidados, como datos de formularios o cookies.

Contaminación de prototipos del lado del cliente

Se envía una sonda que intenta establecer una propiedad con nombre único en el prototipo a través de una fuente candidata. Las dos codificaciones siguientes expresan la misma intención:

https://example.com/#__proto__[testpolluted]=reflected
https://example.com/#constructor[prototype][testpolluted]=reflected

Luego se confirma en la consola de desarrollador del navegador si la propiedad se filtró al prototipo global, leyéndola desde un objeto vacío completamente nuevo:

({}).testpolluted;
// "reflected" -> Object.prototype is polluted via this source
// undefined   -> not polluted through this source

Si se devuelve el valor, la fuente es explotable y el siguiente paso es encontrar un gadget que convierta la propiedad contaminada en XSS basado en DOM (por ejemplo, una propiedad que una biblioteca lee al construir marcado o al configurar el comportamiento de scripts). Las herramientas de navegador que buscan tanto fuentes como gadgets, como DOM Invader (véase Herramientas), aceleran significativamente esta fase.

Contaminación de prototipos del lado del servidor

Aquí el evaluador no puede leer el prototipo desde una consola, por lo que la detección es indirecta: se contamina una propiedad y se observa un cambio de comportamiento visible externamente. Se envía un cuerpo JSON que anida la clave especial dentro de un objeto por lo demás normal, dirigido a un endpoint que mezcla o clona los datos de la petición:

POST /api/update HTTP/1.1
Host: example.com
Content-Type: application/json

{"name":"test","__proto__":{"json spaces":10}}

Un indicador fiable y no destructivo en aplicaciones Express es contaminar la propiedad json spaces: si una respuesta JSON posterior de la aplicación llega con formato legible (con sangría) cuando antes no lo tenía, el servidor leyó el ajuste de sangría del prototipo contaminado, lo que confirma la vulnerabilidad. Otros indicadores de comportamiento incluyen:

  • Una propiedad que el cliente nunca envió apareciendo en respuestas JSON posteriores.
  • Un cambio en el estado HTTP, las cabeceras o la negociación de contenido después de contaminar una propiedad que el framework lee internamente.
  • Un error distintivo o un cambio de análisis para entradas que antes se aceptaban.

Evaluar el impacto

Dado que el impacto depende del gadget, se debe analizar cada contaminación confirmada en busca de consecuencias realistas. Del lado del cliente, esto es con mayor frecuencia XSS basado en DOM o la elusión de un control de seguridad. Del lado del servidor, los gadgets han escalado históricamente a denegación de servicio, elusión de autenticación o autorización y ejecución remota de código. Cualquier contaminación de prototipos confirmada debe tratarse como de severidad potencialmente alta hasta que el análisis de gadgets descarte el impacto.

Pruebas de caja gris

Cuando se dispone del código fuente, se buscan directamente los patrones vulnerables en lugar de sondear a ciegas.

Se buscan rutinas recursivas de mezcla (merge), clonación (clone), extensión (extend) o asignación profunda, ya sean escritas a mano o proporcionadas por una biblioteca de utilidades. Las funciones que recorren una ruta anidada de claves y asignan dentro de un objeto son los principales sinks. Un grep típico se dirigiría a las funciones auxiliares de mezcla y asignación, a las utilidades de clonación profunda y al acceso a propiedades mediante una ruta controlada por el usuario.

Para cada sink candidato, se confirma si las claves se validan antes de la asignación. El código seguro rechaza u omite __proto__, constructor y prototype, o usa objetos sin prototipo:

// Vulnerable: blindly assigns into a nested key path
target[key] = source[key];

// Safer: refuse dangerous keys
if (key === "__proto__" || key === "constructor" || key === "prototype") {
    continue;
}

También se confirman las versiones de cualquier dependencia con avisos conocidos de contaminación de prototipos, ya que muchas utilidades populares han sido parcheadas con el tiempo. Cuando se dispone del código fuente, es sencillo rastrear la entrada del usuario desde el analizador de peticiones hasta estos sinks y establecer su alcanzabilidad, así como identificar gadgets en la aplicación o sus dependencias.

Corrección

  • Sanear las claves de las propiedades antes de la asignación, rechazando explícitamente __proto__, constructor y prototype.
  • Usar objetos sin prototipo para datos de tipo mapa, por ejemplo Object.create(null), o usar la estructura de datos Map en lugar de objetos simples.
  • Congelar el prototipo base con Object.freeze(Object.prototype) donde el comportamiento de la aplicación lo permita.
  • Validar los datos estructurados entrantes contra un esquema estricto (por ejemplo, JSON Schema) para que se descarten las claves inesperadas.
  • Preferir utilidades de mezcla y clonación bien mantenidas, y mantener todas las dependencias actualizadas a versiones que mitiguen la contaminación de prototipos.
  • En Node.js, la opción de ejecución --disable-proto=delete elimina el accesor __proto__ como medida de defensa en profundidad.
