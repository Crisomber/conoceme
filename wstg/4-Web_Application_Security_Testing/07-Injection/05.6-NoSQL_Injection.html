Inyección NoSQL

Resumen

Las bases de datos NoSQL ofrecen restricciones de consistencia más laxas que las bases de datos SQL tradicionales. Al requerir menos restricciones relacionales y comprobaciones de consistencia, las bases de datos NoSQL a menudo ofrecen beneficios de rendimiento y escalabilidad. Sin embargo, estas bases de datos siguen siendo potencialmente vulnerables a ataques de inyección, aunque no usen la sintaxis SQL tradicional. Dado que estos ataques de inyección NoSQL pueden ejecutarse dentro de un lenguaje procedimental, en lugar de en el lenguaje declarativo SQL, el impacto potencial es mayor que el de la inyección SQL tradicional.

Las llamadas a las bases de datos NoSQL se escriben en el lenguaje de programación de la aplicación, en una llamada de API personalizada o con un formato acorde a una convención común (como XML, JSON, LINQ, etc.). La entrada maliciosa dirigida a esas especificaciones puede no activar las comprobaciones de sanitización principales de la aplicación. Por ejemplo, filtrar los caracteres especiales HTML comunes, como < > & ;, no evitará ataques contra una API JSON, donde los caracteres especiales incluyen / { } :.

Existen cientos de bases de datos NoSQL disponibles para usar dentro de una aplicación, que ofrecen API en una variedad de lenguajes y modelos de relación. Cada una ofrece características y restricciones diferentes. Dado que no hay un lenguaje común entre ellas, el código de inyección de ejemplo no se aplicará por igual a todas las bases de datos NoSQL. Por esta razón, cualquiera que pruebe ataques de inyección NoSQL necesitará familiarizarse con la sintaxis, el modelo de datos y el lenguaje de programación subyacente para elaborar pruebas específicas.

Los ataques de inyección NoSQL pueden ejecutarse en áreas diferentes de una aplicación en comparación con la inyección SQL tradicional. Mientras que la inyección SQL se ejecutaría dentro del motor de la base de datos, las variantes de NoSQL pueden ejecutarse en la capa de aplicación o en la capa de la base de datos, según la API de NoSQL utilizada y el modelo de datos. Normalmente, los ataques de inyección NoSQL se ejecutan donde la cadena de ataque se analiza (parsing), se evalúa o se concatena en una llamada a la API de NoSQL.

También pueden ser relevantes ataques adicionales de temporización debido a la falta de comprobaciones de concurrencia dentro de una base de datos NoSQL. Estos no se tratan en las pruebas de inyección. Al momento de escribir esto, MongoDB es la base de datos NoSQL más utilizada, por lo que todos los ejemplos usarán las API de MongoDB.

Cómo probar

Vulnerabilidades de inyección NoSQL en MongoDB

La API de MongoDB espera llamadas en BSON (Binary JSON) e incluye una herramienta segura de ensamblado de consultas BSON. Sin embargo, según la documentación de MongoDB, se permite JSON no serializado y expresiones JavaScript en varios parámetros de consulta alternativos. La llamada de API más comúnmente usada que permite entrada JavaScript arbitraria es el operador $where.

El operador $where de MongoDB normalmente se usa como un filtro o comprobación simple, igual que en SQL.

db.myCollection.find( { $where: "this.credits`` ``==`` ``this.debits" } );

Opcionalmente, también se evalúa JavaScript para permitir condiciones más avanzadas.

db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );

Ejemplo 1

Si un atacante pudiera manipular los datos pasados al operador $where, ese atacante podría incluir JavaScript arbitrario para que se evaluara como parte de la consulta de MongoDB. En el siguiente código se expone una vulnerabilidad de ejemplo, si la entrada del usuario se pasa directamente a la consulta de MongoDB sin sanitizar.

db.myCollection.find( { active: true, $where: function() { return obj.credits - obj.debits < $userInput; } } );;

Como en las pruebas de otros tipos de inyección, no es necesario explotar por completo la vulnerabilidad para demostrar un problema. Inyectando caracteres especiales relevantes para el lenguaje de la API objetivo, y observando los resultados, un evaluador puede determinar si la aplicación sanitizó correctamente la entrada. Por ejemplo, en MongoDB, si se pasara sin sanitizar una cadena que contuviera alguno de los siguientes caracteres especiales, se provocaría un error de la base de datos.

' " \ ; { }

Con la inyección SQL normal, una vulnerabilidad similar permitiría a un atacante ejecutar comandos SQL arbitrarios, exponiendo o manipulando los datos a voluntad. Sin embargo, como JavaScript es un lenguaje con todas sus funciones, esto no solo permite a un atacante manipular datos, sino también ejecutar código arbitrario. Por ejemplo, en lugar de simplemente causar un error al probar, un exploit completo usaría los caracteres especiales para elaborar JavaScript válido.

Esta entrada 0;var date=new Date(); do{curDate = new Date();}while(curDate-date<10000), insertada en $userInput en el código de ejemplo anterior, daría como resultado la ejecución de la siguiente función JavaScript. Esta cadena de ataque específica haría que toda la instancia de MongoDB se ejecutara al 100% de uso de CPU durante 10 segundos.

function() { return obj.credits - obj.debits < 0;var date=new Date(); do{curDate = new Date();}while(curDate-date<10000); }

Ejemplo 2

Incluso si la entrada utilizada dentro de las consultas está completamente sanitizada o parametrizada, existe una ruta alternativa por la que se podría activar una inyección NoSQL. Muchas instancias de NoSQL tienen sus propios nombres de variable reservados, independientes del lenguaje de programación de la aplicación.

Por ejemplo, en MongoDB, la propia sintaxis $where es un operador de consulta reservado. Debe pasarse a la consulta exactamente como se muestra; cualquier alteración causaría un error de la base de datos. Sin embargo, como $where también es un nombre de variable válido en PHP, podría ser posible que un atacante insertara código en la consulta creando una variable PHP llamada $where. La documentación de PHP MongoDB advierte explícitamente a los desarrolladores:

Asegúrense de usar comillas simples para todos los operadores de consulta especiales (que comienzan con $), de modo que PHP no intente reemplazar $exists con el valor de la variable $exists.

Incluso si una consulta no dependiera de ninguna entrada del usuario, como en el siguiente ejemplo, un atacante podría explotar MongoDB reemplazando el operador con datos maliciosos.

db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );

Una forma de asignar potencialmente datos a variables PHP es mediante la contaminación de parámetros HTTP (véase: HTTP Parameter pollution). Al crear una variable llamada $where mediante contaminación de parámetros, se podría provocar un error de MongoDB que indique que la consulta ya no es válida. Cualquier valor de $where distinto de la propia cadena $where debería bastar para demostrar la vulnerabilidad. Un atacante desarrollaría un exploit completo insertando lo siguiente:

$where: function() { //arbitrary JavaScript here }
