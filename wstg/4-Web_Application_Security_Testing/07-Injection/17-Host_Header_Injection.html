Inyección en la cabecera Host

ID
WSTG-INJT-17

Resumen

Un servidor web suele alojar varias aplicaciones web en la misma dirección IP, haciendo referencia a cada aplicación mediante el host virtual. En una petición HTTP entrante, los servidores web suelen despachar la petición al host virtual de destino según el valor suministrado en la cabecera Host. Sin una validación adecuada del valor de la cabecera, el atacante puede suministrar una entrada inválida para hacer que el servidor web:

  • Despache las peticiones al primer host virtual de la lista.
  • Realice una redirección a un dominio controlado por el atacante.
  • Realice envenenamiento de caché web (web cache poisoning).
  • Manipule la funcionalidad de restablecimiento de contraseña.
  • Permita el acceso a hosts virtuales que no estaban destinados a ser accesibles externamente.

Objetivos de la prueba

  • Evaluar si la cabecera Host se analiza dinámicamente en la aplicación.
  • Eludir los controles de seguridad que dependen de la cabecera.

Cómo probar

La prueba inicial es tan simple como suministrar otro dominio (p. ej., attacker.com) en el campo de la cabecera Host. Es la forma en que el servidor web procesa el valor de la cabecera lo que determina el impacto. El ataque es válido cuando el servidor web procesa la entrada para enviar la petición a un host controlado por el atacante que reside en el dominio suministrado, y no a un host virtual interno que reside en el servidor web.

GET / HTTP/1.1
Host: www.attacker.com
[...]

En el caso más simple, esto puede provocar una redirección 302 al dominio suministrado.

HTTP/1.1 302 Found
[...]
Location: https://www.attacker.com/login.php

Alternativamente, el servidor web puede enviar la petición al primer host virtual de la lista.

Elusión mediante la cabecera X-Forwarded-Host

En caso de que la inyección en la cabecera Host se mitigue comprobando las entradas inválidas inyectadas mediante la cabecera Host, se puede suministrar el valor en la cabecera X-Forwarded-Host.

GET / HTTP/1.1
Host: www.example.com
X-Forwarded-Host: www.attacker.com
[...]

Potencialmente produciendo una salida del lado del cliente como:

[...]
<link src="https://www.attacker.com/link" />
[...]

Una vez más, esto depende de cómo el servidor web procese el valor de la cabecera.

Envenenamiento de caché web

Usando esta técnica, un atacante puede manipular una caché web para servir contenido envenenado a cualquiera que lo solicite. Esto depende de la capacidad de envenenar el proxy de caché que ejecuta la propia aplicación, las CDN u otros proveedores intermedios. Como resultado, la víctima no tendrá control sobre la recepción del contenido malicioso al solicitar la aplicación vulnerable.

GET / HTTP/1.1
Host: www.attacker.com
[...]

Lo siguiente se servirá desde la caché web cuando una víctima visite la aplicación vulnerable.

[...]
<link src="https://www.attacker.com/link" />
[...]

Envenenamiento del restablecimiento de contraseña

Es habitual que la funcionalidad de restablecimiento de contraseña incluya el valor de la cabecera Host al crear enlaces de restablecimiento que utilizan un token secreto generado. Si la aplicación procesa un dominio controlado por el atacante para crear un enlace de restablecimiento de contraseña, la víctima puede hacer clic en el enlace del correo electrónico y permitir que el atacante obtenga el token de restablecimiento, restableciendo así la contraseña de la víctima.

El siguiente ejemplo muestra un enlace de restablecimiento de contraseña generado en PHP usando el valor de $_SERVER['HTTP_HOST'], que se establece según el contenido de la cabecera HTTP Host:

$reset_url = "https://" . $_SERVER['HTTP_HOST'] . "/reset.php?token=" .$token;
send_reset_email($email,$rset_url);

Al realizar una petición HTTP a la página de restablecimiento de contraseña con una cabecera Host manipulada, podemos modificar a dónde apunta la URL:

POST /request_password_reset.php HTTP/1.1
Host: www.attacker.com
[...]

email=user@example.org

El dominio especificado (www.attacker.com) se utilizará entonces en el enlace de restablecimiento, que se envía por correo electrónico al usuario. Cuando el usuario haga clic en este enlace, el atacante puede robar el token y comprometer su cuenta.

... Email snippet ...

Click on the following link to reset your password:

https://www.attacker.com/reset.php?token=12345

... Email snippet ...

Acceso a hosts virtuales privados

En algunos casos, un servidor puede tener hosts virtuales que no están destinados a ser accesibles externamente. Esto es más común con una configuración de DNS de horizonte dividido (split-horizon) (donde los servidores DNS internos y externos devuelven registros diferentes para el mismo dominio).

Por ejemplo, una organización puede tener un único servidor web en su red interna, que aloja tanto su sitio web público (en www.example.org) como su Intranet interna (en intranet.example.org, pero ese registro solo existe en el servidor DNS interno). Aunque no sería posible navegar directamente a intranet.example.org desde fuera de la red (ya que el dominio no se resolvería), puede ser posible acceder a la Intranet realizando una petición desde fuera con la siguiente cabecera Host:

Host: intranet.example.org

Esto también podría lograrse añadiendo una entrada para intranet.example.org en su archivo hosts con la dirección IP pública de www.example.org, o sobrescribiendo la resolución DNS en su herramienta de pruebas.
