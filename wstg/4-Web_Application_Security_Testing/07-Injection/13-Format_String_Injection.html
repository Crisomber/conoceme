Inyección de cadenas de formato

ID
WSTG-INJT-13

Resumen

Una cadena de formato es una secuencia de caracteres terminada en nulo que además contiene especificadores de conversión que se interpretan o convierten en tiempo de ejecución. Si el código del lado del servidor concatena la entrada de un usuario con una cadena de formato, un atacante puede añadir especificadores de conversión adicionales para provocar un error en tiempo de ejecución, divulgación de información o un desbordamiento de búfer.

El peor caso de vulnerabilidades de cadenas de formato se da en lenguajes que no comprueban los argumentos y que además incluyen un especificador %n que escribe en memoria. Estas funciones, si un atacante las explota modificando una cadena de formato, podrían causar divulgación de información y ejecución de código:

  • C y C++ printf y métodos similares fprintf, sprintf, snprintf
  • Perl printf y sprintf

Estas funciones de cadenas de formato no pueden escribir en memoria, pero los atacantes aún pueden provocar divulgación de información cambiando las cadenas de formato para que muestren valores que los desarrolladores no pretendían enviar:

  • Python str.format puede ser abusado inyectando cadenas de formato que alcancen otras variables en el contexto de formateo

Las siguientes funciones de cadenas de formato pueden causar errores en tiempo de ejecución si el atacante añade especificadores de conversión:

  • Java String.format y PrintStream.format
  • PHP printf

El patrón de código que causa una vulnerabilidad de cadena de formato es una llamada a una función de formato de cadenas que contiene entrada del usuario sin sanear. El siguiente ejemplo muestra cómo un printf de depuración podría hacer vulnerable a un programa:

El ejemplo en C:

char *userName = /* input from user controlled field */;

printf("DEBUG Current user: ");
// Vulnerable debugging code
printf(userName);

El ejemplo en Java:

final String userName = /* input from user controlled field */;

System.out.printf("DEBUG Current user: ");
// Vulnerable code:
System.out.printf(userName);

En este ejemplo particular, si el atacante estableciera su userName con uno o más especificadores de conversión, habría un comportamiento no deseado. El ejemplo en C imprimiría el contenido de la memoria si userName contuviera %p%p%p%p%p, y puede corromper el contenido de la memoria si hay un %n en la cadena. En el ejemplo de Java, un username que contenga cualquier especificador que necesite una entrada (incluidos %x o %s) haría que el programa fallara con IllegalFormatException. Aunque los ejemplos siguen estando sujetos a otros problemas, la vulnerabilidad puede corregirse mediante los argumentos de printf printf("DEBUG Current user: %s", userName).

Objetivos de la prueba

  • Evaluar si inyectar especificadores de conversión de cadenas de formato en campos controlados por el usuario provoca un comportamiento no deseado de la aplicación.

Cómo probar

Las pruebas incluyen el análisis del código y la inyección de especificadores de conversión como entrada del usuario en la aplicación bajo prueba.

Análisis estático

Las herramientas de análisis estático pueden encontrar vulnerabilidades de cadenas de formato tanto en el código como en binarios. Ejemplos de herramientas incluyen:

  • C y C++: Flawfinder
  • Java: regla de FindSecurityBugs FORMAT_STRING_MANIPULATION
  • PHP: String formatter Analyzer en phpsa

Inspección manual del código

El análisis estático puede pasar por alto casos más sutiles, incluidas las cadenas de formato generadas por código complejo. Para buscar vulnerabilidades manualmente en una base de código, un evaluador puede buscar todas las llamadas en la base de código que acepten una cadena de formato y rastrearlas hacia atrás para asegurarse de que una entrada no confiable no pueda cambiar la cadena de formato.

Inyección de especificadores de conversión

Los evaluadores pueden comprobarlo a nivel de pruebas unitarias o de pruebas del sistema completo enviando especificadores de conversión en cualquier entrada de cadena. Se debe aplicar fuzzing al programa usando todos los especificadores de conversión de todos los lenguajes que utiliza el sistema bajo prueba. Consulte la página OWASP Format string attack para ver posibles entradas a utilizar. Si la prueba falla, el programa se bloqueará o mostrará una salida inesperada. Si la prueba pasa, el intento de enviar un especificador de conversión debería ser bloqueado, o la cadena debería atravesar el sistema sin problemas, como cualquier otra entrada válida.

Los ejemplos de las siguientes subsecciones tienen una URL de esta forma:

https://vulnerable_host/userinfo?username=x

  • El valor controlado por el usuario es x (para el parámetro username).

Inyección manual

Los evaluadores pueden realizar una prueba manual usando un navegador web u otras herramientas de depuración de APIs web. Se navega a la aplicación o sitio web de modo que la consulta contenga especificadores de conversión. Hay que considerar que la mayoría de los especificadores de conversión necesitan codificación si se envían dentro de una URL, porque contienen caracteres especiales como % y {. La prueba puede introducir una cadena de especificadores %s%s%s%n navegando con la siguiente URL:

https://vulnerable_host/userinfo?username=%25s%25s%25s%25n

Si el sitio web es vulnerable, el navegador o la herramienta debería recibir un error, que puede incluir un tiempo de espera agotado o un código de retorno HTTP 500.

El código Java devuelve el error

java.util.MissingFormatArgumentException: Format specifier '%s'

Dependiendo de la implementación de C, el proceso puede bloquearse por completo con Segmentation Fault.

Fuzzing asistido por herramientas

Las herramientas de fuzzing, incluida wfuzz, pueden automatizar las pruebas de inyección. Para wfuzz, se comienza con un archivo de texto (fuzz.txt en este ejemplo) con una entrada por línea:

fuzz.txt:

alice
%s%s%s%n
%p%p%p%p%p
{event.__init__.__globals__[CONFIG][SECRET_KEY]}

El archivo fuzz.txt contiene lo siguiente:

  • Una entrada válida alice para verificar que la aplicación puede procesar una entrada normal
  • Dos cadenas con especificadores de conversión de tipo C
  • Un especificador de conversión de Python para intentar leer variables globales

Para enviar el archivo de entrada de fuzzing a la aplicación web bajo prueba, se usa el siguiente comando:

wfuzz -c -z file,fuzz.txt,urlencode https://vulnerable_host/userinfo?username=FUZZ

En la llamada anterior, el argumento urlencode habilita el escape apropiado para las cadenas y FUZZ (con letras mayúsculas) le indica a la herramienta dónde introducir las entradas.

Un ejemplo de salida es el siguiente

ID           Response   Lines    Word     Chars       Payload
===================================================================

000000002:   500        0 L      5 W      142 Ch      "%25s%25s%25s%25n"
000000003:   500        0 L      5 W      137 Ch      "%25p%25p%25p%25p%25p"
000000004:   200        0 L      1 W      48 Ch       "%7Bevent.__init__.__globals__%5BCONFIG%5D%5BSECRET_KEY%5D%7D"
000000001:   200        0 L      1 W      5 Ch        "alice"

El resultado anterior valida la debilidad de la aplicación ante la inyección de especificadores de conversión de tipo C %s y %p.
