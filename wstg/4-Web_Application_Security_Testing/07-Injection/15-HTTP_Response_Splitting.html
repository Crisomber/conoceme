División de respuestas HTTP (HTTP Response Splitting)

ID
WSTG-INJT-15

Resumen

HTTP Response Splitting es una vulnerabilidad que se produce cuando una aplicación incorpora entradas del usuario sin sanear en las cabeceras de respuesta HTTP, lo que permite a un atacante inyectar caracteres de retorno de carro (Carriage Return, CR) y salto de línea (Line Feed, LF). Como resultado, una sola respuesta HTTP puede ser interpretada como varias respuestas distintas por clientes o sistemas intermediarios.

La explotación exitosa de HTTP Response Splitting puede conducir a diversos impactos, incluidos envenenamiento de caché web (web cache poisoning), Cross-Site Scripting (XSS), suplantación de contenido (content spoofing), fijación de sesión (session fixation) u otros ataques del lado del cliente, dependiendo de cómo se procese la respuesta inyectada.

Esta sección se centra exclusivamente en identificar y probar vulnerabilidades de HTTP Response Splitting en la capa de aplicación. HTTP Request Smuggling, que se basa en inconsistencias de análisis entre múltiples agentes HTTP, se trata en un capítulo aparte.

Objetivos de la prueba

  • Identificar la entrada controlada por el usuario que se refleja en las cabeceras de respuesta HTTP.
  • Evaluar si es posible inyectar caracteres CR (\r) y LF (\n) en las cabeceras de respuesta.
  • Determinar el impacto potencial de ataques exitosos de HTTP Response Splitting, como el envenenamiento de caché o la explotación del lado del cliente.

Cómo probar

Pruebas de caja negra

Algunas aplicaciones web utilizan entradas proporcionadas por el usuario para generar los valores de ciertas cabeceras de respuesta HTTP. Un ejemplo común es la lógica de redirección, donde la URL de destino se deriva de un parámetro de la petición.

Por ejemplo, supongamos que se pide al usuario elegir entre una interfaz estándar o una avanzada. La opción seleccionada se pasa como parámetro y se refleja en una cabecera de respuesta de redirección.

Si el parámetro interface tiene el valor advanced, la aplicación puede responder con:

HTTP/1.1 302 Moved Temporarily
Date: Sun, 03 Dec 2005 16:22:19 GMT
Location: https://victim.com/main.jsp?interface=advanced

Cuando el navegador recibe esta respuesta, sigue la URL especificada en la cabecera Location. Sin embargo, si la aplicación no valida ni sanea adecuadamente la entrada del usuario, un atacante puede inyectar la secuencia %0d%0a, que representa los caracteres CRLF utilizados para separar las líneas de cabecera HTTP.

Al inyectar secuencias CRLF, un evaluador puede hacer que la respuesta sea interpretada como dos respuestas HTTP separadas por clientes o sistemas intermediarios descendentes, como las cachés web. Este comportamiento puede explotarse para envenenar cachés o entregar contenido malicioso a los usuarios.

Por ejemplo, el evaluador proporciona el siguiente valor para el parámetro interface:

advanced%0d%0aContent-Length:%200%0d%0a%0d%0aHTTP/1.1%20200%20OK%0d%0aContent-Type:%20text/html%0d%0aContent-Length:%2035%0d%0a%0d%0a<html>Sorry,%20System%20Down</html>

La respuesta resultante de la aplicación vulnerable puede ser:

HTTP/1.1 302 Moved Temporarily
Date: Sun, 03 Dec 2005 16:22:19 GMT
Location: https://victim.com/main.jsp?interface=advanced
Content-Length: 0

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 35

<html>Sorry,%20System%20Down</html>

Una caché web que procese esta respuesta puede interpretarla como dos respuestas distintas. Si el atacante emite inmediatamente una petición posterior para /index.html, la caché puede asociar esa petición con la segunda respuesta y almacenarla. Como resultado, todos los usuarios posteriores que accedan a victim.com/index.html a través de esa caché pueden recibir el contenido controlado por el atacante.

Alternativamente, el atacante puede inyectar un payload JavaScript para realizar un ataque de Cross-Site Scripting contra los usuarios servidos por la caché envenenada. Aunque la vulnerabilidad reside en la aplicación, los objetivos principales son sus usuarios.

Para identificar este problema, los evaluadores deben localizar toda la entrada controlada por el usuario que influya en las cabeceras de respuesta HTTP y verificar si es posible inyectar secuencias CRLF.

Las cabeceras de respuesta más comúnmente asociadas con HTTP Response Splitting incluyen:

  • Location
  • Set-Cookie

La explotación exitosa en escenarios reales puede requerir considerar cuidadosamente factores adicionales:

  • Es posible que el evaluador deba elaborar cabeceras de respuesta adecuadas para el almacenamiento en caché (p. ej., Last-Modified establecido en una fecha futura) y potencialmente invalidar entradas de caché existentes mediante cabeceras como Pragma: no-cache.
  • Las aplicaciones pueden filtrar los caracteres CRLF pero permitir codificaciones o representaciones alternativas de caracteres, que a veces pueden aprovecharse para eludir la validación de entrada.
  • Algunas plataformas codifican en URL partes de las cabeceras de respuesta (como la ruta en la cabecera Location) pero dejan sin codificar la cadena de consulta (query string), lo que permite la inyección a través de componentes específicos de la URL.

Para una discusión más profunda de esta clase de ataque y de escenarios de explotación adicionales, consulte los documentos técnicos (whitepapers) listados en la sección de Referencias.

Pruebas de caja gris

En un escenario de pruebas de caja gris, el conocimiento de la arquitectura de la aplicación y del comportamiento del servidor mejora la fiabilidad de la explotación.

Diferentes servidores o intermediarios pueden determinar los límites de los mensajes de manera distinta (p. ej., usando búferes de tamaño fijo), lo que requiere desplazamientos (offsets) o relleno (padding) precisos. Cuando los parámetros vulnerables se transmiten mediante GET, los límites de longitud de la URL pueden truncar los payloads. Los evaluadores deben identificar puntos de inyección o métodos de petición alternativos, como POST, para obtener un mejor control sobre la longitud y la posición del payload.

Corrección

Asegúrese de que la entrada proporcionada por el usuario nunca se coloque en cabeceras HTTP sin una validación y un saneamiento estrictos.

  • Validación de entrada: rechace o elimine la entrada que contenga caracteres de retorno de carro (\r, %0d) o de salto de línea (\n, %0a) antes de que se utilice en cabeceras HTTP.
  • Codificación URL: si la entrada forma parte de una URL (p. ej., en una cabecera Location), asegúrese de que esté correctamente codificada en URL para evitar que los caracteres de control se interpreten como delimitadores.
  • Uso de frameworks seguros: utilice las funciones integradas del framework para establecer cabeceras (p. ej., setHeader(), addHeader()) en lugar de construir manualmente cadenas de respuesta HTTP en bruto. Los entornos modernos normalmente bloquean la inyección de cabeceras por defecto.
