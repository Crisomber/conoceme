Contrabando de peticiones HTTP (HTTP Request Smuggling)

ID
WSTG-INJT-16

Resumen

HTTP Request Smuggling es una clase de vulnerabilidades causadas por inconsistencias en la forma en que los componentes de frontend y de backend analizan las peticiones HTTP. Cuando intermediarios como proxies inversos, balanceadores de carga o API gateways interpretan los límites de las peticiones de manera distinta a los servidores de backend, los atacantes pueden inyectar o "pasar de contrabando" (smuggle) peticiones ocultas que se procesan fuera de secuencia.

Las infraestructuras modernas amplían significativamente la superficie de ataque al introducir HTTP/2, degradaciones de protocolo (HTTP/2 → HTTP/1.1) y actualizaciones en texto claro (H2C), donde la lógica de normalización y traducción de peticiones con frecuencia se aparta de lo que esperan las RFC.

Las explotaciones de request smuggling surgen cuando dos o más analizadores HTTP discrepan sobre dónde comienza o termina una petición. Históricamente, esta discrepancia se observaba con mayor frecuencia en interpretaciones contradictorias de las cabeceras Content-Length (CL) y Transfer-Encoding (TE).

En las arquitecturas modernas, surgen vectores de desincronización adicionales a partir de:

  • Capas de traducción de HTTP/2 a HTTP/1.1
  • Mecanismos de actualización de HTTP/2 en texto claro (H2C)
  • Discrepancias en la normalización de cabeceras
  • Cabeceras prohibidas reintroducidas durante la degradación de protocolo
  • Reutilización de conexiones entre fronteras de protocolo

Estos comportamientos pueden conducir a desincronización persistente, envenenamiento de caché, secuestro de credenciales y elusión del control de acceso.

Objetivos de la prueba

  • Identificar inconsistencias en los límites de las peticiones entre los componentes de frontend y de backend
  • Detectar vulnerabilidades clásicas de desincronización CL/TE
  • Evaluar la lógica de traducción de protocolos (HTTP/2 → HTTP/1.1)
  • Evaluar el manejo de la actualización H2C y la seguridad de la degradación
  • Confirmar el envenenamiento de la cola de peticiones del backend

Cómo probar

Pruebas de caja negra

Desincronización CL.TE

En un escenario CL.TE, el frontend utiliza Content-Length para determinar el tamaño de la petición, mientras que el backend respeta Transfer-Encoding.

POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 35
Transfer-Encoding: chunked

0

GET /404 HTTP/1.1
Foo: x

Resultado esperado:

  • El backend deja de analizar en el fragmento (chunk) 0
  • La petición de contrabando permanece en el búfer
  • Las peticiones legítimas posteriores se corrompen o devuelven respuestas inesperadas (p. ej., 404)

Desincronización TE.CL

En un escenario TE.CL, el frontend procesa correctamente la codificación fragmentada (chunked), pero el backend se basa en Content-Length.

POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Transfer-Encoding: chunked

5c
GET /admin HTTP/1.1
Content-Length: 0

0

Resultado esperado:

  • El backend se detiene antes de tiempo
  • El resto del payload se interpreta como una nueva petición
  • Puede producirse acceso no autorizado a endpoints o envenenamiento de peticiones

TE.TE (Transfer-Encoding ofuscado)

Si ambos servidores admiten Transfer-Encoding, la ofuscación de la cabecera puede hacer que uno de los analizadores la ignore.

Las técnicas comunes incluyen:

  • Manipulación de espacios en blanco
  • Duplicación de cabeceras
  • Separadores no estándar
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 44
Transfer-Encoding:\tchunked
Transfer-Encoding: identity

0

GET /404 HTTP/1.1
Foo: bar

Vectores de ataque modernos

Desincronización de HTTP/2 a HTTP/1.1

En muchos despliegues, los clientes se comunican con los servidores de borde (edge) mediante HTTP/2, mientras que los servicios de backend aún operan sobre HTTP/1.1. Durante la traducción de protocolo, los intermediarios deben reconstruir peticiones HTTP/1.1 a partir de tramas (frames) HTTP/2.

Los puntos de fallo comunes incluyen:

  • Reconstrucción incorrecta de Content-Length
  • Reintroducción de cabeceras hop-by-hop
  • Múltiples peticiones lógicas colapsadas en una sola petición de backend

Nota: la degradación de HTTP/2 no es vulnerable por sí misma.
La explotación es posible cuando la traducción de protocolo reconstruye una petición HTTP/1.1 que viola los supuestos de análisis del backend, lo que lleva a la desincronización de los límites de las peticiones.

Enfoque de prueba:

  • Enviar múltiples tramas DATA de HTTP/2 con semánticas de longitud contradictorias
  • Observar el comportamiento del backend mediante discrepancias de tiempo o división de respuestas
  • Vigilar el envenenamiento de la cola de peticiones
Ejemplo: contrabando por degradación de HTTP/2 mediante reconstrucción de la petición

En este escenario, el cliente se comunica con el frontend mediante HTTP/2, mientras que el backend solo admite HTTP/1.1. El intermediario reconstruye una petición HTTP/1.1 a partir de múltiples tramas DATA de HTTP/2.

HTTP/2 (representación conceptual):

  • Trama DATA 1:
0\r\n\r\n
  • Trama DATA 2:
GET /admin HTTP/1.1
Host: internal

Petición HTTP/1.1 reconstruida (vista del backend):

POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 0

GET /admin HTTP/1.1
Host: internal

Si el frontend trata la petición como completa mientras el backend continúa analizando los datos almacenados en el búfer, la segunda petición puede procesarse fuera de secuencia, dando lugar a request smuggling.

Degradaciones implícitas: Incluso en ausencia de un mecanismo explícito Upgrade: h2c, muchas CDN y proxies inversos degradan silenciosamente las conexiones de clientes HTTP/2 a HTTP/1.1 al reenviar peticiones a los servicios de backend.
Estas degradaciones implícitas amplían la superficie de ataque de smuggling, especialmente cuando se combinan con la reutilización de conexiones y una normalización insuficiente de las peticiones.

Smuggling H2C (actualización de HTTP/2 en texto claro)

H2C permite actualizar una conexión HTTP/1.1 a HTTP/2 mediante el mecanismo Upgrade: h2c.
A diferencia de las degradaciones de protocolo, el smuggling H2C ocurre durante una transición de protocolo in situ, donde los componentes de frontend y de backend pueden discrepar temporalmente sobre el estado de análisis activo de la misma conexión, lo que potencialmente deja bytes residuales en el búfer del backend.

POST / HTTP/1.1
Host: vulnerable-website.com
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c
HTTP2-Settings: AAMAAABkAARAAAAAAAIAAAAA

0

GET /admin HTTP/1.1
Host: internal

Factores de riesgo:

  • Aceptación parcial de la actualización
  • El backend continúa analizando como HTTP/1.1
  • La petición de contrabando se procesa tras la actualización

Envenenamiento de la cola de peticiones mediante degradación de protocolo

Algunos proxies degradan peticiones HTTP/2 a HTTP/1.1 pero no sanean por completo:

  • Content-Length
  • Cabeceras duplicadas
  • Orden inválido de pseudocabeceras

Los atacantes pueden explotar esto para envenenar conexiones persistentes del backend, afectando a múltiples usuarios.

Indicadores de vulnerabilidad

  • Respuestas inconsistentes ante peticiones idénticas
  • Respuestas 404 o 400 inesperadas
  • Respuestas retrasadas o que no corresponden
  • Filtración de respuestas entre usuarios

Corrección

  • Aplicar un análisis estricto conforme a las RFC
  • Normalizar el manejo de peticiones en todos los intermediarios
  • Deshabilitar H2C donde no sea necesario
  • Evitar degradaciones de protocolo en conexiones no confiables
  • Terminar y revalidar las conexiones del backend ante errores de análisis
