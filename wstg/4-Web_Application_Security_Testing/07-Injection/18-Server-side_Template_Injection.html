Inyección de plantillas del lado del servidor (Server-side Template Injection)

ID
WSTG-INJT-18

Resumen

Las aplicaciones web suelen utilizar tecnologías de plantillas del lado del servidor (Jinja2, Twig, FreeMaker, etc.) para generar respuestas HTML dinámicas. Las vulnerabilidades de Server-side Template Injection (SSTI) ocurren cuando la entrada del usuario se incrusta en una plantilla de forma insegura y resulta en ejecución remota de código en el servidor. Cualquier funcionalidad que admita marcado avanzado suministrado por el usuario puede ser vulnerable a SSTI, incluidas las páginas wiki, las reseñas, las aplicaciones de marketing, los sistemas CMS, etc. Algunos motores de plantillas emplean diversos mecanismos (p. ej., sandbox, listas de permitidos, etc.) para protegerse contra SSTI.

Ejemplo - Twig

El siguiente ejemplo es un extracto del proyecto Extreme Vulnerable Web Application.

public function getFilter($name)
{
        [snip]
        foreach ($this->filterCallbacks as $callback) {
        if (false !== $filter = call_user_func($callback, $name)) {
            return $filter;
        }
    }
    return false;
}

En la función getFilter, call_user_func($callback, $name) es vulnerable a SSTI: el parámetro name se obtiene de la petición HTTP GET y es ejecutado por el servidor:

Ejemplo - Flask/Jinja2

El siguiente ejemplo utiliza Flask y el motor de plantillas Jinja2. La función page acepta un parámetro 'name' de una petición HTTP GET y renderiza una respuesta HTML con el contenido de la variable name:

@app.route("/page")
def page():
    name = request.values.get('name')
    output = Jinja2.from_string('Hello ' + name + '!').render()
    return output

Este fragmento de código es vulnerable a XSS, pero también es vulnerable a SSTI. Usando lo siguiente como payload en el parámetro name:

$ curl -g 'https://www.target.com/page?name={{7*7}}'
Hello 49!

Objetivos de la prueba

  • Detectar los puntos vulnerables a inyección de plantillas.
  • Identificar el motor de plantillas.
  • Construir el exploit.

Cómo probar

Las vulnerabilidades SSTI existen en contexto de texto o de código. En el contexto de texto plano se permite a los usuarios usar 'texto' de forma libre con código HTML directo. En el contexto de código, la entrada del usuario también puede colocarse dentro de una sentencia de plantilla (p. ej., en el nombre de una variable).

Identificar la vulnerabilidad de inyección de plantillas

El primer paso para probar SSTI en contexto de texto plano es construir, como payloads, expresiones de plantilla comunes utilizadas por varios motores de plantillas y monitorear las respuestas del servidor para identificar qué expresión de plantilla fue ejecutada por el servidor.

Ejemplos de expresiones de plantilla comunes:

a{{bar}}b
a{{7*7}}
{var} ${var} {{var}} <%var%> [% var %]

La sintaxis de expresiones no es la única superficie alcanzable. Apache Velocity y FreeMarker también evalúan sintaxis de directivas, que ninguna de las pruebas anteriores activará. Una directiva de asignación almacena su resultado en lugar de imprimirlo, por lo que se debe combinar con una interpolación para hacer observable el valor:

#set($x=7*7)$x
<#assign x=7*7>${x}

Ambas muestran 49 donde se evaluó la directiva. Enviadas sin la interpolación final no muestran nada en absoluto, lo cual es importante al construir el exploit: una asignación como <#assign result=runner("id")>, donde runner es un objeto instanciado por una directiva anterior y no algo proporcionado por el motor, invoca el método y no devuelve ninguna salida. Por lo tanto, una respuesta sin cambios no es evidencia de que el payload no se haya ejecutado. Cuando la salida está suprimida, se debe confirmar la evaluación mediante un efecto secundario observable, como una consulta DNS fuera de banda o un retardo medible.

En este paso se recomienda una extensa lista de cadenas/payloads de prueba de expresiones de plantilla.

Probar SSTI en contexto de código es ligeramente diferente. Primero, el evaluador construye la petición que resulta en respuestas del servidor en blanco o con error. En el ejemplo siguiente, el parámetro HTTP GET se inserta en la variable personal_greeting en una sentencia de plantilla:

personal_greeting=username
Hello user01

Usando el siguiente payload, la respuesta del servidor es "Hello" en blanco:

personal_greeting=username<tag>
Hello

En el siguiente paso se debe salir de la sentencia de plantilla e inyectar una etiqueta HTML después de ella, usando el siguiente payload

personal_greeting=username}}<tag>
Hello user01 <tag>

Identificar el motor de plantillas

Con base en la información del paso anterior, ahora el evaluador debe identificar qué motor de plantillas se utiliza suministrando varias expresiones de plantilla. A partir de las respuestas del servidor, el evaluador deduce el motor de plantillas utilizado. Este enfoque manual se analiza con mayor detalle en este artículo de PortSwigger. Para automatizar la identificación de la vulnerabilidad SSTI y del motor de plantillas, hay varias herramientas disponibles, incluidas SSTImap o la extensión Backslash Powered Scanner de Burp Suite.

Construir el exploit de RCE

El objetivo principal en este paso es obtener un mayor control sobre el servidor con un exploit de RCE, estudiando la documentación de la plantilla y la investigación existente. Las áreas clave de interés son:

  • Las secciones para autores de plantillas que cubren la sintaxis básica.
  • Las secciones de consideraciones de seguridad.
  • Listas de métodos, funciones, filtros y variables integrados.
  • Listas de extensiones/plugins.

El evaluador también puede identificar qué otros objetos, métodos y propiedades pueden estar expuestos centrándose en el objeto self. Si el objeto self no está disponible y la documentación no revela los detalles técnicos, se recomienda aplicar fuerza bruta al nombre de la variable. Una vez identificado el objeto, el siguiente paso es recorrerlo en un bucle para identificar todos los métodos, propiedades y atributos accesibles a través del motor de plantillas. Esto podría conducir a otros tipos de hallazgos de seguridad, incluidas escaladas de privilegios, divulgación de información sobre contraseñas de la aplicación, claves de API, configuraciones y variables de entorno, etc.
