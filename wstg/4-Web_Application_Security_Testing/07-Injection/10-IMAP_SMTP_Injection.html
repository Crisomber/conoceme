Inyección IMAP SMTP

ID
WSTG-INJT-10

Resumen

Esta amenaza afecta a todas las aplicaciones que se comunican con servidores de correo (IMAP/SMTP), generalmente aplicaciones de webmail. El objetivo de esta prueba es verificar la capacidad de inyectar comandos IMAP/SMTP arbitrarios en los servidores de correo, debido a que los datos de entrada no se sanean adecuadamente.

La técnica de inyección IMAP/SMTP es más efectiva si el servidor de correo no es directamente accesible desde Internet. Cuando es posible una comunicación completa con el servidor de correo del back-end, se recomienda realizar pruebas directas.

Una inyección IMAP/SMTP permite acceder a un servidor de correo que de otro modo no sería directamente accesible desde Internet. En algunos casos, estos sistemas internos no tienen el mismo nivel de seguridad de infraestructura y endurecimiento (hardening) que se aplica a los servidores web del front-end. Por lo tanto, los servidores de correo pueden ser más vulnerables a ataques de usuarios finales (véase el esquema presentado en la Figura 1).


Figura 4.7.10-1: Comunicación con los servidores de correo mediante la técnica de inyección IMAP/SMTP

La Figura 1 muestra el flujo de tráfico que se observa generalmente al usar tecnologías de webmail. Los pasos 1 y 2 corresponden al usuario interactuando con el cliente de webmail, mientras que el paso 2 corresponde al evaluador eludiendo el cliente de webmail e interactuando directamente con los servidores de correo del back-end.

Esta técnica permite una amplia variedad de acciones y ataques. Las posibilidades dependen del tipo y alcance de la inyección y de la tecnología del servidor de correo que se esté probando.

Algunos ejemplos de ataques que usan la técnica de inyección IMAP/SMTP son:

  • Explotación de vulnerabilidades en el protocolo IMAP/SMTP
  • Evasión de restricciones de la aplicación
  • Evasión de procesos anti-automatización
  • Fugas de información
  • Relay/SPAM

Objetivos de la prueba

  • Identificar los puntos de inyección IMAP/SMTP.
  • Comprender el flujo de datos y la estructura de despliegue del sistema.
  • Evaluar el impacto de la inyección.

Cómo probar

Identificación de parámetros vulnerables

Para detectar parámetros vulnerables, el evaluador debe analizar la capacidad de la aplicación para manejar la entrada. La prueba de validación de entrada requiere que el evaluador envíe peticiones falsas o maliciosas al servidor y analice la respuesta. En una aplicación segura, la respuesta debería ser un error con alguna acción correspondiente que indique al cliente que algo ha salido mal. En una aplicación vulnerable, la petición maliciosa puede ser procesada por la aplicación del back-end, que responderá con un mensaje de respuesta HTTP 200 OK.

Es importante tener en cuenta que las peticiones enviadas deben corresponder a la tecnología que se está probando. Enviar cadenas de inyección SQL para Microsoft SQL Server cuando se está utilizando un servidor MySQL dará lugar a respuestas de falsos positivos. En este caso, enviar comandos IMAP maliciosos es el modus operandi, ya que IMAP es el protocolo subyacente que se está probando.

Los parámetros especiales de IMAP que deben utilizarse son:

En el servidor IMAP En el servidor SMTP
Autenticación Correo del emisor
operaciones con buzones (listar, leer, crear, eliminar, renombrar) Correo del destinatario
operaciones con mensajes (leer, copiar, mover, eliminar) Asunto
Desconexión Cuerpo del mensaje
Archivos adjuntos

En este ejemplo, se prueba el parámetro "mailbox" manipulando todas las peticiones con el parámetro en:

https://<webmail>/src/read_body.php?mailbox=INBOX&passed_id=46106&startMessage=1

Se pueden utilizar los siguientes ejemplos.

  • Asignar un valor nulo al parámetro:

https://<webmail>/src/read_body.php?mailbox=&passed_id=46106&startMessage=1

  • Sustituir el valor por un valor aleatorio:

https://<webmail>/src/read_body.php?mailbox=NOTEXIST&passed_id=46106&startMessage=1

  • Añadir otros valores al parámetro:

https://<webmail>/src/read_body.php?mailbox=INBOX PARAMETER2&passed_id=46106&startMessage=1

  • Añadir caracteres especiales no estándar (p. ej.: \, ', ", @, #, !, |):

https://<webmail>/src/read_body.php?mailbox=INBOX"&passed_id=46106&startMessage=1

  • Eliminar el parámetro:

https://<webmail>/src/read_body.php?passed_id=46106&startMessage=1

El resultado final de las pruebas anteriores le da al evaluador tres situaciones posibles:

  1. La aplicación devuelve un código/mensaje de error
  2. La aplicación no devuelve un código/mensaje de error, pero no realiza la operación solicitada
  3. La aplicación no devuelve un código/mensaje de error y realiza la operación solicitada normalmente

Las situaciones S1 y S2 representan una inyección IMAP/SMTP exitosa.

El objetivo de un atacante es recibir la respuesta S1, ya que es un indicador de que la aplicación es vulnerable a la inyección y a una manipulación posterior.

Supongamos que un usuario obtiene las cabeceras de un correo mediante la siguiente petición HTTP:

https://<webmail>/src/view_header.php?mailbox=INBOX&passed_id=46105&passed_ent_id=0

Un atacante podría modificar el valor del parámetro INBOX inyectando el carácter " (%22 usando codificación URL):

https://<webmail>/src/view_header.php?mailbox=INBOX%22&passed_id=46105&passed_ent_id=0

En este caso, la respuesta de la aplicación puede ser:

ERROR: Bad or malformed request.
Query: SELECT "INBOX""
Server responded: Unexpected extra arguments to Select

La situación S2 es más difícil de probar con éxito. El evaluador necesita utilizar inyección de comandos a ciegas (blind) para determinar si el servidor es vulnerable.

Por otro lado, la última situación (S3) no es relevante en este apartado.

Comprensión del flujo de datos y la estructura de despliegue del cliente

Después de identificar todos los parámetros vulnerables (por ejemplo, passed_id), el evaluador necesita determinar qué nivel de inyección es posible y luego diseñar un plan de pruebas para explotar aún más la aplicación.

En este caso de prueba, hemos detectado que el parámetro passed_id de la aplicación es vulnerable y se utiliza en la siguiente petición:

https://<webmail>/src/read_body.php?mailbox=INBOX&passed_id=46225&startMessage=1

Usando el siguiente caso de prueba (proporcionar un valor alfabético cuando se requiere un valor numérico):

https://<webmail>/src/read_body.php?mailbox=INBOX&passed_id=test&startMessage=1

se generará el siguiente mensaje de error:

ERROR : Bad or malformed request.
Query: FETCH test:test BODY[HEADER]
Server responded: Error in IMAP command received by server.

En este ejemplo, el mensaje de error devolvió el nombre del comando ejecutado y los parámetros correspondientes.

En otras situaciones, el mensaje de error (no controlado por la aplicación) contiene el nombre del comando ejecutado, pero la lectura de la RFC adecuada permite al evaluador comprender qué otros comandos pueden ejecutarse.

Si la aplicación no devuelve mensajes de error descriptivos, el evaluador necesita analizar la funcionalidad afectada para deducir todos los posibles comandos (y parámetros) asociados con dicha funcionalidad. Por ejemplo, si se ha detectado un parámetro vulnerable en la funcionalidad de crear buzón, es lógico suponer que el comando IMAP afectado es CREATE. Según la RFC, el comando CREATE acepta un parámetro que especifica el nombre del buzón que se va a crear.

Inyección de comandos IMAP/SMTP

Una vez que el evaluador ha identificado los parámetros vulnerables y ha analizado el contexto en el que se ejecutan, la siguiente etapa es explotar la funcionalidad.

Esta etapa tiene dos posibles resultados:

  1. La inyección es posible en un estado no autenticado: la funcionalidad afectada no requiere que el usuario esté autenticado. Los comandos (IMAP) inyectados disponibles se limitan a: CAPABILITY, NOOP, AUTHENTICATE, LOGIN y LOGOUT.
  2. La inyección solo es posible en un estado autenticado: la explotación exitosa requiere que el usuario esté completamente autenticado antes de que las pruebas puedan continuar.

En cualquier caso, la estructura típica de una inyección IMAP/SMTP es la siguiente:

  • Encabezado (Header): finalización del comando esperado;
  • Cuerpo (Body): inyección del nuevo comando;
  • Pie (Footer): comienzo del comando esperado.

Es importante recordar que, para ejecutar un comando IMAP/SMTP, el comando anterior debe terminarse con la secuencia CRLF (%0d%0a).

Supongamos que en la etapa Identificación de parámetros vulnerables el atacante detecta que el parámetro message_id de la siguiente petición es vulnerable:

https://<webmail>/read_email.php?message_id=4791

Supongamos también que el resultado del análisis realizado en la etapa 2 ("Comprensión del flujo de datos y la estructura de despliegue del cliente") ha identificado el comando y los argumentos asociados con este parámetro como:

FETCH 4791 BODY[HEADER]

En este escenario, la estructura de la inyección IMAP sería:

https://<webmail>/read_email.php?message_id=4791 BODY[HEADER]%0d%0aV100 CAPABILITY%0d%0aV101 FETCH 4791

Lo cual generaría los siguientes comandos:

???? FETCH 4791 BODY[HEADER]
V100 CAPABILITY
V101 FETCH 4791 BODY[HEADER]

donde:

Header = 4791 BODY[HEADER]
Body   = %0d%0aV100 CAPABILITY%0d%0a
Footer = V101 FETCH 4791
