Contaminación de parámetros HTTP

ID
WSTG-INJT-04

Resumen

La contaminación de parámetros HTTP (HTTP Parameter Pollution) prueba la respuesta de las aplicaciones al recibir varios parámetros HTTP con el mismo nombre; por ejemplo, si el parámetro username se incluye dos veces en los parámetros GET o POST.

Suministrar varios parámetros HTTP con el mismo nombre puede hacer que una aplicación interprete los valores de formas imprevistas. Aprovechando estos efectos, un atacante podría eludir la validación de entrada, provocar errores en la aplicación o modificar los valores de variables internas. Como la contaminación de parámetros HTTP (HPP, por sus siglas en inglés) afecta a un componente básico de todas las tecnologías web, existen ataques del lado del servidor y del lado del cliente.

Los estándares HTTP actuales no incluyen orientación sobre cómo interpretar varios parámetros de entrada con el mismo nombre. Por ejemplo, la RFC 3986 simplemente define el término Query String como una serie de pares campo-valor, y la RFC 2396 define clases de caracteres reservados y no reservados de la query string. Sin un estándar vigente, los componentes de las aplicaciones web manejan este caso límite de diversas maneras (véase la tabla siguiente para más detalles).

Por sí mismo, esto no es necesariamente un indicio de vulnerabilidad. Sin embargo, si el desarrollador no es consciente del problema, la presencia de parámetros duplicados puede producir un comportamiento anómalo en la aplicación que un atacante podría explotar. Como suele ocurrir en seguridad, los comportamientos inesperados son una fuente habitual de debilidades que, en este caso, podrían dar lugar a ataques de contaminación de parámetros HTTP. Para presentar mejor esta clase de vulnerabilidades y el resultado de los ataques HPP, resulta interesante analizar algunos ejemplos reales descubiertos en el pasado.

Evasión de la validación de entrada y de los filtros

En 2009, inmediatamente después de la publicación de la primera investigación sobre la contaminación de parámetros HTTP, la técnica recibió la atención de la comunidad de seguridad como una posible forma de eludir los web application firewalls.

Uno de estos fallos, que afectaba a las ModSecurity SQL Injection Core Rules, representa un ejemplo perfecto de la discordancia de impedancia (impedance mismatch) entre las aplicaciones y los filtros. El filtro de ModSecurity aplicaba correctamente una lista de denegación a la cadena select 1,2,3 from table, bloqueando así que el servidor web procesara esta URL de ejemplo: /index.aspx?page=select 1,2,3 from table. Sin embargo, aprovechando la concatenación de varios parámetros HTTP, un atacante podía hacer que el servidor de aplicaciones concatenara la cadena después de que el filtro de ModSecurity ya hubiera aceptado la entrada. Por ejemplo, la URL /index.aspx?page=select 1&page=2,3 from table no activaría el filtro de ModSecurity, pero la capa de aplicación volvería a concatenar la entrada en la cadena maliciosa completa.

Otra vulnerabilidad HPP resultó afectar a Apple Cups, el conocido sistema de impresión utilizado por muchos sistemas Unix. Explotando HPP, un atacante podía provocar fácilmente una vulnerabilidad de Cross-Site Scripting mediante la siguiente URL: https://127.0.0.1:631/admin/?kerberos=onmouseover=alert(1)&kerberos. El punto de control de validación de la aplicación podía eludirse añadiendo un argumento kerberos adicional con una cadena válida (por ejemplo, una cadena vacía). Como el punto de control de validación solo consideraba la segunda aparición, el primer parámetro kerberos no se sanitizaba correctamente antes de usarse para generar contenido HTML dinámico. Una explotación exitosa daba como resultado la ejecución de código JavaScript en el contexto del sitio anfitrión.

Evasión de la autenticación

Se descubrió una vulnerabilidad HPP aún más crítica en Blogger, la popular plataforma de blogs. El error permitía a usuarios maliciosos adueñarse del blog de la víctima mediante la siguiente petición HTTP (https://www.blogger.com/add-authors.do):

POST /add-authors.do HTTP/1.1
[...]

security_token=attackertoken&blogID=attackerblogidvalue&blogID=victimblogidvalue&authorsList=goldshlager19test%40gmail.com(attacker email)&ok=Invite

El fallo residía en el mecanismo de autenticación que usaba la aplicación web, ya que la comprobación de seguridad se realizaba sobre el primer parámetro blogID, mientras que la operación real utilizaba la segunda aparición.

Comportamiento esperado según el servidor de aplicaciones

La forma en que se manejan los parámetros duplicados depende del framework, del servidor y de cómo la aplicación lee el valor (por ejemplo, el primer valor, el último valor o la colección completa). Se debe tratar cualquier tabla de comportamientos por defecto solo como punto de partida: hay que verificar el comportamiento real de la pila tecnológica objetivo, incluidos los proxies inversos, los web application firewalls (WAF) y las API gateways, que pueden normalizar las query strings de forma distinta.

Dada la URL y la query string: https://example.com/?color=red&color=blue

Pila típica Análisis por defecto habitual Ejemplo
ASP.NET / IIS Todas las apariciones concatenadas con una coma color=red,blue
ASP.NET Core / Kestrel Todas las apariciones disponibles (StringValues; unidas por comas al convertirse en cadena) color=red,blue
PHP (Apache / php-fpm / Nginx) Solo la última aparición color=blue
Java Servlet (Tomcat, Jetty y similares) Solo la primera aparición color=red
Node.js / Express Solo la primera aparición color=red
Python (Django, Flask y similares) Todas las apariciones en una lista / MultiDict color=['red','blue']

El comportamiento de otros servidores y de plataformas más antiguas varía; siempre hay que confirmarlo en el sistema bajo prueba. La investigación histórica sobre este tema incluye AppSec EU 2009 (Carettoni & di Paola).

Objetivos de la prueba

  • Identificar el back end y el método de análisis (parsing) utilizado.
  • Evaluar los puntos de inyección e intentar eludir los filtros de entrada mediante HPP.

Cómo probar

Que una página o un endpoint de API concretos sean vulnerables a HPP dependerá de la interacción entre varios componentes, entre ellos la aplicación, el servidor web, el web application firewall y cualquier middleware. Cuando estos varían entre distintas partes de una aplicación (como en una arquitectura de microservicios), algunas partes de la aplicación pueden ser vulnerables y otras no.

Como se requiere un conocimiento profundo de la lógica de negocio, probar HPP exige pruebas manuales. Las herramientas automáticas solo pueden asistir parcialmente a los auditores, ya que tienden a generar demasiados falsos positivos. Además, HPP puede manifestarse en componentes del lado del cliente y del lado del servidor.

HPP del lado del servidor

Para probar vulnerabilidades HPP, hay que identificar cualquier formulario o acción que admita entrada proporcionada por el usuario. Los parámetros de la query string en peticiones HTTP GET son fáciles de modificar en la barra de navegación del navegador. Si la acción del formulario envía datos mediante POST, el evaluador tendrá que usar un proxy de interceptación para manipular los datos POST al enviarse al servidor. Una vez identificado un parámetro de entrada concreto para probar, se pueden editar los datos GET o POST interceptando la petición, o cambiar la query string después de que cargue la página de respuesta. Para probar vulnerabilidades HPP basta con añadir el mismo parámetro a los datos GET o POST, pero con un valor distinto asignado.

Por ejemplo: si se prueba el parámetro search_string en la query string, la URL de la petición incluiría el nombre y el valor de ese parámetro:

https://example.com/?search_string=kittens

El parámetro en cuestión podría estar oculto entre otros parámetros, pero el enfoque es el mismo; se dejan los demás parámetros en su sitio y se añade el duplicado:

https://example.com/?mode=guest&search_string=kittens&num_results=100

Se añade el mismo parámetro con un valor diferente:

https://example.com/?mode=guest&search_string=kittens&num_results=100&search_string=puppies

Para endpoints basados en JSON, el payload (carga útil) tendría este aspecto:

POST /search HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "search_string": "kittens",
  "search_string": "puppies"
}

y se envía la nueva petición.

Hay que analizar la página de respuesta para determinar qué valor(es) se procesaron. En el ejemplo anterior, los resultados de la búsqueda pueden mostrar kittens, puppies, alguna combinación de ambos (kittens,puppies, kittens~puppies o ['kittens','puppies']), o bien dar un resultado vacío o una página de error.

Que este comportamiento por defecto revele o no una posible vulnerabilidad depende de la validación de entrada y del filtrado específicos de cada aplicación. Como regla general: si la validación de entrada existente y otros mecanismos de seguridad son suficientes para entradas únicas, y si el servidor asigna solo el primer o el último de los parámetros contaminados, la contaminación de parámetros no revela una vulnerabilidad. Si los parámetros duplicados se concatenan, distintos componentes de la aplicación web usan apariciones diferentes o la prueba genera un error, aumenta la probabilidad de poder usar la contaminación de parámetros para desencadenar vulnerabilidades de seguridad.

Un análisis más profundo requeriría tres peticiones HTTP por cada parámetro HTTP:

  1. Enviar una petición HTTP que contenga el nombre y el valor estándar del parámetro, y registrar la respuesta HTTP. Por ejemplo, page?par1=val1
  2. Reemplazar el valor del parámetro por un valor manipulado, enviar y registrar la respuesta HTTP. Por ejemplo, page?par1=HPP_TEST1
  3. Enviar una nueva petición que combine los pasos (1) y (2). De nuevo, guardar la respuesta HTTP. Por ejemplo, page?par1=val1&par1=HPP_TEST1
  4. Comparar las respuestas obtenidas en todos los pasos anteriores. Si la respuesta de (3) es distinta de la de (1) y la respuesta de (3) también es distinta de la de (2), existe una discordancia de impedancia que podría llegar a abusarse para desencadenar vulnerabilidades HPP.

Elaborar un exploit completo a partir de una debilidad de contaminación de parámetros queda fuera del alcance de este texto. Véanse las referencias para ejemplos y detalles.

HPP del lado del cliente

De forma similar a la HPP del lado del servidor, las pruebas manuales son la única técnica fiable para auditar aplicaciones web con el fin de detectar vulnerabilidades de contaminación de parámetros que afecten a componentes del lado del cliente. Mientras que en la variante del lado del servidor el atacante aprovecha una aplicación web vulnerable para acceder a datos protegidos o realizar acciones que no están permitidas o que no deberían ejecutarse, los ataques del lado del cliente buscan subvertir componentes y tecnologías del lado del cliente.

Para probar vulnerabilidades HPP del lado del cliente, hay que identificar cualquier formulario o acción que admita entrada del usuario y muestre de vuelta al usuario un resultado de esa entrada. Una página de búsqueda es ideal, pero un cuadro de inicio de sesión podría no funcionar (ya que podría no mostrar de vuelta al usuario un nombre de usuario no válido).

De forma similar a la HPP del lado del servidor, hay que contaminar cada parámetro HTTP con %26HPP_TEST y buscar apariciones decodificadas de URL del payload proporcionado por el usuario:

  • &HPP_TEST
  • &amp;HPP_TEST
  • etc.

En particular, hay que prestar atención a las respuestas que tengan vectores HPP dentro de los atributos data, src, href o en las acciones de formularios. De nuevo, que este comportamiento por defecto revele o no una posible vulnerabilidad depende de la validación de entrada, del filtrado y de la lógica de negocio específicos de la aplicación. Esto también puede afectar a los parámetros de la query string usados en XMLHttpRequest (XHR), fetch y la creación de atributos en tiempo de ejecución.
