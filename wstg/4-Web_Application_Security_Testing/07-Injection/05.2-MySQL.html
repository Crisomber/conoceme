MySQL

Resumen

Las vulnerabilidades de Inyección SQL ocurren siempre que se utiliza una entrada en la construcción de una consulta SQL sin estar adecuadamente restringida o sanitizada. El uso de SQL dinámico (la construcción de consultas SQL mediante concatenación de cadenas) abre la puerta a estas vulnerabilidades. La inyección SQL permite a un atacante acceder a los servidores SQL. Permite la ejecución de código SQL con los privilegios del usuario utilizado para conectarse a la base de datos.

MySQL server tiene algunas particularidades, por lo que algunos exploits deben personalizarse especialmente para esta aplicación. Ese es el tema de esta sección. Dado que MariaDB es un fork de MySQL, el contenido de esta página también es relevante para MariaDB.

Cómo probar

Cuando se encuentra una vulnerabilidad de inyección SQL en una aplicación respaldada por una base de datos MySQL, se pueden realizar varios ataques dependiendo de la versión de MySQL y de los privilegios del usuario en el DBMS.

MySQL tiene al menos cuatro versiones que se utilizan en producción en todo el mundo: 3.23.x, 4.0.x, 4.1.x y 5.0.x. Cada versión tiene un conjunto de características proporcional al número de versión.

  • Desde la versión 4.0: UNION
  • Desde la versión 4.1: subconsultas
  • Desde la versión 5.0: procedimientos almacenados, funciones almacenadas y la vista denominada INFORMATION_SCHEMA
  • Desde la versión 5.0.2: triggers

Cabe señalar que, para las versiones de MySQL anteriores a la 4.0.x, solo se podían usar ataques de inyección ciega booleanos o basados en tiempo, ya que la funcionalidad de subconsultas o las sentencias UNION no estaban implementadas.

De ahora en adelante, supondremos que existe una vulnerabilidad de inyección SQL clásica, que puede activarse mediante una petición similar a la descrita en la sección sobre Inyección SQL.

https://www.example.com/page.php?id=2

El problema de las comillas simples

Antes de aprovechar las características de MySQL, hay que tener en cuenta cómo pueden representarse las cadenas en una sentencia, ya que a menudo las aplicaciones web escapan las comillas simples.

El escape de comillas en MySQL es el siguiente:

'A string with \'quotes\''

Es decir, MySQL interpreta los apóstrofos escapados \' como caracteres y no como metacaracteres.

Así que si la aplicación, para funcionar correctamente, necesita usar cadenas constantes, hay que diferenciar dos casos:

  1. La aplicación web escapa las comillas simples ' => \'
  2. La aplicación web no escapa las comillas simples ' => '

En MySQL existe una forma estándar de evitar la necesidad de comillas simples, declarando una cadena constante sin necesidad de ellas.

Supongamos que queremos conocer el valor de un campo llamado password en un registro, con una condición como la siguiente:

  1. password like 'A%'
  2. Los valores ASCII en un hexadecimal concatenado: password LIKE 0x4125
  3. La función char(): password LIKE CHAR(65,37)

Múltiples consultas mixtas

Los conectores de las bibliotecas de MySQL no admiten múltiples consultas separadas por ;, por lo que no hay forma de inyectar varios comandos SQL no homogéneos dentro de una única vulnerabilidad de inyección SQL como en Microsoft SQL Server.

Por ejemplo, la siguiente inyección dará como resultado un error:

1 ; update tablename set code='javascript code' where 1 --

Recopilación de información

Identificación de MySQL (fingerprinting)

Por supuesto, lo primero que hay que saber es si hay un DBMS MySQL como base de datos de backend. MySQL server tiene una característica que se utiliza para que otros DBMS ignoren una cláusula del dialecto de MySQL. Cuando un bloque de comentario '/**/' contiene un signo de exclamación '/*! sql here*/', MySQL lo interpreta, y los demás DBMS lo consideran un bloque de comentario normal, como se explica en el manual de MySQL.

Ejemplo:

1 /*! and 1=0 */

Si MySQL está presente, se interpretará la cláusula dentro del bloque de comentario.

Versión

Hay tres maneras de obtener esta información:

  1. Usando la variable global @@version
  2. Usando la función VERSION()
  3. Usando la identificación mediante comentarios con un número de versión /*!40110 and 1=0*/

lo cual significa

if(version >= 4.1.10)
   add 'and 1=0' to the query.

Estas son equivalentes, ya que el resultado es el mismo.

Inyección in band:

1 AND 1=0 UNION SELECT @@version /*

Inyección inferencial:

1 AND @@version like '4.0%'

La respuesta contendría algo parecido a:

5.0.22-log

Usuario de inicio de sesión

Hay dos tipos de usuarios en los que se basa MySQL Server.

  1. USER(): el usuario conectado a MySQL Server.
  2. CURRENT_USER(): el usuario interno que está ejecutando la consulta.

Existe alguna diferencia entre 1 y 2. La principal es que un usuario anónimo podría conectarse (si se permite) con cualquier nombre, pero el usuario interno de MySQL tiene un nombre vacío (''). Otra diferencia es que un procedimiento almacenado o una función almacenada se ejecutan como el usuario creador, si no se declara otra cosa. Esto puede saberse usando CURRENT_USER.

Inyección in band:

1 AND 1=0 UNION SELECT USER()

Inyección inferencial:

1 AND USER() like 'root%'

La respuesta contendría algo parecido a:

user@hostname

Nombre de la base de datos en uso

Existe la función nativa DATABASE()

Inyección in band:

1 AND 1=0 UNION SELECT DATABASE()

Inyección inferencial:

1 AND DATABASE() like 'db%'

Resultado esperado, una cadena como esta:

dbname

INFORMATION_SCHEMA

Desde MySQL 5.0 se creó una vista llamada INFORMATION_SCHEMA. Nos permite obtener toda la información sobre bases de datos, tablas y columnas, así como sobre procedimientos y funciones.

Tables_in_INFORMATION_SCHEMA DESCRIPCIÓN
SCHEMATA Todas las bases de datos sobre las que el usuario tiene (al menos) SELECT_priv
SCHEMA_PRIVILEGES Los privilegios que el usuario tiene para cada base de datos
TABLES Todas las tablas sobre las que el usuario tiene (al menos) SELECT_priv
TABLE_PRIVILEGES Los privilegios que el usuario tiene para cada tabla
COLUMNS Todas las columnas sobre las que el usuario tiene (al menos) SELECT_priv
COLUMN_PRIVILEGES Los privilegios que el usuario tiene para cada columna
VIEWS Todas las columnas sobre las que el usuario tiene (al menos) SELECT_priv
ROUTINES Procedimientos y funciones (requiere EXECUTE_priv)
TRIGGERS Triggers (requiere INSERT_priv)
USER_PRIVILEGES Privilegios del usuario conectado

Toda esta información podría extraerse usando las técnicas conocidas descritas en la sección de Inyección SQL.

Vectores de ataque

Escribir en un archivo

Si el usuario conectado tiene privilegios FILE y las comillas simples no se escapan, la cláusula into outfile puede usarse para exportar los resultados de la consulta a un archivo.

Select * from table into outfile '/tmp/file'

Nota: no hay forma de evitar las comillas simples que rodean un nombre de archivo. Así que si existe alguna sanitización de comillas simples, como escapar \', no habrá forma de usar la cláusula into outfile.

Este tipo de ataque podría usarse como una técnica out-of-band para obtener información sobre los resultados de una consulta o para escribir un archivo que pudiera ejecutarse dentro del directorio del servidor web.

Ejemplo:

1 limit 1 into outfile '/var/www/root/test.jsp' FIELDS ENCLOSED BY '//' LINES TERMINATED BY '\n<%jsp code here%>';

Los resultados se almacenan en un archivo con privilegios rw-rw-rw cuyo propietario es el usuario y grupo de MySQL.

Donde /var/www/root/test.jsp contendrá:

//field values// <%jsp code here%>

Leer de un archivo

load_file es una función nativa que puede leer un archivo cuando lo permiten los permisos del sistema de archivos. Si un usuario conectado tiene privilegios FILE, podría usarse para obtener el contenido de los archivos. La sanitización por escape de comillas simples puede eludirse usando las técnicas descritas anteriormente.

load_file('filename')

Todo el archivo estará disponible para su exportación usando técnicas estándar.

Ataque estándar de inyección SQL

En una inyección SQL estándar, los resultados pueden mostrarse directamente en una página como salida normal o como un error de MySQL. Usando los ataques de inyección SQL ya mencionados y las características de MySQL ya descritas, la inyección SQL directa puede lograrse fácilmente, con un nivel de profundidad que depende principalmente de la versión de MySQL a la que se enfrente el pentester.

Un buen ataque consiste en conocer los resultados forzando a una función, a un procedimiento o al propio servidor a lanzar un error. Puede encontrarse una lista de los errores lanzados por MySQL, y en particular por las funciones nativas, en el MySQL Manual.

Inyección SQL out-of-band

La inyección out-of-band puede lograrse usando la cláusula into outfile.

Inyección SQL ciega

Para la inyección SQL ciega, existe un conjunto de funciones útiles proporcionadas de forma nativa por MySQL server.

  • Longitud de una cadena:
    • LENGTH(str)
  • Extraer una subcadena de una cadena dada:
    • SUBSTRING(string, offset, #chars_returned)
  • Inyección ciega basada en tiempo:
    • BENCHMARK y SLEEP BENCHMARK(#ofcycles,action_to_be_performed) La función benchmark puede usarse para realizar ataques de temporización cuando la inyección ciega mediante valores booleanos no produce ningún resultado. Véase SLEEP() (MySQL > 5.0.x) como alternativa a benchmark.

Para una lista completa, consúltese el manual de MySQL
