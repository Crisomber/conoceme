Asignación masiva (Mass Assignment)

ID
WSTG-INJT-20

Resumen

Las aplicaciones web modernas se basan muy a menudo en frameworks. Muchos de estos frameworks de aplicaciones web permiten el enlace automático de la entrada del usuario (en forma de parámetros de petición HTTP) a objetos internos. Esto suele denominarse autobinding. Esta funcionalidad a veces puede explotarse para acceder a campos que nunca estuvieron destinados a ser modificados desde el exterior, lo que conduce a escalada de privilegios, manipulación de datos, elusión de mecanismos de seguridad y más. En este caso existe una vulnerabilidad de Mass Assignment.

Ejemplos de propiedades sensibles:

  • Propiedades relacionadas con permisos: solo deberían ser establecidas por usuarios con privilegios (p. ej., is_admin, role, approved).
  • Propiedades dependientes de un proceso: solo deberían establecerse internamente, después de que se complete un proceso (p. ej., balance, status, email_verified)
  • Propiedades internas: solo deberían ser establecidas internamente por la aplicación (p. ej., created_at, updated_at)

Objetivos de la prueba

  • Identificar las peticiones que modifican objetos
  • Evaluar si es posible modificar campos que nunca estuvieron destinados a ser modificados desde el exterior

Cómo probar

El siguiente es un ejemplo clásico que puede ayudar a ilustrar el problema.

Supongamos una aplicación web Java con un objeto User similar al siguiente:

public class User {
   private String username;
   private String password;
   private String email;
   private boolean isAdmin;

   //Getters & Setters
}

Para crear un nuevo User, la aplicación web implementa la siguiente vista:

<form action="/createUser" method="POST">
     <input name="username" type="text">
     <input name="password" type="text">
     <input name="email" text="text">
     <input type="submit" value="Create">
</form>

El controlador que maneja la petición de creación (Spring proporciona el enlace automático con el modelo User):

@RequestMapping(value = "/createUser", method = RequestMethod.POST)
public String createUser(User user) {
   userService.add(user);
   return "successPage";
}

Cuando se envía el formulario, el navegador genera la siguiente petición:

POST /createUser
[...]
username=bob&password=supersecretpassword&email=bob@domain.test

Sin embargo, debido al autobinding, un atacante puede añadir el parámetro isAdmin a la petición, que el controlador enlazará automáticamente al modelo.

POST /createUser
[...]
username=bob&password=supersecretpassword&email=bob@domain.test&isAdmin=true

El usuario se crea entonces con la propiedad isAdmin establecida en true, lo que le otorga derechos administrativos en la aplicación.

Pruebas de caja negra

Detectar los manejadores (handlers)

Para determinar qué parte de la aplicación es vulnerable a mass assignment, se enumeran todas las partes de la aplicación que aceptan contenido del usuario y que potencialmente pueden mapearse con un modelo. Esto incluye todas las peticiones HTTP (muy probablemente GET, POST y PUT) que parezcan permitir operaciones de creación o actualización en el back-end. Uno de los indicadores más simples de posibles asignaciones masivas es la presencia de sintaxis de corchetes en los nombres de los parámetros de entrada, como por ejemplo:

<input name="user[name]" type="text">

Cuando se encuentren estos patrones, se debe intentar añadir una entrada relacionada con un atributo inexistente (p. ej., user[nonexistingattribute]) y analizar la respuesta/comportamiento. Si la aplicación no implementa ningún control (p. ej., una lista de campos permitidos), es probable que responda con un error (p. ej., 500) debido a que la aplicación no encuentra el atributo asociado al objeto. Más interesante aún, estos errores a veces facilitan el descubrimiento de los nombres de atributos y de los tipos de datos de valores necesarios para explotar el problema, sin acceso al código fuente.

Identificar los campos sensibles

Dado que en las pruebas de caja negra el evaluador no tiene visibilidad del código fuente, es necesario encontrar otras formas de recopilar información sobre los atributos asociados a los objetos. Se analizan las respuestas recibidas del back-end, prestando particular atención a:

  • El código fuente de la página HTML
  • El código JavaScript personalizado
  • Las respuestas de las API

Por ejemplo, muy a menudo es posible explotar manejadores que devuelven detalles sobre un objeto para obtener pistas sobre los campos asociados. Supongamos, por ejemplo, un manejador que devuelve el perfil del usuario (p. ej., GET /profile); este puede incluir otros atributos relacionados con el usuario (en este ejemplo, el atributo isAdmin parece particularmente interesante).

{"_id":12345,"username":"bob","age":38,"email":"bob@domain.test","isAdmin":false}

Luego se intenta explotar los manejadores que permiten la modificación o creación de usuarios, añadiendo el atributo isAdmin configurado en true.

Otro enfoque es usar listas de palabras (wordlists) para intentar enumerar todos los atributos potenciales. La enumeración puede entonces automatizarse (p. ej., mediante wfuzz, Burp Intruder, el fuzzer de ZAP, etc.). La herramienta sqlmap incluye una lista de palabras common-columns.txt que puede ser útil para identificar posibles atributos sensibles. Un pequeño ejemplo de nombres de atributos interesantes comunes son los siguientes:

  • is_admin
  • is_administrator
  • isAdmin
  • isAdministrator
  • admin
  • administrator
  • role

Cuando hay varios roles disponibles, se debe intentar comparar las peticiones realizadas por distintos niveles de usuario (prestando particular atención a los roles con privilegios). Por ejemplo, si se incluyen parámetros adicionales en las peticiones realizadas por un usuario administrativo, se deben probar esos parámetros como usuario con pocos privilegios o anónimo.

Comprobar el impacto

El impacto de una asignación masiva puede variar según el contexto; por lo tanto, para cada entrada de prueba intentada en la fase anterior, se debe analizar el resultado y determinar si representa una vulnerabilidad con un impacto realista en la seguridad de la aplicación web. Por ejemplo, la modificación del id de un objeto puede conducir a denegación de servicio de la aplicación o a escalada de privilegios. Otro ejemplo está relacionado con la posibilidad de modificar el rol/estado del usuario (p. ej., role o isAdmin), lo que lleva a una escalada vertical de privilegios.

Pruebas de caja gris

Cuando el análisis se realiza con un enfoque de pruebas de caja gris, es posible seguir la misma metodología para verificar el problema. Sin embargo, el mayor conocimiento de la aplicación permite identificar con más facilidad los frameworks y manejadores sujetos a la vulnerabilidad de mass assignment. En particular, cuando el código fuente está disponible, es posible buscar los vectores de entrada con más facilidad y precisión. Durante una revisión del código fuente, se utilizan herramientas simples (como el comando grep) para buscar uno o más patrones comunes dentro del código de la aplicación. El acceso al esquema de la base de datos o al código fuente también permite identificar fácilmente los campos sensibles.

Java

Spring MVC permite enlazar automáticamente la entrada del usuario a un objeto. Se identifican los controladores que manejan peticiones que cambian el estado (p. ej., se buscan las apariciones de @RequestMapping) y luego se verifica si existen controles (tanto en el controlador como en los modelos involucrados). Las limitaciones a la explotación de la asignación masiva pueden presentarse, por ejemplo, en la forma de:

  • lista de campos enlazables mediante el método setAllowedFields de la clase DataBinder (p. ej., binder.setAllowedFields(["username","password","email"]))
  • lista de campos no enlazables mediante el método setDisallowedFields de la clase DataBinder (p. ej., binder.setDisallowedFields(["isAdmin"]))

También es aconsejable prestar atención al uso de la anotación @ModelAttribute, que permite especificar un nombre/clave diferente.

PHP

Laravel Eloquent ORM proporciona un método create que permite la asignación automática de atributos. Sin embargo, las últimas versiones de Eloquent ORM ofrecen protección por defecto contra vulnerabilidades de asignación masiva, requiriendo especificar explícitamente los atributos permitidos que pueden asignarse automáticamente, mediante el arreglo $fillable, o los atributos que deben protegerse (no enlazables), mediante el arreglo $guarded. Por lo tanto, analizando los modelos (clases que extienden la clase Model) es posible identificar qué atributos están permitidos o denegados y, por consiguiente, señalar posibles vulnerabilidades.

.NET

El enlace de modelos (model binding) en ASP.NET enlaza automáticamente las entradas del usuario a las propiedades de un objeto. Esto también funciona con tipos complejos y convertirá automáticamente los datos de entrada a las propiedades si los nombres de las propiedades coinciden con la entrada. Se identifican los controladores y luego se verifica si existen controles (tanto dentro del controlador como en los modelos involucrados). Las limitaciones a la explotación de la asignación masiva pueden presentarse, por ejemplo, en la forma de:

  • campos declarados como ReadOnly
  • lista de campos enlazables mediante el atributo Bind (p. ej., [Bind(Include = "FirstName, LastName")] Student std), mediante includeProperties (p. ej., includeProperties: new[] { "FirstName, LastName" }) o a través de TryUpdateModel
  • lista de campos no enlazables mediante el atributo Bind (p. ej., [Bind(Exclude = "Status")] Student std) o mediante excludeProperties (p. ej., excludeProperties: new[] { "Status" })

Corrección

Utilice las funcionalidades integradas, proporcionadas por los frameworks, para definir los campos enlazables y no enlazables. Es preferible un enfoque basado en campos permitidos (enlazables), en el que solo se definan explícitamente las propiedades que el usuario debe poder actualizar. Un enfoque arquitectónico para prevenir el problema es utilizar el patrón Data Transfer Object (DTO) para evitar el enlace directo. El DTO debe incluir únicamente los campos que están destinados a ser editables por el usuario.
