Almacenamiento en la nube

ID
WSTG-CONF-11

Resumen

Los servicios de almacenamiento en la nube (AWS S3, Azure Blob Storage, Google Cloud Storage y equivalentes) permiten a las aplicaciones web almacenar y acceder a objetos sin ejecutar sus propios servidores de archivos. Sin embargo, una configuración inadecuada del control de acceso puede dar lugar a la exposición de información sensible, la manipulación de datos o el acceso no autorizado. Por defecto, el almacenamiento de los tres principales proveedores es privado y accesible solo para las identidades a las que se ha concedido acceso explícitamente, pero un bucket/contenedor, o los objetos individuales que contiene, pueden hacerse públicos, ya sea deliberadamente (y de forma demasiado amplia) o por error, lo que permite a un usuario no autorizado leer, subir o modificar datos.

Más allá del acceso público a nivel de bucket, esta clase de problema también abarca: configuraciones incorrectas de ACL/políticas IAM que otorgan a principales específicos más acceso del previsto; debilidades en las URL firmadas/prefirmadas utilizadas para conceder acceso limitado en el tiempo sin credenciales completas; y la configuración del versionado/ciclo de vida de objetos, que puede dejar recuperables datos sensibles más antiguos o supuestamente eliminados, o trasladarlos a ubicaciones con controles de acceso más débiles.

Objetivos de la prueba

  • Evaluar que la configuración del control de acceso de los servicios de almacenamiento (acceso público a nivel de bucket/contenedor, y ACL o políticas IAM a nivel de objeto/principal) esté correctamente establecida.
  • Evaluar si las URL firmadas/prefirmadas tienen un alcance acotado, están limitadas en el tiempo y se manejan de forma adecuada.
  • Evaluar si el versionado de objetos y la configuración del ciclo de vida podrían exponer datos sensibles antiguos o supuestamente eliminados.

Cómo probar

Primero, hay que identificar la URL del bucket/contenedor, que normalmente se encuentra mediante referencias en las respuestas HTTP (etiquetas <img>/<script>, bundles de JS, respuestas de API) en pruebas de caja negra, o mediante la consola del proveedor/el código fuente/la documentación en pruebas de caja gris. Luego se ejecutan los mismos tres sondeos contra cada proveedor: listar (¿el bucket/contenedor expone su contenido sin autenticación?), obtener (¿se puede leer un objeto específico o adivinado?) y escribir (¿se puede subir o sobrescribir un objeto arbitrario?). Hay que probar listar y obtener incluso cuando el nombre del bucket no se conoce de antemano; los nombres adivinables y comunes se tratan en Artefactos en el almacenamiento de objetos en la nube en lugar de duplicarse aquí.

Las tablas siguientes muestran tanto sondeos de caja negra (curl, sin asumir autenticación) como sondeos de caja gris (herramientas de línea de comandos del proveedor cuando se dispone de credenciales). Se usa curl para las pruebas de acceso sin autenticación; se usan las CLI de los proveedores, cuando las credenciales estén dentro del alcance, para confirmar directamente los permisos configurados.

Amazon S3

Formatos de URL: estilo virtual-hosted (https://<bucket>.s3.<region>.amazonaws.com/<key>) o estilo de ruta (https://s3.<region>.amazonaws.com/<bucket>/<key>); el endpoint global heredado (sin región) también funciona en algunas regiones.

Sondeo curl AWS CLI
Listar curl "https://<bucket>.s3.amazonaws.com/" aws s3 ls s3://<bucket>
Obtener curl "https://<bucket>.s3.amazonaws.com/<key>" aws s3 cp s3://<bucket>/<key> -
Escribir curl -X PUT -d 'test' "https://<bucket>.s3.amazonaws.com/test.txt" aws s3 cp test.txt s3://<bucket>/test.txt

Un listado sin autenticación exitoso devuelve un cuerpo XML <ListBucketResult>; una escritura fallida devuelve AccessDenied en el cuerpo de la respuesta o en el error de la CLI.

Azure Blob Storage

Formato de URL: https://<account-name>.blob.core.windows.net/<container-name>/<blob-name>.

Sondeo curl Azure CLI (caja gris)
Listar curl "https://<account>.blob.core.windows.net/<container>?restype=container&comp=list" az storage blob list --container-name <container>
Obtener curl "https://<account>.blob.core.windows.net/<container>/<blob>" az storage blob download --container-name <container> --name <blob>
Escribir curl -X PUT -d 'test' -H "x-ms-blob-type: BlockBlob" -H "x-ms-version: <current>" "https://<account>.blob.core.windows.net/<container>/test.txt" az storage blob upload --container-name <container> --name test.txt

Un 200 con un cuerpo XML <EnumerationResults> en el sondeo de listado significa que el nivel de acceso público del contenedor es Container (lectura pública + listado), y no Private ni Blob (lectura solo de nombres conocidos). az storage container show-permission confirma directamente el nivel configurado cuando se dispone de credenciales.

Google Cloud Storage (GCS)

Formato de URL (endpoint público de estilo XML): https://storage.googleapis.com/<bucket-name>/<object-name>.

Sondeo curl gsutil (caja gris)
Listar curl "https://storage.googleapis.com/storage/v1/b/<bucket>/o" gsutil ls gs://<bucket>
Obtener curl "https://storage.googleapis.com/<bucket>/<object>" gsutil cat gs://<bucket>/<object>
Escribir curl -X POST --data-binary @test.txt "https://storage.googleapis.com/upload/storage/v1/b/<bucket>/o?uploadType=media&name=test.txt" gsutil cp test.txt gs://<bucket>/test.txt

Un 200 con una lista de objetos en JSON en el sondeo de listado significa que el listado público está habilitado, comúnmente mediante un enlace IAM allUsers/allAuthenticatedUsers o una ACL heredada y no por el comportamiento predeterminado de GCS. gsutil iam get gs://<bucket> confirma directamente el enlace cuando se dispone de credenciales.

En Windows, se deben reemplazar las comillas simples (') por comillas dobles (") en los comandos curl anteriores.

Configuraciones incorrectas de ACL y políticas IAM

Más allá de un simple interruptor público/privado, los tres proveedores admiten concesiones de acceso de grano fino que es fácil dejar con un alcance excesivo:

  • AWS S3: revisar las políticas de buckets y las ACL en busca de concesiones a AllUsers/AuthenticatedUsers (el equivalente de S3 a "público"), y de políticas de buckets que concedan s3:* amplio o s3:GetObject/s3:PutObject a un principal comodín ("Principal": "*") o a otra cuenta de AWS que no debería necesitar acceso. También hay que confirmar que S3 Block Public Access esté habilitado a nivel de cuenta/bucket, salvo que se requiera explícitamente lo contrario: actúa como red de seguridad incluso si una política individual está mal configurada. aws s3api get-bucket-acl y aws s3api get-bucket-policy muestran la configuración efectiva en pruebas de caja gris.
  • Azure Blob Storage: revisar el nivel de acceso público del contenedor (Private/Blob/Container) como se indicó antes y, por separado, revisar las políticas de Shared Access Signature (SAS) y las asignaciones de roles RBAC (Storage Blob Data Reader/Contributor) con alcance sobre la cuenta de almacenamiento en busca de concesiones más amplias de lo necesario.
  • GCS: revisar los enlaces IAM (gsutil iam get gs://<bucket>) y cualquier ACL heredada por objeto/bucket en busca de enlaces allUsers (público) o allAuthenticatedUsers (cualquier cuenta de Google, no solo los usuarios de esta aplicación), ya que este último a menudo se confunde con "sigue siendo privado" cuando no lo es.

En los tres casos, hay que distinguir los objetos que son públicos por diseño (p. ej., recursos estáticos de un sitio, descargas públicas) de los objetos de configuración, respaldos o datos de usuario que acabaron siendo públicos sin intención: la intención detrás del objeto, y no solo su accesibilidad, determina si un hallazgo es real.

Debilidades de las URL firmadas/prefirmadas

Las URL firmadas (URL prefirmadas de S3, tokens SAS de Azure, URL firmadas de GCS) permiten a una aplicación conceder acceso limitado en el tiempo a un objeto privado sin compartir credenciales completas. Se debe revisar:

  • Expiración: confirmar que la expiración establecida en la URL firmada (X-Amz-Expires en S3, se= en Azure SAS, Expires/X-Goog-Expires en GCS) sea tan corta como lo permita el caso de uso; una URL firmada con una expiración de varios días o varios años es, en la práctica, una credencial permanente si se filtra (p. ej., mediante el historial del navegador, cabeceras referer, logs de proxy/acceso, o por haber sido compartida/reenviada).
  • Alcance: confirmar que la firma tenga como alcance únicamente el objeto/acción específicos que se necesitan (p. ej., las firmas de GCS/S3 pueden limitarse a un solo objeto y a un solo método HTTP; los tokens SAS de Azure pueden tener alcance sobre toda la cuenta si se generan como SAS a nivel de cuenta en lugar de SAS a nivel de servicio/contenedor/blob; hay que comprobar qué nivel se usó).
  • Filtración y reutilización: comprobar si las URL firmadas se registran en texto plano en proxies intermedios, CDN o logs de la aplicación, y si la misma URL firmada se reutiliza entre múltiples usuarios/sesiones en lugar de generarse por petición; una URL filtrada es válida para cualquiera hasta que expire o se revoque, y la mayoría de los esquemas no tienen forma de revocar anticipadamente una única URL firmada, salvo rotando la clave/credencial subyacente.
  • Validación de la firma: como comprobación básica de manipulación, hay que intentar modificar la ruta del objeto o los parámetros de consulta de una URL firmada válida (p. ej., apuntándola a un objeto distinto manteniendo la misma firma) y confirmar que la petición sea rechazada y no atendida.

Problemas de versionado y ciclo de vida

El versionado de objetos (conservar versiones anteriores de un objeto después de que se sobrescribe o elimina) y las políticas de ciclo de vida (reglas que trasladan o hacen expirar objetos con el tiempo) suelen habilitarse por razones de durabilidad/cumplimiento, pero pueden socavar la expectativa de que los datos "eliminados" realmente hayan desaparecido:

  • Si el versionado está habilitado, confirmar que un objeto "eliminado" (p. ej., uno que contiene datos que deberían borrarse por cumplimiento normativo, o un archivo de credenciales antiguo que fue rotado) no siga siendo recuperable mediante un ID de versión anterior. Para S3: aws s3api list-object-versions --bucket <bucket>; para GCS: gsutil ls -a gs://<bucket>/<object>; para Azure: instantáneas/versiones de blobs mediante az storage blob list --include v.
  • Confirmar que los ajustes de control de acceso se aplican de forma coherente en todas las versiones: una corrección del control de acceso de un bucket/contenedor aplicada después de un incidente puede afectar solo a la versión actual, dejando accesibles versiones anteriores del mismo objeto si el proveedor gestiona por separado el acceso versionado.
  • Revisar las reglas de ciclo de vida que trasladan objetos a una clase/nivel de almacenamiento diferente o a un bucket/cuenta diferente (p. ej., niveles de archivado, replicación entre regiones); confirmar que el destino tenga controles de acceso equivalentes, ya que un traslado por ciclo de vida puede mover silenciosamente datos sensibles a una ubicación que no estaba dentro del alcance de la revisión original del control de acceso.
  • Cuando una aplicación depende de "eliminar" para borrar datos sensibles (p. ej., en una solicitud de eliminación de datos de un usuario), confirmar que esto da lugar a una eliminación real (incluidas todas las versiones y cualquier copia replicada o trasladada por ciclo de vida) y no solo a quitar la accesibilidad de la versión actual.
