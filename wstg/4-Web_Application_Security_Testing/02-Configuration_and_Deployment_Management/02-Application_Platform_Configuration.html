Configuración de la plataforma de aplicaciones

ID
WSTG-CONF-02

Resumen

La configuración adecuada de cada uno de los elementos que componen la arquitectura de una aplicación es importante para evitar errores que puedan comprometer la seguridad de toda la arquitectura.

Revisar y probar las configuraciones son tareas críticas al crear y mantener una arquitectura. Esto se debe a que muchos sistemas vienen con configuraciones genéricas, que pueden no ajustarse bien a las tareas que deben realizar en los sitios específicos donde se instalan.

Si bien la instalación típica de un servidor web y de aplicaciones contiene mucha funcionalidad (como aplicaciones de ejemplo, documentación y páginas de prueba), lo que no sea esencial debe eliminarse antes del despliegue para evitar la explotación posterior a la instalación.

Objetivos de la prueba

  • Asegurar que los archivos predeterminados, de ejemplo y conocidos se hayan eliminado de la plataforma desplegada, de la imagen de contenedor o del paquete serverless.
  • Validar que no se haya dejado habilitado en producción ningún código de depuración, endpoint de depuración, modo de depuración ni módulo/dependencia sin uso.
  • Revisar los mecanismos de registro (logging) establecidos para la aplicación, incluidos los datos sensibles que pueden capturarse y quién o qué puede acceder a ellos o conservarlos.
  • Confirmar que se aplican los ajustes de endurecimiento para producción específicos de cada framework, contenedor y entorno serverless, en lugar de dejarlos en sus valores predeterminados inseguros.

Cómo probar

Pruebas de caja negra

Archivos y directorios de ejemplo y conocidos

En una instalación predeterminada, muchos servidores web, servidores de aplicaciones y frameworks proporcionan aplicaciones de ejemplo, andamiaje (scaffolding) y páginas de prueba para beneficio del desarrollador, de modo que pueda confirmar que el servidor funciona correctamente justo después de la instalación o de init. Históricamente, esta clase de problema estuvo ejemplificada por casos como CVE-1999-0449 (denegación de servicio en IIS cuando se había instalado el sitio de ejemplo Exair), CAN-2002-1744 (vulnerabilidad de recorrido de directorios en CodeBrws.asp en Microsoft IIS 5.0) o CAN-2003-1172 (recorrido de directorios en el ejemplo view-source de Cocoon de Apache). El problema de fondo (contenido de ejemplo o de andamiaje sin eliminar que llega a producción) no ha cambiado hoy, solo los objetivos:

  • Andamiaje de frameworks que se deja en su lugar: páginas de bienvenida predeterminadas de Django/Rails/Laravel, páginas de error/whitelabel predeterminadas de Spring Boot, páginas de inicio predeterminadas de create-react-app/Next.js/Vite, o un index.html sin modificar de una plantilla inicial. Cada una puede filtrar el framework y la versión exactos en uso y, a veces, rutas de andamiaje sobrantes.
  • Documentación/consolas de API autogeneradas que quedan accesibles en producción: Swagger UI/OpenAPI (/swagger-ui, /swagger.json, /v2/api-docs), GraphQL Playground/GraphiQL o gRPC reflection. Con frecuencia exponen el esquema completo, incluidas operaciones no documentadas o exclusivas de administración, y algunas permiten la ejecución directa de peticiones ("try it out") sin comprobaciones de autorización adicionales.
  • Clases de archivos de ejemplo heredados: phpinfo.php, test.php, info.php, scripts de instalación/configuración predeterminados de CMS (p. ej., wp-admin/install.php, installation/ de Joomla) que siguen accesibles después de la puesta en producción.

Los escáneres CGI/web con una base de datos de archivos y directorios de ejemplo conocidos son una forma rápida de comprobar esto; el descubrimiento automatizado debe complementarse con una revisión manual del sitio para detectar el andamiaje específico de cada framework que los escáneres genéricos no identifican.

Endpoints y modos de depuración

La mayoría de los frameworks modernos incluyen un modo de depuración/desarrollo que es explícitamente inseguro para producción, ya que está diseñado para dar al desarrollador la máxima visibilidad (trazas de pila completas, ejecución de código en el navegador, volcados de variables de entorno) a costa de exponer exactamente la misma información a un atacante si se deja habilitado:

  • Django: DEBUG=True muestra trazas de pila completas, los valores de las variables locales y la lista de aplicaciones/ajustes instalados ante cualquier excepción no controlada. Hay que provocar un error (p. ej., solicitar una ruta inexistente o enviar una entrada mal formada) y comprobar si la respuesta es una página de depuración de Django en lugar de un 404/500 genérico.
  • Flask/Werkzeug: el depurador de Werkzeug, si está habilitado (app.run(debug=True) o FLASK_DEBUG=1), expone una consola de Python en el navegador ante excepciones no controladas. Aunque nominalmente está protegido con un PIN, en versiones antiguas de Werkzeug el PIN a menudo puede derivarse de información presente también en la página de error o de valores predecibles del propio host. Cualquier depurador de Werkzeug accesible en producción debe tratarse como un hallazgo crítico (ejecución remota de código), no solo como una fuga de información.
  • Spring Boot Actuator: endpoints como /actuator/env, /actuator/heapdump, /actuator/httptrace y /actuator/mappings pueden exponer variables de entorno/secretos, un volcado completo del heap (que puede contener credenciales y datos de sesión) y el enrutamiento interno. Hay que comprobar si los endpoints de Actuator son accesibles en producción y, de serlo, si management.endpoints.web.exposure.include se ha limitado desde un valor predeterminado excesivamente amplio.
  • Rails: config.consider_all_requests_local = true (valor predeterminado en desarrollo) muestra páginas de error detalladas con fragmentos de código fuente y datos de la petición/sesión; hay que confirmar que sea false en la configuración del entorno de producción.
  • Express/Node.js: manejadores de errores predeterminados que devuelven err.stack al cliente, o dejar montado en una compilación de producción el middleware de desarrollo integrado de un framework (p. ej., el middleware del servidor de desarrollo de un bundler).
  • Next.js/React y otras herramientas de compilación de SPA: compilaciones de producción que aún incluyen source maps de JavaScript (archivos .map) o dejan accesible un servidor de desarrollo; ambos pueden reconstruir el código fuente original a partir de bundles minificados.
  • Introspección de GraphQL: incluso sin una interfaz de Playground, si en producción se responde la consulta de introspección ({ __schema { types { name } } }), se revela el esquema completo, incluidos campos/mutaciones no expuestos en la superficie de API documentada.

Como prueba general: hay que provocar deliberadamente un error de la aplicación (entrada mal formada, parámetro faltante, excepción forzada) en cada componente/framework distinto en uso, y confirmar que la respuesta sea un error genérico que no revele información, en lugar de una página de depuración del framework.

Revisión de comentarios

Es muy común que los programadores añadan comentarios al desarrollar aplicaciones web de gran tamaño. Sin embargo, los comentarios incluidos en línea en el código HTML pueden revelar información interna que no debería estar disponible para un atacante. A veces, una parte del código fuente se deja comentada cuando una funcionalidad ya no es necesaria, pero ese comentario se filtra sin querer a las páginas HTML devueltas a los usuarios.

La revisión de comentarios debe hacerse para determinar si se está filtrando información a través de ellos. Esta revisión solo puede hacerse de forma exhaustiva mediante un análisis del contenido estático y dinámico del servidor web y mediante búsquedas en archivos. Puede ser útil navegar por el sitio de forma automática o guiada y almacenar todo el contenido obtenido. Luego se puede buscar en este contenido para analizar los comentarios HTML disponibles en el código.

Configuración del sistema

Pueden utilizarse diversas herramientas, documentos o listas de verificación para dar a los profesionales de TI y de seguridad una evaluación detallada de la conformidad de los sistemas objetivo con distintas líneas base o benchmarks de configuración. Estas herramientas incluyen, entre otras, las siguientes:

  • CIS-CAT Lite
  • Microsoft's Attack Surface Analyzer
  • NIST's National Checklist Program

Pruebas de caja gris

Revisión de la configuración

La configuración del servidor web o del servidor de aplicaciones cumple un papel importante en la protección del contenido del sitio y debe revisarse cuidadosamente para detectar errores de configuración comunes. Obviamente, la configuración recomendada varía según la política del sitio y la funcionalidad que debe proporcionar el software del servidor. En la mayoría de los casos, sin embargo, deben seguirse las guías de configuración (proporcionadas por el proveedor del software o por terceros) para determinar si el servidor se ha asegurado correctamente.

Es imposible decir de forma genérica cómo debe configurarse un servidor; no obstante, deben tenerse en cuenta algunas pautas comunes:

  • Habilitar únicamente los módulos del servidor (extensiones ISAPI en el caso de IIS) que la aplicación necesita. Esto reduce la superficie de ataque, ya que el servidor se reduce en tamaño y complejidad al deshabilitar módulos de software. También evita que las vulnerabilidades que puedan aparecer en el software del proveedor afecten al sitio si solo están presentes en módulos que ya se han deshabilitado. El mismo principio se aplica a las pilas modernas de middleware/módulos: hay que revisar los módulos del servidor web (módulos de Apache/Nginx, módulos de IIS), el middleware del framework de aplicación y las listas de paquetes/dependencias instalados (npm ls, pip list, etc.) en busca de cualquier elemento incluido por una plantilla predeterminada pero que no se use realmente; una dependencia sin uso sigue siendo superficie de ataque y una carga de parcheo aunque el código de la aplicación nunca la invoque.
  • Manejar los errores del servidor (40x o 50x) con páginas personalizadas en lugar de las páginas predeterminadas del servidor web. En concreto, hay que asegurarse de que ningún error de la aplicación se devuelva al usuario final y de que no se filtre código a través de estos errores, ya que ayudaría a un atacante. De hecho, es muy común olvidar este punto, porque los desarrolladores sí necesitan esta información en los entornos de preproducción.
  • Asegurarse de que el software del servidor se ejecute con privilegios mínimos en el sistema operativo. Esto evita que un error en el software del servidor comprometa directamente todo el sistema, aunque un atacante podría escalar privilegios una vez que ejecute código como el servidor web.
  • Asegurarse de que el software del servidor registre correctamente tanto los accesos legítimos como los errores.
  • Asegurarse de que el servidor esté configurado para manejar adecuadamente las sobrecargas y evitar ataques de denegación de servicio. Garantizar que el servidor se haya ajustado correctamente en cuanto a rendimiento.
  • No conceder nunca a identidades no administrativas (con la excepción de NT SERVICE\WMSvc) acceso a applicationHost.config, redirection.config y administration.config (ni de lectura ni de escritura).
  • No compartir nunca en la red los archivos applicationHost.config, redirection.config y administration.config.
  • No almacenar información sensible en archivos de configuración legibles.
  • Cifrar los datos de configuración sensibles cuando sea necesario.
  • Restringir el acceso a la configuración compartida y protegerla de manera apropiada.

Registro (logging)

El registro es una parte importante de la seguridad de las aplicaciones. Apoya la monitorización, la respuesta a incidentes y las investigaciones. Hay que revisar tanto el registro de la plataforma como el de la aplicación para determinar si se registran los eventos relevantes para la seguridad, si los registros son útiles y si el proceso de registro introduce riesgos adicionales.

Durante la revisión, se debe verificar lo siguiente:

  • Se registran los eventos relevantes para la seguridad (autenticación, fallos de autorización, acciones administrativas, fallos de validación de entrada).
  • Las entradas del log contienen suficiente contexto para apoyar una investigación.
  • Datos sensibles en los logs: comprobar que los logs no capturen contraseñas, tokens/claves de API, identificadores de sesión, números completos de tarjetas de pago ni otros datos personales regulados. Una fuente sorprendentemente común de esto es el registro detallado o a nivel de depuración que se deja habilitado en producción (p. ej., un framework que registra los cuerpos completos de petición/respuesta, o una biblioteca que registra objetos de excepción que incluyen credenciales pasadas como argumentos), y las integraciones de seguimiento de errores/APM de terceros que, por defecto, envían fuera del host datos sin procesar de las peticiones (cabeceras, cuerpos).
  • Los datos registrados se manejan de forma segura antes de almacenarse y mostrarse (p. ej., las entradas del log no se muestran posteriormente sin escapar en una interfaz visor de logs, lo que puede habilitar XSS almacenado mediante inyección en logs).
  • Acceso a los logs: restringido al personal/servicios autorizados. Hay que comprobar tanto los archivos/flujos de logs en sí (permisos de archivos, véase Permisos de archivos) como cualquier plataforma de registro centralizado (SIEM, servicio de logging en la nube) en busca de acceso de lectura excesivamente amplio o de falta de aislamiento por inquilino en sistemas multiinquilino.
  • Retención: confirmar que existe y se aplica un periodo de retención definido (tanto "logs conservados durante muy poco tiempo para investigar un incidente" como "logs conservados indefinidamente, convirtiéndose en un repositorio creciente de datos sensibles" son hallazgos que vale la pena reportar).
  • Los logs están protegidos contra manipulación (almacenamiento de solo anexado/escritura única o controles de integridad equivalentes cuando sea viable).
  • Los fallos del registro no exponen información de depuración sensible al usuario final (un fallo del subsistema de registro no debería recurrir a mostrar el error no registrado directamente en la respuesta).
  • Los logs pueden centralizarse o correlacionarse en entornos distribuidos (los contenedores, las funciones serverless y los nodos con balanceo de carga necesitan, cada uno, una forma coherente de correlacionar una misma petición/traza entre componentes; hay que verificar que esto exista, en lugar de que cada componente registre de forma aislada sin un ID de petición/traza compartido).

Las pruebas deben confirmar que los logs son utilizables, coherentes y apoyan eficazmente las actividades de detección y respuesta, sin convertirse ellos mismos en una fuente de exposición de datos sensibles.

Imágenes de contenedor

Cuando la aplicación se despliega como una imagen de contenedor, el mismo principio de "eliminar lo que no se necesita" del endurecimiento tradicional de servidores se aplica a lo que se incorpora en la imagen. La mayoría de estas comprobaciones requieren la imagen misma (caja gris); las excepciones se indican. Para los campos de securityContext de tiempo de ejecución relacionados (runAsNonRoot, readOnlyRootFilesystem, capabilities, seccompProfile, namespaces del host), véase la Lista de verificación de SecurityContext y endurecimiento de contenedores en Permisos de archivos.

  • Revisar el Dockerfile/la construcción de la imagen en busca de archivos predeterminados/de ejemplo sobrantes, secretos en tiempo de compilación (claves de API o credenciales pasadas como argumentos de compilación y dejadas en una capa intermedia aunque se hayan eliminado de la capa final) y herramientas de compilación innecesarias (compiladores, cachés de gestores de paquetes, shells) que una compilación multietapa debería haber dejado en la etapa de compilación. Caja gris: ejecutar docker history --no-trunc <image> o una herramienta de inspección de capas (p. ej., dive) contra la imagen real; un hallazgo requiere que el secreto o la herramienta sean visibles en una capa retenida, no solo que se sospechen a partir del código fuente del Dockerfile.
  • Preferir imágenes base mínimas (slim/distroless/basadas en scratch) para la capa final de ejecución. Caja gris: comparar la imagen base indicada en la etapa final del Dockerfile con la lista real de paquetes instalados en la imagen (docker run --rm <image> sh -c "..." donde exista un shell, o inspección de capas donde no).
  • Confirmar que las variables de entorno del modo de depuración/desarrollo no estén establecidas como valores predeterminados de la imagen (p. ej., ENV FLASK_DEBUG=1, ENV NODE_ENV=development). Caja negra: provocar un error de la aplicación contra el contenedor en ejecución y comprobar si aparece una página de depuración/traza de pila (la misma prueba que en Endpoints y modos de depuración más arriba); esta es la evidencia de que el valor predeterminado realmente surtió efecto en tiempo de ejecución, ya que una sobrescritura en la capa de orquestación podría haber corregido un valor predeterminado inseguro de la imagen. Caja gris: confirmar mediante docker inspect --format '{{.Config.Env}}' <image> que el valor predeterminado a nivel de imagen es seguro por sí mismo, independientemente de cualquier sobrescritura.
  • Confirmar que el contenedor no se ejecute como root por defecto y que la imagen no incorpore .git, .env ni otros archivos sensibles copiados mediante un COPY . . amplio sin un .dockerignore correspondiente. Caja gris: docker inspect --format '{{.Config.User}}' <image> (vacío o 0 significa root) y una inspección de capas/sistema de archivos en busca de los archivos no deseados.

Ejemplo de hallazgo: docker history --no-trunc sobre una imagen publicada muestra una capa de compilación con RUN echo $DB_PASSWORD > /tmp/debug.log, lo que filtra la contraseña de la base de datos de producción a cualquiera que pueda descargar la imagen, aunque la capa final ya no contenga el archivo. La evidencia es el valor visible en el historial de esa capa, no simplemente que un Dockerfile use un argumento de compilación con un nombre similar.

Entornos de ejecución serverless

Las funciones serverless (AWS Lambda, Azure Functions, Google Cloud Functions/Cloud Run functions) cambian el lugar donde aparecen los errores de configuración, pero se aplican las mismas categorías de configuración incorrecta. Las consolas y CLI de los proveedores difieren (AWS, Azure y GCP exponen esta configuración de forma distinta); hay que adaptar el comando o la ruta de la consola al proveedor real en el alcance, en lugar de asumir que uno es universal.

  • Código predeterminado/de ejemplo: confirmar que el código de andamiaje generado por sam init/serverless create/plantillas equivalentes (manejadores de ejemplo, payloads de eventos de ejemplo) se haya eliminado en lugar de desplegarse junto con la función real. Caja negra: invocar cualquier ruta/path de manejador de ejemplo descubierto y confirmar que devuelve datos de la aplicación o un error, y no la salida de marcador de posición del andamiaje.
  • Registro detallado/de depuración y respuestas de error: muchos frameworks serverless registran el payload completo del evento o devuelven una traza de pila completa en la respuesta HTTP por defecto en modo local/de desarrollo. Caja negra: provocar un error de la aplicación mediante el punto de entrada público de la función y comprobar si la respuesta HTTP contiene una traza de pila. Caja gris: revisar los logs de la función (p. ej., CloudWatch Logs) en busca de cuerpos completos de petición/respuesta capturados, según la guía anterior sobre datos sensibles en los logs.
  • Permisos IAM/del rol de ejecución excesivamente amplios: el rol de ejecución de una función debe limitarse únicamente a los recursos/acciones que necesita. Caja gris solamente en la mayoría de los trabajos: leer la política adjunta al rol de ejecución (p. ej., aws iam get-role-policy) y comparar las acciones/recursos concedidos con lo que el código de la función realmente invoca. Cuando se confirma de forma independiente un error de ejecución de código o de inyección en la función, la evidencia de caja negra (leer/escribir con éxito un recurso que el alcance previsto no debería permitir) eleva esto de una observación de configuración a un hallazgo demostrado.
  • Variables de entorno para secretos: confirmar que los secretos se obtienen de un gestor de secretos/almacén de parámetros en tiempo de ejecución, en lugar de almacenarse en texto plano en la configuración de la función. Caja gris: leer las variables de entorno configuradas de la función mediante la consola/CLI del proveedor y comprobar si los valores parecen secretos en bruto o una referencia (ARN/ID de recurso) a una entrada de un gestor de secretos.
  • Consolas de prueba/invocación: confirmar que la función nativa de "invocación de prueba" de la consola esté protegida por el mismo control de acceso que la propia consola/cuenta, y que no se haya dejado ningún endpoint HTTP de prueba complementario invocable públicamente. Caja negra: intentar alcanzar directamente cualquier ruta HTTP de prueba/invocación descubierta.

Ejemplo de hallazgo: al rol de ejecución de una función se le concede s3:* sobre todos los buckets en lugar de s3:GetObject sobre uno solo (confirmado en caja gris mediante la política IAM del rol), y un error de recorrido de rutas encontrado de forma independiente en el propio código de la función (confirmado en caja negra) se usa para leer/escribir en un bucket no relacionado, lo que demuestra que un error acotado se convirtió en una vulnerabilidad de lectura/escritura de S3 a nivel de toda la cuenta debido al rol con un alcance excesivo.

Endurecimiento para producción específico de cada framework

Hay que confirmar que cada framework en uso tenga aplicados los ajustes de endurecimiento para producción documentados, y no solo sus valores predeterminados. La tabla siguiente da un ajuste representativo por framework como sondeo inicial, no como una prueba completa de endurecimiento ni como una lista de verificación que basta con cumplir: el nombre exacto, el valor predeterminado e incluso la disponibilidad de un ajuste pueden cambiar entre versiones mayores del mismo framework, y un despliegue aún puede ser inseguro con todos los ajustes listados "correctos" si se pasó por alto algo más de la lista de verificación del mismo framework.

Framework Ajuste representativo que se debe sondear
Django DEBUG = False, ALLOWED_HOSTS restringido a los nombres de host reales
Flask FLASK_DEBUG=0 / debug=False, app.config['ENV'] = 'production'
Ruby on Rails RAILS_ENV=production, config.consider_all_requests_local = false
Spring Boot management.endpoints.web.exposure.include restringido a lo necesario; server.error.include-stacktrace=never
Express/Node.js NODE_ENV=production (muchas bibliotecas de middleware cambian su comportamiento, incluida la verbosidad de los errores, según este valor)
Next.js/otros frameworks de SPA se sirve la compilación de producción (no el servidor de desarrollo), con los source maps excluidos o con acceso restringido

Para cada framework en el alcance:

  • Tratar la entrada de la tabla como una comprobación representativa para orientar la prueba, no como prueba de que el despliegue está endurecido; hay que recorrer la lista de verificación oficial vigente de despliegue en producción de ese framework (enlazada en Referencias) para obtener el conjunto completo.
  • Verificar la configuración efectiva en tiempo de ejecución, no solo el archivo de configuración fuente: una variable de entorno, un indicador de línea de comandos o una sobrescritura en la capa de orquestación (variables de entorno del contenedor, ConfigMap/Secret de Kubernetes, ajuste del panel de una PaaS) puede cambiar el valor realmente vigente en tiempo de ejecución aunque el archivo versionado parezca correcto. Siempre que sea viable, hay que confirmarlo mediante el comportamiento de la aplicación en ejecución (p. ej., ¿emite una página de depuración ante un error? ¿expone el endpoint?), en lugar de solo mediante la revisión estática de archivos.
  • No inferir que un ajuste correcto implica que el framework esté endurecido en otros aspectos; pueden seguir faltando ajustes no relacionados de la misma lista de verificación.
