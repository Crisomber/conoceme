Toma de control de subdominios (Subdomain Takeover)

ID
WSTG-CONF-10

Resumen

La explotación exitosa de este tipo de vulnerabilidad permite a un adversario reclamar y tomar el control del subdominio de la víctima. Este ataque depende de lo siguiente:

  1. El registro del subdominio en el servidor DNS externo de la víctima está configurado para apuntar a un recurso/servicio externo/endpoint inexistente o inactivo. La proliferación de productos XaaS (Anything as a Service) y de servicios de nube pública ofrece muchos objetivos potenciales que considerar.
  2. El proveedor de servicios que aloja el recurso/servicio externo/endpoint no gestiona correctamente la verificación de la propiedad del subdominio.

Si la toma de control del subdominio tiene éxito, son posibles una gran variedad de ataques (servir contenido malicioso, phishing, robar cookies de sesión de los usuarios, credenciales, etc.). Esta vulnerabilidad podría explotarse con una amplia variedad de registros de recursos DNS, entre ellos: A, CNAME, MX, NS, TXT, etc. En términos de gravedad del ataque, una toma de control de subdominio mediante NS (aunque menos probable) tiene el mayor impacto, porque un ataque exitoso podría resultar en el control total de toda la zona DNS y del dominio de la víctima.

GitHub

  1. La víctima (victim.com) usa GitHub para el desarrollo y configuró un registro DNS (coderepo.victim.com) para acceder a él.
  2. La víctima decide migrar su repositorio de código de GitHub a una plataforma comercial y no elimina coderepo.victim.com de su servidor DNS.
  3. Un adversario descubre que coderepo.victim.com está alojado en GitHub y lo reclama usando GitHub Pages y su propia cuenta de GitHub.

Dominio expirado

  1. La víctima (victim.com) es propietaria de otro dominio (victimotherdomain.com) y usa un registro CNAME (www) para hacer referencia al otro dominio (www.victim.com --> victimotherdomain.com)
  2. En algún momento, victimotherdomain.com expira y queda disponible para que cualquiera lo registre. Como el registro CNAME no se elimina de la zona DNS de victim.com, cualquiera que registre victimotherdomain.com tiene control total sobre www.victim.com hasta que el registro DNS se elimine o se actualice.

Objetivos de la prueba

  • Enumerar todos los dominios posibles (anteriores y actuales), incluidos los nombres cubiertos por comodines.
  • Identificar los dominios olvidados o mal configurados, y cualquier firma de servicio colgante (dangling) no cubierta por una huella de respuesta conocida.
  • Cuando se confirme que una toma de control es factible, evaluar si las cookies, la política CORS, la validación de redirecciones de OAuth o la lista de permitidos de CSP de la aplicación padre extienden la confianza al subdominio reclamado.

Cómo probar

Pruebas de caja negra

Las pruebas de toma de control de subdominios siguen tres fases: enumeración de subdominios, detección automatizada basada en huellas y validación manual.

Un registro DNS colgante (dangling) ocurre cuando una entrada DNS apunta a un recurso externo que ya no existe o que ha sido desaprovisionado. Por ejemplo, un registro CNAME que apunta a un sitio de GitHub Pages que el propietario eliminó sigue resolviéndose, pero el recurso subyacente no está reclamado. Un atacante puede registrar ese recurso y tomar el control del subdominio.

Enumeración de subdominios

Se usa subfinder para descubrir subdominios del dominio objetivo: subfinder -d victim.com -o subdomains.txt

Esto produce una lista de subdominios para usar en la fase de detección.

Antes de la identificación por huellas, hay que resolver y filtrar la lista para conservar solo los subdominios con un registro CNAME, NS o MX, ya que son los tipos de registro que con más frecuencia quedan colgantes. dnsx puede hacerlo de forma masiva: dnsx -l subdomains.txt -cname -resp -o resolved.txt

Detección basada en huellas

La detección basada en huellas funciona comparando la respuesta HTTP de cada subdominio con una base de datos de respuestas conocidas de servicios vulnerables. El proyecto can-i-take-over-xyz mantiene esta base de datos, catalogando las cadenas de respuesta específicas que devuelven proveedores de servicios como GitHub Pages, AWS S3, Heroku y Fastly cuando un recurso no está reclamado.

Se usa subzy para un primer escaneo rápido: subzy run --targets subdomains.txt

Se continúa con nuclei usando las plantillas dedicadas a tomas de control para obtener un resultado más preciso: nuclei -l subdomains.txt -t takeovers/

Un resultado positivo de cualquiera de las dos herramientas indica que la respuesta de un subdominio coincidió con una huella vulnerable conocida, lo que sugiere un registro DNS colgante que apunta a un recurso no reclamado en un servicio de terceros.

Por ejemplo, un subdominio que apunta a un sitio de GitHub Pages no reclamado devuelve la siguiente respuesta:

HTTP/1.1 404 Not Found
...
<p>There isn't a GitHub Pages site here.</p>

Esta cadena específica figura en can-i-take-over-xyz como la huella de GitHub Pages. Cuando subzy o nuclei encuentran esta respuesta, marcan el subdominio como potencialmente vulnerable.

Validación manual

Las herramientas automatizadas producen falsos positivos. Cada hallazgo debe validarse manualmente antes de reportarlo.

  1. Confirmar el registro DNS y a dónde apunta: dig CNAME subdomain.victim.com
  2. Confirmar que la respuesta coincide con la huella esperada para ese proveedor de servicios según figura en can-i-take-over-xyz: curl -i http://subdomain.victim.com
  3. Confirmar que el recurso no está reclamado en la plataforma del proveedor de servicios. No se debe reclamar.

Para los registros NS en concreto, hay que comprobar si un servidor de nombres delegado no está registrado: dig NS subdomain.victim.com, y luego comprobar si el dominio del propio servidor de nombres devuelto está disponible para su registro. Un dominio de servidor de nombres sin registrar significa que cualquiera puede registrarlo y responder a las consultas DNS de la zona delegada, la variante de toma de control de mayor impacto.

Tomas de control específicas de la nube

Los principales proveedores de nube y los servicios PaaS/JAMstack tienen patrones de toma de control distintos que merecen atención específica. Esta lista cambia a medida que los proveedores corrigen las brechas de verificación, por lo que hay que contrastar el estado actual con can-i-take-over-xyz antes de reportar:

  • AWS S3: un CNAME que apunta a la URL de un bucket de S3 (por ejemplo, bucket.s3.amazonaws.com) donde el bucket ya no existe devuelve una respuesta NoSuchBucket. Cualquiera que cree un bucket con el mismo nombre en cualquier cuenta de AWS puede reclamar el subdominio.
  • Azure: los CNAME colgantes que apuntan a recursos de Azure desaprovisionados, como App Services, endpoints de Azure CDN/Front Door o perfiles de Traffic Manager, pueden reclamarse registrando el mismo nombre de recurso en una suscripción de Azure diferente.
  • GCP: existen patrones similares para buckets de Cloud Storage y endpoints de Firebase Hosting.
  • GitHub Pages: cubierto anteriormente en GitHub; sigue siendo uno de los hallazgos más comunes en la práctica.
  • Vercel y Netlify: un CNAME que apunta a un dominio de proyecto (p. ej., *.vercel.app, *.netlify.app) que ha sido eliminado o renombrado normalmente puede reclamarse de nuevo creando un proyecto nuevo con el nombre coincidente.
  • Dominios personalizados de Cloudflare Pages / Workers: los CNAME colgantes a *.pages.dev a veces pueden reclamarse dependiendo de las protecciones a nivel de cuenta; hay que verificar el comportamiento actual, ya que Cloudflare lo ha endurecido con el tiempo.
  • Heroku: un CNAME a *.herokuapp.com para una app que ha sido eliminada devuelve una respuesta "No such app" y puede reclamarse de nuevo creando una app con el nombre coincidente (sujeto a las reglas de nombres de Heroku).
  • Fastly y Shopify: ambos han aparecido históricamente en reportes de tomas de control por configuraciones de dominios personalizados colgantes; cualquier coincidencia con sus huellas en can-i-take-over-xyz debe tratarse igual que en los proveedores anteriores.

Firmas de servicios colgantes

Más allá de las huellas de cadenas de respuesta ya cubiertas arriba, un registro colgante también puede manifestarse mediante señales que no son en sí mismas una coincidencia en el cuerpo HTTP:

  • Una respuesta NXDOMAIN, SERVFAIL o un registro A vacío al resolver el nombre de host del propio servicio al que apunta el CNAME de un objetivo (por ejemplo, el propio destino del CNAME no se resuelve) es una señal más fuerte que una coincidencia de huella HTTP, ya que muestra que el recurso de origen ha desaparecido por completo y no solo que devuelve una página de "no encontrado".
  • Los errores de certificado TLS (discrepancia de nombre de host, certificado de un dominio no relacionado) en un subdominio que debería ser servido por un proveedor específico pueden indicar que el proveedor ya no tiene un certificado aprovisionado para ese nombre de host, lo cual es coherente con un recurso desaprovisionado.
  • Las páginas de error específicas de un proveedor que aún no coinciden con una huella conocida de can-i-take-over-xyz (servicios nuevos o menos comunes) siguen justificando una investigación manual con los mismos pasos de validación con dig/curl; la base de datos de huellas debe tratarse como un punto de partida, no como una lista exhaustiva.

Riesgo de CNAME comodín

Un registro DNS comodín (por ejemplo, *.victim.com CNAME target.example-paas.com) que apunta a un servicio propenso a tomas de control multiplica el impacto de una sola configuración colgante: cualquier subdominio que un atacante elija solicitar (anything.victim.com, admin.victim.com, login.victim.com) se resuelve a través del comodín, de modo que reclamar el recurso de destino otorga control sobre un conjunto ilimitado de subdominios y no sobre uno solo. Al enumerar, hay que comprobar explícitamente los registros comodín (dig CNAME nonexistent-random-string.victim.com, comparando el resultado con un subdominio real conocido), ya que los nombres cubiertos por comodines suelen estar ausentes de las listas de subdominios de reconocimiento pasivo y solo aparecen al probar directamente una etiqueta arbitraria.

Impacto más allá del control del contenido

Una toma de control exitosa no se limita a servir contenido controlado por el atacante en el subdominio recuperado; como el subdominio comparte el límite de confianza del dominio padre en varios mecanismos de navegador y de protocolo, el impacto puede extenderse a:

  • Cookies: una cookie con un alcance sin la restricción Secure/solo host (por ejemplo, establecida con un atributo Domain que cubre el dominio padre, o sin él y por tanto accesible a un subdominio hermano mediante el comportamiento de dominios relacionados) puede leerse o sobrescribirse desde el subdominio reclamado, lo que permite el secuestro de sesiones contra la aplicación principal.
  • CORS: si la política CORS de la aplicación principal permite el patrón de origen que incluye el subdominio reclamado (una coincidencia de subdominio comodín, o una comprobación de Origin reflejado que confía en *.victim.com), el atacante puede hacer peticiones autenticadas de origen cruzado contra la aplicación real desde el subdominio reclamado.
  • OAuth: una configuración de cliente OAuth con un URI de redirección en el subdominio reclamado (o una validación del URI de redirección que solo comprueba el sufijo del dominio padre) permite al atacante recibir códigos de autorización o tokens destinados a la aplicación legítima.
  • CSP: una Content-Security-Policy en la aplicación principal que incluye en la lista de permitidos el dominio padre con un comodín (*.victim.com) como origen de scripts o de conexión permite al atacante servir scripts o exfiltrar datos desde un origen de confianza según la política.

Al reportar un hallazgo de toma de control, hay que comprobar si alguno de estos puntos aplica al subdominio específico reclamado, ya que cambian el hallazgo de "suplantación de contenido en un subdominio aislado" a "compromiso de la confianza de sesión/autorización/scripts de la aplicación principal".

Pruebas de caja gris

El evaluador dispone del archivo de zona DNS, lo que significa que la enumeración DNS no es necesaria. La metodología de prueba es la misma.

Corrección

Para mitigar el riesgo de toma de control de subdominios, deben eliminarse de la zona DNS los registros de recursos DNS vulnerables. Se recomienda como buena práctica la monitorización continua y las revisiones periódicas.
