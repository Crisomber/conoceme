Métodos HTTP

ID
WSTG-CONF-06

Resumen

HTTP ofrece varios métodos (o verbos) que pueden usarse para realizar acciones en el servidor web. Si bien GET y POST son, con mucho, los métodos más comunes para acceder a la información que proporciona un servidor web, pueden ser compatibles otros métodos que, en ocasiones, pueden ser explotados por los atacantes.

La RFC 7231 define los principales métodos (o verbos) válidos de petición HTTP, aunque en otras RFC se han añadido métodos adicionales, como la RFC 5789. Varios de estos verbos se han reutilizado con distintos fines en aplicaciones RESTful, como se lista en la tabla siguiente.

Método Propósito original Propósito en RESTful
GET Solicitar un archivo. Solicitar un objeto.
HEAD Solicitar un archivo, pero devolver solo las cabeceras HTTP.
POST Enviar datos.
PUT Subir un archivo. Crear un objeto.
DELETE Eliminar un archivo Eliminar un objeto.
CONNECT Establecer una conexión con otro sistema.
OPTIONS Listar los métodos HTTP admitidos. Realizar una petición CORS Preflight.
TRACE Devolver como eco la petición HTTP con fines de depuración.
PATCH Modificar un objeto.
QUERY Recuperación segura de datos con un cuerpo de petición. Consultar objetos o recursos con parámetros complejos.

Objetivos de la prueba

  • Enumerar los métodos HTTP admitidos.
  • Probar la evasión del control de acceso.
  • Probar técnicas de sobrescritura de métodos HTTP.

Cómo probar

Descubrir los métodos admitidos

Para realizar esta prueba, el evaluador necesita una forma de identificar qué métodos HTTP admite el servidor web que se está examinando. La manera más sencilla de hacerlo es enviar una petición OPTIONS al servidor:

OPTIONS / HTTP/1.1
Host: example.org

El servidor debería responder entonces con una lista de los métodos admitidos:

HTTP/1.1 200 OK
Allow: OPTIONS, GET, HEAD, POST

Sin embargo, no todos los servidores responden a las peticiones OPTIONS, y algunos incluso pueden devolver información inexacta. También vale la pena señalar que los servidores pueden admitir distintos métodos para distintas rutas. Esto significa que, aunque un método no esté admitido para el directorio raíz /, eso no indica necesariamente que el mismo método no vaya a estar admitido en otro lugar.

Una forma más fiable de probar los métodos admitidos es simplemente enviar una petición con ese tipo de método y examinar la respuesta del servidor. Si el método no está permitido, el servidor debería devolver un estado 405 Method Not Allowed.

Vale la pena señalar que algunos servidores tratan los métodos desconocidos como equivalentes a GET, por lo que pueden responder a métodos arbitrarios, como en la petición que se muestra a continuación. Esto en ocasiones puede ser útil para evadir un firewall de aplicaciones web o cualquier otro filtrado que bloquee métodos específicos.

FOO / HTTP/1.1
Host: example.org

Las peticiones con métodos arbitrarios también pueden hacerse con curl usando la opción -X:

curl -X FOO https://example.org

También existen diversas herramientas automatizadas que pueden intentar determinar los métodos admitidos, como el script de Nmap http-methods. Sin embargo, estas herramientas pueden no probar los métodos peligrosos (es decir, los que pueden causar cambios, como PUT o DELETE), o pueden causar cambios no intencionados en el servidor web si estos métodos están admitidos. Por ello, deben usarse con cuidado.

Pruebas a través de proxies y CDN

Cuando la aplicación se encuentra detrás de un proxy inverso, balanceador de carga, CDN o WAF, el manejo de métodos en el borde puede diferir del del origen, y los resultados deben compararse:

  • Muchos CDN almacenan en caché y reenvían por defecto solo un conjunto limitado de métodos (normalmente GET/HEAD, a veces OPTIONS), y pueden rechazar o eliminar otros (TRACE, CONNECT, a veces PUT/DELETE) antes de que lleguen al origen. Por lo tanto, una cabecera Allow o una respuesta a OPTIONS observada en el borde no refleja necesariamente lo que admite el propio origen.
  • Cuando sea viable (p. ej., en una prueba de caja gris con acceso al origen, o mediante una conexión directa basada en una cabecera Host/IP), hay que probar el origen directamente además de a través del borde, ya que un método bloqueado en el borde pero admitido en el origen es explotable si el origen llega a ser alcanzable directamente (reglas de firewall mal configuradas, SSRF, otros hosts virtuales que comparten el origen, etc.).
  • Algunos proxies/WAF normalizan o convierten a un mismo caso el token del método antes de compararlo con una lista de bloqueo; probar con mayúsculas y minúsculas mezcladas (DeLeTe) o con espacios en blanco no estándar puede revelar una aplicación inconsistente de las reglas entre el proxy y el origen.

PUT y DELETE

Los métodos PUT y DELETE pueden tener diferentes efectos, dependiendo de si los interpreta el servidor web o la aplicación que se ejecuta en él.

Servidores web heredados

Algunos servidores web heredados permitían el uso del método PUT para crear archivos en el servidor. Por ejemplo, si el servidor está configurado para permitirlo, la siguiente petición crearía en el servidor un archivo llamado test.html con el contenido <script>alert(1)</script>.

PUT /test.html HTTP/1.1
Host: example.org
Content-Length: 25

<script>alert(1)</script>

También pueden hacerse peticiones similares con curl:

curl https://example.org --upload-file test.html

Esto permite a un atacante subir archivos arbitrarios al servidor web, lo que podría resultar en un compromiso total del sistema si se le permite subir código ejecutable, como archivos PHP. Sin embargo, esta configuración es extremadamente rara y es poco probable que se vea en sistemas modernos.

De manera similar, el método DELETE puede usarse para eliminar archivos del servidor web. Cabe señalar que esta es una acción destructiva; por lo tanto, se debe tener un cuidado extremo al probar este método.

DELETE /test.html HTTP/1.1
Host: example.org

O con curl:

curl https://example.org/test.html -X DELETE

APIs RESTful

En contraste, los métodos PUT y DELETE son utilizados comúnmente por las aplicaciones RESTful modernas para crear y eliminar objetos. Por ejemplo, la siguiente petición de API podría usarse para crear un usuario llamado "foo" con el rol "user":

PUT /api/users/foo HTTP/1.1
Host: example.org
Content-Length: 34

{
    "role": "user"
}

Una petición similar con el método DELETE podría usarse para eliminar un objeto.

DELETE /api/users/foo HTTP/1.1
Host: example.org

Aunque las herramientas de escaneo automatizadas puedan reportarlo, la presencia de estos métodos en una API RESTful no es un problema de seguridad. Sin embargo, esta funcionalidad puede tener otras vulnerabilidades (como un control de acceso débil) y debe probarse a fondo.

TRACE

El método TRACE (o el método equivalente de Microsoft, TRACK) hace que el servidor devuelva como eco el contenido de la petición. Esto llevó a que se publicara en 2003 (PDF) una vulnerabilidad llamada Cross-Site Tracing (XST), que podía usarse para acceder a cookies que tenían el indicador HttpOnly. El método TRACE está bloqueado desde hace muchos años en todos los navegadores y plugins; por ello, este problema ya no es explotable. Sin embargo, las herramientas de escaneo automatizadas todavía pueden señalarlo, y el hecho de que el método TRACE esté habilitado en un servidor web sugiere que no ha sido endurecido adecuadamente.

CONNECT

El método CONNECT hace que el servidor web abra una conexión TCP con otro sistema y luego transmita el tráfico del cliente a ese sistema. Esto podría permitir a un atacante canalizar tráfico a través del servidor para ocultar su dirección de origen, acceder a sistemas internos o acceder a servicios vinculados a localhost. A continuación se muestra un ejemplo de una petición CONNECT:

CONNECT 192.168.0.1:443 HTTP/1.1
Host: example.org

PATCH

El método PATCH está definido en la RFC 5789 y se utiliza para proporcionar instrucciones sobre cómo debe modificarse un objeto. La propia RFC no define en qué formato deben estar estas instrucciones, pero otros estándares definen varios métodos, como la RFC 6902 - JavaScript Object Notation (JSON) Patch.

Por ejemplo, si tenemos un usuario llamado "foo" con las siguientes propiedades:

{
    "role": "user",
    "email": "foo@example.org"
}

La siguiente petición JSON PATCH podría usarse para cambiar el rol de este usuario a "admin", sin modificar la dirección de correo electrónico:

PATCH /api/users/foo HTTP/1.1
Host: example.org

{ "op": "replace", "path": "/role", "value": "admin" }

Aunque la RFC establece que debe incluir instrucciones sobre cómo modificar el objeto, el método PATCH se usa (mal) comúnmente para incluir en su lugar el contenido modificado, como se muestra a continuación. Al igual que la petición anterior, esto cambiaría el valor "role" a "admin" sin modificar el resto del objeto. Esto contrasta con el método PUT, que sobrescribiría el objeto completo y, por tanto, daría como resultado un objeto sin el atributo "email".

PATCH /api/users/foo HTTP/1.1
Host: example.org

{
    "role": "admin"
}

Al igual que con el método PUT, esta funcionalidad puede tener debilidades de control de acceso u otras vulnerabilidades. Además, las aplicaciones pueden no realizar el mismo nivel de validación de entrada al modificar un objeto que al crearlo. Esto podría permitir inyectar valores maliciosos (como en un ataque de cross-site scripting almacenado) o permitir objetos rotos o inválidos que pueden dar lugar a problemas relacionados con la lógica de negocio.

Métodos WebDAV

Cuando el servidor web tiene WebDAV habilitado (p. ej., IIS con el rol WebDAV Publishing o mod_dav de Apache), pueden quedar expuestos métodos adicionales como PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK y UNLOCK. El soporte de WebDAV es heredado y rara vez lo requieren las aplicaciones web modernas, por lo que su presencia merece ser señalada por sí misma, independientemente de cualquier vulnerabilidad específica.

PROPFIND puede usarse para enumerar listados de directorios y metadatos de recursos incluso cuando la navegación de directorios está deshabilitada:

PROPFIND /uploads/ HTTP/1.1
Host: example.org
Depth: 1

MKCOL, COPY y MOVE pueden usarse para crear directorios o reubicar/duplicar archivos, lo que, combinado con un PUT permisivo, ha permitido históricamente evadir las restricciones de carga de archivos (p. ej., subir un archivo con una extensión bloqueada y luego usar MOVE/COPY para renombrarlo con una extensión ejecutable). Hay que probar si los filtros de carga basados en extensiones se aplican de forma coherente en PUT, MOVE y COPY.

Si WebDAV está presente pero no es necesario, se recomienda deshabilitarlo; si es necesario, hay que asegurar que esté limitado solo a las rutas que lo necesitan y que no sea alcanzable en rutas que sirven a la aplicación principal.

QUERY

El método QUERY es un método HTTP relativamente nuevo, definido en la RFC 9110, diseñado para operaciones de recuperación seguras que requieren un cuerpo de petición. Al igual que POST, acepta datos estructurados en el cuerpo de la petición; a diferencia de POST, es seguro e idempotente, lo que significa que no modifica el estado del servidor y puede almacenarse en caché. Esto lo hace semánticamente similar a GET, pero permite la expresividad de parámetros de filtro complejos, etc., que serían engorrosos en una URL.

Por ejemplo, el método QUERY podría usarse para enviar una consulta de búsqueda compleja con múltiples criterios de filtro:

QUERY /api/users/search HTTP/1.1
Host: example.org
Content-Type: application/json

{
    "filters": {
        "role": "admin",
        "status": "active",
        "lastLogin": {"after": "2024-01-01"}
    }
}

El método QUERY está diseñado para ser almacenable en caché y seguro (solo lectura), lo que lo distingue de POST. No debe usarse para operaciones que modifiquen el estado del servidor. Los evaluadores deben verificar que:

  • El servidor trate correctamente QUERY como una operación segura y no modifique el estado del servidor.
  • El control de acceso se aplique correctamente a las peticiones QUERY.
  • El método no se use como alternativa para evadir controles de seguridad que restringen otros métodos.

Evasión del control de acceso

Si una página de la aplicación redirige a los usuarios a una página de inicio de sesión con un código 302 cuando intentan acceder a ella directamente, puede ser posible evadir esto haciendo una petición con un método HTTP diferente, como HEAD, POST o incluso un método inventado como FOO. Si la aplicación web responde con un HTTP/1.1 200 OK en lugar del esperado HTTP/1.1 302 Found, puede ser posible evadir la autenticación o la autorización. El siguiente ejemplo muestra cómo una petición HEAD puede dar lugar a que una página establezca cookies administrativas, en lugar de redirigir al usuario a una página de inicio de sesión:

HEAD /admin/ HTTP/1.1
Host: example.org

HTTP/1.1 200 OK
[...]
Set-Cookie: adminSessionCookie=[...];

Alternativamente, puede ser posible hacer peticiones directas a páginas que provocan acciones, como:

HEAD /admin/createUser.php?username=foo&password=bar&role=admin HTTP/1.1
Host: example.org

O:

FOO /admin/createUser.php
Host: example.org
Content-Length: 36

username=foo&password=bar&role=admin

Sobrescritura de métodos HTTP

Algunos frameworks web proporcionan una forma de sobrescribir el método HTTP real de la petición. Lo logran emulando los verbos HTTP que faltan y pasando algunas cabeceras personalizadas en las peticiones. El propósito principal de esto es sortear una aplicación intermedia (como un proxy o un firewall de aplicaciones web) que bloquea métodos específicos. Podrían usarse potencialmente las siguientes cabeceras HTTP alternativas:

  • X-HTTP-Method
  • X-HTTP-Method-Override
  • X-Method-Override

Para probar esto, hay que considerar escenarios en los que verbos restringidos como PUT o DELETE devuelven un 405 Method not allowed. En tales casos, se debe repetir la misma petición, pero añadiendo las cabeceras alternativas de sobrescritura del método HTTP. Luego, hay que observar la respuesta del sistema. La aplicación debería responder con un código de estado diferente (p. ej., 200 OK) en los casos en que se admita la sobrescritura de métodos.

Varios frameworks también admiten la sobrescritura de métodos mediante un parámetro de la petición en lugar de (o además de) una cabecera, comúnmente _method en la cadena de consulta o en el cuerpo del formulario (p. ej., POST /resource.html?_method=DELETE). Hay que probar esto junto con las variantes basadas en cabeceras, ya que un filtro que solo inspecciona cabeceras podría pasarlo por alto.

Como el propósito de la sobrescritura de métodos suele ser hacer pasar una petición por un intermediario, siempre hay que comparar el comportamiento en el borde (proxy/CDN/WAF) con el del origen: un método que se bloquea en el borde pero que se sobrescribe y se acepta en el origen indica que el origen confía en señales de sobrescritura proporcionadas por el cliente que el borde no pretendía dejar pasar.

El servidor web del siguiente ejemplo no permite el método DELETE y lo bloquea:

DELETE /resource.html HTTP/1.1
Host: example.org

HTTP/1.1 405 Method Not Allowed
[...]

Después de añadir la cabecera X-HTTP-Method, el servidor responde a la petición con un 200:

GET /resource.html HTTP/1.1
Host: example.org
X-HTTP-Method: DELETE

HTTP/1.1 200 OK
[...]

Corrección

  • Asegurar que solo se permitan los métodos necesarios y que estos estén correctamente configurados.
  • Asegurar que no se implementen soluciones alternativas para evadir las medidas de seguridad implementadas por los agentes de usuario, los frameworks o los servidores web.
  • Deshabilitar WebDAV (mod_dav, IIS WebDAV Publishing) a menos que se requiera explícitamente y, si se requiere, limitar su alcance estrictamente.
  • Asegurar que las restricciones de métodos se apliquen de forma coherente entre cualquier proxy de borde/CDN/WAF y el servidor de origen, y que el origen no confíe en cabeceras ni parámetros de sobrescritura de método proporcionados por el cliente, a menos que el borde dependa explícitamente de ellos.
