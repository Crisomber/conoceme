Evasión de seguridad mediante feature flags

ID
WSTG-CONF-15

Resumen

Los feature flags se utilizan comúnmente para controlar la funcionalidad de la aplicación y habilitar la entrega progresiva. Permiten activar, desactivar o desplegar gradualmente funcionalidades sin un despliegue completo de la aplicación. Las aplicaciones modernas utilizan cada vez más feature flags y kill-switches para condicionar funcionalidades relevantes para la seguridad, como la autenticación, la autorización, la detección de fraude, la limitación de tasa y los controles de riesgo, ya sea mediante servicios de feature flags (LaunchDarkly, Split, Flagsmith, ConfigCat) o soluciones a medida.

Cuando los controles de seguridad dependen de feature flags, los estados inconsistentes de los flags pueden introducir vulnerabilidades. Un control puede estar habilitado en un servicio y deshabilitado en otro, o un rollback puede restaurar el código de la aplicación sin restaurar la configuración de seguridad correspondiente. Los flags del lado del cliente también pueden manipularse para revelar funcionalidades que deberían permanecer protegidas.

Un patrón de fallo común ocurre cuando un kill-switch deshabilita la lógica de aplicación del control pero deja atrás una aserción de confianza. Por ejemplo, un control de prevención de fraude puede deshabilitarse por problemas de rendimiento, pero un servicio de backend sigue confiando en un parámetro fraud_checked=true que el control (ahora deshabilitado) habría establecido previamente. Un atacante puede reproducir una petición capturada anteriormente que contenga ese parámetro para que el backend trate una petición no verificada como si hubiera pasado la comprobación de fraude.

Esta prueba evalúa si los controles de seguridad se siguen aplicando de forma coherente en todos los estados de los feature flags, incluidos la habilitación, la deshabilitación, el rollback, el despliegue parcial, el despliegue canario y la falla del servicio de feature flags.

Objetivos de la prueba

  • Identificar los feature flags y kill-switches que controlan funcionalidades relevantes para la seguridad.
  • Determinar si un cliente no autorizado puede manipular los estados de los feature flags, y verificar que los controles de seguridad del backend se sigan aplicando independientemente del estado del flag del lado del cliente.
  • Verificar que los controles de seguridad se sigan aplicando de forma coherente a lo largo de las transiciones de flags, los rollbacks, los despliegues por etapas y entre servicios o instancias, incluyendo si se pueden reutilizar aserciones de seguridad obsoletas o el estado de sesión después de una transición.
  • Evaluar el comportamiento a prueba de fallos (fail-safe) cuando el servicio de feature flags no está disponible.
  • Identificar la información sensible expuesta a través de las configuraciones de feature flags, y los flags obsoletos que pueden exponer rutas de código en desuso o sin parchear.

Cómo probar

Las pruebas de feature flags pueden realizarse como pruebas de caja negra, infiriendo el comportamiento condicionado por flags mediante la comparación de respuestas entre etapas de despliegue, la reproducción de peticiones capturadas y el análisis de tiempos; o como pruebas de caja gris, donde el evaluador tiene visibilidad del sistema de gestión de flags y puede alternar directamente los estados para evaluar la coherencia de la aplicación de los controles. Siempre que sea posible, conviene combinar ambos enfoques: las pruebas de caja negra confirman lo que un atacante externo puede explotar realmente, mientras que las de caja gris confirman si el backend aplica los controles independientemente del estado del propio flag.

Identificar los feature flags relevantes para la seguridad

Hay que identificar los feature flags, kill-switches y valores de configuración que controlan comportamientos relevantes para la seguridad, incluidos la autenticación, la autenticación multifactor, la autorización, la detección de fraude, la limitación de tasa, la autenticación basada en riesgo, la recuperación de cuentas, las funcionalidades administrativas y la monitorización de seguridad.

Analizar los recursos del lado del cliente

Se deben inspeccionar los bundles de JavaScript y otros recursos del lado del cliente en busca de patrones comunes de feature flags:

featureFlags
isFeatureEnabled
featureEnabled
flags
killSwitch
securityFeature

Herramientas como source-map-explorer o el webpack Bundle Analyzer pueden ayudar a localizar el código relacionado con flags dentro de bundles minificados.

Monitorear el tráfico de red y las respuestas de la API

Se usa un proxy de intercepción (Burp Suite, ZAP) para capturar las peticiones realizadas a los servicios de feature flags o a los endpoints de configuración internos (por ejemplo, llamadas a app.launchdarkly.com, /api/config o /api/flags). Hay que revisar los payloads de las respuestas en busca de nombres de flags, valores predeterminados y reglas de segmentación, y comprobar si algún endpoint devuelve el conjunto completo de flags evaluados para una sesión, incluidos los flags no relacionados con la página actual. Los payloads de flags excesivamente amplios son una fuente común de divulgación de información (véase más abajo).

Probar la manipulación de flags del lado del cliente

Cuando los flags se evalúan o se almacenan en caché del lado del cliente (por ejemplo, en un objeto JavaScript, una cookie o un valor de almacenamiento local), se usa un proxy para modificar el valor del flag y se reproduce la petición:

PUT /api/user/settings HTTP/1.1
Host: example.com
Content-Type: application/json

{"flags": {"betaAdminPanel": true}}
  • Vulnerable: la aplicación expone funcionalidades ocultas, o el valor modificado del flag es aceptado sin una comprobación correspondiente del lado del servidor.
  • Seguro: el valor del lado del cliente no tiene ningún efecto sobre lo que el servidor autorizará; el servidor reevalúa el flag de forma independiente.

Verificar la independencia de la autorización en el backend

Para cada flag relevante para la seguridad que se haya identificado, hay que confirmar que ocultar una funcionalidad en la interfaz de usuario va acompañado de una restricción equivalente en el lugar donde realmente se implementa esa funcionalidad (un endpoint de API, una llamada a un servicio de backend, un manejador de mensajes, etc.). Se debe intentar invocar directamente la funcionalidad subyacente mientras el flag está deshabilitado para el usuario actual, por ejemplo:

GET /api/admin/reports HTTP/1.1
Host: example.com
Authorization: Bearer {low-privilege-token}

Resultado esperado: el servidor debe aplicar la autorización independientemente del estado del flag del lado del cliente: se debe denegar el acceso a un usuario no autorizado (por ejemplo, 401 Unauthorized o 403 Forbidden) incluso si el flag se manipula en el cliente. Si la funcionalidad está deshabilitada globalmente por diseño, debe permanecer inaccesible para todos los usuarios, en lugar de que el flag solo oculte el elemento de la interfaz mientras la funcionalidad subyacente sigue siendo alcanzable.

Probar el comportamiento durante las transiciones de flags y los rollbacks

  • Evasión mediante kill-switch: deshabilitar un flag relevante para la seguridad (comprobación de fraude, limitación de tasa, autenticación escalonada) y reproducir una petición capturada antes de que el flag se deshabilitara, que contenga un parámetro, token o claim de sesión establecido previamente por ese control (p. ej., fraud_checked=true). Confirmar que el backend no sigue confiando en esa aserción obsoleta.
  • Rollback: simular u observar un rollback de la aplicación y confirmar que cualquier configuración de seguridad asociada a la versión revertida también se restaura, en lugar de quedar en su estado previo (potencialmente deshabilitado).
  • Despliegue parcial / canario: cuando varias instancias o servicios pueden estar ejecutándose con estados de flags diferentes al mismo tiempo, enviar peticiones repetidas y comparar las respuestas entre instancias para detectar una aplicación inconsistente de los controles.
  • Segundo escenario - kill-switch de MFA: deshabilitar la verificación escalonada/MFA para un subconjunto de usuarios mediante un kill-switch. Confirmar que un servicio posterior no siga confiando en un claim de sesión existente (p. ej., mfa_verified=true) que solo era válido porque antes se aplicaba MFA. Si el claim es aceptado después de deshabilitar el control, un atacante con una sesión obsoleta puede evadir por completo la verificación escalonada.

Evaluar el comportamiento a prueba de fallos cuando el servicio de flags no está disponible

Se bloquea o limita el acceso al servicio de feature flags (por ejemplo, mediante reglas de proxy o un agujero negro de DNS en un entorno de pruebas) y se observa cómo se comporta la aplicación cuando no puede obtener el estado de los flags.

  • Vulnerable: la aplicación falla de forma abierta (fail open), dejando por defecto los flags relevantes para la seguridad en un estado habilitado/permisivo.
  • Resultado esperado: los controles relevantes para la seguridad siguen aplicándose o recurren a una configuración segura documentada cuando el servicio de feature flags no está disponible.

Analizar las configuraciones de feature flags en busca de divulgación de información

Hay que revisar cualquier configuración de flags que el cliente pueda obtener (mediante una respuesta de API, un bundle de JS o un panel de administración expuesto) en busca de:

  • Nombres de funcionalidades no publicadas o de servicios internos.
  • Reglas de segmentación que revelen segmentos internos de usuarios, cuentas de empleados o cohortes de prueba.
  • Valores de configuración (URL, descripciones de funcionalidades) que expongan detalles de implementación.

Identificar los feature flags obsoletos

Se debe buscar en la base de código (cuando sea accesible) o pedir una lista de los flags que ya no se alternan activamente. Los flags obsoletos que condicionan rutas de código ya sin uso pueden seguir siendo alcanzables y pueden hacer referencia a lógica que no ha recibido parches de seguridad posteriores. Hay que confirmar si esas rutas siguen siendo alcanzables en la aplicación en ejecución y, de ser así, si todavía se aplican correctamente.

Corrección

  • Aplicar todas las comprobaciones de autorización relevantes para la seguridad en el backend, independientemente de cualquier estado de flag suministrado por el cliente o visible para él.
  • Asegurar que los kill-switches eliminen la confianza en cualquier parámetro, token o claim de sesión que solo era válido porque el control asociado estaba activo.
  • Vincular la configuración de seguridad al mismo control de despliegue/versiones que el código de la aplicación, para que los rollbacks restauren ambos conjuntamente.
  • Asegurar que los servicios de feature flags usen una alternativa segura documentada para los flags relevantes para la seguridad cuando no estén disponibles.
  • Evitar exponer al cliente la configuración completa de flags; devolver solo los flags relevantes para el usuario y el contexto actuales.
  • Auditar periódicamente y eliminar los flags obsoletos, junto con las rutas de código que condicionan, una vez completado un despliegue.
  • Aplicar una evaluación de flags coherente en todos los servicios e instancias que manejan una petición determinada.
