Confusión de rutas (Path Confusion)

ID
WSTG-CONF-13

Resumen

La confusión de rutas (Path Confusion) ocurre cuando distintos componentes de la cadena de la petición (enrutadores, proxies, cachés, WAF, la propia aplicación) no coinciden en qué identifica una ruta de URL determinada, debido a diferencias en la normalización de rutas, las barras finales, la distinción entre mayúsculas y minúsculas o la codificación. Esta discrepancia permite a un atacante hacer que un componente trate una ruta de una manera mientras otro la trata de forma diferente, evadiendo un control de seguridad que depende de la coincidencia de rutas (p. ej., una regla de control de acceso, un manejador de rutas o una clave de caché).

Por ejemplo, si las rutas no están configuradas correctamente y el objetivo también usa un CDN, un atacante puede aprovechar la discrepancia entre lo que sirve el origen y lo que la caché almacena o usa como clave para ejecutar ataques de web cache deception.

Nota de alcance: esta prueba trata de la confusión de identidad sobre la propia cadena de la ruta entre componentes que deberían coincidir en ella; no trata de suministrar secuencias ../ o de recorrido codificadas para escapar de un directorio (eso es path traversal, cubierto en las pruebas de validación de entrada / inyección, p. ej., WSTG-ATHZ-01 / pruebas de recorrido de directorios). Los hallazgos de Path Confusion normalmente implican una ruta sintácticamente válida que no intenta salir del directorio previsto, pero que es interpretada de forma inconsistente por distintas capas.

Por lo tanto, para evitar otros ataques, el evaluador debe valorar esta configuración.

Objetivos de la prueba

  • Asegurar que las rutas de la aplicación estén configuradas y normalizadas de manera coherente en todos los componentes (aplicación, proxy, caché, CDN, WAF) que toman decisiones basadas en la ruta.
  • Identificar los casos en que las barras finales, la distinción entre mayúsculas y minúsculas o las diferencias de codificación hacen que un control de seguridad (reglas de autenticación/acceso, enrutamiento, claves de caché) sea evadido o se comporte de forma inconsistente.

Cómo probar

Pruebas de caja negra

En un escenario de pruebas de caja negra, el evaluador debe reemplazar todas las rutas existentes por rutas que no existan y luego examinar el comportamiento y el código de estado del objetivo.

Por ejemplo, hay una ruta en la aplicación que es un panel (dashboard) y muestra el saldo de la cuenta del usuario (dinero, créditos de juego, etc.).

Suponiendo que la ruta es https://example.com/user/dashboard, el evaluador debe probar los distintos modos que el desarrollador pudo haber considerado para esta ruta. Para vulnerabilidades de Web Cache Deception, el analista debe considerar una ruta como https:// example.com/user/dashboard/non.js; si la información del panel es visible y el objetivo usa un CDN (u otra caché web), es probable que los ataques de Web Cache Deception sean aplicables.

Para cada ruta protegida o enrutada, también hay que probar las siguientes variantes y comparar el código de estado, el cuerpo de la respuesta y qué control (si lo hay) se aplica, frente a la ruta de referencia:

  • Barra final: /user/dashboard vs /user/dashboard/ - comprobar si una regla de control de acceso, una ruta o una clave de caché se aplica solo a una de las variantes.
  • Distinción entre mayúsculas y minúsculas: /user/dashboard vs /User/Dashboard - comprobar si el origen y cualquier proxy/caché/WAF frontal normalizan las mayúsculas y minúsculas de forma coherente.
  • Normalización de rutas / segmentos de puntos que se mantienen dentro del alcance: /user/dashboard/./ o /user//dashboard (barras repetidas) - no es un recorrido fuera del directorio, solo codificaciones alternativas del mismo recurso.
  • Codificación porcentual de separadores de ruta o caracteres reservados: /user%2Fdashboard, /user/dashboard%2F..%2F (donde el resultado decodificado sigue resolviéndose dentro del alcance) - comprobar si el componente que aplica el control de seguridad decodifica antes o después de hacer la coincidencia.
  • Combinaciones de codificación/mayúsculas y minúsculas mezcladas para ver si un WAF o una capa de control de acceso hace la coincidencia sobre la cadena en bruto mientras que la aplicación lo hace sobre la cadena decodificada/normalizada (o viceversa).

Existe un hallazgo cuando alguna variante alcanza un resultado distinto (evade la autenticación, llega a un manejador de ruta diferente, o es almacenada en caché/servida) del de la ruta canónica, debido a que los componentes no coinciden en la identidad de la ruta, y no porque la ruta haya escapado de su directorio previsto.

Pruebas de caja blanca

Hay que examinar la configuración de enrutamiento de la aplicación. La mayoría de las veces, los desarrolladores usan expresiones regulares en el enrutamiento de la aplicación.

En este ejemplo, en el archivo urls.py de una aplicación del framework Django, vemos un ejemplo de Path Confusion. El desarrollador no usó la expresión regular correcta, lo que dio como resultado una vulnerabilidad:

    from django.urls import re_path
    from . import views

    urlpatterns = [

        re_path(r'.*^dashboard', views.path_confusion ,name = 'index'),

    ]

Si el usuario también abre en el navegador la ruta https://example.com/dashboard/none.js, puede mostrarse la información del panel del usuario y, si el objetivo usa un CDN o una caché web, puede llevarse a cabo un ataque de Web Cache Deception.

Herramientas

  • Zed Attack Proxy
  • Burp Suite

Corrección

  • Evitar clasificar/manejar el contenido en caché según la extensión del archivo o la ruta (aprovechar el content-type).
  • Asegurar que los mecanismos de caché respeten las cabeceras cache-control especificadas por la aplicación.
  • Implementar un manejo de File Not Found y de redirecciones conforme a las RFC.
  • Normalizar las rutas (mayúsculas y minúsculas, barra final, codificación, separadores repetidos) de forma coherente, y a la misma forma canónica, en cada componente que tome una decisión de seguridad basada en la ruta (aplicación, proxy inverso, caché, CDN, WAF).
  • Realizar la coincidencia de rutas relevante para la seguridad (control de acceso, enrutamiento) después de la normalización/decodificación, y no sobre la cadena en bruto de la línea de petición.
