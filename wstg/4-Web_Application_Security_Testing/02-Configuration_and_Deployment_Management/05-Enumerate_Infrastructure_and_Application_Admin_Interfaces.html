Enumeración de interfaces de administración de la infraestructura y de la aplicación

ID
WSTG-CONF-05

Resumen

Pueden existir interfaces de administración en la aplicación o en el servidor de aplicaciones para permitir que ciertos usuarios realicen actividades privilegiadas en el sitio. Se deben realizar pruebas para revelar si es posible que un usuario no autorizado o estándar acceda a esta funcionalidad privilegiada y cómo.

Una aplicación puede requerir una interfaz de administración para que un usuario privilegiado acceda a funcionalidades que pueden modificar el funcionamiento del sitio. Dichos cambios pueden incluir:

  • Aprovisionamiento de cuentas de usuario
  • Diseño y disposición del sitio
  • Manipulación de datos
  • Cambios de configuración

En muchos casos, estas interfaces no cuentan con controles suficientes para protegerlas del acceso no autorizado. Las pruebas tienen como objetivo descubrir estas interfaces de administración y acceder a las funcionalidades destinadas a los usuarios privilegiados.

Objetivos de la prueba

  • Identificar interfaces y funcionalidades de administración ocultas, incluidas las consolas de gestión de nube, orquestación de contenedores, gestión de APIs y CI/CD.
  • Comprobar en cada interfaz descubierta la existencia de credenciales predeterminadas, débiles o reutilizadas, y su exposición a redes/usuarios más allá de los previstos.

Cómo probar

Pruebas de caja negra

La siguiente sección describe vectores que pueden usarse para probar la presencia de interfaces de administración. Estas técnicas también pueden usarse para probar problemas relacionados, como la escalada de privilegios, y se describen con mayor detalle en otras partes de esta guía (por ejemplo, evasión del esquema de autorización y Referencias directas inseguras a objetos).

  • Enumeración de directorios y archivos: puede existir una interfaz de administración que no sea visible para el evaluador. La ruta de la interfaz de administración puede adivinarse con peticiones simples como /admin o /administrator. En algunos escenarios, estas rutas pueden revelarse en segundos usando técnicas avanzadas de búsqueda en Google: Google dorks. Hay muchas herramientas disponibles para realizar fuerza bruta sobre el contenido del servidor; véase la sección de herramientas más abajo para más información. Es posible que el evaluador también deba identificar el nombre de archivo de la página de administración. Navegar forzosamente a la página identificada puede dar acceso a la interfaz.
  • Comentarios y enlaces en el código fuente: muchos sitios usan código común que se carga para todos los usuarios del sitio. Al examinar todo el código fuente enviado al cliente, pueden descubrirse enlaces a funcionalidades de administración que deben investigarse.
  • Revisión de la documentación del servidor y de la aplicación: si el servidor de aplicaciones o la aplicación se despliega con su configuración predeterminada, puede ser posible acceder a la interfaz de administración usando información descrita en la documentación de configuración o de ayuda. Si se encuentra una interfaz de administración y se requieren credenciales, deben consultarse las listas de contraseñas predeterminadas.
  • Información disponible públicamente: muchas aplicaciones, como WordPress, tienen interfaces de administración disponibles por defecto.
  • Puerto alternativo del servidor: las interfaces de administración pueden encontrarse en un puerto distinto del host que el de la aplicación principal. Por ejemplo, la interfaz de administración de Apache Tomcat suele encontrarse en el puerto 8080.
  • Manipulación de parámetros: puede requerirse un parámetro GET o POST, o una cookie, para habilitar la funcionalidad de administración. Las pistas de ello incluyen la presencia de campos ocultos como:
<input type="hidden" name="admin" value="no">

o en una cookie:

Cookie: session_cookie; useradmin=0

Una vez descubierta una interfaz de administración, puede usarse una combinación de las técnicas anteriores para intentar evadir la autenticación. Si esto falla, el evaluador puede querer intentar un ataque de fuerza bruta. En tal caso, el evaluador debe ser consciente de la posibilidad de bloqueo de la cuenta de administración si existe dicha funcionalidad.

Pruebas de caja gris

Debe realizarse un examen más detallado de los componentes del servidor y de la aplicación para asegurar el endurecimiento (es decir, que las páginas de administración no sean accesibles para todos mediante el uso de filtrado por IP u otros controles) y, cuando corresponda, verificar que ningún componente use credenciales o configuraciones predeterminadas. Debe revisarse el código fuente para asegurar que el modelo de autorización y autenticación garantice una separación clara de funciones entre los usuarios normales y los administradores del sitio. Deben revisarse las funciones de la interfaz de usuario compartidas entre usuarios normales y administradores para asegurar una separación clara entre la presentación de dichos componentes y la fuga de información desde dicha funcionalidad compartida.

Interfaces modernas de administración, gestión de APIs, contenedores y CI/CD

Más allá de las rutas de administración clásicas de aplicaciones/frameworks, los despliegues modernos suelen exponer interfaces privilegiadas adicionales que los evaluadores deben enumerar específicamente y comprobar en busca de credenciales predeterminadas o exposición no deseada:

Consolas de proveedores de nube

  • Las propias consolas web de la nube (AWS, Azure, GCP) no son directamente alcanzables a través de la superficie de ataque de la aplicación, pero el acceso filtrado o mal configurado suele aflorar a través de la aplicación: hay que comprobar si hay credenciales de nube expuestas en JS del lado del cliente, archivos de configuración o mensajes de error, y confirmar que no otorguen acceso a la consola/API más allá de lo que la aplicación necesita.
  • Es común encontrar expuestas interfaces de gestión autoalojadas de servicios adyacentes a la nube: navegadores de almacenamiento de objetos, consolas de administración de bases de datos (p. ej., proxies de RDS/Cloud SQL con interfaces de administración expuestas) y paneles de monitoreo proporcionados por IaaS. Cualquier instancia descubierta debe tratarse como una interfaz de administración sujeta a las mismas comprobaciones de credenciales/exposición que se indican más abajo.

Paneles de Kubernetes y de orquestación de contenedores

  • Kubernetes Dashboard: históricamente se ha expuesto sin autenticación o con un inicio de sesión mediante service-account-token con privilegios excesivos, lo que permite el control total del clúster. Hay que buscar /api/v1/namespaces/kubernetes-dashboard/... o un ingress/NodePort dedicado al dashboard, y confirmar que requiera autenticación y use una cuenta de servicio de mínimo privilegio en lugar de cluster-admin (kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa>, según Permisos de archivos).
  • La API de solo lectura de kubelet (puerto 10255, obsoleta) y la API autenticada de kubelet (puerto 10250): hay que comprobar si alguna de ellas es alcanzable desde fuera de la red del clúster y si el acceso anónimo está habilitado.
  • etcd (puerto 2379/2380): si es alcanzable, el acceso sin autenticación expone todo el estado del clúster, incluidos los Secrets.
  • Interfaces de plataformas de contenedores como Portainer, Rancher o el proxy de consola de Kubernetes administrado de un proveedor de nube: hay que comprobar si existen credenciales de administrador predeterminadas y si los endpoints de configuración inicial/registro siguen siendo alcanzables después del despliegue (algunas herramientas permiten que cualquiera reclame la primera cuenta de administrador si no se completó la configuración).

Endpoints de gestión de aplicaciones/Actuator

  • Spring Boot Actuator: /actuator, /actuator/env, /actuator/heapdump, /actuator/httptrace y /actuator/mappings son interfaces de gestión por derecho propio, no solo salida de depuración: /actuator/env puede exponer credenciales, y algunas versiones/configuraciones de Actuator permiten reconfigurar (p. ej., /actuator/loggers cambiando los niveles de log) en lugar de ofrecer solo acceso de lectura. Véase Endpoints y modos de depuración para la lista completa de endpoints; cualquier endpoint de Actuator alcanzable y sin autenticación debe tratarse aquí como un hallazgo de exposición de interfaz de administración, no solo como una fuga de información.
  • Endpoints de gestión equivalentes de otros frameworks: middleware de health-check/diagnóstico de ASP.NET Core, Django admin (/admin/ con DEBUG=True o un superusuario débil/predeterminado) y blueprints/módulos de administración nativos del framework similares que se entregan habilitados por defecto.

Consolas de gestión de APIs

  • Las interfaces de administración de gateways/gestión de APIs (p. ej., Kong Admin API, Apigee, acceso a la consola de AWS API Gateway mediante claves filtradas, Tyk Dashboard) suelen escuchar en un puerto o ruta distintos de los de la API pública y pueden no tener autenticación por defecto (por ejemplo, la Kong Admin API históricamente tenía por defecto acceso sin autenticar en el puerto 8001).
  • Hay que buscar documentación de API expuesta o portales para desarrolladores que además expongan funcionalidades de gestión (generación de claves, cambios de cuota) y no solo documentación, y confirmar que requieran una autenticación proporcional a las acciones disponibles.

Interfaces de gestión de CI/CD

  • Consolas comunes de CI/CD autoalojadas que se deben enumerar: Jenkins (/login, consola /script, /asynchPeople/), el área de administración de GitLab CI/CD, TeamCity, Argo CD y los endpoints de gestión de los runners autoalojados de GitHub/GitLab Actions.
  • Estas interfaces tienen un impacto especialmente alto si están expuestas, ya que los sistemas de CI/CD normalmente contienen credenciales de despliegue, acceso al código fuente y la capacidad de ejecutar pasos de compilación arbitrarios. Hay que comprobar:
    • Credenciales predeterminadas o documentadas por defecto que nunca se rotaron (p. ej., el archivo de contraseña inicial de administrador de Jenkins que quedó legible, o asistentes de configuración que quedaron incompletos).
    • Acceso anónimo/de invitado dejado habilitado (Jenkins históricamente lo permite mediante una configuración de "lectura/compilación anónima").
    • Consolas de scripts o creación arbitraria de pipelines/jobs alcanzables sin autenticación completa, ya que normalmente equivalen a ejecución remota de código.

Comprobaciones de credenciales predeterminadas y de exposición

Para cualquier interfaz de tipo administración encontrada mediante lo anterior (clásica o moderna), se deben realizar las mismas comprobaciones básicas:

  • Probar las credenciales predeterminadas documentadas para ese producto/versión específico (consultar la documentación del proveedor y listas como Cirt: Default Password list o SecLists); no hacer fuerza bruta más allá de una lista pequeña y documentada de valores predeterminados sin autorización.
  • Confirmar que la interfaz no es alcanzable desde internet público cuando solo está destinada a uso interno/de operadores (comprobarlo mediante un escaneo directo de IP/puerto además de por nombre de host, ya que puede ser alcanzable por IP aunque no esté enlazada en ningún lado).
  • Confirmar que se aplica TLS y que la interfaz no acepta HTTP en texto plano para el envío de credenciales.
  • Cuando la interfaz exponga un asistente de configuración/primera ejecución, confirmar que no pueda volver a activarse ni alcanzarse tras el despliegue para reclamar una cuenta de administrador.

Herramientas

Varias herramientas pueden ayudar a identificar interfaces y funcionalidades de administración ocultas, entre ellas:

  • ZAP - Forced Browse es un uso mantenido actualmente del antiguo proyecto DirBuster de OWASP.
  • THC-HYDRA es una herramienta que permite la fuerza bruta sobre muchas interfaces, incluida la autenticación HTTP basada en formularios.
  • Un programa de fuerza bruta es mucho más efectivo cuando usa un buen diccionario, como el diccionario de Netsparker.
  • nuclei con los conjuntos de plantillas exposed-panels y default-logins puede identificar a escala muchas de las interfaces modernas de administración/CI/CD/orquestación descritas anteriormente.
  • kube-hunter - identifica el servidor de la API de Kubernetes, kubelet y endpoints de dashboard expuestos.
  • SecLists - Default Credentials
