Manejo inadecuado de errores

ID
WSTG-ERRH-01

Resumen

Todo tipo de aplicaciones (aplicaciones web, servidores web, bases de datos, APIs, etc.) generarán errores por diversas razones. Los desarrolladores con frecuencia ignoran el manejo de estos errores, o descartan la idea de que un usuario intentará provocar un error a propósito (p. ej. enviar una cadena donde se espera un entero). Cuando el desarrollador solo considera el camino feliz, olvida todas las demás entradas posibles que el código puede recibir pero no sabe manejar.

Los errores a veces aparecen como:

  • Stack traces
  • Timeouts de red
  • Discrepancias en la entrada
  • Volcados de memoria
  • Páginas o consolas de depuración que se dejaron habilitadas en producción
  • Respuestas de error detalladas de APIs, GraphQL o servicios en la nube

El manejo inadecuado de errores puede permitir a los atacantes:

  • Entender las APIs que se utilizan internamente.
  • Mapear los diversos servicios que se integran entre sí obteniendo información sobre los sistemas internos y frameworks utilizados, lo que abre las puertas al encadenamiento de ataques.
  • Recopilar las versiones y los tipos de aplicaciones utilizadas.
  • Identificar rutas del sistema de archivos, nombres de host internos y secretos (p. ej. cadenas de conexión, claves de API o prompts) incrustados en la salida de errores.
  • Provocar una denegación de servicio forzando al sistema a un deadlock o a una excepción no controlada que haga caer el proceso que lo ejecuta.
  • Evadir controles cuando una excepción determinada no está restringida por la lógica establecida alrededor del camino feliz, o cuando una verificación fallida falla de forma abierta (p. ej. una verificación de autorización que permite el acceso cuando lanza una excepción; véase CWE-636).

Objetivos de la prueba

  • Identificar la salida de errores existente.
  • Analizar las diferentes salidas devueltas.
  • Determinar si los errores exponen información sensible o hacen que la aplicación falle de forma abierta (fail open).

Cómo probar

Los errores suelen verse como inofensivos, ya que proporcionan datos de diagnóstico y mensajes que podrían ayudar al usuario a entender el problema en cuestión, o al desarrollador a depurar ese error.

Al intentar enviar datos inesperados, o forzar al sistema a ciertos casos límite y escenarios, el sistema o la aplicación, la mayoría de las veces, revelará un poco de lo que ocurre internamente, a menos que los desarrolladores hayan desactivado todos los errores posibles y devuelvan un mensaje personalizado.

Servidores web

Todas las aplicaciones web se ejecutan sobre un servidor web, ya sea uno integrado o uno completo. Las aplicaciones web deben manejar y analizar peticiones HTTP, y para ello un servidor web siempre forma parte de la pila. Algunos de los servidores web y proxies más comunes son Nginx, Apache, IIS, Caddy y Envoy. Delante de estos suele haber una CDN, un WAF, un balanceador de carga o un API gateway (p. ej. Cloudflare, CloudFront, Azure Front Door) que tiene sus propias páginas de error.

Los servidores web tienen mensajes de error y formatos conocidos. Si no se está familiarizado con su aspecto, buscarlos en línea proporcionaría ejemplos. Otra manera sería consultar su documentación, o simplemente configurar un servidor localmente y descubrir los errores navegando por las páginas que utiliza el servidor web.

Para provocar mensajes de error, un evaluador debe:

  • Buscar archivos y carpetas aleatorios que no se encontrarán (404).
  • Intentar solicitar carpetas que existen y ver el comportamiento del servidor (403, página en blanco o listado de directorio).
  • Intentar enviar una petición que rompa las especificaciones HTTP (RFC 9110 para la semántica, RFC 9112 para la sintaxis de mensajes HTTP/1.1). Algunos ejemplos son una ruta muy larga (414), cabeceras o cookies sobredimensionadas (431), un cuerpo sobredimensionado (413), un formato de cabecera roto, un método inválido o una versión de HTTP modificada.
    • Incluso si los errores se manejan a nivel de la aplicación, romper la especificación HTTP puede hacer que el servidor web integrado se muestre, ya que debe manejar la petición, y los desarrolladores olvidan sobrescribir estos errores.
    • Comparar las páginas de error devueltas por cada capa (CDN, WAF, proxy, servidor de aplicaciones) para identificar los componentes de la pila y, en algunos casos, el servidor de origen que hay detrás.
    • Las peticiones malformadas sobre HTTP/2 y HTTP/3 (p. ej. pseudocabeceras inválidas) y las pruebas de request smuggling o desincronización (desync) también pueden hacer que un componente de frontend o backend devuelva su propia página de error.

Aplicaciones

Las aplicaciones son las más susceptibles de dejar salir una amplia variedad de mensajes de error, entre ellos: stack traces, volcados de memoria, excepciones mal manejadas y errores genéricos. Esto ocurre porque las aplicaciones, la mayoría de las veces, se construyen a medida y los desarrolladores deben observar y manejar todos los casos de error posibles (o contar con un mecanismo global de captura de errores), y estos errores pueden aparecer por las integraciones con otros servicios.

Para hacer que una aplicación lance estos errores, un evaluador debe:

  1. Identificar los posibles puntos de entrada donde la aplicación espera datos.
  2. Analizar el tipo de entrada esperado (cadenas, enteros, JSON, XML, etc.).
  3. Hacer fuzzing de cada punto de entrada con base en los pasos anteriores para tener un escenario de prueba más enfocado.
    • Hacer fuzzing de cada entrada con todas las inyecciones posibles no es la mejor solución, a menos que se tenga tiempo de prueba ilimitado y que la aplicación pueda manejar tanta entrada.
    • Si el fuzzing no es una opción, se deben elegir manualmente las entradas viables que tengan la mayor probabilidad de romper un determinado analizador (parser) (p. ej. un corchete de cierre para un cuerpo JSON, un texto largo donde solo se esperan un par de caracteres, inyección CRLF con parámetros que podrían ser analizados por servidores y controles de validación de entrada, caracteres especiales que no son aplicables a nombres de archivo, etc.).
    • El fuzzing con datos malformados o basura debe ejecutarse para cada tipo, ya que a veces los intérpretes fallarán fuera del manejo de excepciones del desarrollador.
  4. Entender el servicio que responde con el mensaje de error e intentar elaborar una lista de fuzzing más refinada para obtener más información o detalles del error de ese servicio (podría ser una base de datos, un servicio independiente, etc.).

Los mensajes de error a veces son la principal debilidad al mapear sistemas, especialmente en una arquitectura de microservicios. Si los servicios no están configurados adecuadamente para manejar errores de manera genérica y uniforme, los mensajes de error permitirían al evaluador identificar qué servicio maneja qué peticiones y permitirían un ataque más enfocado por servicio.

El evaluador debe estar atento al tipo de respuesta. A veces los errores se devuelven como éxito con un cuerpo de error, ocultan el error en un 302, o simplemente tienen una forma personalizada de representar ese error.

Modos de depuración y páginas de error de frameworks

Los frameworks y los entornos de ejecución suelen incluir páginas de error detalladas, depuradores interactivos o endpoints de diagnóstico pensados únicamente para desarrollo. Se debe comprobar si alguno es accesible en producción, por ejemplo:

  • Django con DEBUG = True.
  • Depurador interactivo de Flask/Werkzeug.
  • Páginas de depuración y profilers de Laravel (Ignition) y Symfony.
  • Endpoints de Spring Boot Actuator y páginas de error predeterminadas que incluyen campos trace o message.
  • Páginas de error de desarrollo de Ruby on Rails.
  • Páginas de excepciones para desarrolladores de ASP.NET.
  • Frameworks de Node.js (p. ej. Express, Next.js) ejecutándose en modo de desarrollo, que devuelven stack traces por defecto.

Véanse también Enumerate Infrastructure and Application Admin Interfaces y Review Web Page Content for Information Leakage.

APIs

Las APIs con frecuencia devuelven errores estructurados que exponen más de lo previsto:

  • Enviar JSON o XML malformado, o un Content-Type incorrecto, tipos incorrectos, campos obligatorios ausentes y valores fuera de rango, y revisar el cuerpo del error estructurado. Muchas APIs usan RFC 9457 application/problem+json, donde detail o los miembros de extensión pueden filtrar detalles internos.
  • Para GraphQL, revisar el arreglo errors, en particular extensions (que puede contener stack traces) y las sugerencias de campos ("Did you mean ...?") que revelan detalles del esquema incluso cuando la introspección está deshabilitada.
  • Comparar las respuestas de error para recursos o usuarios válidos e inválidos para encontrar diferencias que permitan la enumeración (véase Account Enumeration and Guessable User Account).

Servicios en la nube y aplicaciones con IA

  • Las peticiones que llegan directamente a almacenamiento en la nube, funciones serverless o API gateways pueden devolver errores XML o JSON específicos del proveedor que revelan nombres de buckets, regiones, identificadores de cuenta o nombres de funciones.
  • Las aplicaciones que llaman a servicios de LLM u otros servicios de IA pueden devolver errores crudos del proveedor, fallos de llamadas a herramientas o detalles de plantillas de prompts cuando la llamada upstream falla o la entrada está malformada. Se debe buscar la filtración de prompts de sistema, claves de API, nombres de modelos o proveedores y endpoints internos.

Comportamiento fail-open

Cuando se provoca un error, se debe observar si los controles de seguridad se siguen aplicando. Hay que comprobar si se omite un paso de autenticación, autorización, limitación de tasa (rate limiting) o validación cuando ocurre una excepción (p. ej. un token malformado, un servicio de respaldo no disponible o un timeout), y la petición se procesa entonces como si la verificación se hubiera superado.

Herramientas

  • Las reglas de escaneo pasivo y activo de ZAP como Application Error Disclosure, además de su Fuzzer.
  • Burp Suite Repeater e Intruder.
  • ffuf para hacer fuzzing de rutas, parámetros y cabeceras.
  • Plantillas de Nuclei para páginas de depuración expuestas y errores detallados.
