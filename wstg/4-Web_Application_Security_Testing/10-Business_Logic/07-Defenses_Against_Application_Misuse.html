Defensas contra el uso indebido de la aplicación

ID
WSTG-BUSL-07

Resumen

El uso indebido e inválido de funcionalidad válida puede identificar ataques que intentan enumerar la aplicación web, identificar debilidades y explotar vulnerabilidades. Se deben realizar pruebas para determinar si existen mecanismos defensivos en la capa de aplicación que protejan la aplicación.

La falta de defensas activas permite a un atacante buscar vulnerabilidades sin ninguna consecuencia. Por lo tanto, el propietario de la aplicación no sabrá que su aplicación está bajo ataque.

Ejemplo

Un usuario autenticado realiza la siguiente secuencia (poco probable) de acciones:

  1. Intenta acceder a un archivo cuyo ID sus roles no le permiten descargar
  2. Sustituye el número de ID del archivo por una comilla simple '
  3. Altera una petición GET para convertirla en POST
  4. Añade un parámetro adicional
  5. Duplica un par nombre/valor de parámetro

La aplicación está monitoreando el uso indebido y responde tras el quinto evento con una confianza extremadamente alta de que el usuario es un atacante. Por ejemplo, la aplicación:

  • Deshabilita la funcionalidad crítica
  • Habilita pasos de autenticación adicionales para la funcionalidad restante
  • Añade retrasos de tiempo en cada ciclo de petición-respuesta
  • Comienza a registrar datos adicionales sobre las interacciones del usuario (p. ej., cabeceras de petición HTTP, cuerpos y cuerpos de respuesta sanitizados)

Si la aplicación no responde de ninguna manera y el atacante puede seguir abusando de la funcionalidad y enviando contenido claramente malicioso a la aplicación, la aplicación ha fallado este caso de prueba. En la práctica, es poco probable que las acciones discretas del ejemplo anterior ocurran así. Es mucho más probable que se use una herramienta de fuzzing para identificar debilidades en cada parámetro por turno. Esto es también lo que habrá hecho un evaluador de seguridad.

Objetivos de la prueba

  • Generar notas de todas las pruebas realizadas contra el sistema.
  • Revisar qué pruebas tuvieron una funcionalidad distinta ante una entrada agresiva.
  • Comprender las defensas existentes y verificar si son suficientes para proteger el sistema contra técnicas de elusión.

Cómo probar

Esta prueba es inusual en cuanto a que el resultado se puede extraer de todas las demás pruebas realizadas contra la aplicación web. Mientras se realizan todas las demás pruebas, hay que tomar nota de las medidas que puedan indicar que la aplicación tiene una autodefensa integrada:

  • Respuestas modificadas
  • Peticiones bloqueadas
  • Acciones que cierran la sesión de un usuario o bloquean su cuenta

Estas pueden ser solo localizadas. Las defensas localizadas (por función) más comunes son:

  • Rechazar entradas que contienen ciertos caracteres
  • Bloquear una cuenta temporalmente tras un número de fallos de autenticación

Los controles de seguridad localizados no son suficientes. A menudo no hay defensas contra el uso indebido general, como:

  • Navegación forzada (forced browsing)
  • Elusión de la validación de entrada de la capa de presentación
  • Múltiples errores de control de acceso
  • Nombres de parámetros adicionales, duplicados o ausentes
  • Múltiples fallos de validación de entrada o de verificación de la lógica de negocio con valores que no pueden ser resultado de errores o erratas del usuario
  • Recepción de datos estructurados (p. ej., JSON, XML) con formato inválido
  • Recepción de payloads flagrantes de Cross-Site Scripting (XSS) o de Inyección SQL
  • Uso de la aplicación a una velocidad mayor de la que sería posible sin herramientas de automatización
  • Cambio de ubicación geográfica continental de un usuario
  • Cambio de user agent
  • Acceso a un proceso de negocio de varias etapas en el orden incorrecto
  • Gran número, o alta tasa de uso, de funcionalidad específica de la aplicación (p. ej., envío de códigos de cupón, pagos fallidos con tarjeta de crédito, cargas de archivos, descargas de archivos, cierres de sesión, etc.).

Tergiversación de la interfaz de usuario / suplantación de contenido (Content Spoofing)

La tergiversación de la interfaz de usuario ocurre cuando una entrada controlada por el usuario se muestra en elementos de interfaz de confianza de una manera que puede engañar a usuarios o administradores, sin requerir la ejecución de scripts. A diferencia del Cross-Site Scripting, estos problemas se basan en el engaño visual o contextual y pueden permitir el abuso de flujos de trabajo o la ingeniería social dentro de la aplicación.

Estos problemas representan un uso indebido de la aplicación porque abusan de flujos de trabajo legítimos de la interfaz y de límites de confianza en lugar de explotar una vulnerabilidad técnica.

Algunos ejemplos comunes incluyen:

  • Nombres de archivo, títulos o etiquetas controlados por el usuario que se muestran como mensajes generados por el sistema
  • Cargas de archivos renombrados que aparecen como documentos de confianza o artefactos del sistema
  • Texto suministrado por el usuario que se muestra como estados de aprobación, nombres de remitente o indicadores de flujo de trabajo

Por ejemplo: una aplicación permite a los usuarios nombrar los archivos cargados. Un atacante carga un archivo llamado "Payment Approved - Finance System". Cuando este nombre de archivo se muestra en un flujo de trabajo de revisión administrativa sin una indicación clara de que lo suministró un usuario, los revisores pueden ser engañados para aprobar un proceso fraudulento.

Durante las pruebas, hay que evaluar si:

  • Los datos controlados por el usuario se reflejan en contextos de interfaz privilegiados o con autoridad
  • El texto inyectado puede imitar mensajes del sistema, estados del flujo de trabajo o etiquetas de confianza
  • La presentación de la interfaz podría influir en las decisiones de los usuarios o en los procesos de negocio aunque no ocurra ninguna explotación técnica

Estas defensas funcionan mejor en las partes autenticadas de la aplicación, aunque la tasa de creación de cuentas nuevas o de acceso a contenido (p. ej., para extraer información) puede ser útil en las áreas públicas.

No es necesario que la aplicación monitoree todo lo anterior, pero hay un problema si no monitorea nada de ello. Al probar la aplicación web y realizar el tipo de acciones anteriores, ¿se tomó alguna respuesta contra el evaluador? Si no, el evaluador debe informar de que la aplicación parece no tener defensas activas a nivel de toda la aplicación contra el uso indebido. Nótese que a veces es posible que todas las respuestas a la detección de ataques sean silenciosas para el usuario (p. ej., cambios en el registro, mayor monitoreo, alertas a los administradores y retransmisión de peticiones mediante proxy), por lo que no se puede garantizar la confianza en este hallazgo. En la práctica, muy pocas aplicaciones (o infraestructuras relacionadas, como un firewall de aplicaciones web) detectan este tipo de uso indebido.

Corrección

Las aplicaciones deben implementar defensas activas para repeler a atacantes y abusadores.
