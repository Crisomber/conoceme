Carga de tipos de archivo inesperados

ID
WSTG-BUSL-08

Resumen

Los procesos de negocio de muchas aplicaciones permiten la carga y manipulación de datos que se envían mediante archivos. Pero el proceso de negocio debe comprobar los archivos y permitir solo ciertos tipos de archivo "aprobados". Decidir qué archivos están "aprobados" lo determina la lógica de negocio y es específico de cada aplicación o sistema. El riesgo es que, al permitir que los usuarios carguen archivos, los atacantes puedan enviar un tipo de archivo inesperado que podría ejecutarse y afectar negativamente a la aplicación o al sistema mediante ataques que pueden desfigurar el sitio, ejecutar comandos remotos, explorar los archivos del sistema, explorar los recursos locales, atacar otros servidores o explotar vulnerabilidades locales, por nombrar solo algunos.

Las vulnerabilidades relacionadas con la carga de tipos de archivo inesperados son particulares en cuanto a que la carga debería rechazar rápidamente un archivo si no tiene una extensión específica. Además, esto es distinto de la carga de archivos maliciosos en que, en la mayoría de los casos, un formato de archivo incorrecto puede no ser inherentemente "malicioso" por sí mismo, pero sí perjudicial para los datos guardados. Por ejemplo, si una aplicación acepta archivos de Windows Excel y se carga un archivo de base de datos similar, es posible que se lea, pero los datos extraídos pueden trasladarse a ubicaciones incorrectas.

Es posible que la aplicación espere que se carguen solo ciertos tipos de archivo para su procesamiento, como archivos .csv o .txt. La aplicación puede no validar el archivo cargado por su extensión (validación de archivos de baja garantía) o por su contenido (validación de archivos de alta garantía). Esto puede producir resultados inesperados en el sistema o la base de datos dentro de la aplicación o el sistema, o dar a los atacantes métodos adicionales para explotar la aplicación o el sistema.

Ejemplo

Supóngase que una aplicación para compartir fotos permite a los usuarios cargar al sitio un archivo gráfico .gif o .jpg. ¿Qué pasa si un atacante puede cargar un archivo HTML con una etiqueta <script> o un archivo PHP? El sistema puede mover el archivo desde una ubicación temporal a la ubicación final, donde el código PHP ahora puede ejecutarse contra la aplicación o el sistema.

Objetivos de la prueba

  • Revisar la documentación del proyecto en busca de los tipos de archivo que el sistema rechaza.
  • Verificar que los tipos de archivo no deseados se rechazan y se gestionan de forma segura.
  • Verificar que las cargas de archivos por lotes son seguras y no permiten eludir las medidas de seguridad establecidas.

Cómo probar

Método de prueba específico

  • Estudiar los requisitos lógicos de las aplicaciones.
  • Preparar una biblioteca de archivos "no aprobados" para la carga, que pueden incluir archivos como: jsp, exe o HTML con script.
  • En la aplicación, navegar hasta el mecanismo de envío o carga de archivos.
  • Enviar a carga los archivos "no aprobados" y verificar que se impide correctamente su carga
  • Comprobar si el sitio solo realiza las comprobaciones del tipo de archivo en JavaScript del lado del cliente
  • Comprobar si el sitio solo comprueba el tipo de archivo mediante el "Content-Type" de la petición HTTP.
  • Comprobar si el sitio solo comprueba el tipo de archivo mediante la extensión del archivo.
  • Comprobar si se puede acceder directamente a otros archivos cargados mediante una URL específica.
  • Comprobar si el archivo cargado puede incluir inyección de código o de script.
  • Comprobar si existe alguna verificación de la ruta de los archivos cargados. En particular, los atacantes pueden comprimir archivos con una ruta especificada en un ZIP, de modo que los archivos extraídos puedan colocarse en la ruta deseada tras cargar y descomprimir.

Corrección

Las aplicaciones deben desarrollarse con mecanismos que solo acepten y manipulen archivos "aceptables" que el resto de la funcionalidad de la aplicación esté preparada para manejar y espere. Algunos ejemplos específicos incluyen: listas de denegación o listas de permitidos de extensiones de archivo, usar el "Content-Type" de la cabecera o usar un reconocedor de tipos de archivo, todo ello para permitir en el sistema solo los tipos de archivo especificados.
