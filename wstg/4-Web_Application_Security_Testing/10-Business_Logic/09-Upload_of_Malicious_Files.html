Carga de archivos maliciosos

ID
WSTG-BUSL-09

Resumen

Los procesos de negocio de muchas aplicaciones permiten a los usuarios cargar datos en ellas. Aunque la validación de entrada se entiende ampliamente para los campos de entrada basados en texto, es más complicada de implementar cuando se aceptan archivos. Aunque muchos sitios implementan restricciones simples basadas en una lista de extensiones permitidas (o bloqueadas), esto no es suficiente para impedir que los atacantes carguen tipos de archivo legítimos con contenido malicioso.

Las vulnerabilidades relacionadas con la carga de archivos maliciosos son particulares en cuanto a que estos archivos "maliciosos" pueden rechazarse fácilmente incluyendo lógica de negocio que analice los archivos durante el proceso de carga y rechace los que se perciban como maliciosos. Además, esto es distinto de la carga de archivos inesperados en que, aunque el tipo de archivo pueda ser aceptado, el archivo aún puede ser malicioso para el sistema.

Por último, "malicioso" significa cosas distintas para sistemas distintos; por ejemplo, los archivos maliciosos que pueden explotar vulnerabilidades de SQL Server pueden no considerarse "maliciosos" en un entorno que usa un almacén de datos NoSQL.

La aplicación puede permitir la carga de archivos maliciosos que incluyen exploits o shellcode sin someterlos a un análisis de archivos maliciosos. Los archivos maliciosos podrían detectarse y detenerse en varios puntos de la arquitectura de la aplicación, tales como: un sistema de detección o prevención de intrusiones, el software antivirus del servidor de aplicaciones o el análisis antivirus por parte de la aplicación a medida que se cargan los archivos (quizá delegando el análisis mediante SCAP).

Ejemplo

Un ejemplo común de esta vulnerabilidad es una aplicación como un blog o un foro que permite a los usuarios cargar imágenes y otros archivos multimedia. Aunque estos se consideran seguros, si un atacante puede cargar código ejecutable (como un script PHP), esto podría permitirle ejecutar comandos del sistema operativo, leer y modificar información en el sistema de archivos, acceder a la base de datos del backend y comprometer por completo el servidor.

Objetivos de la prueba

  • Identificar la funcionalidad de carga de archivos.
  • Revisar la documentación del proyecto para identificar qué tipos de archivo se consideran aceptables y cuáles se considerarían peligrosos o maliciosos.
    • Si no hay documentación disponible, considerar qué sería apropiado según el propósito de la aplicación.
  • Determinar cómo se procesan los archivos cargados.
  • Obtener o crear un conjunto de archivos maliciosos para las pruebas.
  • Intentar cargar los archivos maliciosos en la aplicación y determinar si se aceptan y procesan.

Cómo probar

Tipos de archivo maliciosos

Las comprobaciones más simples que puede hacer una aplicación son determinar que solo se puedan cargar tipos de archivo de confianza.

Web Shells

Si el servidor está configurado para ejecutar código, puede ser posible obtener ejecución de comandos en el servidor cargando un archivo conocido como web shell, que permite ejecutar código arbitrario o comandos del sistema operativo. Para que este ataque tenga éxito, el archivo debe cargarse dentro del webroot y el servidor debe estar configurado para ejecutar el código.

Cargar este tipo de shell en un servidor expuesto a internet es peligroso, porque permite a cualquiera que conozca (o adivine) la ubicación de la shell ejecutar código en el servidor. Se pueden usar varias técnicas para proteger la shell del acceso no autorizado, como:

  • Cargar la shell con un nombre generado aleatoriamente.
  • Proteger la shell con contraseña.
  • Implementar restricciones basadas en IP en la shell.

Recuerda eliminar la shell cuando hayas terminado.

El siguiente ejemplo muestra una shell simple basada en PHP, que ejecuta comandos del sistema operativo que se le pasan en un parámetro GET, y a la que solo se puede acceder desde una dirección IP específica:

<?php
    if ($_SERVER['REMOTE_HOST'] === "FIXME") { // Set your IP address here
        if(isset($_REQUEST['cmd'])){
            $cmd = ($_REQUEST['cmd']);
            echo "<pre>\n";
            system($cmd);
            echo "</pre>";
        }
    }
?>

Una vez cargada la shell (con un nombre aleatorio), se pueden ejecutar comandos del sistema operativo pasándolos en el parámetro GET cmd:

https://example.org/7sna8uuorvcx3x4fx.php?cmd=cat+/etc/passwd

Evasión de filtros

El primer paso es determinar qué permiten o bloquean los filtros y dónde se implementan. Si las restricciones se aplican en el lado del cliente mediante JavaScript, pueden eludirse trivialmente con un proxy de interceptación.

Si el filtrado se realiza en el lado del servidor, se pueden intentar diversas técnicas para eludirlo, entre ellas:

  • Cambiar el valor de Content-Type a image/jpeg en la petición HTTP.
  • Cambiar las extensiones por una extensión menos común, como file.php5, file.shtml, file.asa, file.jsp, file.jspx, file.aspx, file.asp, file.phtml, file.cshtml
  • Usar extensiones dobles como file.jpg.php o file.png.php. Para que esto funcione correctamente, primero hay que entender cómo maneja el servidor web los archivos con múltiples extensiones. Por ejemplo, en ciertos escenarios, el servidor web puede comprobar solo si .jpg o .png forma parte de la extensión del archivo, lo que puede permitir a los atacantes eludir el filtro de extensiones de archivo.
  • Cambiar la file signature o magic byte del archivo cargado.
  • Cambiar el uso de mayúsculas y minúsculas de la extensión, como file.PhP o file.AspX
  • Si la petición incluye varios nombres de archivo, cambiarlos por valores distintos.
  • Usar caracteres finales especiales como espacios, puntos o caracteres nulos, como file.asp..., file.php;jpg, file.asp%00.jpg, 1.jpg%00.php
  • En versiones mal configuradas de Nginx, cargar un archivo como test.jpg/x.php puede permitir que se ejecute como x.php.
  • Cargar un archivo .htaccess con el siguiente contenido: AddType application/x-httpd-php .png. Esto hará que el servidor Apache ejecute las imágenes .png como si fueran recursos .php.

En algunas situaciones, puede ser necesario combinar las diferentes técnicas de evasión de filtros descritas anteriormente para eludir con éxito los filtros del lado del servidor.**

Contenido de archivos maliciosos

Una vez validado el tipo de archivo, es importante asegurarse también de que el contenido del archivo es seguro. Esto es significativamente más difícil de hacer, ya que los pasos necesarios variarán según los tipos de archivo permitidos.

Malware

En general, las aplicaciones deben analizar los archivos cargados con software antimalware para asegurar que no contienen nada malicioso. La forma más fácil de probar esto es usar el EICAR test file, que es un archivo seguro que todo el software antimalware marca como malicioso.

Según el tipo de aplicación, puede ser necesario probar otros tipos de archivo peligrosos, como documentos de Office que contengan macros maliciosas. Herramientas como Metasploit Framework y Social Engineer Toolkit (SET) se pueden usar para generar archivos maliciosos de varios formatos.

Cuando se carga este archivo, la aplicación debería detectarlo y ponerlo en cuarentena o eliminarlo. Según cómo procese el archivo la aplicación, puede no ser evidente si esto ha ocurrido.

Directory Traversal en archivos comprimidos

Si la aplicación extrae archivos comprimidos (como ZIP), puede ser posible escribir en ubicaciones no previstas mediante directory traversal. Esto se puede explotar cargando un archivo ZIP malicioso que contenga rutas que recorran el sistema de archivos con secuencias como ..\..\..\..\shell.php. Esta técnica se analiza con más detalle en el snyk advisory.

Una prueba contra Archive Directory Traversal debe incluir dos partes:

  1. Un archivo comprimido malicioso que se salga del directorio de destino al extraerse. Este archivo malicioso debe contener dos archivos: un archivo base, extraído en el directorio de destino, y un archivo traversed que intenta ascender por el árbol de directorios hasta llegar a la carpeta raíz, añadiendo un archivo en el directorio tmp. Una ruta maliciosa contendrá muchos niveles de ../ (es decir, ../../../../../../../../tmp/traversed) para tener más posibilidades de llegar al directorio raíz. Una vez que el ataque tiene éxito, el evaluador puede encontrar /tmp/traversed creado en el servidor web mediante el ataque ZIP slip.
  2. Lógica que extrae archivos comprimidos, ya sea con código personalizado o con una biblioteca. Las vulnerabilidades de Archive Directory Traversal existen cuando la funcionalidad de extracción no valida las rutas de archivo del archivo comprimido. El siguiente ejemplo muestra una implementación vulnerable en Java:
Enumeration<ZipEntry> entries =​ ​zip​.g​etEntries();

while(entries​.h​asMoreElements()){
    ZipEntry e ​= ​entries.nextElement();
    File f = new File(destinationDir, e.getName());
    InputStream input = zip​.g​etInputStream(e);
    IOUtils​.c​opy(input, write(f));
}

Sigue los pasos siguientes para crear un archivo ZIP que pueda abusar del código vulnerable anterior una vez cargado en el servidor web:

# Open a new terminal and create a tree structure
# (more directory levels might be required based on the system being targeted)
mkdir -p a/b/c
# Create a base file
echo 'base' > a/b/c/base
# Create a traversed file
echo 'traversed' > traversed
# You can double check the tree structure using `tree` at this stage
# Navigate to a/b/c root directory
cd a/b/c
# Compress the files
zip test.zip base ../../../traversed
# Verify compressed files content
unzip -l test.zip

Ataques de enlaces simbólicos en archivos comprimidos

Si la aplicación extrae archivos comprimidos (como ZIP o TAR), es importante verificar cómo se manejan los enlaces simbólicos contenidos en el archivo. A diferencia del Archive Directory Traversal (ZIP Slip), esta técnica no depende de secuencias de directory traversal ../.

Un atacante puede crear un archivo comprimido que contenga un enlace simbólico que apunte a un archivo sensible del servidor (por ejemplo, /etc/passwd). Si el proceso de extracción conserva los enlaces simbólicos sin validación, y la aplicación luego procesa o expone los archivos extraídos, esto puede resultar en acceso no previsto a archivos sensibles del sistema.

Por ejemplo, un archivo comprimido malicioso puede contener: link.txt -> /etc/passwd

Si el backend extrae este archivo sin validar ni rechazar los enlaces simbólicos, y la aplicación lee link.txt, podría revelar inadvertidamente el contenido de /etc/passwd.

Cómo probar
  1. Crear un enlace simbólico: ln -s /etc/passwd link.txt
  2. Crear un archivo comprimido: tar -czf malicious.tar.gz link.txt
  3. Cargar el archivo comprimido en la aplicación.
  4. Comprobar:
    • ¿Se extrae el enlace simbólico?
    • ¿La aplicación sigue el enlace?
    • ¿Se puede acceder al contenido de archivos sensibles?
Impacto
  • Lectura arbitraria de archivos
  • Divulgación de información sensible

ZIP Bombs

Una ZIP bomb (más generalmente conocida como bomba de descompresión) es un archivo comprimido que contiene un gran volumen de datos. Su propósito es causar una denegación de servicio agotando el espacio en disco o la memoria del sistema objetivo que intenta extraer el archivo. Aunque el formato ZIP es el ejemplo más usado, otros formatos también se ven afectados, incluido gzip (que se usa con frecuencia para comprimir datos en tránsito).

En su nivel más simple, una ZIP bomb se puede crear comprimiendo un archivo grande formado por un único carácter. El siguiente ejemplo muestra cómo crear un archivo de 1 MB que se descomprimirá a 1 GB:

dd if=/dev/zero bs=1M count=1024 | zip -9 > bomb.zip

Existen varios métodos para lograr relaciones de compresión mucho más altas, incluidos múltiples niveles de compresión, abusing the ZIP format y quines (que son archivos comprimidos que contienen una copia de sí mismos, causando recursión infinita).

Un ataque exitoso de ZIP bomb producirá una denegación de servicio y también puede generar mayores costos si se usa una plataforma en la nube con escalado automático. No se debe realizar este tipo de ataque a menos que se hayan considerado estos riesgos y se cuente con aprobación por escrito para hacerlo.

Archivos XML

Los archivos XML tienen varias vulnerabilidades potenciales, como XML eXternal Entities (XXE) y ataques de denegación de servicio como el billion laughs attack.

Estas se analizan con más detalle en la guía de XML Injection.

Otros formatos de archivo

Muchos otros formatos de archivo también tienen preocupaciones de seguridad específicas que deben tenerse en cuenta, como:

  • Los archivos de imagen deben comprobarse en cuanto a tamaño máximo de píxeles o de fotogramas.
  • Los archivos CSV pueden permitir CSV injection attacks.
  • Los archivos de Office pueden contener macros maliciosas o código PowerShell.
  • Los PDF pueden contener JavaScript malicioso.

Se deben revisar con cuidado los formatos de archivo permitidos en busca de funcionalidad potencialmente peligrosa y, cuando sea posible, se debe intentar explotarla durante las pruebas.

Revisión del código fuente

Cuando se admite la función de carga de archivos, es común encontrar en el código fuente las siguientes API o métodos.

  • Java: new file, import, upload, getFileName, Download, getOutputString
  • C/C++: open, fopen
  • PHP: move_uploaded_file(), Readfile, file_put_contents(), file(), parse_ini_file(), copy(), fopen(), include(), require()

Casos de prueba relacionados

  • File Extensions Handling for Sensitive Information
  • XML Injection
  • Test Upload of Unexpected File Types

Corrección

Protegerse por completo contra la carga de archivos maliciosos puede ser complejo, y los pasos exactos necesarios variarán según los tipos de archivo que se carguen y cómo se procesen o analicen los archivos en el servidor. Esto se analiza más a fondo en la File Upload Cheat Sheet.
