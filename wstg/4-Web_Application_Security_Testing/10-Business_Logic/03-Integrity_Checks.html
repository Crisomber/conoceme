Comprobaciones de integridad

ID
WSTG-BUSL-03

Resumen

Muchas aplicaciones están diseñadas para mostrar campos distintos según el usuario o la situación, dejando algunas entradas ocultas. Sin embargo, en muchos casos es posible enviar al servidor valores de campos ocultos mediante un proxy. En estos casos, los controles del lado del servidor deben ser lo bastante inteligentes como para realizar ediciones relacionales o del lado del servidor y así garantizar que solo se permitan al servidor los datos adecuados según el usuario y la lógica de negocio específica de la aplicación.

Además, la aplicación no debe depender de controles no editables, menús desplegables o campos ocultos para el procesamiento de la lógica de negocio, porque estos campos permanecen no editables solo en el contexto de los navegadores. Los usuarios pueden editar sus valores con herramientas de edición de proxy e intentar manipular la lógica de negocio. Si la aplicación expone valores relacionados con reglas de negocio, como la cantidad, etc., como campos no editables, debe mantener una copia en el lado del servidor y usarla para el procesamiento de la lógica de negocio. Por último, además de los datos de la aplicación o del sistema, los sistemas de log deben protegerse para impedir su lectura, escritura y actualización.

Las vulnerabilidades de las comprobaciones de integridad de la lógica de negocio son particulares en cuanto a que estos casos de uso indebido son específicos de cada aplicación y, si los usuarios pueden realizar cambios, solo se debería poder escribir o actualizar/editar artefactos específicos en momentos específicos según la lógica del proceso de negocio.

La aplicación debe ser lo bastante inteligente como para comprobar las ediciones relacionales y no permitir que los usuarios envíen directamente al servidor información que no es válida, que se considera confiable porque proviene de controles no editables o que el usuario no está autorizado a enviar a través del frontend. Además, los artefactos del sistema, como los logs, deben estar "protegidos" contra lectura, escritura y eliminación no autorizadas.

Ejemplo 1

Imagínese una aplicación GUI en ASP.NET que solo permite al usuario administrador cambiar la contraseña de otros usuarios del sistema. El usuario administrador verá los campos de nombre de usuario y contraseña para introducir un nombre de usuario y una contraseña, mientras que los demás usuarios no verán ninguno de los dos campos. Sin embargo, si un usuario no administrador envía información en los campos de nombre de usuario y contraseña a través de un proxy, podría "engañar" al servidor para que crea que la petición proviene de un usuario administrador y cambiar la contraseña de otros usuarios.

Ejemplo 2

La mayoría de las aplicaciones web tienen listas desplegables que facilitan al usuario seleccionar rápidamente su estado, mes de nacimiento, etc. Supóngase que una aplicación de gestión de proyectos permitiera a los usuarios iniciar sesión y, según sus privilegios, les presentara una lista desplegable de los proyectos a los que tienen acceso. ¿Qué pasa si un atacante encuentra el nombre de otro proyecto al que no debería tener acceso y envía la información mediante un proxy? ¿La aplicación le dará acceso al proyecto? No debería tener acceso aunque haya omitido una comprobación de lógica de negocio de autorización.

Ejemplo 3

Supóngase que el sistema de administración de vehículos motorizados exigiera que un empleado verifique inicialmente la documentación y la información de cada ciudadano cuando emite una identificación o una licencia de conducir. En este punto, el proceso de negocio ha creado datos con un alto nivel de integridad, ya que la integridad de los datos enviados es comprobada por los empleados. Ahora supóngase que la aplicación se traslada a internet para que los empleados puedan iniciar sesión y acceder al servicio completo o los ciudadanos puedan iniciar sesión en una aplicación de autoservicio reducida para actualizar cierta información. En este punto, un atacante podría usar un proxy de interceptación para añadir o actualizar datos a los que no debería tener acceso y podría destruir la integridad de los datos al declarar que el ciudadano no estaba casado pero proporcionar datos del nombre de un cónyuge. Este tipo de inserción o actualización de datos no verificados destruye la integridad de los datos y podría haberse evitado si se hubiera seguido la lógica del proceso de negocio.

Ejemplo 4

Muchos sistemas incluyen registro (logging) con fines de auditoría y solución de problemas. Pero, ¿qué tan buena o válida es la información de esos logs? ¿Pueden ser manipulados por atacantes, ya sea intencionalmente o accidentalmente, destruyendo su integridad?

Objetivos de la prueba

  • Revisar la documentación del proyecto en busca de los componentes del sistema que mueven, almacenan o manejan datos.
  • Determinar qué tipo de datos es lógicamente aceptable para el componente y contra qué tipos debe protegerse el sistema.
  • Determinar quién debería poder modificar o leer esos datos en cada componente.
  • Intentar insertar, actualizar o eliminar valores de datos usados por cada componente que no deberían permitirse según el flujo de trabajo de la lógica de negocio.

Cómo probar

Método de prueba específico 1

  • Usando un proxy, capturar el tráfico HTTP buscando campos ocultos.
  • Si se encuentra un campo oculto, ver cómo se comparan estos campos con la aplicación GUI y comenzar a interrogar este valor a través del proxy enviando distintos valores de datos para intentar eludir el proceso de negocio y manipular valores a los que no se debía tener acceso.

Método de prueba específico 2

  • Usando un proxy, capturar el tráfico HTTP buscando un lugar donde insertar información en áreas de la aplicación que no son editables.
  • Si se encuentra, ver cómo se comparan estos campos con la aplicación GUI y comenzar a interrogar este valor a través del proxy enviando distintos valores de datos para intentar eludir el proceso de negocio y manipular valores a los que no se debía tener acceso.

Método de prueba específico 3

  • Enumerar los componentes de la aplicación o del sistema que podrían verse afectados, por ejemplo logs o bases de datos.
  • Para cada componente identificado, intentar leer, editar o eliminar su información. Por ejemplo, se deben identificar los archivos de log y los evaluadores deben intentar manipular los datos o la información que se recopila.

Casos de prueba relacionados

Todos los casos de prueba de Injection Testing.

Corrección

La aplicación debe seguir controles de acceso estrictos sobre cómo se pueden modificar y leer los datos y artefactos, y hacerlo a través de canales confiables que garanticen la integridad de los datos. Se debe establecer un registro adecuado para revisar y asegurar que no se produce ningún acceso o modificación no autorizados.

Herramientas

  • Diversas herramientas del sistema o de la aplicación, como editores y herramientas de manipulación de archivos.
  • Zed Attack Proxy (ZAP)
  • Burp Suite
