Escalada de privilegios

ID
WSTG-ATHZ-03

Resumen

Esta sección describe el problema de escalar privilegios de una etapa a otra. Durante esta fase, el evaluador debe verificar que un usuario no pueda modificar sus privilegios o roles dentro de la aplicación de maneras que permitan ataques de escalada de privilegios.

La escalada de privilegios ocurre cuando un usuario obtiene acceso a más recursos o funcionalidades de los que normalmente se le permiten, y dicha elevación o cambios deberían haber sido impedidos por la aplicación. Esto suele deberse a una falla en la aplicación. El resultado es que la aplicación realiza acciones con más privilegios de los previstos por el desarrollador o el administrador del sistema.

El grado de escalada depende de qué privilegios tiene autorizados el atacante y de qué privilegios se pueden obtener con una explotación exitosa. Por ejemplo, un error de programación que permite a un usuario obtener privilegios adicionales tras una autenticación exitosa limita el grado de escalada, porque el usuario ya está autorizado para tener algunos privilegios. Del mismo modo, un atacante remoto que obtiene privilegios de superusuario sin ninguna autenticación representa un mayor grado de escalada.

Normalmente se habla de escalada vertical cuando es posible acceder a recursos concedidos a cuentas con más privilegios (por ejemplo, adquirir privilegios administrativos en la aplicación), y de escalada horizontal cuando es posible acceder a recursos concedidos a una cuenta configurada de manera similar (por ejemplo, en una aplicación de banca en línea, acceder a información de otro usuario).

Objetivos de la prueba

  • Identificar los puntos de inyección relacionados con la manipulación de privilegios.
  • Realizar fuzzing o intentar de otro modo evadir las medidas de seguridad.

Cómo probar

Manipulación de roles/privilegios

En cada parte de la aplicación donde un usuario puede crear información en la base de datos (por ejemplo, hacer un pago, agregar un contacto o enviar un mensaje), recibir información (estado de cuenta, detalles de pedidos, etc.) o eliminar información (eliminar usuarios, mensajes, etc.), es necesario registrar esa funcionalidad. El evaluador debe intentar acceder a tales funciones como otro usuario para verificar si es posible acceder a una función que el rol/privilegio del usuario no debería permitir (pero que podría estar permitida a otro usuario).

Manipulación del grupo de usuario

Por ejemplo: El siguiente HTTP POST permite que el usuario que pertenece a grp001 acceda al pedido n.º 0001:

POST /user/viewOrder.jsp HTTP/1.1
Host: www.example.com
...

groupID=grp001&orderID=0001

Se debe verificar si un usuario que no pertenece a grp001 puede modificar el valor de los parámetros groupID y orderID para obtener acceso a esos datos privilegiados.

Manipulación del perfil de usuario

Por ejemplo: La siguiente respuesta del servidor muestra un campo oculto en el HTML devuelto al usuario después de una autenticación exitosa.

HTTP/1.1 200 OK
Server: Netscape-Enterprise/6.0
Date: Wed, 1 Apr 2006 13:51:20 GMT
Set-Cookie: USER=aW78ryrGrTWs4MnOd32Fs51yDqp; path=/; domain=www.example.com
Set-Cookie: SESSION=k+KmKeHXTgDi1J5fT7Zz; path=/; domain= www.example.com
Cache-Control: no-cache
Pragma: No-cache
Content-length: 247
Content-Type: text/html
Expires: Thu, 01 Jan 1970 00:00:00 GMT
Connection: close

<form  name="autoriz" method="POST" action = "visual.jsp">
<input type="hidden" name="profile" value="SysGuest">\

<body onload="document.forms.autoriz.submit()">
</td>
</tr>

¿Qué pasa si el evaluador modifica el valor de la variable profile a SysAdmin? ¿Es posible convertirse en administrador?

Manipulación del valor de una condición

Por ejemplo: En un entorno donde el servidor envía un mensaje de error contenido como valor de un parámetro específico dentro de un conjunto de códigos de respuesta, como el siguiente:

@0`1`3`3``0`UC`1`Status`OK`SEC`5`1`0`ResultSet`0`PVValid`-1`0`0` Notifications`0`0`3`Command  Manager`0`0`0` StateToolsBar`0`0`0`
StateExecToolBar`0`0`0`FlagsToolBar`0

El servidor otorga una confianza implícita al usuario. Cree que el usuario responderá con el mensaje anterior cerrando la sesión.

En esta condición, se debe verificar que no sea posible escalar privilegios modificando los valores de los parámetros. En este ejemplo particular, al modificar el valor de PVValid de -1 a 0 (sin condiciones de error), puede ser posible autenticarse como administrador en el servidor.

Manipulación de la dirección IP

Algunos sitios limitan el acceso o cuentan el número de intentos fallidos de inicio de sesión según la dirección IP.

Por ejemplo:

X-Forwarded-For: 8.1.1.1

En este caso, si el sitio usa el valor de X-forwarded-For como dirección IP del cliente, el evaluador puede cambiar el valor de IP de la cabecera HTTP X-forwarded-For para eludir la identificación del origen por IP.

Evasión vertical

Una evasión de autorización vertical es específica del caso en que un atacante obtiene un rol superior al suyo. Las pruebas de esta evasión se centran en verificar cómo se ha implementado el esquema de autorización vertical para cada rol. Para cada función, página, rol específico o petición que ejecuta la aplicación, es necesario verificar si es posible:

  • Acceder a recursos que deberían ser accesibles solo a un usuario con un rol superior.
  • Operar funciones sobre recursos que deberían ser operables solo por un usuario con una identidad de rol superior o específica.

Para cada rol:

  1. Registrar un usuario.
  2. Establecer y mantener dos sesiones distintas basadas en los dos roles diferentes.
  3. Para cada petición, cambiar el identificador de sesión del original al identificador de sesión de otro rol y evaluar las respuestas de cada uno.
  4. Se considerará que una aplicación es vulnerable si la sesión con menos privilegios contiene los mismos datos o indica operaciones exitosas en funciones de mayor privilegio.

Escenario de roles en un sitio bancario

La siguiente tabla ilustra los roles del sistema en un sitio bancario. Cada rol está vinculado a permisos específicos para la funcionalidad del menú de eventos:

ROL PERMISO PERMISO ADICIONAL
Administrator Full Control Delete
Manager Modify, Add, Read Add
Staff Read, Modify Modify
Customer Read Only

Se considerará que la aplicación es vulnerable si:

  1. Un cliente (Customer) puede operar funciones de administrador, gerente o personal;
  2. Un usuario de personal (Staff) puede operar funciones de gerente o administrador;
  3. Un gerente (Manager) puede operar funciones de administrador.

Supóngase que la función deleteEvent forma parte del menú de la cuenta de administrador de la aplicación, y que es posible acceder a ella solicitando la siguiente URL: https://www.example.com/account/deleteEvent. Entonces, al invocar la función deleteEvent se genera la siguiente petición HTTP:

POST /account/deleteEvent HTTP/1.1
Host: www.example.com
[other HTTP headers]
Cookie: SessionID=ADMINISTRATOR_USER_SESSION

EventID=1000001

La respuesta válida:

HTTP/1.1 200 OK
[other HTTP headers]

{"message": "Event was deleted"}

El atacante puede intentar ejecutar la misma petición:

POST /account/deleteEvent HTTP/1.1
Host: www.example.com
[other HTTP headers]
Cookie: SessionID=CUSTOMER_USER_SESSION

EventID=1000002

Si la respuesta a la petición del atacante contiene los mismos datos {"message": "Event was deleted"}, la aplicación es vulnerable.

Acceso a la página de administrador

Supóngase que el menú de administrador forma parte de la cuenta de administrador.

Se considerará que la aplicación es vulnerable si cualquier rol distinto del administrador puede acceder al menú de administrador. A veces los desarrolladores realizan la validación de autorización solo a nivel de la interfaz gráfica (GUI) y dejan las funciones sin validación de autorización, lo que puede dar lugar a una vulnerabilidad.

URL Traversal

Se debe intentar recorrer el sitio y comprobar si algunas páginas carecen de la verificación de autorización.

Por ejemplo:

/../.././userInfo.html

Caja blanca

Si la verificación de autorización de URL solo se realiza mediante coincidencia parcial de la URL, es probable que los evaluadores o hackers puedan eludir la autorización mediante técnicas de codificación de URL.

Por ejemplo:

startswith(), endswith(), contains(), indexOf()
