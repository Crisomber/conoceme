Inclusión de archivos y Directory Traversal

ID
WSTG-ATHZ-01

Resumen

Muchas aplicaciones web utilizan y administran archivos como parte de su operación diaria. Si se emplean métodos de validación de entrada mal diseñados o mal implementados, un agresor podría explotar el sistema para leer o escribir archivos que no deberían ser accesibles. En ciertas situaciones, incluso podría ser posible ejecutar código arbitrario o comandos del sistema.

Tradicionalmente, los servidores web y las aplicaciones web implementan mecanismos de autenticación para controlar el acceso a archivos y recursos. Los servidores web intentan confinar los archivos de los usuarios dentro de un "directorio raíz" o "raíz de documentos web", que representa un directorio físico en el sistema de archivos. Los usuarios deben considerar este directorio como el directorio base dentro de la estructura jerárquica de la aplicación web.

La definición de los privilegios se hace mediante Listas de Control de Acceso (ACL), que identifican qué usuarios o grupos pueden acceder, modificar o ejecutar un archivo específico en el servidor. Estos mecanismos están diseñados para impedir que usuarios maliciosos accedan a archivos sensibles (por ejemplo, el común archivo /etc/passwd en una plataforma tipo UNIX) o para evitar la ejecución de comandos del sistema.

Muchas aplicaciones web utilizan scripts del lado del servidor para incluir distintos tipos de archivos. Es bastante común usar este método para administrar imágenes, plantillas, cargar textos estáticos, etc. Lamentablemente, estas aplicaciones exponen vulnerabilidades de seguridad si los parámetros de entrada (es decir, parámetros de formularios, valores de cookies) no se validan correctamente.

En los servidores web y las aplicaciones web, este tipo de problema se manifiesta en los ataques de path traversal y de inclusión de archivos. Al explotar este tipo de vulnerabilidad, un atacante puede leer directorios o archivos que normalmente no podría leer, acceder a datos fuera de la raíz de documentos web o incluir scripts y otros tipos de archivos desde sitios externos.

Para los fines de la Guía de Pruebas de OWASP, solo se considerarán las amenazas de seguridad relacionadas con aplicaciones web y no las amenazas a los servidores web (por ejemplo, el infame código de escape %5c en el servidor web Microsoft IIS). En la sección de referencias se ofrecen sugerencias de lectura adicional para los lectores interesados.

Este tipo de ataque también se conoce como ataque punto-punto-barra (../), directory traversal, escalada de directorios (directory climbing) o retroceso (backtracking).

Durante una evaluación, para descubrir fallas de path traversal e inclusión de archivos, los evaluadores deben realizar dos etapas distintas:

  1. Enumeración de vectores de entrada (una evaluación sistemática de cada vector de entrada)
  2. Técnicas de prueba (una evaluación metódica de cada técnica de ataque utilizada por un atacante para explotar la vulnerabilidad)

Objetivos de la prueba

  • Identificar los puntos de inyección relacionados con path traversal.
  • Evaluar las técnicas de evasión e identificar el alcance del path traversal.

Cómo probar

Pruebas de caja negra

Enumeración de vectores de entrada

Para determinar qué parte de la aplicación es vulnerable a la evasión de la validación de entrada, el evaluador debe enumerar todas las partes de la aplicación que aceptan contenido del usuario. Esto incluye también las consultas HTTP GET y POST y opciones comunes como la carga de archivos y los formularios HTML.

A continuación se presentan algunos ejemplos de las comprobaciones que se deben realizar en esta etapa:

  • ¿Hay parámetros de la petición que podrían usarse para operaciones relacionadas con archivos?
  • ¿Hay extensiones de archivo inusuales?
  • ¿Hay nombres de variables interesantes?
    • https://example.com/getUserProfile.jsp?item=ikki.html
    • https://example.com/index.php?file=content
    • https://example.com/main.cgi?home=index.htm
  • ¿Es posible identificar cookies utilizadas por la aplicación web para la generación dinámica de páginas o plantillas?
    • Cookie: ID=d9ccd3f4f9f18cc1:TM=2166255468:LM=1162655568:S=3cFpqbJgMSSPKVMV:TEMPLATE=flower
    • Cookie: USER=1826cc8f:PSTYLE=GreenDotRed

Técnicas de prueba

La siguiente etapa de las pruebas consiste en analizar las funciones de validación de entrada presentes en la aplicación web. Siguiendo el ejemplo anterior, la página dinámica llamada getUserProfile.jsp carga información estática desde un archivo y muestra el contenido a los usuarios. Un atacante podría insertar la cadena maliciosa ../../../../etc/passwd para incluir el archivo de hashes de contraseñas de un sistema Linux/UNIX. Obviamente, este tipo de ataque solo es posible si falla el punto de control de validación; según los privilegios del sistema de archivos, la propia aplicación web debe ser capaz de leer el archivo.

Nota: Para probar con éxito esta falla, el evaluador necesita conocer el sistema que se está probando y la ubicación de los archivos solicitados. No tiene sentido solicitar /etc/passwd a un servidor web IIS.

https://example.com/getUserProfile.jsp?item=../../../../etc/passwd

Otro ejemplo común es incluir contenido de una fuente externa:

https://example.com/index.php?file=https://www.owasp.org/malicioustxt

Lo mismo puede aplicarse a las cookies o a cualquier otro vector de entrada que se utilice para la generación dinámica de páginas.

Se pueden encontrar más payloads de inclusión de archivos en PayloadsAllTheThings - File Inclusion

Es importante tener en cuenta que distintos sistemas operativos utilizan distintos separadores de ruta

  • SO tipo Unix:
    • directorio raíz: /
    • separador de directorios: /
  • SO Windows:
    • directorio raíz: <drive letter>:
    • separador de directorios: \ o /
  • macOS clásico:
    • directorio raíz: <drive letter>:
    • separador de directorios: :

Es un error común de los desarrolladores no prever todas las formas de codificación y, por ello, validar únicamente contenido con codificaciones básicas. Si al principio la cadena de prueba no tiene éxito, se debe intentar con otro esquema de codificación.

Se pueden encontrar técnicas de codificación y payloads de directory traversal listos para usar en PayloadsAllTheThings - Directory Traversal

Consideraciones específicas de Windows

  • Shell de Windows: añadir cualquiera de los siguientes elementos a las rutas usadas en un comando de shell no produce ninguna diferencia en su funcionamiento:
    • Corchetes angulares < y > al final de la ruta
    • Comillas dobles (cerradas correctamente) al final de la ruta
    • Marcadores de directorio actual superfluos como ./ o .\\
    • Marcadores de directorio padre superfluos con elementos arbitrarios que pueden existir o no:
      • file.txt
      • file.txt...
      • file.txt<spaces>
      • file.txt""""
      • file.txt<<<>>><
      • ./././file.txt
      • nonexistent/../file.txt
  • API de Windows: los siguientes elementos se descartan cuando se usan en cualquier comando de shell o llamada a la API en la que se tome una cadena como nombre de archivo:
    • puntos
    • espacios
  • Rutas UNC de Windows: se usan para referenciar archivos en recursos compartidos SMB. A veces es posible lograr que una aplicación haga referencia a archivos en una ruta UNC remota. De ser así, el servidor SMB de Windows puede enviar al atacante las credenciales almacenadas, que pueden ser capturadas y descifradas. También pueden usarse con una dirección IP o nombre de dominio autorreferencial para evadir filtros, o para acceder a archivos en recursos compartidos SMB inaccesibles para el atacante pero accesibles desde el servidor web.
    • \\server_or_ip\path\to\file.abc
    • \\?\server_or_ip\path\to\file.abc
  • Espacio de nombres de dispositivos de Windows NT: se usa para referirse al espacio de nombres de dispositivos de Windows. Ciertas referencias permiten acceder a sistemas de archivos usando una ruta diferente.
    • Puede ser equivalente a una letra de unidad como c:\, o incluso a un volumen de unidad sin letra asignada: \\.\GLOBALROOT\Device\HarddiskVolume1\
    • Se refiere a la primera unidad de disco de la máquina: \\.\CdRom0\

Pruebas de caja blanca

Cuando el análisis se realiza con un enfoque de caja blanca, los evaluadores deben seguir la misma metodología que en las pruebas de caja negra. Sin embargo, como pueden revisar el código fuente, es posible buscar los vectores de entrada de manera más fácil y precisa. Durante una revisión de código fuente, pueden usar herramientas simples (como el comando grep) para buscar uno o más patrones comunes dentro del código de la aplicación: funciones/métodos de inclusión, operaciones del sistema de archivos, etc.

  • PHP: include(), include_once(), require(), require_once(), fopen(), readfile(), ...
  • JSP/Servlet: java.io.File(), java.io.FileReader(), ...
  • ASP: include file, include virtual, ...

Usando motores de búsqueda de código en línea (por ejemplo, Searchcode), también puede ser posible encontrar fallas de path traversal en software de código abierto publicado en internet.

Para PHP, los evaluadores pueden usar la siguiente expresión regular:

(include|require)(_once)?\s*['"(]?\s*\$_(GET|POST|COOKIE)

Con el método de caja blanca es posible descubrir vulnerabilidades que normalmente son más difíciles de descubrir, o incluso imposibles de encontrar durante una evaluación estándar de caja negra.

Algunas aplicaciones web generan páginas dinámicas usando valores y parámetros almacenados en una base de datos. Puede ser posible insertar cadenas de path traversal especialmente diseñadas cuando la aplicación agrega datos a la base de datos. Este tipo de problema de seguridad es difícil de descubrir porque los parámetros dentro de las funciones de inclusión parecen internos y seguros, pero en realidad no lo son.

Además, al revisar el código fuente es posible analizar las funciones que se supone que manejan entradas inválidas: algunos desarrolladores intentan modificar la entrada inválida para volverla válida, evitando advertencias y errores. Estas funciones suelen ser propensas a fallas de seguridad.

Considérese una aplicación web con estas instrucciones:

filename = Request.QueryString("file");
Replace(filename, "/","\");
Replace(filename, "..\","");

La falla se prueba mediante:

file=....//....//boot.ini
file=....\\....\\boot.ini
file= ..\..\boot.ini
