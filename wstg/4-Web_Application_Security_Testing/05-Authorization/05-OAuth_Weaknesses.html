Debilidades de OAuth

ID
WSTG-ATHZ-05

Resumen

OAuth2.0 (en adelante, OAuth) es un framework de autorización que permite a un cliente acceder a recursos en nombre de su usuario.

Para lograrlo, OAuth depende en gran medida de tokens para comunicarse entre las distintas entidades, cada una con un rol diferente:

  • Resource Owner (propietario del recurso): La entidad que concede acceso a un recurso, el propietario, y que en la mayoría de los casos es el propio usuario
  • Client (cliente): La aplicación que solicita acceso a un recurso en nombre del Resource Owner. Estos clientes son de dos tipos:
    • Públicos: clientes que no pueden proteger un secreto (p. ej. aplicaciones centradas en el frontend, como SPAs, aplicaciones móviles, etc.)
    • Confidenciales: clientes que pueden autenticarse de forma segura con el servidor de autorización manteniendo a salvo sus secretos registrados (p. ej. servicios de backend)
  • Authorization Server (servidor de autorización): El servidor que guarda la información de autorización y concede el acceso
  • Resource Server (servidor de recursos): La aplicación que sirve el contenido al que accede el cliente

Dado que la responsabilidad de OAuth es delegar derechos de acceso del propietario al cliente, es un objetivo muy atractivo para los atacantes, y las malas implementaciones conducen al acceso no autorizado a los recursos y la información de los usuarios.

Para proporcionar acceso a una aplicación cliente, OAuth se apoya en varios tipos de concesión de autorización (authorization grant types) para generar un token de acceso:

  • Authorization Code: usado tanto por clientes confidenciales como públicos para intercambiar un código de autorización por un token de acceso, pero recomendado solo para clientes confidenciales
  • Proof Key for Code Exchange (PKCE): PKCE se construye sobre la concesión Authorization Code, proporcionándole mayor seguridad para que sea usada por clientes públicos y mejorando la postura de los confidenciales
  • Client Credentials: usado para la comunicación máquina a máquina, donde el "usuario" es la máquina que solicita al Resource Server acceso a sus propios recursos
  • Device Code: usado para dispositivos con capacidades de entrada limitadas.
  • Refresh Token: tokens proporcionados por el servidor de autorización para permitir a los clientes renovar los tokens de acceso de los usuarios cuando dejan de ser válidos o expiran. Este tipo de concesión se usa en conjunto con algún otro tipo de concesión.

Dos flujos quedarán obsoletos con la publicación de OAuth2.1, y no se recomienda su uso:

  • Implicit Flow*: la implementación segura de PKCE vuelve obsoleto este flujo. Antes de PKCE, el flujo implícito era usado por aplicaciones del lado del cliente como las aplicaciones de una sola página, ya que CORS flexibilizó la política del mismo origen para que los sitios pudieran comunicarse entre sí. Para más información sobre por qué no se recomienda la concesión implícita, revise esta sección.
  • Resource Owner Password Credentials: usado para intercambiar las credenciales de los usuarios directamente con el cliente, que luego las envía al servidor de autorización para intercambiarlas por un token de acceso. Para información sobre por qué no se recomienda este flujo, revise esta sección.

*: El flujo implícito en OAuth es el único que está obsoleto, pero sigue siendo una solución viable dentro de Open ID Connect (OIDC) para obtener id_tokens. Hay que tener cuidado de entender cómo se está usando el flujo implícito, lo cual puede identificarse si solo se usa el endpoint /authorization para obtener un token de acceso, sin depender en absoluto del endpoint /token. Un ejemplo de esto puede encontrarse aquí.

Tenga en cuenta que los flujos de OAuth son un tema complejo, y lo anterior incluye solo un resumen de las áreas clave. Las referencias en línea contienen más información sobre los flujos específicos.

Objetivos de la prueba

  • Determinar si la implementación de OAuth2 es vulnerable o si utiliza una implementación obsoleta o personalizada.

Cómo probar

Tipos de concesión obsoletos

Los tipos de concesión obsoletos quedaron en desuso por razones de seguridad y funcionalidad. Identificar si se están utilizando permite revisar rápidamente si son susceptibles a alguna de las amenazas asociadas a su uso. Algunos pueden estar fuera del alcance del atacante, como la forma en que un cliente podría estar usando las credenciales de los usuarios. Esto debe documentarse y comunicarse a los equipos internos de ingeniería.

En el caso de los clientes públicos, generalmente es posible identificar el tipo de concesión en la petición al endpoint /token. Se indica en el intercambio de tokens con el parámetro grant_type.

El siguiente ejemplo muestra la concesión Authorization Code con PKCE.

POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
  "client_id":"example-client",
  "code_verifier":"example",
  "grant_type":"authorization_code",
  "code":"example",
  "redirect_uri":"https://client.example.com"
}

Los valores del parámetro grant_type y el tipo de concesión que indican son:

  • password: Indica la concesión ROPC.
  • client_credentials: Indica la concesión Client Credential.
  • authorization_code: Indica la concesión Authorization Code.

El tipo Implicit Flow no se indica con el parámetro grant_type, ya que el token se presenta en la respuesta a la petición al endpoint /authorization, y en cambio puede identificarse mediante response_type. A continuación se muestra un ejemplo.

GET /authorize
  ?client_id=<some_client_id>
  &response_type=token 
  &redirect_uri=https%3A%2F%2Fclient.example.com%2F
  &scope=openid%20profile%20email
  &state=<random_state>

Los siguientes parámetros de URL indican el flujo de OAuth que se está utilizando:

  • response_type=token: Indica Implicit Flow, ya que el cliente solicita directamente al servidor de autorización que devuelva un token.
  • response_type=code: Indica el flujo Authorization Code, ya que el cliente solicita al servidor de autorización que devuelva un código, que luego se intercambiará por un token.
  • code_challenge=sha256(xyz): Indica la extensión PKCE, ya que ningún otro flujo utiliza este parámetro.

El siguiente es un ejemplo de petición de autorización para el flujo Authorization Code con PKCE:

GET /authorize
    ?redirect_uri=https%3A%2F%2Fclient.example.com%2F
    &client_id=<some_client_id>
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=query
    &state=<random_state>
    &nonce=<random_nonce>
    &code_challenge=<random_code_challenge>
    &code_challenge_method=S256 HTTP/1.1
Host: as.example.com
[...]

Clientes públicos

Para los clientes públicos se recomienda la concesión Authorization Code con la extensión PKCE. Una petición de autorización para el flujo Authorization Code con PKCE debe contener response_type=code y code_challenge=sha256(xyz).

El intercambio de tokens debe contener el tipo de concesión authorization_code y un code_verifier.

Los tipos de concesión inadecuados para clientes públicos son:

  • Concesión Authorization Code sin la extensión PKCE
  • Client Credentials
  • Implicit Flow
  • ROPC

Clientes confidenciales

Para los clientes confidenciales se recomienda la concesión Authorization Code. También se puede usar la extensión PKCE.

Los tipos de concesión inadecuados para clientes confidenciales son:

  • Client Credentials (excepto para máquina a máquina; véase más abajo)
  • Implicit Flow
  • ROPC
Máquina a máquina

En situaciones en las que no hay interacción de un usuario y los clientes son únicamente confidenciales, puede utilizarse la concesión Client Credentials.

Si se conocen el client_id y el client_secret, es posible obtener un token pasando el tipo de concesión client_credentials.

$ curl --request POST \
  --url https://as.example.com/oauth/token \
  --header 'content-type: application/json' \
  --data '{"client_id":"<some_client_id>","client_secret":"<some_client_secret>","grant_type":"client_credentials"}' --proxy https://localhost:8080/ -k

Filtración de credenciales

Dependiendo del flujo, OAuth transporta varios tipos de credenciales como parámetros de URL.

Los siguientes tokens pueden considerarse credenciales filtradas:

  • access token
  • refresh token
  • authorization code
  • PKCE code challenge / code verifier

Debido a cómo funciona OAuth, el code de autorización, así como el code_challenge y el code_verifier, pueden formar parte de la URL. El flujo implícito transporta el token de autorización como parte de la URL si el response_mode no está configurado como form_post. Esto puede provocar la filtración del token o código solicitado en la cabecera referrer, en archivos de log y en proxies, debido a que estos parámetros se pasan en la query o en el fragmento.

El riesgo que conlleva la filtración de tokens en el flujo implícito es mucho mayor que el de filtrar el code o cualquier otro parámetro code_*, ya que estos están vinculados a clientes específicos y son más difíciles de abusar en caso de filtración.

Para probar este escenario, se debe usar un proxy interceptor HTTP como ZAP e interceptar el tráfico de OAuth.

  • Recorrer el proceso de autorización e identificar cualquier credencial presente en la URL.
  • Si se incluyen recursos externos en una página involucrada en el flujo de OAuth, analizar la petición que se les realiza. Las credenciales podrían filtrarse en la cabecera referrer.

Después de recorrer el flujo de OAuth y usar la aplicación, se capturan algunas peticiones en el historial de peticiones de un proxy interceptor HTTP. Se debe buscar en el historial de peticiones la cabecera HTTP referrer (p. ej. Referer: https://idp.example.com/) que contenga las URL del servidor de autorización y del cliente.

Revisar las metaetiquetas HTML (aunque esta etiqueta no es compatible con todos los navegadores) o la cabecera Referrer-Policy puede ayudar a evaluar si se está produciendo alguna filtración de credenciales a través de la cabecera referrer.

Corrección

  • Al implementar OAuth, siempre se debe considerar la tecnología utilizada y si la aplicación es una aplicación del lado del servidor que puede evitar revelar secretos, o una aplicación del lado del cliente que no puede.
  • En casi cualquier caso, se debe usar el flujo Authorization Code con PKCE. Una excepción pueden ser los flujos máquina a máquina.
  • Usar parámetros POST o valores de cabeceras para transportar secretos.
  • Cuando no exista otra posibilidad (por ejemplo, en aplicaciones heredadas que no se pueden migrar), implementar cabeceras de seguridad adicionales como Referrer-Policy.
