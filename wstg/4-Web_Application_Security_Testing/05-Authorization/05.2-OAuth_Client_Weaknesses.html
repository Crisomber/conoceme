Debilidades del cliente OAuth

Resumen

OAuth concede derechos de acceso sobre recursos a los clientes. Esto les permite actuar en nombre del propietario del recurso. El cliente recibe el código de autorización y el refresh token en el intercambio de tokens y los almacena.

No proteger el intercambio de tokens y las credenciales puede resultar en acceso no autorizado a recursos y en la elevación de privilegios.

Objetivos de la prueba

  • Identificar debilidades en el cliente OAuth.

Cómo probar

Para probar las debilidades del cliente, el objetivo será:

  1. Obtener las credenciales utilizadas para la autorización.
  2. Concederse acceso a recursos arbitrarios mediante forced browsing.
  3. Evadir la autorización.

Secreto de cliente expuesto

El secreto de cliente (client secret) se utiliza para autenticar al cliente frente al servidor de autorización (AS) con el fin de demostrar que el cliente es un origen de confianza.

Los clientes públicos generalmente no pueden almacenar el secreto de cliente de forma segura.

Para identificar el secreto de cliente en el código del lado del cliente, se debe realizar un reconocimiento del código del lado del cliente.

  1. Navegar a la aplicación.
  2. Abrir las herramientas de desarrollo del navegador.
  3. Ir a la pestaña Debugger.
  4. Presionar Ctrl+Shift+F para abrir la búsqueda.
  5. Buscar términos similares a client-secret y determinar si se encuentra alguno.

Si esto no tiene éxito, también se puede:

  1. Recorrer el proceso de autorización con un proxy interceptor HTTP como ZAP.
  2. Obtener el secreto de cliente del URI en el parámetro client-secret.
  3. Reemplazar el término de búsqueda de la búsqueda anterior por el valor del secreto de cliente y determinar si está expuesto.

Almacenamiento inadecuado de tokens

El cliente recibe access tokens e idealmente los almacena en una ubicación donde puedan estar protegidos de los atacantes.

Los clientes confidenciales deben almacenar los tokens en memoria volátil para evitar el acceso mediante otros ataques como la inclusión de archivos locales, atacantes que logren acceder al entorno o ataques de Inyección SQL.

Los clientes públicos, como las aplicaciones de una sola página, no tienen la posibilidad de almacenar tokens de forma segura. Por ejemplo, un ataque de Cross-Site Scripting permite a los atacantes acceder a las credenciales almacenadas en el navegador.

Los clientes públicos pueden almacenar tokens en el session storage del navegador o en una cookie, pero no en el local storage. Para determinar si los tokens están almacenados de forma inadecuada:

  1. Navegar a la aplicación.
  2. Obtener un access token.
  3. Abrir las herramientas de desarrollo del navegador.
  4. Ir a la pestaña Application.
  5. Localizar el Local Storage y ver los datos almacenados.
  6. Localizar el Session Storage y ver los datos almacenados.
  7. Localizar el Cookie Store y ver los datos almacenados.

Inyección de access token

Este ataque solo es posible cuando el cliente utiliza un tipo de respuesta que emite directamente un access token al cliente. Esto ocurre con los tipos de concesión Implicit Flows, Resource Owner Password Credential y los flujos máquina a máquina. Véase Debilidades de OAuth para una descripción más detallada.

La inyección de access token tiene éxito cuando un access token se filtra a un atacante y luego se usa para autenticarse con el cliente legítimo.

Para probar la inyección de access token, se siguen los pasos a continuación. En este ejemplo, se filtró el token de autorización (ZXhhbXBsZQo=).

  1. Interceptar el tráfico entre el cliente y el servidor de autorización.
  2. Iniciar un flujo de OAuth con un cliente que utilice el tipo de concesión Implicit Flow.
  3. Inyectar el access token robado:
    • Enviar al cliente una respuesta de autorización falsificada con el access token robado (ZXhhbXBsZQo=).
    • Interceptar una respuesta de autorización válida y reemplazar el access token (dGVzdGluZwo=) por el filtrado (ZXhhbXBsZQo=).

Casos de prueba relacionados

  • Cross Site Request Forgery
  • Client-side URL Redirect
  • Testing JSON Web Tokens
  • Clickjacking
  • Testing Cross Origin Resource Sharing

Corrección

  • Usar un secreto de cliente solo si el cliente tiene la capacidad de almacenarlo de forma segura.
  • Seguir las mejores prácticas para almacenar tokens de forma segura. Tratarlos con las mismas consideraciones de seguridad que otras credenciales.
  • Evitar los tipos de concesión de OAuth obsoletos. Véase Debilidades de OAuth para una descripción más detallada.
