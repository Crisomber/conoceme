Debilidades del servidor de autorización OAuth

Resumen

OAuth almacena las identidades de los usuarios y sus correspondientes derechos de acceso en el servidor de autorización (Authorization Server, AS). El AS desempeña un papel crucial durante el flujo de OAuth, ya que concede a los clientes acceso a los recursos. Para poder hacerlo de forma segura, debe validar correctamente los parámetros que forman parte del flujo de OAuth.

No validar los parámetros puede conducir a la toma de control de cuentas, al acceso no autorizado a recursos y a la elevación de privilegios.

Objetivos de la prueba

  • Identificar debilidades en el servidor de autorización.

Cómo probar

Para probar las debilidades del AS, el objetivo será:

  1. Obtener las credenciales utilizadas para la autorización.
  2. Concederse acceso a recursos arbitrarios mediante forced browsing.
  3. Evadir la autorización.

Validación insuficiente del Redirect URI

Si el redirect_uri no se valida correctamente, se puede construir un enlace que contenga una URL que apunte a un servidor controlado por un atacante. Esto puede usarse para engañar al AS y hacer que envíe un código de autorización al atacante. En el siguiente ejemplo, se usa client.evil.com como redirect_uri falsificado.

https://as.example.com/authorize?client_id=example-client&redirect_uri=http%3A%2F%client.evil.com%2F&state=example&response_mode=fragment&response_type=code&scope=openid&nonce=example

Si un usuario abre este enlace en el user agent, el AS redirigirá al user agent a la URL maliciosa.

Un atacante puede capturar el valor de code pasado en la URL falsificada y luego enviarlo al endpoint de tokens del AS.

La siguiente petición ilustra una petición de autorización que envía el redirect_uri al servidor de autorización. El cliente client.example.com envía una petición de autorización al AS as.example.com con el URI de redirección codificado en URL http%3A%2F%2Fclient.example.com%2F.

GET /authorize
    ?redirect_uri=http%3A%2F%2Fclient.example.com%2F
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=query
    &state=example
    &nonce=example
    &code_challenge=example
    &code_challenge_method=S256 HTTP/1.1
Host: as.example.com

El AS responde con una redirección que contiene el código de autorización. Este puede intercambiarse por un token de acceso en la petición de token. Como se muestra a continuación, la URL en la cabecera Location es el URI dado en el parámetro redirect_uri anterior.

HTTP/1.1 302 Found
Date: Mon, 18 Oct 2021 20:46:44 GMT
Content-Type: text/html; charset=utf-8
Content-Length: 340
Location: https://client.example.com/?code=example&state=example

Para probar si el AS es vulnerable a una validación insuficiente del redirect URI, se debe capturar el tráfico con un proxy interceptor HTTP como ZAP.

  1. Iniciar el flujo de OAuth y pausarlo en la petición de autorización.
  2. Cambiar el valor del redirect_uri y observar la respuesta.
  3. Investigar la respuesta e identificar si el AS aceptó el parámetro redirect_uri arbitrario.

Si el AS redirige al user agent al redirect_uri que se especificó, el AS no valida correctamente el redirect_uri.

Además, véase la sección Common Filter Bypass en Server-Side Request Forgery para identificar evasiones comunes de la validación del redirect URI.

Inyección de código de autorización

Durante el intercambio de código en el flujo Authorization Code, el AS emite un código al cliente, que luego se intercambia en el endpoint de tokens para obtener un token de autorización y un refresh token.

Se deben realizar las siguientes pruebas contra el AS:

  1. Enviar un código válido para otro client_id.
  2. Enviar un código válido para otro propietario del recurso.
  3. Enviar un código válido para otro redirect_uri.
  4. Reenviar el código más de una vez (repetición del código).

Clientes públicos

La petición enviada al endpoint de tokens contiene el código de autorización, que se intercambia por el token. Se debe capturar esta petición con un proxy interceptor HTTP como ZAP y reenviarla con valores modificados.

POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
    "errorPath":"/error",
    "client_id":"example-client",
    "code":"INJECT_CODE_HERE",
    "grant_type":"authorization_code",
    "redirect_uri":"https://client.example.com"
}

Si el AS responde con un access_token, el código se inyectó con éxito.

Probar clientes confidenciales

Como el flujo de OAuth para clientes confidenciales está protegido además por un secreto de cliente, no es posible enviar directamente un código de autorización al endpoint de tokens. En su lugar, se inyecta el código de autorización en el cliente. Este código inyectado se enviará entonces en la petición de token, emitida por el cliente confidencial junto con el secreto del cliente.

Primero, se captura un código de autorización del AS:

  1. Iniciar el flujo de código de autorización con el usuario Alice. Pausar cuando se reciba un código del AS.
  2. No enviar el código al cliente y anotar el código y el state correspondiente.

Luego, se inyecta el código:

  1. Iniciar el flujo de código de autorización con el usuario Mallory e inyectar en el proceso los valores de código y state obtenidos previamente para el usuario Alice.
  2. Cuando el ataque tiene éxito, el cliente debería estar ahora en posesión de un authorization_token que concede acceso a los recursos propiedad del usuario Alice.
GET /callback?code=INJECT_CODE_HERE&state=example HTTP/1.1
Host: client.example.com
[...]

Ataque de degradación de PKCE

En determinadas circunstancias, la extensión PKCE puede eliminarse del flujo de código de autorización. Esto puede dejar a los clientes públicos vulnerables a ataques que la extensión PKCE mitiga.

Esto puede ocurrir cuando:

  • El AS no admite PKCE.
  • El AS no valida correctamente PKCE.

Ambos casos pueden probarse con un proxy interceptor HTTP como ZAP. Se deben realizar las siguientes pruebas:

  1. Enviar la petición de autorización sin los parámetros code_challenge=sha256(xyz) y code_challenge_method.
  2. Enviar la petición de autorización con un valor vacío para el parámetro code_challenge=sha256(xyz).
  3. Enviar la petición de autorización con un valor falsificado para el parámetro code_challenge=sha256(xyz)

El siguiente ejemplo resalta los valores que se deben modificar:

GET /authorize
    ?redirect_uri=http%3A%2F%client.example.com
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=web_message
    &state=example-state
    &nonce=example-nonce
    &code_challenge=MODIFY_OR_OMIT_THIS
    &code_challenge_method=MODIFY_OR_OMIT_THIS
    &prompt=none HTTP/1.1
Host: as.example.com
[...]

El AS debe verificar el valor de code_verifier en el intercambio de tokens. Para probarlo:

  1. Enviar la petición de token sin el code_verifier.
  2. Enviar la petición de token con un code_verifier vacío.
  3. Enviar la petición de token con un code_verifier válido para un código de autorización diferente.
POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
"client_id":"example-client",
"code_verifier":"MODIFY_OR_OMIT_THIS",
"code":"example",
"grant_type":"authorization_code",
"redirect_uri":"https://client.example.com"
}

Cross-Site Request Forgery en la página de consentimiento

Los ataques CSRF se describen en CSRF. OAuth puede ser atacado con CSRF.

Para prevenir ataques CSRF, OAuth utiliza el parámetro state como token anti-CSRF.

Otras medidas también pueden prevenir ataques CSRF. El flujo PKCE mitiga CSRF. Un valor nonce también puede actuar como token anti-CSRF.

Se debe probar cada petición que contenga uno de los parámetros anti-CSRF utilizados por OAuth conforme a las pruebas descritas en los casos de prueba de CSRF.

La página de consentimiento se muestra a un usuario para verificar que este consiente que el cliente acceda al recurso en su nombre. Atacar la página de consentimiento con CSRF puede conceder a un cliente arbitrario acceso a un recurso en nombre del usuario. Los pasos de este flujo son:

  1. El cliente genera un parámetro state y lo envía con la petición de consentimiento.
  2. El user agent muestra la página de consentimiento.
  3. El propietario del recurso concede acceso al cliente.
  4. El consentimiento se envía al AS junto con los scopes aceptados.

Se debe usar un proxy interceptor HTTP como ZAP para probar si el parámetro state se valida correctamente.

POST /u/consent?state=Tampered_State HTTP/1.1
Host: as.example.com
[...]

state=MODIFY_OR_OMIT_THIS
&audience=https%3A%2F%2Fas.example.com%2Fuserinfo
&scope%5B%5D=profile
&scope%5B%5D=email
&action=accept

Clickjacking

El clickjacking se describe en Clickjacking. Cuando la página de consentimiento es propensa a clickjacking y el atacante posee el client_id (para clientes públicos, o el secreto del cliente para clientes confidenciales), el atacante puede falsificar el consentimiento del usuario y obtener acceso al recurso solicitado a través de un cliente malicioso.

Cómo probar

Para que este ataque tenga éxito, el atacante necesita cargar la página de autorización en un iframe.

La siguiente página HTML puede usarse para cargar la página de autorización en un iframe:

<html>
    <head>
        <title>Clickjack test page</title>
    </head>
    <body>
        <iframe src="https://as.example.com/auth/realms/example/login-actions/required-action?execution=OAUTH_GRANT&client_id=example-client" width="500" height="500"></iframe>
    </body>
</html>

Si se carga con éxito, el sitio es vulnerable a clickjacking.

Véase Clickjacking para una descripción detallada de cómo puede llevarse a cabo un ataque de este tipo.

Duración de los tokens

OAuth tiene dos tipos de tokens: el access token y el refresh token. Un access token debe tener una validez limitada en el tiempo. Eso significa que es de corta duración: una buena duración depende de la aplicación y puede ser de 5 a 15 minutos.

El refresh token debe ser válido por un período más largo. Debe ser un token de un solo uso que se reemplaza cada vez que se ha usado.

Probar la validación de la duración del access token

Cuando se usa un JSON Web Token (JWT) como access token, es posible obtener la validez del access token a partir del JWT decodificado. Esto se describe en Testing JSON Web Tokens. Es posible que el AS no valide correctamente la duración del JWT.

Para probar la duración del access token, se debe usar un proxy interceptor HTTP como ZAP. Se intercepta una petición a un endpoint que contenga un access token. Se coloca esta petición en el repeater y se deja transcurrir el tiempo objetivo. La validez de un access token debe ser de entre 5 y 15 minutos, según la sensibilidad de los recursos.

Estas peticiones pueden verse como el siguiente ejemplo. El token también podría transportarse de otras maneras, por ejemplo, en una cookie.

GET /userinfo HTTP/1.1
Host: as.example.com
[...]
Authorization: Bearer eyJhbGciOiJkaXIiL[...]

Se debe probar la validación de la duración enviando la petición después de que hayan transcurrido distintos lapsos de tiempo, por ejemplo, después de 5 minutos, 10 minutos y 30 minutos.

Este proceso puede optimizarse automatizando los pasos y registrando la respuesta del servidor. Cuando se recibe una respuesta con estado HTTP 403 (en lugar de estado HTTP 200), esto puede indicar que el access token ya no es válido.

Probar la validación de la duración del refresh token

Los refresh tokens tienen un período de validez más largo que los access tokens. Debido a su larga validez, deben invalidarse después de usarse en un intercambio por un access token.

Los refresh tokens se emiten en la misma petición de token en la que se entrega el access token al cliente.

Se debe usar un proxy interceptor HTTP como ZAP. Se prepara la prueba de la siguiente manera:

  1. Obtener un refresh token válido.
  2. Capturar la petición que se usa para intercambiar el refresh token por un nuevo access token.
  3. Enviar la petición capturada al repeater de peticiones.

En el siguiente ejemplo, el refresh token se envía como parte del cuerpo del POST.

POST /token HTTP/1.1
Host: as.example.com
Cookie: [...]
[...]

grant_type=refresh_token
&refresh_token=eyJhbGciOiJIUz[...]
&client_id=example-client

Se deben realizar las siguientes pruebas:

  1. Enviar el refresh token y determinar si el AS entrega un access token.
  2. Repetir los pasos con el mismo refresh token para evaluar cuántas veces se acepta un mismo refresh token.

Cuando se usa un JWT como refresh token, es posible obtener la validez del refresh token a partir del JWT decodificado. Esto se describe en Testing JSON Web Tokens. El refresh token puede ser válido por un período más largo, pero debe tener una fecha de expiración.

Se puede obtener seguridad adicional con un mecanismo de detección de robo. Si un refresh token se usa en un intercambio de tokens más allá de su validez (o duración), el AS invalida todos los refresh tokens. Para probar este mecanismo:

  1. Enviar el refresh token y determinar si el AS entrega un access token.
  2. Repetir los pasos con el mismo refresh token hasta que sea invalidado.
  3. Usar el refresh token de la última respuesta de token

Si todos los refresh tokens que se emitieron al cliente para este propietario del recurso quedan invalidados, el AS cuenta con detección de robo de tokens.

Corrección

La mayoría de los ataques contra el AS de OAuth pueden mitigarse validando la existencia y el contenido de los parámetros durante el intercambio del código de autorización y de tokens.

Se deben restringir el período de validez y el uso permitido de credenciales como el código de autorización y el refresh token. Esto puede mitigar algunos tipos de ataques y también limita el uso de dichas credenciales por parte de un atacante, si llega a obtenerlas.

Una configuración adecuada de mitigaciones de seguridad como CORS, tokens anti-CSRF y cabeceras anti-clickjacking puede mitigar o limitar el impacto de los ataques.

  • Validar siempre que todos los parámetros estén presentes y validar sus valores.
  • Usar la extensión PKCE para proteger adecuadamente el intercambio del código de autorización y de tokens.
  • No permitir un mecanismo de respaldo (fallback) para funciones de seguridad como la extensión PKCE.
  • Restringir la duración de las credenciales.
  • Usar las credenciales una sola vez cuando sea posible, p. ej. el código de autorización.
  • Configurar las mitigaciones de seguridad disponibles como CORS, tokens anti-CSRF y cabeceras anti-clickjacking.
