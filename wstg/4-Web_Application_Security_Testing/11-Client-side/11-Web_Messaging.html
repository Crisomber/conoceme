Mensajería web (Web Messaging)

ID
WSTG-CLNT-11

Resumen

Web Messaging (también conocido como Cross Document Messaging) permite que aplicaciones que se ejecutan en dominios diferentes se comuniquen de manera segura. Antes de la introducción de la mensajería web, la comunicación entre orígenes distintos (entre iframes, pestañas y ventanas) estaba restringida por la política del mismo origen (same origin policy) y era impuesta por el navegador. Los desarrolladores utilizaban múltiples trucos para lograr estas tareas, y la mayoría eran principalmente inseguros.

Esta restricción dentro del navegador existe para evitar que un sitio web malicioso lea datos confidenciales de otros iframes, pestañas, etc.; sin embargo, hay algunos casos legítimos en los que dos sitios web de confianza necesitan intercambiar datos entre sí. Para satisfacer esta necesidad, se introdujo Cross Document Messaging en el borrador de especificación WHATWG HTML5 y se implementó en todos los navegadores principales. Permite comunicaciones seguras entre múltiples orígenes a través de iframes, pestañas y ventanas.

La API de mensajería introdujo el método postMessage(), con el que se pueden enviar mensajes de texto plano entre orígenes. Consta de dos parámetros: el mensaje y el dominio.

Existen algunas preocupaciones de seguridad al usar * como dominio, que se tratan más abajo. Para recibir mensajes, el sitio web receptor necesita añadir un nuevo manejador de eventos, que tiene los siguientes atributos:

  • Data, el contenido del mensaje entrante;
  • Origin del documento emisor; y
  • Source, la ventana de origen.

Este es un ejemplo del uso de la API de mensajería. Para enviar un mensaje:

iframe1.contentWindow.postMessage("Hello world","https://www.example.com");

Para recibir un mensaje:

window.addEventListener("message", handler, true);
function handler(event) {
    if(event.origin === 'chat.example.com') {
        /* process message (event.data) */
    } else {
        /* ignore messages from untrusted domains */
    }
}

Seguridad del origen

El origen está compuesto por un esquema, un nombre de host y un puerto. Identifica de forma única el dominio que envía o recibe el mensaje, y no incluye la ruta ni la parte de fragmento de la URL. Por ejemplo, https://example.com se considerará diferente de http://example.com porque el esquema del primero es https, mientras que el del segundo es http. Esto también aplica a servidores web que se ejecutan en el mismo dominio pero en puertos diferentes.

Objetivos de la prueba

  • Evaluar la seguridad del origen del mensaje.
  • Validar que se usan métodos seguros y que se valida su entrada.

Cómo probar

Examinar la seguridad del origen

Los evaluadores deben comprobar si el código de la aplicación filtra y procesa los mensajes provenientes de dominios de confianza. Dentro del dominio emisor, también hay que asegurarse de que el dominio receptor se indique explícitamente y de que no se use * como segundo argumento de postMessage(). Esta práctica podría introducir problemas de seguridad y podría conducir a que, en caso de una redirección o si el origen cambia por otros medios, el sitio web envíe datos a hosts desconocidos y, por tanto, filtre datos confidenciales a servidores maliciosos.

Si el sitio web no añade controles de seguridad para restringir los dominios u orígenes que pueden enviarle mensajes, es probable que introduzca un riesgo de seguridad. Los evaluadores deben examinar el código en busca de listeners de eventos de mensaje y obtener la función callback del método addEventListener para su análisis posterior. Siempre se deben verificar los dominios antes de manipular los datos.

Examinar la validación de entrada

Aunque en teoría el sitio web solo acepte mensajes de dominios de confianza, los datos deben tratarse igualmente como datos de origen externo y no confiables, y procesarse con los controles de seguridad adecuados. Los evaluadores deben analizar el código y buscar métodos inseguros, en particular donde los datos se evalúan mediante eval() o se insertan en el DOM mediante la propiedad innerHTML, lo que puede crear vulnerabilidades de XSS basado en DOM.

Análisis estático de código

Se debe analizar el código JavaScript para determinar cómo se implementa la mensajería web. En particular, a los evaluadores les debe interesar cómo el sitio web restringe los mensajes de dominios no confiables y cómo se manejan los datos incluso de dominios de confianza.

En este ejemplo, se necesita acceso para todos los subdominios (www, chat, forums, ...) dentro del dominio owasp.org. El código intenta aceptar cualquier dominio con .owasp.org:

window.addEventListener("message", callback, true);

function callback(e) {
    if(e.origin.indexOf(".owasp.org")!=-1) {
        /* process message (e.data) */
    }
}

La intención es permitir subdominios como:

  • www.owasp.org
  • chat.owasp.org
  • forums.owasp.org

Lamentablemente, esto introduce vulnerabilidades. Un atacante puede eludir fácilmente el filtro, ya que un dominio como www.owasp.org.attacker.com coincidirá.

Este es un ejemplo de código que carece de una comprobación de origen. Esto es muy inseguro, ya que aceptará entrada de cualquier dominio:

window.addEventListener("message", callback, true);

function callback(e) {
        /* process message (e.data) */
}

Este es un ejemplo con vulnerabilidades de validación de entrada que pueden conducir a un ataque de XSS:

window.addEventListener("message", callback, true);

function callback(e) {
        if(e.origin === "trusted.domain.com") {
            element.innerHTML= e.data;
        }
}

Un enfoque más seguro sería usar la propiedad innerText en lugar de innerHTML.
