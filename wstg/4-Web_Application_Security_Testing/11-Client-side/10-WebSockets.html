WebSockets

ID
WSTG-CLNT-10

Resumen

Tradicionalmente, el protocolo HTTP solo permite una petición/respuesta por conexión TCP. Asynchronous JavaScript and XML (AJAX) permite a los clientes enviar y recibir datos de forma asíncrona (en segundo plano, sin recargar la página) hacia y desde el servidor; sin embargo, AJAX requiere que el cliente inicie las peticiones y espere las respuestas del servidor (half-duplex).

WebSockets permite que el cliente o el servidor creen un canal de comunicación 'full-duplex' (bidireccional), lo que permite que cliente y servidor se comuniquen de manera verdaderamente asíncrona. Los WebSockets realizan su handshake inicial de actualización (upgrade) sobre HTTP y, a partir de ahí, toda la comunicación se lleva a cabo sobre canales TCP mediante el uso de tramas (frames). Para más información, consulte el WebSocket Protocol.

Origin

Es responsabilidad del servidor verificar la cabecera Origin en el handshake HTTP inicial de WebSocket. Si el servidor no valida la cabecera origin en el handshake inicial de WebSocket, el servidor WebSocket puede aceptar conexiones de cualquier origen. Esto podría permitir a los atacantes comunicarse con el servidor WebSocket entre dominios, dando lugar a problemas similares a CSRF. Consulte también A01:2025 Broken Access Control. El exploit de esta debilidad se denomina Cross-Site Websocket Hijacking (CSWH o CSWSH).

Confidencialidad e integridad

Los WebSockets pueden utilizarse sobre TCP sin cifrar o sobre TLS cifrado. Para usar WebSockets sin cifrar se utiliza el esquema de URI ws:// (puerto predeterminado 80); para usar WebSockets cifrados (TLS) se utiliza el esquema de URI wss:// (puerto predeterminado 443). Consulte también A04:2025 Cryptographic Failures.

Saneamiento de entrada

Como con cualquier dato proveniente de fuentes no confiables, los datos deben sanearse y codificarse adecuadamente. Consulte también A05:2025 Injection (incluye XSS).

Objetivos de la prueba

  • Identificar el uso de WebSockets.
  • Evaluar su implementación aplicando las mismas pruebas que en los canales HTTP normales.

Cómo probar

Pruebas de caja negra

  1. Identificar que la aplicación utiliza WebSockets.
    • Inspeccionar el código fuente del lado del cliente en busca del esquema de URI ws:// o wss://.
    • Usar las Herramientas para desarrolladores de Google Chrome para ver la comunicación WebSocket en Network.
    • Usar la pestaña WebSocket de ZAP.
  2. Origin.
    • Usando un cliente WebSocket (se puede encontrar uno en la sección Herramientas más abajo), intentar conectarse al servidor WebSocket remoto. Si se establece una conexión, es posible que el servidor no esté comprobando la cabecera origin del handshake de WebSocket.
  3. Confidencialidad e integridad.
    • Comprobar que la conexión WebSocket utiliza TLS para transportar información sensible wss://.
    • Comprobar la implementación de HTTPS en busca de problemas de seguridad (certificado válido, BEAST, CRIME, RC4, etc.). Consulte la sección Weak Transport Layer Security de esta guía.
  4. Autenticación.
    • Los WebSockets no manejan la autenticación; se deben realizar las pruebas normales de autenticación de caja negra. Consulte las secciones de Authentication Testing de esta guía.
  5. Autorización.
    • Los WebSockets no manejan la autorización; se deben realizar las pruebas normales de autorización de caja negra. Consulte las secciones de Authorization Testing de esta guía.
  6. Saneamiento de entrada.
    • Usar la pestaña WebSocket de ZAP para reproducir y realizar fuzzing de peticiones y respuestas WebSocket. Consulte la sección Injection Testing de esta guía.

Una vez que hemos identificado que la aplicación utiliza WebSockets (como se describió antes), podemos usar el Zed Attack Proxy (ZAP) para interceptar las peticiones y respuestas WebSocket. Luego, ZAP puede utilizarse para reproducir y realizar fuzzing de las peticiones/respuestas WebSocket.

Pruebas de caja gris

Las pruebas de caja gris son similares a las de caja negra. En las pruebas de caja gris, el pentester tiene un conocimiento parcial de la aplicación. La única diferencia es que puede disponerse de documentación de la API de la aplicación evaluada, que incluya las peticiones y respuestas WebSocket esperadas.
