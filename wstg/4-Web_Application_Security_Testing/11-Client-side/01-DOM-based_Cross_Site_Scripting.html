Cross-Site Scripting basado en DOM

ID
WSTG-CLNT-01

Resumen

El cross-site scripting basado en DOM es el nombre habitual de los errores de XSS que resultan de que el contenido activo del lado del navegador en una página, normalmente JavaScript, obtiene entrada del usuario a través de una fuente (source) y la utiliza en un sumidero (sink), lo que conduce a la ejecución de código inyectado. Este documento solo trata los errores de JavaScript que conducen a XSS.

El DOM, o Document Object Model, es el formato estructural utilizado para representar documentos en un navegador. El DOM permite que scripts dinámicos como JavaScript hagan referencia a componentes del documento, como un campo de formulario o una cookie de sesión. El navegador también utiliza el DOM por motivos de seguridad, por ejemplo para impedir que scripts de distintos dominios obtengan las cookies de sesión de otros dominios. Una vulnerabilidad de XSS basado en DOM puede ocurrir cuando el contenido activo, como una función de JavaScript, es modificado por una petición especialmente construida de manera que un elemento del DOM pueda ser controlado por un atacante.

No todos los errores de XSS requieren que el atacante controle el contenido devuelto por el servidor; también pueden abusar de malas prácticas de programación en JavaScript para lograr los mismos resultados. Las consecuencias son las mismas que las de un fallo de XSS típico; solo cambia el medio de entrega.

En comparación con otros tipos de vulnerabilidades de cross site scripting (reflejado y almacenado, en los que el servidor recibe un parámetro sin sanear y lo devuelve al usuario, donde se ejecuta en el contexto de su navegador), una vulnerabilidad de XSS basado en DOM controla el flujo del código utilizando elementos del Document Object Model (DOM) junto con código creado por el atacante para alterar dicho flujo.

Por su naturaleza, las vulnerabilidades de XSS basado en DOM pueden ejecutarse en muchos casos sin que el servidor pueda determinar qué se está ejecutando realmente. Esto puede volver ineficaces muchas de las técnicas generales de filtrado y detección de XSS frente a estos ataques.

Este ejemplo hipotético utiliza el siguiente código del lado del cliente:

<script>
document.write("Site is at: " + document.location.href + ".");
</script>

Un atacante puede añadir #<script>alert('xss')</script> a la URL de la página afectada, lo que, al ejecutarse, mostrará el cuadro de alerta. En este caso, el código añadido no se enviaría al servidor, ya que todo lo que sigue al carácter # no es tratado por el navegador como parte de la consulta, sino como un fragmento. En este ejemplo, el código se ejecuta de inmediato y la página muestra una alerta con "xss". A diferencia de los tipos más comunes de cross site scripting (reflejado y almacenado, en los que el código se envía al servidor y luego de vuelta al navegador), este se ejecuta directamente en el navegador del usuario sin contacto con el servidor.

Las consecuencias de los fallos de XSS basado en DOM son tan amplias como las de las formas más conocidas de XSS, e incluyen la obtención de cookies, la inyección de más scripts maliciosos, etc., por lo que deben tratarse con la misma gravedad.

Objetivos de la prueba

  • Identificar los sumideros (sinks) del DOM.
  • Construir payloads (cargas útiles) correspondientes a cada tipo de sumidero.

Cómo probar

Las aplicaciones JavaScript difieren de manera significativa de otros tipos de aplicaciones porque con frecuencia son generadas dinámicamente por el servidor. Para entender qué código se está ejecutando, hay que rastrear (crawl) el sitio web evaluado para determinar todas las instancias de JavaScript que se ejecutan y los lugares donde se acepta entrada del usuario. Muchos sitios web dependen de grandes bibliotecas de funciones, que a menudo abarcan cientos de miles de líneas de código y no han sido desarrolladas internamente. En estos casos, las pruebas de arriba hacia abajo suelen ser la única opción viable, ya que muchas funciones de bajo nivel nunca se utilizan, y analizarlas para determinar cuáles son sumideros consumirá más tiempo del que normalmente se tiene. Lo mismo puede decirse de las pruebas de arriba hacia abajo si de entrada no se identifican las entradas o su ausencia.

La entrada del usuario se presenta en dos formas principales:

  • Entrada escrita en la página por el servidor de una manera que no permite XSS directo, y
  • Entrada obtenida de objetos de JavaScript del lado del cliente.

A continuación se muestran dos ejemplos de cómo el servidor puede insertar datos en JavaScript:

var data = "<escaped data from the server>";
var result = someFunction("<escaped data from the server>");

A continuación se muestran dos ejemplos de entrada proveniente de objetos de JavaScript del lado del cliente:

var data = window.location;
var result = someFunction(window.referrer);

Aunque hay poca diferencia en el código JavaScript respecto a cómo se obtienen, es importante tener en cuenta que cuando la entrada se recibe a través del servidor, este puede aplicar a los datos cualquier transformación que desee. En cambio, las transformaciones que realizan los objetos de JavaScript son bastante bien conocidas y están documentadas. Si someFunction en el ejemplo anterior fuera un sumidero, la explotabilidad en el primer caso dependería del filtrado realizado por el servidor, mientras que en el segundo dependería de la codificación que haga el navegador sobre el objeto window.referrer. Stefano Di Paulo ha escrito un excelente artículo sobre lo que devuelven los navegadores al solicitar los distintos elementos de una URL mediante los atributos document y location.

Además, JavaScript suele ejecutarse fuera de los bloques <script>, como lo demuestran los muchos vectores que en el pasado han permitido eludir filtros de XSS. Al rastrear la aplicación, es importante tomar nota del uso de scripts en lugares como los manejadores de eventos y los bloques CSS con atributos expression. Asimismo, hay que tener en cuenta que cualquier objeto CSS o script alojado fuera del sitio deberá evaluarse para determinar qué código se ejecuta.

Las pruebas automatizadas tienen un éxito muy limitado para identificar y validar XSS basado en DOM, ya que normalmente identifican XSS enviando un payload específico e intentando observarlo en la respuesta del servidor. Esto puede funcionar bien en el ejemplo sencillo que se muestra a continuación, donde el parámetro message se refleja al usuario:

<script>
var pos=document.URL.indexOf("message=")+5;
document.write(document.URL.substring(pos,document.URL.length));
</script>

Sin embargo, puede no detectarse en el siguiente caso artificioso:

<script>
var navAgt = navigator.userAgent;

if (navAgt.indexOf("MSIE")!=-1) {
        document.write("You are using IE as a browser and visiting site: " + document.location.href + ".");
}
else
{
    document.write("You are using an unknown browser.");
}
</script>

Por esta razón, las pruebas automatizadas no detectarán las áreas que puedan ser susceptibles a XSS basado en DOM, a menos que la herramienta de pruebas pueda realizar un análisis adicional del código del lado del cliente.

Por lo tanto, se deben realizar pruebas manuales, que pueden llevarse a cabo examinando las áreas del código donde se hace referencia a parámetros que pudieran ser útiles para un atacante. Ejemplos de tales áreas son los lugares donde se escribe código dinámicamente en la página, así como otros donde se modifica el DOM o incluso donde se ejecutan scripts directamente.
