Inyección de plantillas del lado del cliente

ID
WSTG-CLNT-15

Resumen

La Client-Side Template Injection (CSTI), también conocida como DOM-based Template Injection, surge cuando las aplicaciones que usan frameworks del lado del cliente (como Angular, Vue.js o Alpine.js) incrustan dinámicamente entrada del usuario en el DOM de la página web. Si esta entrada se incrusta en una expresión de plantilla o es interpretada por el motor de plantillas del framework, un atacante puede inyectar directivas maliciosas.

A diferencia de la Server-Side Template Injection (SSTI), en la que la plantilla se renderiza en el servidor, la CSTI ocurre por completo dentro del navegador del usuario. Cuando el framework recorre el DOM en busca de contenido dinámico, puede ejecutar las expresiones de plantilla inyectadas. Esto suele conducir a Cross-Site Scripting (XSS), pero el método de inyección y explotación difiere del XSS estándar porque el payload debe seguir la sintaxis específica del motor de plantillas (p. ej., {{ 7*7 }}).

Esta vulnerabilidad es particularmente común en las Single Page Applications (SPA), donde los desarrolladores pueden depender del renderizado del lado del cliente sin una separación estricta de contextos.

Objetivos de la prueba

  • Identificar el framework del lado del cliente y su versión utilizados por la aplicación.
  • Detectar los puntos de inyección donde la entrada del usuario se refleja en el DOM y es procesada por el motor de plantillas.
  • Evaluar si la inyección permite la ejecución arbitraria de JavaScript (XSS) mediante la sintaxis de plantillas.

Cómo probar

Pruebas de caja negra

Identificación del framework

El primer paso es identificar si se usa un framework del lado del cliente. Los evaluadores deben buscar atributos específicos en el código fuente HTML o cabeceras de respuesta HTTP específicas.

  • Angular: Buscar atributos como ng-app, ng-model o ng-bind.
  • Vue.js: Buscar atributos que comiencen con v-, como v-if, v-for, o la presencia del objeto global Vue en la consola.
  • Alpine.js: Buscar x-data, x-html.

Detección de la inyección

Para detectar CSTI, los evaluadores deben inyectar caracteres sintácticamente significativos para el motor de plantillas. La sintaxis más común de interpolación en muchos frameworks son las dobles llaves {{ }}.

Una operación aritmética sencilla es la sonda estándar. Si la aplicación evalúa la operación, es vulnerable.

Sonda genérica:

Inject the string: {{ 7*7 }}
  • Si la aplicación muestra 49, hay CSTI.
  • Si la aplicación muestra {{ 7*7 }}, probablemente no es vulnerable o existe un escapado contextual estricto.

Angular

Angular actúa sobre el DOM. Si un atacante puede inyectar en el DOM una cadena que contenga expresiones de Angular antes de que Angular se inicialice (bootstrap) o lo compile, la expresión se ejecutará.

Payloads para detección:

  • {{ 7*7 }}
  • {{ constructor.constructor('alert(1)')() }}

En las versiones antiguas de Angular (1.x), el motor de plantillas funciona en un sandbox. La explotación requiere salir de este sandbox. La complejidad del payload depende en gran medida de la versión específica.

Payload de ejemplo (evasión del sandbox de Angular 1.5.x):

{{x={'y':''.constructor.prototype};x['y'].charAt=[].join;$eval('x=alert(1)');}}

Vue.js

Vue.js también es susceptible si los desarrolladores usan la directiva v-html con entrada del usuario o si montan una instancia de Vue sobre un elemento del DOM que ya contiene HTML controlado por el usuario.

Payloads para detección:

  • {{ 7*7 }}

Payload de ejemplo (Vue.js 2.x):

{{_v.constructor('alert(1)')()}}

Alpine.js

Alpine.js depende en gran medida de los atributos del DOM. Si un atacante puede controlar el nombre de un atributo o inyectar en una directiva, puede ejecutar código.

Payload de ejemplo:

<div x-data="" x-html="'<img src=x onerror=alert(1)>'"></div>

Pruebas de caja gris

Revisión de código

En un escenario de caja gris, los evaluadores verifican cómo se maneja la entrada del usuario en el código del frontend. La clave es identificar dónde se usan "sinks" que interpretan HTML o sintaxis de plantillas con fuentes "contaminadas" (entrada del usuario).

Sinks de Angular: Buscar usos de $compile o ng-bind-html. Si se usa ng-bind-html, comprobar si $sce (Strict Contextual Escaping) está configurado correctamente o si se usa $sce.trustAsHtml() sobre datos no confiables.

// Vulnerable example in Angular
$scope.htmlSnippet = $sce.trustAsHtml(userInput);

Sinks de Vue.js: Buscar la directiva v-html. Usar v-html sobre contenido proporcionado por el usuario es una causa principal de CSTI/XSS en Vue.

<div v-html="userProvidedComment"></div>

Sinks de React: Aunque React es generalmente más seguro respecto a la inyección de plantillas porque no recorre el DOM en busca de plantillas (JSX se compila), el uso indebido de dangerouslySetInnerHTML permite XSS basado en DOM, que es el equivalente en React del perfil de riesgo que se analiza aquí.

// Vulnerable example in React
<div dangerouslySetInnerHTML={{__html: userContent}} />

Revisión de la configuración

Hay que revisar específicamente las cabeceras de Content Security Policy (CSP). Una CSP robusta puede mitigar el impacto de la CSTI al restringir desde dónde se pueden cargar scripts o al impedir la ejecución de scripts en línea (incluidos los generados por motores de plantillas).

Hay que buscar unsafe-eval en la CSP. Muchos motores de plantillas (especialmente los más antiguos) requieren unsafe-eval para compilar plantillas dinámicamente. Si unsafe-eval está presente, los ataques de CSTI son significativamente más fáciles de explotar.

Corrección

  • Evitar renderizar entrada del usuario como HTML: Siempre que sea posible, usar directivas seguras que traten la entrada solo como texto.
    • Angular: Usar ng-bind en lugar de ng-bind-html.
    • Vue: Usar v-text o llaves {{ }} (que escapan HTML automáticamente) en lugar de v-html.
    • React: Evitar dangerouslySetInnerHTML.
  • Saneamiento: Si se requiere renderizar HTML, usar una biblioteca de saneamiento dedicada (como DOMPurify) para eliminar etiquetas y atributos peligrosos antes de pasar los datos al framework.
  • Content Security Policy (CSP): Implementar una CSP estricta que deshabilite unsafe-eval y restrinja las fuentes de scripts.
  • Usar compilación offline: Para frameworks como Vue o React, es preferible usar pasos de compilación (webpack, vite) que compilen las plantillas con antelación en lugar de usar el compilador en tiempo de ejecución que analiza el contenido del DOM.

Herramientas

  • DOMPurify: A DOM-only, super-fast, uber-tolerant XSS sanitizer for HTML, MathML, and SVG.
