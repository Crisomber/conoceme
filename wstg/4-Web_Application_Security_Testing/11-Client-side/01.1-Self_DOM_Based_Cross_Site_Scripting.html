Cross-Site Scripting basado en DOM autoinfligido (Self DOM-Based XSS)

Resumen

El Self DOM-Based Cross-Site Scripting es un ataque específico que requiere conocimiento previo del cross site scripting basado en DOM e ingeniería social exitosa. El término "self" hace referencia a que el usuario necesita inyectar el payload en el campo de entrada y, por tanto, ejecuta la vulnerabilidad él mismo. La vulnerabilidad es además específica porque la Content Security Policy (CSP) del sitio web puede bloquear la ejecución de scripts.

Este escenario utilizará el término "sink" (sumidero) de la siguiente manera: en computación, un sink, event sink o data sink es una clase o función diseñada para recibir entrada o eventos de otro objeto o función. Por lo tanto, para encontrar posibles vulnerabilidades primero hay que identificar los sinks de la aplicación que se desea probar.

Cómo probar

El proceso de pruebas de Self DOM-Based cross site scripting es el siguiente:

  1. Buscar sinks vulnerables que permitan entrada del usuario.
  2. Una vez identificado un posible sink, se puede insertar un payload.
  3. Revisar el registro de errores en las herramientas de desarrollo del navegador para ver el resultado y extraer conclusiones.
  4. Comprobar si un atacante podría convencer a un usuario de insertar el payload sin que se requieran conocimientos técnicos extensos.

Ejemplo

Este ejemplo específico proviene de este reporte de HackerOne.

En el ejemplo, la siguiente función de JavaScript se ejecuta en el sitio web https://example.com.

//Marketo Form Code
function strip(html) {
    var tmp = document.createElement("DIV");
    tmp.innerHTML = html;
    return tmp.textContent || tmp.innerText || "";
}

$('form').submit(function() {
    $('textarea').val(function() {
        return strip($(this).val());
    });
});

El abuso de esta funcionalidad puede describirse de la siguiente manera:

  1. El manejador del evento submit pasa el valor actual de cualquier elemento textarea a la función strip.
  2. Esta función crea un nuevo elemento div y asigna el valor proporcionado a la propiedad innerHTML.
  3. En el último paso devuelve la propiedad textContent del div resultante.

Este tipo de código se utiliza normalmente para eliminar etiquetas HTML de una cadena, ya que la propiedad textContent contiene la cadena que el navegador renderizó al analizar el HTML. Este método es inherentemente inseguro porque utiliza innerHTML. Cuando se proporciona entrada del usuario a la propiedad innerHTML, el navegador web la analiza y, por tanto, puede conducir a la ejecución de JavaScript malicioso.

Se puede utilizar el siguiente payload para probar la vulnerabilidad.<img src=x onerror=alert(1) />

La consola de desarrollo mostraría dos errores: uno que indica que se solicitó https://www.example.com/x y devolvió un 404 (debido al atributo src de la etiqueta img). Otro que informaba de una violación de la CSP del sitio web.

Este segundo error ocurrió porque el navegador intenta ejecutar el código JavaScript del atributo onerror, pero la CSP del sitio web impidió la ejecución. Al realizar las mismas acciones en un navegador con la CSP deshabilitada, el JavaScript del atributo onerror se ejecutó.

Un atacante podría explotar esta vulnerabilidad convenciendo a un usuario de pegar un payload malicioso en el campo 'message' del formulario de contacto y luego hacer clic en el botón "send message". Este ataque podría potenciarse convenciendo al usuario de utilizar una versión de navegador que no soporte CSP.
