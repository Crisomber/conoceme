Reconocimiento de WebAssembly

ID
WSTG-WASM-01

Resumen

WebAssembly (Wasm) es un formato de instrucciones binarias que se entrega al navegador como un módulo compilado. Como a primera vista no es legible para las personas, a menudo se trata como algo opaco y, por lo tanto, más seguro que JavaScript. En la práctica, igual que los binarios de escritorio tradicionales, los módulos Wasm pueden localizarse, identificarse (fingerprinting) y analizarse.

El reconocimiento es el primer paso de las pruebas de seguridad de WebAssembly. Esta fase se centra en localizar los módulos Wasm dentro de la aplicación web, identificar la cadena de herramientas (toolchain) que los produjo, comprobar si hay artefactos de depuración expuestos, como source maps, DWARF (Debugging With Attributed Record Formats) y la sección name, y mapear la superficie de ataque de la infraestructura (URLs, endpoints de API, hosts) que los módulos revelan.

Esta fase solo recopila información sobre el objetivo. Se detiene deliberadamente antes de descompilar el código, leer su lógica o ejecutar el módulo en un depurador. Reunir con éxito esta inteligencia proporciona el mapa fundamental necesario para las fases de prueba posteriores.

Este capítulo se centra en los módulos Wasm entregados por el navegador. El reconocimiento de Wasm que se ejecuta fuera del navegador (runtimes WASI, plataformas de borde o serverless) es distinto, porque los módulos normalmente no se sirven al cliente y deben obtenerse por otros medios. Véase la Visión general de las pruebas de WebAssembly para la distinción.

Objetivos de la prueba

  • Encontrar todos los módulos WebAssembly que carga la aplicación objetivo, incluidos los que no se llaman .wasm, los comprimidos, los de carga diferida (lazy-loaded), los cargados mediante fetch e instanciación manual, o los incrustados en JavaScript.
  • Identificar la cadena de herramientas del compilador y el lenguaje de origen (p. ej., C/C++, Rust, Go, .NET) a partir de los metadatos de las secciones, las importaciones, las exportaciones y el código pegamento (glue code).
  • Detectar artefactos de depuración expuestos: source maps, información DWARF y la sección personalizada name.
  • Mapear la superficie de ataque de la infraestructura extrayendo URLs incrustadas, endpoints de API y nombres de host o direcciones IP internos.

Cómo probar

Localización de módulos WebAssembly

Los binarios de WebAssembly son cargados por JavaScript, normalmente de forma asíncrona. La forma más directa de descubrirlos es mediante las herramientas para desarrolladores del navegador y la inspección del JavaScript del lado del cliente.

Herramientas para desarrolladores del navegador

  1. Abrir las Herramientas para desarrolladores e ir a la pestaña Network.
  2. Recargar la aplicación objetivo e interactuar con ella para que se activen las funciones de carga diferida.
  3. En Chrome y Edge, seleccionar el filtro Wasm para mostrar solo las peticiones de WebAssembly. Firefox no tiene un filtro dedicado a Wasm, por lo que hay que buscar .wasm en la lista de peticiones y revisar la columna de tipo de contenido en busca de application/wasm.
  4. Revisar también los Web Workers y los Service Workers. Son lugares comunes donde se carga Wasm, y su tráfico puede aparecer bajo destinos separados en las DevTools.

Inspección del código JavaScript

Si la aplicación usa carga diferida o empaquetado (bundling), hay que buscar en los archivos JavaScript las API de carga de WebAssembly:

  • WebAssembly.instantiate / WebAssembly.instantiateStreaming
  • WebAssembly.compile / WebAssembly.compileStreaming
  • new WebAssembly.Module / new WebAssembly.Instance

Las aplicaciones no siempre cargan Wasm mediante una URL .wasm simple. Un módulo puede obtenerse con fetch o XMLHttpRequest y luego instanciarse manualmente a partir de un ArrayBuffer, descomprimirse en JavaScript antes de la instanciación o ensamblarse a partir de varios fragmentos. En estos casos, la pestaña Network solo muestra una petición genérica, por lo que buscar las API de carga anteriores es el enfoque más fiable.

Si un módulo se crea en tiempo de ejecución y nunca aparece como una petición descargable, se puede capturar en el momento de la instanciación. Por ejemplo, un script inyectado antes de que se ejecute el código de la aplicación (usando Local Overrides de las DevTools, un snippet ejecutado antes de la carga de la página o una extensión de user-scripts) puede envolver la API y conservar una copia de los bytes:

const _instantiate = WebAssembly.instantiate;
window.__wasmDumps = [];
WebAssembly.instantiate = function (source, ...rest) {
  if (source instanceof ArrayBuffer || ArrayBuffer.isView(source)) {
    window.__wasmDumps.push(new Uint8Array(source.buffer || source).slice());
  }
  return _instantiate.call(this, source, ...rest);
};

El mismo enfoque de envoltura se aplica a WebAssembly.compile, WebAssembly.Module y las variantes de streaming (que reciben una Response en lugar de bytes y requieren clonarla). Los bytes capturados pueden guardarse luego en un archivo para los pasos de análisis siguientes.

Módulos incrustados

Los binarios Wasm también pueden incrustarse directamente en JavaScript para evitar una petición HTTP adicional. Hay que buscar:

  • Cadenas Base64 grandes que se pasan mediante atob o un decodificador personalizado a un Uint8Array.
  • URIs data: como data:application/octet-stream;base64,.
  • Literales de cadena muy largos, que a menudo contienen muchos caracteres escapados o no ASCII, que una función auxiliar decodifica al inicio y pasa a una de las API anteriores.

Las compilaciones de Emscripten con la opción SINGLE_FILE hacen esto. Las versiones recientes de Emscripten incrustan el binario con una codificación de cadena UTF-8 personalizada de forma predeterminada (Base64 se usa solo si SINGLE_FILE_BINARY_ENCODE está deshabilitado), por lo que el segundo y el tercer patrón son los que con más probabilidad se verán en las compilaciones actuales. Véase la Emscripten settings reference para más detalles. Como la codificación difiere entre versiones, la captura en el momento de la instanciación mostrada arriba suele ser más fácil que decodificar la cadena a mano.

Identificación de archivos Wasm por su contenido

No hay que confiar únicamente en la extensión del archivo ni en el tipo MIME. Los módulos pueden servirse como .bin, .dat o sin extensión, o comprimidos como .wasm.gz o .wasm.br. Los archivos comprimidos deben descomprimirse primero (por ejemplo con gunzip o brotli -d) antes de poder comprobar la cabecera. Los navegadores descomprimen de forma transparente las respuestas con Content-Encoding, por lo que un archivo guardado desde las DevTools suele estar ya descomprimido, mientras que uno obtenido con una herramienta de línea de comandos puede no estarlo.

Todo binario Wasm comienza con la misma cabecera de 8 bytes (los bytes mágicos \0asm seguidos de la versión):

00 61 73 6D 01 00 00 00

Un archivo descargado puede comprobarse con file module.bin o od -An -tx1 -N8 module.bin. En el código fuente JavaScript, la misma cabecera aparece como el prefijo Base64 AGFzbQ.

Si un archivo que la aplicación carga como módulo no comienza con estos bytes y no está comprimido, la aplicación puede codificarlo o cifrarlo y decodificarlo en JavaScript antes de cargarlo. En ese caso, hay que leer la rutina de decodificación en el código pegamento y aplicarla al archivo descargado para obtener el binario real.

Una vez confirmada la cabecera, se comprueba que el módulo sea válido con wasm-validate del WebAssembly Binary Toolkit (WABT):

wasm-validate module.wasm

Si la validación falla porque el módulo usa características más recientes del lenguaje (por ejemplo, recolección de basura), se reintenta con --enable-all.

Hay que tener en cuenta que WebAssembly.instantiateStreaming y WebAssembly.compileStreaming requieren que el servidor envíe el tipo MIME application/wasm, por lo que un archivo Wasm servido con un tipo distinto puede indicar una mala configuración del servidor.

Inspección de secciones personalizadas

Una vez descargado un módulo, se listan sus secciones con wasm-objdump (parte de WABT). La mayoría de los pasos de reconocimiento restantes se responden con esta única salida:

wasm-objdump -h module.wasm

Hay que buscar las siguientes secciones personalizadas:

Sección Qué revela Tratada en
producers Lenguaje de origen y herramientas usadas para construir el módulo Identificación del compilador y la cadena de herramientas
sourceMappingURL URL de un source map externo Source Maps
.debug_*, external_debug_info Información de depuración DWARF, incrustada o en un archivo separado Información de depuración DWARF
name Nombres originales de funciones y variables Sección name

Las secciones personalizadas son opcionales y pueden eliminarse en cualquier momento. Es común que un módulo de una compilación de producción no tenga ninguna sección personalizada.

Identificación del compilador y la cadena de herramientas

Saber si un módulo fue compilado desde C/C++, Rust, Go u otro lenguaje ayuda al evaluador a comprender su modelo de memoria, sus convenciones de llamada, su comportamiento en tiempo de ejecución y el código pegamento de JavaScript esperado.

Esta información también puede ayudar a priorizar las pruebas de seguridad posteriores. Por ejemplo, una cadena de herramientas de lenguaje nativo puede indicar que merecen un examen más detallado la seguridad de memoria, el manejo de la memoria lineal, las operaciones inseguras y las interacciones en el límite entre el código nativo y JavaScript, mientras que las cadenas de herramientas específicas de un framework pueden señalar sus correspondientes superficies de runtime e integración.

La identificación del compilador debe usarse para guiar la selección y priorización de pruebas, no como evidencia de que exista una vulnerabilidad concreta.

Detección automatizada

Herramientas como WASM-Hunter pueden proporcionar una identificación rápida del compilador o la cadena de herramientas analizando el binario Wasm en busca de cadenas características, símbolos, importaciones y marcadores de runtime.

wasm-hunter -compiler -i target_module.wasm

La identificación automatizada es heurística y no definitiva. Los módulos optimizados, despojados (stripped) u ofuscados pueden eliminar o alterar los marcadores usados para la detección, por lo que el resultado debe tratarse como una clasificación inicial y verificarse manualmente cuando sea posible.

Identificación manual

Cuando la detección automatizada no está disponible o produce un resultado incierto, hay que inspeccionar múltiples indicadores en lugar de confiar en una sola firma.

La sección personalizada producers suele ser un indicador directo útil, porque las cadenas de herramientas pueden registrar los lenguajes y herramientas usados para construir el módulo, como clang, rustc o wasm-bindgen. Se puede inspeccionar con wasm-objdump de WABT:

wasm-objdump -s -j producers module.wasm

La sección producers es opcional y con frecuencia falta en las compilaciones optimizadas o endurecidas. En ese caso, hay que examinar las importaciones, las exportaciones, las cadenas de runtime, el código pegamento de JavaScript asociado y los artefactos de compilación circundantes. Las importaciones y exportaciones pueden listarse con wasm-objdump -x -j Import module.wasm y wasm-objdump -x -j Export module.wasm. Los indicadores individuales deben tratarse como pistas y, cuando sea posible, confirmar la identificación con un segundo indicador independiente:

  • Emscripten (C/C++): Importaciones como emscripten_resize_heap, __syscall_* o invoke_*. Un módulo de importación genérico env no es evidencia suficiente porque otras cadenas de herramientas también lo usan. Las compilaciones de release suelen minificar los nombres de las importaciones (por ejemplo, un módulo llamado a), lo que oculta estos patrones.
  • WASI: Un módulo de importación como wasi_snapshot_preview1 o wasi_unstable indica una compilación que usa llamadas al sistema WASI. No identifica el lenguaje de origen, y los módulos de Emscripten también lo importan, por lo que deben comprobarse marcadores adicionales.
  • Rust (wasm-bindgen): Importaciones o exportaciones que comienzan con __wbindgen_ o __wbg_, un módulo de importación llamado wbg y un archivo generado *_bg.wasm junto a un archivo de código pegamento *_bg.js. La sección producers normalmente lista rustc y wasm-bindgen.
  • Go: El archivo de código pegamento wasm_exec.js, un módulo de importación llamado gojs (Go 1.21 y posteriores) o go (versiones anteriores), y cadenas como runtime.wasmExit, runtime.gopanic o Go build ID. Las versiones recientes de Go también añaden una sección personalizada llamada go:buildid.
  • .NET (Blazor WebAssembly): Un archivo dotnet.wasm o dotnet.native.wasm cargado desde una ruta _framework/. Antes de .NET 10, también hay un manifiesto blazor.boot.json. A partir de .NET 10, la configuración de arranque se incorpora en línea en dotnet.js.
  • AssemblyScript: Las compilaciones de release casi no tienen marcadores: normalmente una única importación env.abort y una exportación memory. Las compilaciones de depuración conservan rutas como ~lib/rt/ en la sección name, y los módulos construidos con --exportRuntime exportan funciones como __new y __pin.

Ningún marcador individual debe considerarse concluyente. La identificación más sólida surge de combinar múltiples indicadores independientes, como los metadatos de producers, los símbolos de runtime, las importaciones y exportaciones, el código pegamento y los artefactos de despliegue.

El stripping y la ofuscación pueden anular la mayoría de los marcadores anteriores. Eliminar las secciones producers y name, minificar los nombres de importaciones y exportaciones y eliminar mediante tree-shaking los auxiliares de runtime son prácticas comunes en las compilaciones de release, y es posible que el evaluador no pueda identificar la cadena de herramientas en absoluto. Un resultado no concluyente es un resultado válido de esta fase y debe registrarse como tal, en lugar de adivinarse.

Pruebas de source maps y símbolos de depuración

A veces los desarrolladores dejan artefactos de depuración en las compilaciones de producción. Esto es un hallazgo en sí mismo y además proporciona al evaluador una gran cantidad de contexto.

Source Maps

Igual que en JavaScript, un módulo WebAssembly puede hacer referencia a un source map externo. La referencia se almacena en una sección personalizada llamada sourceMappingURL, cuyo contenido es la URL del archivo del mapa (por ejemplo module.wasm.map).

Si la sección no está presente, hay que solicitar directamente ubicaciones probables como module.wasm.map. El código pegamento de JavaScript también puede hacer referencia a su propio source map, mediante un comentario //# sourceMappingURL= o una cabecera de respuesta SourceMap. Ese mapa describe el JavaScript y no el módulo, pero aun así puede exponer archivos fuente originales.

Si un mapa es accesible, se abre la pestaña Sources (o Debugger) del navegador. El navegador analiza el mapa y muestra la estructura original de archivos. Cuánto se recupera depende del mapa:

  • Si el mapa contiene sourcesContent, o los archivos fuente referenciados se pueden descargar, se puede leer el código fuente original.
  • De lo contrario, solo se recuperan las rutas de archivo y las asignaciones de línea, lo cual aun así revela la estructura del proyecto, los nombres de dependencias y las rutas de los desarrolladores.

Información de depuración DWARF

Para C, C++ y Rust, los datos de depuración se entregan con más frecuencia como DWARF que como source map. En la etapa de reconocimiento, solo hay que comprobar si está presente: ya sea como secciones .debug_* dentro del módulo, o como una sección external_debug_info que apunta a un archivo de depuración separado ("split DWARF") que puede ser descargable desde el servidor.

Sección name

Incluso cuando se eliminan los source maps y DWARF, a veces se deja la sección personalizada name. Contiene los nombres originales de las funciones y, en algunos casos, de las variables locales. Hay que comprobar su presencia en el listado de secciones y volcarla con:

wasm-objdump -x -j name module.wasm

Los nombres de Rust y C++ suelen estar mangled. Nombres recuperados como check_license_key o encrypt_password proporcionan objetivos inmediatos para análisis posteriores.

Mapeo de la superficie de ataque (URLs, API e IP)

Los módulos WebAssembly suelen contener detalles de infraestructura codificados de forma fija (hardcoded). Ejemplos típicos incluyen:

  • URLs base y rutas de API de backend (https://api.example.com/v2/, /internal/admin/).
  • WebSocket y otros endpoints no HTTP (wss://realtime.example.com).
  • Nombres de host de staging, desarrollo o internos (build-server.corp.local, staging-api.example.com).
  • Direcciones IP privadas y puertos (10.x.x.x, 172.16-31.x.x, 192.168.x.x).
  • URLs de servicios de terceros, como servidores de analítica, de comprobación de licencias o de actualización.

Extraer esta información de enrutamiento permite mapear la arquitectura de backend de la aplicación y puede revelar endpoints que no se mencionan en ninguna parte del JavaScript visible.

Extracción automatizada

wasm-hunter puede automatizar esta extracción a partir de un archivo local o de una URL remota:

wasm-hunter -i target_module.wasm

Extracción manual

La misma información se puede recopilar con herramientas genéricas, lo cual es útil cuando no se dispone de una herramienta dedicada. Los literales de cadena se almacenan en los segmentos de datos del módulo, por lo que pueden buscarse directamente en el binario:

# URLs and endpoints
strings -n 6 module.wasm | grep -Eio '(https?|wss?|ftp)://[^[:space:]"'"'"']+'

# Common internal hostname patterns and API paths
strings -n 6 module.wasm | grep -Ei '\.(internal|local|corp|lan)\b|/api/|/v[0-9]+/'

# Private IPv4 addresses
strings -n 6 module.wasm | grep -Eo '\b(10\.[0-9]{1,3}|172\.(1[6-9]|2[0-9]|3[01])|192\.168)\.[0-9]{1,3}\.[0-9]{1,3}\b'

# Same search for UTF-16 strings (used by some toolchains such as .NET)
strings -n 6 -el module.wasm | grep -Ei 'https?://'

Los segmentos de datos sin procesar también pueden volcarse para su revisión manual con wasm-objdump -s -j Data module.wasm. Las cadenas que están comprimidas, cifradas o ensambladas en tiempo de ejecución no aparecerán en estos resultados, y también deben recopilarse las cadenas que se encuentren en el código pegamento de JavaScript o en archivos de configuración acompañantes.

(Nota: Extraer del binario credenciales, tokens y claves criptográficas reales queda fuera del alcance del reconocimiento.)

Corrección

  • No enviar a producción source maps, datos DWARF ni archivos de depuración divididos. Mantener la información de depuración y de símbolos en un servidor de símbolos restringido o en otro entorno controlado.
  • Eliminar de las compilaciones de release la depuración y los metadatos de compilación innecesarios. Por ejemplo, wasm-strip (WABT) elimina todas las secciones personalizadas, y wasm-opt --strip-debug --strip-producers (Binaryen) elimina la información de depuración y la sección producers. Configurar el compilador y el enlazador (linker) para producir artefactos de release despojados (stripped) cuando se admita.
  • No codificar de forma fija (hardcode) nombres de host internos, direcciones IP, credenciales ni endpoints sensibles en los módulos entregados al cliente. Hay que tratar como público todo lo que se entrega al navegador.
  • Servir Wasm con el tipo MIME correcto application/wasm, y verificar que los source maps, los artefactos de depuración y otros archivos de compilación que no son de producción no sean accesibles públicamente.

Herramientas

  • WebAssembly Binary Toolkit (WABT) - Incluye wasm-objdump para listar secciones, importaciones, exportaciones y nombres, y wasm-strip. También proporciona wasm2wat y wasm-decompile, que pertenecen a fases de análisis posteriores.
  • wasm-tools - Kit de herramientas de la Bytecode Alliance con un volcado de secciones y estructura (wasm-tools objdump) y un analizador que puede servir como alternativa a WABT.
  • Binaryen - Proporciona wasm-opt, usado para eliminar la información de depuración y la sección producers, y wasm-dis para el desensamblado.
  • WASM-Hunter - Herramienta de análisis estático para el mapeo de la superficie de ataque y la detección rápida de compilador, con análisis directo de URL remotas.
  • strings, od, file, grep - Utilidades genéricas suficientes para comprobar cabeceras y extraer cadenas básicas.
