Visión general de las pruebas de WebAssembly

Introducción a WebAssembly

WebAssembly (abreviado Wasm) es un formato de instrucciones binarias para una máquina virtual basada en pila. Wasm está diseñado como un destino de compilación portable para lenguajes de programación, lo que permite su despliegue en la web tanto para aplicaciones cliente como servidor. Ofrece una forma de ejecutar en la web, a velocidades casi nativas, código escrito en múltiples lenguajes, como C, C++, Rust y Go.

La adopción de WebAssembly ha sido impulsada por la necesidad de alto rendimiento en las aplicaciones web (p. ej., edición de video, motores de videojuegos, bibliotecas criptográficas) y por el deseo de portar aplicaciones de escritorio heredadas a la web sin reescribirlas en JavaScript.

Como ocurre con la introducción de cualquier arquitectura nueva, WebAssembly presenta fallos y vulnerabilidades propios. Aunque la máquina virtual de Wasm está aislada (sandboxed) del entorno anfitrión, el código que se ejecuta dentro del módulo Wasm conserva las vulnerabilidades de seguridad de memoria inherentes al lenguaje de origen. Además, el límite entre el anfitrión y el módulo Wasm puede ofrecer una vía sin restricciones para comprometer la aplicación si no se protege adecuadamente.

Este capítulo pretende guiar al investigador de seguridad en los conceptos necesarios para probar aplicaciones WebAssembly, investigando sus tecnologías centrales, sus entornos de ejecución y sus paradigmas de vulnerabilidad.

Historia

Debido a sus beneficios de rendimiento, WebAssembly ha evolucionado rápidamente de ser una característica específica del navegador a una tecnología versátil que se ejecuta en servidores, redes de borde (edge) y dispositivos embebidos.

WebAssembly se anunció por primera vez en 2015 como un esfuerzo conjunto de ingenieros de Mozilla, Google, Microsoft y Apple. En 2017, el Producto Mínimo Viable (MVP) fue publicado y distribuido por todos los principales motores de navegador, estableciendo a Wasm como el cuarto lenguaje en ejecutarse de forma nativa en los navegadores (junto con HTML, CSS y JavaScript).

En diciembre de 2019, el World Wide Web Consortium (W3C) publicó la WebAssembly Core Specification como estándar web oficial. Más o menos en la misma época se introdujo la WebAssembly System Interface (WASI). WASI estandarizó la forma en que los módulos WebAssembly interactúan con los sistemas operativos, impulsando a Wasm fuera del navegador hacia servicios de backend, microservicios y plataformas de cómputo de borde sin servidor (serverless) (como Cloudflare Workers y Fastly Compute).

¿Qué entorno de WebAssembly?

Antes de hacer suposiciones sobre la superficie de ataque, conviene conocer el entorno en el que opera el módulo WebAssembly. El investigador de seguridad puede encontrarse con:

  • Wasm del lado del cliente (navegador): El archivo .wasm es descargado y ejecutado por el navegador del usuario. Depende de "código pegamento" (glue code) de JavaScript para interactuar con el DOM y las Web API.
  • Del lado del servidor: El módulo Wasm se ejecuta en el backend, procesando peticiones de API o realizando cómputos pesados. Las vulnerabilidades aquí pueden llevar directamente al compromiso del servidor.
  • Serverless / cómputo de borde (Edge Computing): Se levantan instancias de Wasm en nodos de borde para interceptar y procesar peticiones HTTP. Estos entornos suelen reutilizar instancias de memoria para reducir la latencia, lo que introduce riesgos de filtración de estado entre inquilinos (cross-tenant).
  • WASI independiente (standalone): El módulo se ejecuta de forma nativa en el sistema operativo mediante runtimes como Wasmtime o Wasmer, regido por un modelo de seguridad basado en capacidades.

Componentes centrales de WebAssembly

La arquitectura de WebAssembly se basa en varios conceptos fundamentales. Comprenderlos es crucial para analizar cómo se manifiestan las vulnerabilidades.

Módulos

Un Módulo de WebAssembly es un archivo binario .wasm compilado. No tiene estado y contiene el bytecode compilado, las firmas de tipos y los segmentos de datos. En formato de texto se representa como WebAssembly Text Format (WAT).

Memoria lineal

A diferencia de las aplicaciones nativas que utilizan heaps y pilas administrados por el sistema operativo, una instancia de WebAssembly almacena sus datos de ejecución dentro de un único arreglo de bytes contiguo llamado Memoria lineal (Linear Memory). Esta memoria se expone al anfitrión como un ArrayBuffer. La pila, el heap, los literales de cadena y las variables globales del módulo Wasm comparten todos este espacio de memoria plano y no administrado.

Tablas

Una Tabla (Table) es un arreglo de valores opacos, normalmente referencias a funciones. Dado que WebAssembly impone Control-Flow Integrity (CFI) y no permite la ejecución directa de código desde la memoria lineal, los punteros a función a nivel de código fuente (como en C, C++ o Rust) y los destinos de llamada dinámicos se compilan en índices enteros que apuntan a posiciones específicas de una Tabla. Posteriormente, las llamadas indirectas (call_indirect) se ejecutan usando esos índices.

Importaciones y exportaciones

WebAssembly no puede interactuar con el mundo exterior de forma autónoma.

  • Importaciones (Imports): Funciones o variables proporcionadas por el anfitrión (p. ej., una función de JS como console.log) que el módulo Wasm puede llamar.
  • Exportaciones (Exports): Funciones o instancias de memoria dentro del módulo Wasm que se hacen accesibles al anfitrión.

El paradigma de seguridad

WebAssembly está aislado por naturaleza (sandboxed); un módulo no puede escapar de su máquina virtual para leer archivos arbitrarios o sockets de red sin que el anfitrión importe explícitamente esas capacidades.

Sin embargo, la seguridad de memoria interna no está garantizada. Cuando el código heredado de C/C++ se compila a WebAssembly, algunos supuestos de endurecimiento nativo cambian:

  • Sin ASLR dentro del módulo: Los desplazamientos (offsets) dentro de la memoria lineal son deterministas, aunque el proceso anfitrión use ASLR.
  • Los protectores de pila dependen de la compilación: Los canarios pueden estar ausentes a menos que se habiliten explícitamente en la cadena de herramientas.
  • La memoria lineal no es ejecutable, pero su integridad no está protegida: La corrupción de memoria puede alterar datos que influyen en el flujo de control (p. ej., los índices de función usados en call_indirect) y en la lógica de la aplicación.

En consecuencia, las vulnerabilidades clásicas de corrupción de memoria (desbordamientos de búfer, Use-After-Free, cadenas de formato) sobreviven a la compilación. Un atacante puede sobrescribir datos adyacentes en la memoria lineal para manipular la lógica de la aplicación, alterar los índices de la tabla de llamadas indirectas (ret2win) o corromper búferes de salida consumidos por el anfitrión, convirtiendo una vulnerabilidad de Wasm en DOM-Based XSS o en ejecución remota de código (RCE) del lado del servidor.
