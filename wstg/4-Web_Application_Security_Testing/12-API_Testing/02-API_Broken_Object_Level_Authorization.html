Autorización rota a nivel de objeto en API (BOLA)

ID
WSTG-APIT-02

Resumen

Broken Object Level Authorization (BOLA) ocurre cuando una API no aplica correctamente las comprobaciones de autorización para cada objeto al que accede el cliente. Los atacantes pueden manipular los identificadores de objetos en las peticiones a la API (como IDs, GUIDs o tokens) para acceder a recursos, o modificarlos, sin tener autorización. Esta vulnerabilidad es crítica en las API debido a su acceso directo a los objetos subyacentes y a la prevalencia de las API en las aplicaciones modernas.

Explotar BOLA puede conducir al acceso no autorizado a datos sensibles, la suplantación de usuarios, la escalada horizontal de privilegios (acceder a los recursos de otros usuarios) y la escalada vertical de privilegios (obtener acceso no autorizado a nivel de administrador).

Objetivos de la prueba

  • El objetivo de esta prueba es identificar si la API aplica comprobaciones adecuadas de autorización a nivel de objeto, asegurando que los usuarios solo puedan acceder y manipular los objetos con los que están autorizados a interactuar.

Cómo probar

Comprender los endpoints de la API y las referencias a objetos

Revisar la documentación de la API (p. ej., la especificación OpenAPI), el tráfico, o usar un proxy de interceptación (p. ej., Burp Suite, ZAP) para identificar los endpoints que aceptan identificadores de objetos de interés. Estos pueden presentarse en forma de IDs, UUIDs u otras referencias.

Ejemplos:

  • GET /api/users/{user_id}
  • GET /api/orders/{order_id}
  • POST /graphql
    query: {user(id: "123") }

Con el conocimiento obtenido en el paso anterior, revisar y recopilar identificadores de objetos de terceros (p. ej., IDs de usuarios, IDs de pedidos, etc.) que puedan usarse posteriormente en la manipulación de identificadores de objetos.

Además, generar una lista de posibles identificadores de objetos para fuerza bruta. Por ejemplo, si una API recupera una orden de compra de un usuario autenticado, generar varios IDs de órdenes de compra para las pruebas.

Manipular los identificadores de objetos en las peticiones a la API

Con el objetivo de determinar si los usuarios pueden acceder o modificar objetos que no les pertenecen alterando los identificadores de objetos en la petición a la API, cambiar el identificador del objeto (p. ej., ID de usuario, ID de pedido) en la URL o en el cuerpo de la petición.

Ejemplo: Modificar una petición como GET /api/users/123/profile (donde 123 es el ID del usuario actual) a GET /api/users/124/profile (donde 124 es el ID de otro usuario).

Dependiendo del contexto de la aplicación, utilizar dos cuentas diferentes para realizar las pruebas. Con una cuenta A, crear recursos que pertenezcan exclusivamente a esa cuenta (p. ej., una orden de compra) y, con una cuenta B, intentar acceder al recurso de la cuenta A (p. ej., la orden de compra).

Probar el acceso a nivel de objeto con distintos métodos HTTP

Probar varios métodos HTTP en busca de vulnerabilidades BOLA:

  • GET: Intentar acceder a objetos no autorizados manipulando el ID del objeto en la petición.
  • POST/PUT/PATCH: Intentar crear o modificar objetos que pertenecen a otros usuarios.
  • DELETE: Intentar eliminar un objeto que pertenece a otro usuario.

Probar BOLA en API GraphQL

Para las API GraphQL, enviar una consulta con un ID de objeto modificado en los parámetros de la consulta (consulte GraphQL):

Ejemplo: query { user(id: "124") { name, email } }.

Probar el acceso masivo a objetos

Probar si la API permite el acceso masivo no autorizado a objetos. Esto podría ocurrir en endpoints que devuelven listas de objetos.

Ejemplo: GET /api/users devuelve los datos de todos los usuarios en lugar de solo los datos del usuario autenticado.

Indicadores de BOLA

  • Explotación exitosa: Si modificar un ID de objeto en la petición devuelve datos o permite acciones sobre objetos que pertenecen a otros usuarios, la API es vulnerable a BOLA.
  • Respuestas de error: Las API correctamente protegidas, en general, devolverían 403 Forbidden o 401 Unauthorized ante un acceso no autorizado a un objeto. Una respuesta 200 OK para el objeto de otro usuario indica BOLA.
  • Respuestas inconsistentes: Si algunos endpoints aplican la autorización y otros no, esto apunta a controles de seguridad incompletos o inconsistentes.

Corrección

  • Comprobaciones de propiedad del objeto: Asegurar que se realicen comprobaciones de autorización a nivel de objeto en cada petición a la API. Verificar siempre que el usuario que realiza la petición esté autorizado a acceder al objeto solicitado.
  • Control de acceso basado en roles (RBAC): Implementar políticas RBAC que definan qué roles pueden acceder a objetos específicos o modificarlos.
  • Principio de mínimo privilegio: Aplicar el principio de mínimo privilegio para asegurar que los usuarios solo puedan acceder al conjunto mínimo de objetos que necesitan para su rol.
  • Usar UUIDs o IDs no secuenciales: Preferir identificadores de objetos no predecibles y no secuenciales (p. ej., UUIDs en lugar de enteros simples) para dificultar la enumeración y los ataques de fuerza bruta.

Herramientas

  • ZAP: Los escáneres automatizados o las herramientas manuales de proxy pueden ayudar a probar las referencias a objetos en las peticiones a la API.
  • Burp Suite: Usar las herramientas Repeater o Intruder para manipular IDs de objetos y enviar múltiples peticiones con el fin de probar el control de acceso.
  • Postman: Enviar peticiones con IDs de objetos alterados y observar las respuestas.
  • Herramientas de fuzzing: Usar fuzzers para aplicar fuerza bruta a los IDs de objetos y comprobar si hay acceso no autorizado.
