GraphQL

ID
WSTG-APIT-99

Resumen

GraphQL se ha vuelto muy popular en las API modernas. Ofrece simplicidad y objetos anidados, lo que facilita un desarrollo más rápido. Si bien toda tecnología tiene ventajas, también puede exponer la aplicación a nuevas superficies de ataque. El propósito de este escenario es presentar algunas configuraciones erróneas y vectores de ataque comunes en aplicaciones que utilizan GraphQL. Algunos vectores son exclusivos de GraphQL (p. ej., la consulta de introspección) y otros son genéricos de las API (p. ej., la inyección SQL).

Los ejemplos de esta sección se basan en una aplicación GraphQL vulnerable, poc-graphql, que se ejecuta en un contenedor de docker que asigna localhost:8080/GraphQL como el nodo GraphQL vulnerable.

Objetivos de la prueba

  • Evaluar que se haya desplegado una configuración segura y lista para producción.
  • Validar todos los campos de entrada contra ataques genéricos.
  • Asegurar que se apliquen los controles de acceso adecuados.

Cómo probar

Probar nodos GraphQL no es muy diferente de probar otras tecnologías de API. Considere los siguientes pasos:

Consultas de introspección

Las consultas de introspección son el método mediante el cual GraphQL permite preguntar qué consultas se soportan, qué tipos de datos están disponibles y muchos otros detalles que se necesitarán al abordar una prueba de un despliegue de GraphQL.

El sitio web de GraphQL describe la introspección:

"It's often useful to ask a GraphQL schema for information about what queries it supports. GraphQL allows us to do so using the introspection system!"

Hay un par de maneras de extraer esta información y visualizar la salida, como se indica a continuación.

Uso de la introspección nativa de GraphQL

La forma más sencilla es enviar una petición HTTP (usando un proxy personal) con el siguiente payload, tomado de un artículo en Medium:

query IntrospectionQuery {
  __schema {
    queryType {
      name
    }
    mutationType {
      name
    }
    subscriptionType {
      name
    }
    types {
      ...FullType
    }
    directives {
      name
      description
      locations
      args {
        ...InputValue
      }
    }
  }
}
fragment FullType on __Type {
  kind
  name
  description
  fields(includeDeprecated: true) {
    name
    description
    args {
      ...InputValue
    }
    type {
      ...TypeRef
    }
    isDeprecated
    deprecationReason
  }
  inputFields {
    ...InputValue
  }
  interfaces {
    ...TypeRef
  }
  enumValues(includeDeprecated: true) {
    name
    description
    isDeprecated
    deprecationReason
  }
  possibleTypes {
    ...TypeRef
  }
}
fragment InputValue on __InputValue {
  name
  description
  type {
    ...TypeRef
  }
  defaultValue
}
fragment TypeRef on __Type {
  kind
  name
  ofType {
    kind
    name
    ofType {
      kind
      name
      ofType {
        kind
        name
        ofType {
          kind
          name
          ofType {
            kind
            name
            ofType {
              kind
              name
              ofType {
                kind
                name
              }
            }
          }
        }
      }
    }
  }
}

Uso de GraphiQL

GraphiQL es un IDE basado en web para GraphQL. Forma parte del proyecto GraphQL y se utiliza principalmente con fines de depuración o desarrollo. La mejor práctica es no permitir que los usuarios accedan a él en despliegues de producción. Si se está probando un entorno de staging, es posible que se tenga acceso a él y así se pueda ahorrar tiempo al trabajar con consultas de introspección (aunque, por supuesto, se puede usar la introspección en la interfaz de GraphiQL).

GraphiQL tiene una sección de documentación, que utiliza los datos del esquema para crear un documento de la instancia de GraphQL que se está usando. Este documento contiene los tipos de datos, las mutaciones y básicamente toda la información que puede extraerse mediante introspección.

Uso de GraphQL Playground

GraphQL Playground es un cliente de GraphQL. Se puede usar para probar diferentes consultas, así como para dividir los IDE de GraphQL en distintos playgrounds y agruparlos por tema o asignándoles un nombre. Al igual que GraphiQL, Playground puede crear documentación sin necesidad de enviar manualmente consultas de introspección y procesar la(s) respuesta(s). Tiene otra gran ventaja: no necesita que la interfaz de GraphiQL esté disponible. Se puede dirigir la herramienta al nodo GraphQL mediante una URL, o usarla localmente con un archivo de datos. GraphQL Playground puede usarse para probar vulnerabilidades directamente, por lo que no es necesario usar un proxy personal para enviar peticiones HTTP. Esto significa que se puede usar esta herramienta para una interacción y evaluación sencillas de GraphQL. Para otros payloads más avanzados, se debe usar un proxy personal.

En algunos casos, será necesario establecer las cabeceras HTTP en la parte inferior, para incluir el ID de sesión u otro mecanismo de autenticación. Esto sigue permitiendo crear múltiples "IDE" con diferentes permisos para verificar si realmente existen problemas de autorización.

Fuga del esquema mediante sugerencias de campos

Muchas implementaciones de servidores GraphQL (incluidos Apollo Server y graphql-js) devuelven de forma predeterminada sugerencias del tipo "Did you mean...?" siempre que un cliente hace referencia a un nombre de campo que no existe. Este comportamiento ayuda al desarrollo, pero filtra información del esquema incluso cuando la introspección se ha deshabilitado explícitamente.

Para probarlo, hay que enviar un nombre de campo ligeramente mal escrito. Si el servidor devuelve una sugerencia en la respuesta de error, la respuesta divulga el nombre real del campo sin emitir una consulta de introspección.

Por ejemplo, se envía una petición con un campo inexistente userss:

query {
  userss {
    id
  }
}

Un servidor vulnerable revela el nombre real del campo en su respuesta:

{
  "errors": [
    {
      "message": "Cannot query field \"userss\" on type \"Query\". Did you mean \"users\"?",
      "locations": [{ "line": 2, "column": 3 }]
    }
  ]
}

Se itera sobre variantes de nombres supuestos (p. ej., userss, usesr, usres) para enumerar los nombres válidos de consultas y mutaciones, una sugerencia a la vez. Hacerlo puede reconstruir una parte sustancial del esquema sin acceso a la introspección.

Clairvoyance automatiza este proceso combinando una lista de palabras con las respuestas de sugerencias para construir un esquema de forma incremental.

Conclusión sobre la introspección

La introspección es una herramienta útil que permite a los usuarios obtener más información sobre el despliegue de GraphQL. Sin embargo, esto también permitirá a los usuarios maliciosos acceder a la misma información. La mejor práctica es limitar el acceso a las consultas de introspección, ya que algunas herramientas o peticiones podrían fallar si esta función se deshabilita por completo. Como GraphQL normalmente sirve de puente hacia las API del backend del sistema, es mejor aplicar un control de acceso estricto.

Deshabilitar la introspección por sí sola no es suficiente. También se deben deshabilitar las sugerencias de campos en producción, ya que permiten por sí mismas la enumeración del esquema.

Autorización

La introspección es el primer lugar donde buscar problemas de autorización. Como se indicó, el acceso a la introspección debe restringirse, ya que permite la extracción y recopilación de datos. Una vez que un evaluador tiene acceso al esquema y conoce la información sensible que se puede extraer, debe enviar consultas que no sean bloqueadas por privilegios insuficientes. GraphQL no aplica permisos de forma predeterminada, por lo que corresponde a la aplicación hacer cumplir la autorización.

En los ejemplos anteriores, la salida de la consulta de introspección muestra que existe una consulta llamada auth. Parece un buen lugar para extraer información sensible como tokens de API, contraseñas, etc.


Figura 12.1-4: API de la consulta Auth de GraphQL

Probar la implementación de la autorización varía de un despliegue a otro, ya que cada esquema tendrá información sensible diferente y, por tanto, objetivos distintos en los que centrarse.

En este ejemplo vulnerable, cualquier usuario (incluso sin autenticar) puede obtener acceso a los tokens de autenticación de todos los veterinarios listados en la base de datos. Estos tokens pueden usarse para realizar acciones adicionales que permite el esquema, como asociar o disociar un perro de cualquier veterinario especificado mediante mutaciones, aunque no haya un token de autenticación correspondiente al veterinario en la petición.

Inyección

GraphQL es la implementación de la capa de API de una aplicación y, como tal, normalmente reenvía las peticiones a una API del backend o directamente a la base de datos. Esto permite aprovechar cualquier vulnerabilidad subyacente, como inyección SQL, inyección de comandos, cross-site scripting, etc. Usar GraphQL solo cambia el punto de entrada del payload malicioso.

Se puede consultar otros escenarios de la guía de pruebas de OWASP para obtener ideas.

GraphQL también tiene escalares, que normalmente se utilizan para tipos de datos personalizados que no tienen tipos de datos nativos, como DateTime. Estos tipos de datos no tienen validación de fábrica, lo que los convierte en buenos candidatos para las pruebas.

Inyección SQL

La aplicación de ejemplo es vulnerable por diseño en la consulta dogs(namePrefix: String, limit: Int = 500): [Dog!], ya que el parámetro namePrefix se concatena en la consulta SQL. Concatenar la entrada del usuario es una mala práctica común de las aplicaciones que puede exponerlas a la inyección SQL.

La siguiente consulta extrae información de la tabla CONFIG dentro de la base de datos:

query sqli {
  dogs(namePrefix: "ab%' UNION ALL SELECT 50 AS ID, C.CFGVALUE AS NAME, NULL AS VETERINARY_ID FROM CONFIG C LIMIT ? -- ", limit: 1000) {
    id
    name
  }
}

La respuesta a esta consulta es:

{
  "data": {
    "dogs": [
      {
        "id": 1,
        "name": "Abi"
      },
      {
        "id": 2,
        "name": "Abime"
      },
      {
        "id": 3,
        "name": "..."
      },
      {
        "id": 50,
        "name": "$Nf!S?(.}DtV2~:Txw6:?;D!M+Z34^"
      }
    ]
  }
}

La consulta contiene el secreto que firma los JWT en la aplicación de ejemplo, que es información muy sensible.

Para saber qué buscar en una aplicación determinada, será útil recopilar información sobre cómo está construida la aplicación y cómo están organizadas las tablas de la base de datos. También se pueden usar herramientas como sqlmap para buscar rutas de inyección e incluso automatizar la extracción de datos de la base de datos.

Cross-Site Scripting (XSS)

El cross-site scripting ocurre cuando un atacante inyecta código ejecutable que posteriormente es ejecutado por el navegador. Puede consultar las pruebas de XSS en el capítulo Injection Testing. Se puede probar XSS reflejado usando un payload de Reflected Cross Site Scripting.

En este ejemplo, los errores pueden reflejar la entrada y podrían provocar que ocurra XSS.

Consultas de denegación de servicio (DoS)

GraphQL expone una interfaz muy simple que permite a los desarrolladores usar consultas anidadas y objetos anidados. Esta capacidad también puede usarse de forma maliciosa, llamando a una consulta profundamente anidada, similar a una función recursiva, y provocando una denegación de servicio al consumir CPU, memoria u otros recursos de cómputo.

Si se observa de nuevo la Figura 12.1-1, se puede ver que es posible crear un bucle en el que un objeto Dog contiene un objeto Veterinary. Podría haber una cantidad interminable de objetos anidados.

Esto permite una consulta profunda que tiene el potencial de sobrecargar la aplicación:

query dos {
  allDogs(onlyFree: false, limit: 1000000) {
    id
    name
    veterinary {
      id
      name
      dogs {
        id
        name
        veterinary {
          id
          name
          dogs {
            id
            name
            veterinary {
              id
              name
              dogs {
                id
                name
                veterinary {
                  id
                  name
                  dogs {
                    id
                    name
                    veterinary {
                      id
                      name
                      dogs {
                        id
                        name
                      }
                    }
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}

Existen múltiples medidas de seguridad que pueden implementarse para prevenir este tipo de consultas, enumeradas en la sección Corrección. Las consultas abusivas pueden causar problemas como DoS en los despliegues de GraphQL y deben incluirse en las pruebas.

Ataques de batching

GraphQL soporta el agrupamiento (batching) de múltiples consultas en una sola petición. Esto permite a los usuarios solicitar múltiples objetos o múltiples instancias de objetos de forma eficiente. Sin embargo, un atacante puede utilizar esta funcionalidad para realizar un ataque de batching. Enviar más de una consulta en una sola petición tiene el siguiente aspecto:

[
  {
    query: < query 0 >,
    variables: < variables for query 0 >,
  },
  {
    query: < query 1 >,
    variables: < variables for query 1 >,
  },
  {
    query: < query n >
    variables: < variables for query n >,
  }
]

En la aplicación de ejemplo, se puede enviar una sola petición para extraer todos los nombres de los veterinarios usando el ID adivinable (es un entero creciente). Un atacante puede entonces utilizar los nombres para obtener tokens de acceso. En lugar de hacerlo en muchas peticiones, que podrían ser bloqueadas por una medida de seguridad de red como un firewall de aplicaciones web o un limitador de tasa como Nginx, estas peticiones pueden agruparse. Esto significa que solo habría un par de peticiones, lo que puede permitir una fuerza bruta eficiente sin ser detectado. A continuación se muestra una consulta de ejemplo:

query {
  Veterinary(id: "1") {
    name
  }
  second:Veterinary(id: "2") {
    name
  }
  third:Veterinary(id: "3") {
    name
  }
}

Esto proporcionará al atacante los nombres de los veterinarios y, como se mostró antes, los nombres pueden usarse para agrupar múltiples consultas que solicitan los tokens de autenticación de esos veterinarios. Por ejemplo:

query {
  auth(veterinaryName: "Julien")
  second: auth(veterinaryName:"Benoit")
}

Los ataques de batching pueden utilizarse para eludir muchas medidas de seguridad aplicadas en los sitios. También pueden usarse para enumerar objetos e intentar aplicar fuerza bruta a la autenticación multifactor u otra información sensible.

Elusión de la lista de denegación de consultas mediante alias

GraphQL permite asignar un alias a cualquier campo de una consulta: un nombre alternativo que se usa para etiquetar el resultado. Es una característica estándar del lenguaje, pero puede abusarse de ella para evadir controles de seguridad mal implementados que buscan nombres de campo específicos.

Algunos despliegues implementan una lista de denegación (denylist) de consultas mediante una coincidencia ingenua de cadenas o expresiones regulares sobre el documento GraphQL sin procesar (por ejemplo, rechazar cualquier consulta que contenga el nombre de campo adminUsers solo cuando aparece como adminUsers { o adminUsers(, sin analizar completamente la sintaxis ni construir un AST). Una implementación robusta que busque adminUsers como subcadena en cualquier parte de la petición, o que analice correctamente la estructura de la consulta, seguirá detectando las llamadas con alias, porque el nombre de campo subyacente adminUsers sigue presente en la operación y el alias no lo renombra ni lo elimina. Sin embargo, las comprobaciones simplistas que no manejan la sintaxis aliasName: fieldName pueden eludirse emitiendo el mismo campo bajo un alias, mientras el resolver de adminUsers sigue ejecutándose en el servidor. En la terminología de GraphQL, adminUsers en los ejemplos siguientes es un nombre de campo; un nombre de operación aparecería después de la palabra clave query (por ejemplo, query GetAdmins { ... }).

Primero, se envía la consulta directamente para confirmar que está bloqueada:

query {
  adminUsers {
    id
    name
    email
  }
}

Respuesta (bloqueada por la lista de denegación):

{
  "errors": [
    {
      "message": "400 Bad Request: query not allowed"
    }
  ]
}

Luego, se reenvía la misma consulta usando un alias:

query {
  s: adminUsers {
    id
    name
    email
  }
}

Respuesta (lista de denegación eludida, se devuelven datos):

{
  "data": {
    "s": [
      { "id": 1, "name": "Admin", "email": "admin@example.com" }
    ]
  }
}

El servidor resuelve s como adminUsers porque los alias son una construcción de la capa de GraphQL: el resolver subyacente se ejecuta con normalidad. Una lista de denegación que solo coincide con el nombre literal del campo en el cuerpo de la petición no detectará las llamadas con alias.

Para cada consulta que parezca estar bloqueada o restringida, se debe intentar anteponerle un alias arbitrario (p. ej., x:, s:, bypass:) y observar si la respuesta cambia de un error a una carga de datos exitosa.

Mensajes de error detallados

GraphQL puede encontrar errores inesperados durante la ejecución. Cuando ocurre un error de este tipo, el servidor puede enviar una respuesta de error que revele detalles internos del error o configuraciones o datos de la aplicación. Esto permite a un usuario malicioso obtener más información sobre la aplicación. Como parte de las pruebas, se deben revisar los mensajes de error enviando datos inesperados, un proceso conocido como fuzzing. Se debe buscar en las respuestas información potencialmente sensible que pueda revelarse mediante esta técnica.

Exposición de la API subyacente

GraphQL es una tecnología relativamente nueva y algunas aplicaciones están en transición de API antiguas a GraphQL. En muchos casos, GraphQL se despliega como una API estándar que traduce las peticiones (enviadas con sintaxis GraphQL) a una API subyacente, así como las respuestas. Si las peticiones a la API subyacente no se comprueban adecuadamente en cuanto a autorización, podría producirse una posible escalada de privilegios.

Por ejemplo, una petición que contenga el parámetro id=1/delete podría interpretarse como /api/users/1/delete. Esto podría extenderse a la manipulación de otros recursos pertenecientes a user=1. También es posible que se interprete que la petición tiene la autorización otorgada al nodo GraphQL, en lugar de la del solicitante real.

Un evaluador debe intentar obtener acceso a los métodos de la API subyacente, ya que podría ser posible escalar privilegios.

Corrección

  • Restringir el acceso a las consultas de introspección.
  • Deshabilitar las sugerencias de campos en producción: la mayoría de los servidores GraphQL permiten desactivarlas (p. ej., en Apollo Server, configurar hideSchemaDetailsFromClientErrors). Esto evita la enumeración del esquema mediante respuestas de error "Did you mean?".
  • Implementar validación de entrada.
    • GraphQL no tiene una forma nativa de validar la entrada; sin embargo, existe un proyecto de código abierto llamado "graphql-constraint-directive" que permite la validación de entrada como parte de la definición del esquema.
    • La validación de entrada por sí sola es útil, pero no es una solución completa y deben tomarse medidas adicionales para mitigar los ataques de inyección.
  • Implementar medidas de seguridad para evitar consultas abusivas.
    • Tiempos de espera (timeouts): restringir el tiempo que se permite ejecutar una consulta.
    • Profundidad máxima de consulta: limitar la profundidad de las consultas permitidas, lo que puede impedir que consultas demasiado profundas abusen de los recursos.
    • Establecer una complejidad máxima de consulta: limitar la complejidad de las consultas para mitigar el abuso de los recursos de GraphQL.
    • Usar limitación (throttling) basada en el tiempo del servidor: limitar la cantidad de tiempo de servidor que un usuario puede consumir.
    • Usar limitación basada en la complejidad de las consultas: limitar la complejidad total de las consultas que un usuario puede consumir.
  • Enviar mensajes de error genéricos: usar mensajes de error genéricos que no revelen detalles del despliegue.
  • Mitigar los ataques de batching:
    • Añadir en el código una limitación de tasa de peticiones por objeto.
    • Impedir el batching para objetos sensibles.
    • Limitar el número de consultas que pueden ejecutarse al mismo tiempo.
  • Evitar la elusión de la lista de denegación de consultas: implementar controles de acceso a nivel de resolver en lugar de depender únicamente de listas de bloqueo por nombre de operación, ya que los alias de GraphQL permiten a quien llama invocar cualquier campo con un nombre arbitrario.

Para más información sobre cómo corregir las debilidades de GraphQL, consulte la GraphQL Cheat Sheet.
