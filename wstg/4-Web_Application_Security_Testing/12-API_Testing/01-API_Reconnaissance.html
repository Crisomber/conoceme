Reconocimiento de API

ID
WSTG-APIT-01

Resumen

El reconocimiento es un paso importante en cualquier trabajo de pentesting. Esto incluye el pentesting de API. El reconocimiento mejora significativamente la eficacia del proceso de pruebas al recopilar información sobre la API y desarrollar una comprensión del objetivo. Esta fase no solo aumenta la probabilidad de descubrir problemas de seguridad críticos, sino que también garantiza una evaluación integral de la postura de seguridad de las API.

Esta guía tiene una sección sobre Information Gathering que puede aplicarse al auditar API. Sin embargo, existen algunas diferencias. Como investigadores de seguridad, a menudo nos centramos en áreas específicas, y buscar en esta guía las secciones que aplican puede llevar mucho tiempo. Para asegurar que el investigador tenga un único lugar en el que concentrarse en las API, esta sección se centra en los elementos que aplican a las API y ofrece referencias al contenido de apoyo que se encuentra en otras partes de la guía.

Tipos de API

Las API pueden ser públicas o privadas.

API públicas

Las API públicas normalmente tienen sus detalles publicados en un documento Swagger/OpenAPI. Obtener acceso a este documento es importante para comprender la superficie de ataque. Igualmente importante es encontrar versiones anteriores de este documento que puedan mostrar código obsoleto pero aún funcional que pueda tener vulnerabilidades de seguridad.

Hay que tener presente que este documento, por bien intencionado que sea, puede no ser exacto y también puede no divulgar la API completa.

Las API públicas también pueden estar documentadas en bibliotecas compartidas o directorios de API.

API privadas

La visibilidad de las API privadas depende de quién sea el consumidor previsto. Una API puede ser privada, pero accesible solo para clientes suscritos (también conocidos como partners) o solo accesible para clientes internos, como otros departamentos de la misma empresa. Encontrar API privadas mediante técnicas de reconocimiento también es importante. Estas API pueden descubrirse mediante varias técnicas que se tratan más abajo.

Objetivos de la prueba

  • Encontrar todos los endpoints de API soportados por el código del servidor backend, estén documentados o no.
  • Encontrar todos los parámetros de cada endpoint soportado por el servidor backend, estén documentados o no.
  • Descubrir datos interesantes relacionados con las API en el HTML y JavaScript enviados a los clientes.

Cómo probar

Encontrar la documentación

Tanto en el caso público como en el privado, la documentación de la API será útil según su nivel de calidad y exactitud. La documentación de las API públicas normalmente se comparte con todos, mientras que la documentación de las API privadas solo se comparte con el cliente previsto. Sin embargo, en ambos casos encontrar la documentación, ya sea filtrada accidentalmente o de otro modo, será útil en la investigación.

Independientemente de la visibilidad de la API, buscar documentación de la API puede encontrar documentación antigua, aún no publicada o filtrada accidentalmente. Esta documentación será muy útil para entender qué superficie de ataque expone la API.

En trabajos con tiempo limitado, hay que solicitar al cliente lo antes posible artefactos de API legibles por máquina para que las herramientas de pruebas puedan importarlos o procesarlos directamente. Hay que pedir definiciones OpenAPI, especificaciones Swagger 2.0 heredadas y colecciones de peticiones actualizadas (por ejemplo Postman o Bruno). Para las API que no sean REST dentro del alcance (por ejemplo GraphQL), hay que solicitar esquemas o esquemas exportados cuando la introspección esté deshabilitada. Las definiciones de reproducción de peticiones (por ejemplo Hurl) también son útiles. Si la API es antigua, pueden aparecer archivos WSDL o WADL como artefactos heredados en algunos entornos. Esto es especialmente útil para API privadas, internas o recién desplegadas, para las que puede no existir documentación pública.

Directorios de API

Las fuentes alternativas de documentación de API pueden incluir directorios de API, tales como:

  • GitHub en general
  • GitHub Public APIs Repository
  • APIs.guru
  • RapidAPI
  • PublicAPIs y PublicAPIs
  • Postman API Network

Buscar en lugares conocidos

Si la documentación no es fácilmente evidente, se puede buscar activamente en el objetivo documentación basándose en algunos nombres o rutas obvios. Estos incluyen:

  • /api-docs
  • /doc
  • /swagger
  • /swagger.json
  • /openapi.json
  • /.well-known/schema-discovery

Robots.txt

robots.txt es un archivo de texto que los propietarios de sitios crean para indicar a los rastreadores web (como los bots de los motores de búsqueda) cómo rastrear e indexar su sitio. Forma parte del Robots Exclusion Protocol (REP), que regula cómo interactúan los bots con los sitios.

Este archivo puede ofrecer pistas adicionales sobre la estructura de rutas o los endpoints de la API.

La sección Information Gathering hace referencia a robots.txt en varios casos, incluidos WSTG-INFO-01, WSTG-INFO-03, WSTG-INFO-05 y WSTG-INFO-08.

GitDorking

Si la aplicación utiliza GitHub, GitLab u otros repositorios basados en Git de cara al público, también podemos buscar pistas o contenido sensible (lo que se conoce como GitDorking). Esta información puede incluir contraseñas, claves de API, archivos de configuración y otros datos confidenciales que los desarrolladores pueden confirmar (commit) accidental o inadvertidamente en sus repositorios. Las organizaciones pueden compartir accidentalmente código sensible, de ejemplo o de pruebas que puede ofrecer pistas sobre detalles de implementación. Las cuentas personales de GitHub de los empleados del objetivo también pueden publicar accidentalmente información que ofrezca pistas.

Navegar y rastrear (spidering) la aplicación

Incluso si se dispone de la documentación de la API, navegar por la aplicación es una buena idea. La documentación puede estar desactualizada, ser inexacta o estar incompleta.

Navegar por la aplicación con un proxy de interceptación como ZAP o Burp Suite registra los endpoints para su inspección posterior. Además, mediante su funcionalidad integrada de spidering, los proxies de interceptación pueden ayudar a generar una lista completa de endpoints. A partir de las URLs rastreadas, hay que buscar enlaces con esquemas de nombres evidentes de URL de API. Estos incluyen:

  • https://example.com/api/v1 (o v2, etc.)
  • https://example.com/graphql

O subdominios que las aplicaciones puedan consumir o de los que puedan depender:

  • https://api.example.com/api/v1

Es importante que el pentester intente ejercitar tanta funcionalidad de la aplicación como sea posible. Esto no solo sirve para generar una lista completa de endpoints, sino también para evitar problemas con la carga diferida (lazy loading) y la división de código (code splitting). Además, el trabajo de pentesting debe incluir cuentas de ejemplo con distintos niveles de privilegio para que la navegación y el spidering puedan acceder y exponer los endpoints de la mayor cantidad de funcionalidad posible.

Una vez completado, la información de endpoints obtenida de la navegación y el spidering de la aplicación puede ayudar al pentester a componer documentación y colecciones de la API con herramientas como Postman y Bruno. Las herramientas de reproducción de peticiones como Hurl pueden entonces usar esa información para automatizar flujos de prueba repetibles. Algunos clientes, como Postman y Bruno, también pueden usar scripts previos y posteriores a la petición, que pueden ayudar a reproducir flujos realistas al probar API con estado.

Analizar las peticiones interceptadas

Al auditar API REST, se debe usar un proxy de interceptación para recopilar las peticiones HTTP completas. Los servicios REST utilizan más que solo parámetros de URL, por lo que capturar el cuerpo completo de la petición y las cabeceras es crítico.

Hay que analizar las peticiones recopiladas para identificar parámetros no estándar u ocultos:

  • Identificar las cabeceras HTTP que influyen en el comportamiento de la aplicación o en la selección de recursos.
  • Determinar si un segmento de URL tiene un patrón repetido en múltiples URLs. Los patrones que contienen fechas, números o valores identificadores pueden indicar un parámetro incrustado en la URL. Por ejemplo, en la URL https://api.example.com/user/2026-10-03/profile, el segmento de fecha puede representar un valor de parámetro.
  • Identificar valores de parámetros estructurados con formato JSON, XML u otras estructuras personalizadas.
  • Examinar el último elemento de una URL. Si carece de extensión de archivo, puede ser un parámetro.
  • Buscar segmentos de URL muy variables. Si un único segmento cambia con frecuencia a lo largo de cientos de peticiones, es más probable que represente un valor de parámetro que un componente de ruta estático.
  • Verificar los segmentos de URL variables sospechosos estableciéndolos a un valor obviamente inválido. Esto aplica tanto a los segmentos intermedios que parecen dinámicos como a los segmentos finales sin extensión de archivo. Un 404 a nivel de enrutamiento antes del procesamiento de la aplicación puede indicar un segmento de ruta estático. Las respuestas 404 generadas por la aplicación no son suficientes por sí solas para hacer esa distinción. Si la petición llega a la lógica de la aplicación y devuelve un error de recurso no encontrado o de validación, el segmento puede estar enrutado por la aplicación y ser parametrizado. Debe tratarse como una heurística y correlacionarse el origen de la respuesta con el comportamiento de enrutamiento observado.

Google Dorking

Usar técnicas de reconocimiento pasivo como el Google Dorking con directivas como site e inurl nos permite adaptar una búsqueda a palabras clave comunes de API que el indexador de Google pueda haber encontrado. Consulte Conduct Search Engine Reconnaissance for Information Leakage para más información.

A continuación se muestran algunos ejemplos específicos de API:

site:"mytargetsite.com" inurl:"/api"

inurl:apikey filetype:env

Otras palabras clave pueden incluir "v1", "api", "graphql".

Podemos extender el Google Dorking para incluir subdominios del objetivo.

Las listas de palabras (wordlists) son útiles aquí para obtener una lista completa de las palabras comunes usadas en las API.

Mirar atrás, muy atrás

En general, las API cambian con el tiempo. Pero las versiones obsoletas o anteriores pueden seguir operativas, ya sea a propósito o por una configuración errónea. Estas también deben probarse, ya que hay una buena probabilidad de que contengan vulnerabilidades que las versiones más nuevas han corregido. Además, los cambios en las API muestran funciones más recientes que pueden ser menos robustas y, por tanto, buenas candidatas para las pruebas.

Para descubrir versiones anteriores podemos usar la Wayback machine para ayudar a encontrar endpoints antiguos. Una herramienta útil conocida como WayBackUrls, de TomNomNom, obtiene todas las URLs que la Wayback Machine conoce de un dominio.

  • WayBackUrls. Obtiene todas las URLs que la Wayback Machine conoce de un dominio.
  • waymore. Encuentra mucho más de la Wayback Machine, Common Crawl, Alien Vault OTX, URLScan y VirusTotal.
  • gau. Obtiene URLs conocidas de Open Threat Exchange de AlienVault, la Wayback Machine y Common Crawl.

La aplicación del lado del cliente

Una excelente fuente de información de API y de otro tipo es el HTML y JavaScript que el servidor envía al cliente. A veces, la aplicación cliente filtra información sensible, incluidas API y secretos. La sección Review Web Page Content for Information Leakage contiene información general para revisar el contenido web en busca de fugas. Aquí ampliaremos el enfoque en la revisión del contenido JavaScript en busca de secretos relacionados con API.

Existe una variedad de herramientas que podemos utilizar para ayudarnos a extraer información sensible del JavaScript transmitido al navegador. Estas herramientas suelen basarse en uno de dos enfoques: expresiones regulares o árboles de sintaxis abstracta (AST). Además, hay herramientas generales que nos ayudan a organizar o gestionar archivos JS para su investigación con herramientas de AST y de expresiones regulares.

Las expresiones regulares son más directas, al buscar patrones conocidos en el contenido JS o HTML. Sin embargo, este enfoque puede pasar por alto contenido no identificado explícitamente en la expresión regular. Dada la estructura de algunos JS, este enfoque puede perder mucho. Los AST, por otro lado, son estructuras en forma de árbol que representan la sintaxis del código fuente. Cada nodo del árbol corresponde a una parte del código. Para JavaScript, un AST descompone el código en componentes básicos, lo que permite que las herramientas y los compiladores comprendan y modifiquen el código con facilidad.

Herramientas generales

  1. Uproot. Un plugin de BurpSuite que guarda en disco cualquier archivo JS encontrado. Esto ayuda a extraer los archivos para cualquier análisis con herramientas de línea de comandos.
  2. OpenAPI Support. Este complemento de ZAP permite rastrear e importar definiciones OpenAPI (Swagger), versiones 1.2, 2.0 y 3.0.
  3. OpenAPI Parser. Un plugin de BurpSuite que analiza documentos OpenAPI en Burp Suite para automatizar las evaluaciones de seguridad de API basadas en OpenAPI.

Herramientas de expresiones regulares

  1. JSParser. Un script de python 2.7 que usa Tornado y JSBeautifier para extraer URLs relativas de archivos JavaScript.
  2. JSMiner. Un plugin de BurpSuite que intenta encontrar cosas interesantes dentro de archivos estáticos, principalmente archivos JavaScript y JSON. Esta herramienta escanea de forma "pasiva" mientras se rastrea la aplicación.
  3. JSpector. Un plugin de BurpSuite que rastrea pasivamente archivos JavaScript y crea automáticamente incidencias con las URLs, endpoints y métodos peligrosos encontrados en los archivos JS.
  4. Link Finder. Un script de python que encuentra endpoints en archivos JavaScript.

Herramientas de AST

  1. JSLuice. Una herramienta de línea de comandos que extrae URLs, rutas, secretos y otros datos interesantes del código fuente de JavaScript.

Otras herramientas de reconocimiento

  1. Attack Surface Detector. Un plugin de BurpSuite que utiliza análisis estático de código para identificar endpoints de aplicaciones web analizando las rutas e identificando parámetros.
  2. Param Miner. Un plugin de BurpSuite que identifica parámetros ocultos y no enlazados.
  3. xnLinkFinder. Una herramienta de python usada para descubrir endpoints, posibles parámetros y una lista de palabras específica para un objetivo determinado.
  4. GAP. Extensión de Burp para encontrar posibles endpoints y parámetros, y generar una lista de palabras personalizada para el objetivo.

Código fuente del lado del servidor

Si se tiene acceso al código fuente del lado del servidor, hay que extraer de él los endpoints. OWASP Noir analiza el código de enrutamiento de muchos frameworks web y lista cada endpoint con sus métodos y parámetros, incluidas las API internas u obsoletas a las que ningún cliente actual llama. Consulte Identify Application Entry Points para un recorrido de la herramienta.

Para las pruebas de API, se deben exportar los resultados como OpenAPI. Este comando escribe un documento OpenAPI 3.0 con cada endpoint del código fuente de OWASP RailsGoat:

noir scan railsgoat -f oas3 -o railsgoat-openapi.json

El archivo generado comienza de la siguiente manera:

{
  "openapi": "3.0.3",
  "info": {
    "title": "Generated by Noir",
    "version": "1.0.0"
  },
  "servers": [
    {
      "url": "http://localhost"
    }
  ],
  "paths": {
    "/api/v1/mobile/1": {
      "get": {
        "responses": {
          "200": {
            "description": "Successful response",
            "content": {
              "application/json": {
                "schema": {
                  "type": "object"
                }
              }
            }
          }
        },
        "parameters": [
          {
            "name": "class",
            "in": "query",
            "required": false,
            "schema": {
              "type": "string"
            }
          }
        ],
        "x-noir-unmapped-path-params": [
          "id"
        ]
      }
    },

Se importa el documento con el complemento OpenAPI Support de ZAP o la extensión OpenAPI Parser de Burp Suite (consulte General Tools). El proxy añade cada endpoint a su árbol del sitio, de modo que se pueden ejecutar contra ellos las pruebas de esta sección. Noir reemplaza cada parámetro de ruta por un valor de ejemplo, por lo que una ruta con un marcador :id aparece como /api/v1/mobile/1, y conserva los nombres originales en x-noir-unmapped-path-params. Estos se utilizan al probar API Broken Object Level Authorization.

Escaneo de puertos

Los servidores de API suelen desplegarse en puertos no estándar, o junto con otros servicios expuestos (paneles de administración internos, listeners gRPC o WebSocket, endpoints de depuración/métricas) que una revisión basada solo en la documentación pasaría por alto. naabu es un escáner de puertos rápido que puede enumerar rápidamente los puertos abiertos en los hosts identificados, y puede canalizar sus resultados directamente a Nmap para la detección de servicios solo en los puertos hallados abiertos:

naabu -p - -rate 2000 -c 50 -retries 2 -warm-up-time 1 -silent -host api.example.com -nmap-cli 'nmap -sV -oX scan.xml'

Ejecutar primero este escaneo, y el escaneo más lento de detección completa de servicios de Nmap solo contra los puertos que naabu reporta como abiertos, reduce considerablemente el tiempo total de escaneo en comparación con un escaneo directo de Nmap de todo el rango. Consulte Improving Port Scans Against API Servers para más orientación de ajuste específica para objetivos de API, incluido por qué los escaneos CONNECT pueden superar a los escaneos SYN con alta concurrencia, y cómo evitar pasar por alto servicios debido a limitación de tasa o filtrado por firewall.

Consulte también Attack Surface Identification para más información sobre el descubrimiento de puertos no estándar.

Fuzzing activo

El Active Fuzzing consiste en usar herramientas con listas de palabras y filtrar los resultados de las peticiones para descubrir endpoints mediante fuerza bruta.

Tras el descubrimiento de endpoints y parámetros, se usan los valores de las peticiones recopiladas para optimizar el fuzzing a nivel de valor:

  • Comparar los valores observados para identificar los rangos y formatos probablemente válidos frente a los inválidos.
  • Comenzar con valores inválidos marginales (por ejemplo 0 para campos que siempre son enteros positivos).
  • Buscar secuencias para poder probar valores fuera del rango actualmente asignado al usuario autenticado.

Kiterunner

KiteRunner es una herramienta que realiza el descubrimiento de contenido tradicional y la fuerza bruta de rutas/endpoints en aplicaciones y API modernas.

kr [scan|brute] <input> [flags]

Para escanear un objetivo en busca de API usando una lista de palabras podemos:

kr scan https://example.com/api -w /usr/share/wordlists/apis/routes-large.kite --fail-status-codes 404,403

FFUF/DirBuster/GoBuster

FFUF, DirBuster y GoBuster están diseñados para descubrir rutas y archivos ocultos en servidores web mediante técnicas de fuerza bruta. Los tres utilizan listas de palabras personalizables para generar peticiones al servidor web objetivo, intentando identificar directorios y archivos válidos. Los tres soportan procesamiento multihilo o altamente eficiente para acelerar el proceso de fuerza bruta.

Algunos archivos de listas de palabras comunes para API incluyen: SecLists en la sección Discovery/Web-Content/API, GraphQL Wordlist y Assetnote.

Ejemplo con GoBuster:

gobuster dir -u <target url> -w <wordlist file>

Fuzzing autenticado

Al hacer fuzzing de API autenticadas, hay que reproducir la misma autenticación y gestión de sesiones que espera el objetivo. Se deben incluir tokens personalizados, cabeceras de autorización no estándar, metadatos de petición firmados o cookies según se requiera; de lo contrario, las herramientas pueden producir falsos negativos al no llegar nunca a la lógica de la aplicación. Si el mecanismo usa campos dinámicos (por ejemplo marcas de tiempo, nonces o firmas vinculadas al cuerpo), esos valores se deben recalcular para cada petición mutada, normalmente mediante scripts previos a la petición o interceptores de proxy/peticiones.
