Autorización rota a nivel de función en API (BFLA)

ID
WSTG-APIT-04

Resumen

Broken Function Level Authorization (BFLA) ocurre cuando una API aplica de forma indebida las restricciones sobre los usuarios que acceden a ciertas funciones u operaciones. Esta vulnerabilidad permite a los atacantes invocar funciones sensibles que no están autorizados a ejecutar, como funciones administrativas u otras operaciones de alto privilegio.

BFLA surge comúnmente cuando las API exponen múltiples endpoints que atienden a diferentes roles de usuario (p. ej., usuario frente a administrador) pero no restringen el acceso a estas funciones según el nivel de autorización del usuario.

Explotar BFLA puede tener consecuencias graves, como la escalada de privilegios, el acceso no autorizado a funciones sensibles (p. ej., operaciones administrativas) o la exposición de funcionalidades críticas que solo deberían ser accesibles para roles de usuario específicos.

Objetivos de la prueba

  • El objetivo de esta prueba es determinar si la API aplica un control de acceso basado en roles o privilegios para impedir que los usuarios accedan a funciones, o las ejecuten, que no están autorizados a utilizar. Esto asegura que los límites de seguridad a nivel de función se apliquen correctamente.

Cómo probar

Identificar endpoints a nivel de función

Revisar la documentación de la API (p. ej., la especificación OpenAPI), el tráfico, o usar un proxy de interceptación (p. ej., Burp Suite, ZAP) para identificar los diferentes endpoints a nivel de función. Estos pueden incluir:

  • Funciones administrativas (p. ej., /api/admin/deleteUser, /api/admin/getAllUsers)
  • Operaciones basadas en roles (p. ej., /api/admin/promoteUser, /api/user/createOrder)
  • Funciones críticas para los usuarios (p. ej., /api/user/withdrawFunds)

Centrarse en las diferencias de funcionalidad entre los distintos roles de usuario (p. ej., usuario normal, administrador, socio, invitado) y en los endpoints que ofrecen capacidades más sensibles.

Manipular los controles de acceso basados en roles

Intentar acceder a operaciones sensibles expuestas en los endpoints de la API, o realizarlas, que deberían estar restringidas según los roles de usuario.

Iniciar sesión como un usuario con menos privilegios (p. ej., invitado o usuario normal) y enviar peticiones a endpoints que realizan acciones sensibles reservadas para roles con mayores privilegios (p. ej., administrador).

Ejemplo: como usuario normal, enviar una petición al siguiente endpoint administrativo para eliminar un usuario aleatorio:

POST /api/admin/deleteUser
Authorization: Bearer <regular_user_token>

{ "userId": "12345" }

Probar el acceso a nivel de función con distintos métodos HTTP

Probar varios métodos HTTP en busca de vulnerabilidades BFLA. Probar cada recurso identificado con métodos HTTP alternativos. Emitir peticiones con métodos distintos de los documentados (como PUT, DELETE o PATCH) contra endpoints que normalmente solo aceptan GET o POST. Registrar cualquier diferencia en el comportamiento de la respuesta o en el resultado de la autorización.

  • GET: Intentar acceder a información disponible solo para usuarios con altos privilegios, como los administradores.
    • Ejemplo: GET /api/admin/getAllUsers
  • POST/PUT/PATCH: Intentar modificar o crear recursos sensibles, como cambiar roles de usuario o datos críticos del sistema.
    • Ejemplo: POST /api/admin/promoteUser { "userId": "12345", "newRole": "admin" }
  • DELETE: Intentar eliminar recursos sensibles, como eliminar cuentas de usuario o datos.
    • Ejemplo: DELETE /api/admin/deleteUser/12345

Probar BFLA en API GraphQL

En las API GraphQL, probar si un usuario puede invocar funciones restringidas a roles con mayores privilegios modificando las consultas GraphQL.

Ejemplo: mutation { deleteUser(id: "12345") { success } }.

Indicadores de BFLA

  • Explotación exitosa: Si un usuario con menos privilegios (p. ej., usuario normal o invitado) puede ejecutar funciones de altos privilegios o realizar acciones reservadas para otros roles (p. ej., administrador).
  • Respuestas de error: Las API correctamente protegidas, en general, devolverían 403 Forbidden o 401 Unauthorized al invocar funciones restringidas en lugar de una respuesta 200 OK.
  • Aplicación inconsistente: Algunos endpoints aplican restricciones basadas en roles y otros no, lo que indica controles de seguridad inconsistentes.

Correcciones

Para prevenir las vulnerabilidades BFLA, implementar las siguientes mitigaciones:

  • Aplicar control de acceso basado en roles (RBAC): Asegurar que la API compruebe los roles y permisos del usuario a nivel de función antes de permitir el acceso a ciertas operaciones. Solo se debe permitir que los roles autorizados invoquen funciones sensibles.
  • Principio de mínimo privilegio: Aplicar el principio de mínimo privilegio asegurando que los usuarios solo puedan acceder al conjunto mínimo de funciones que necesitan para su rol.
  • Lógica de control de acceso centralizada: Usar lógica de control de acceso centralizada para asegurar la coherencia en todos los endpoints de la API. Esto evita brechas en las que algunas funciones carezcan de las comprobaciones de acceso adecuadas.

Herramientas

  • ZAP: Usar escáneres automatizados y herramientas manuales de proxy para inspeccionar las peticiones y respuestas de la API en busca de vulnerabilidades BFLA.
  • Burp Suite: Usar Repeater o Intruder para enviar peticiones como usuarios con menos privilegios y probar si se aplican las restricciones a nivel de función.
  • Postman: Enviar manualmente peticiones a la API como diferentes roles de usuario y observar las respuestas.
  • Herramientas de fuzzing: Usar fuzzers para probar diferentes parámetros y métodos de función con el fin de identificar posibles debilidades de autorización.
