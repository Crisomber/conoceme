Descripción general de las pruebas de API

Introducción a las API web

Una interfaz de programación de aplicaciones web (Web API) facilita la comunicación y el intercambio de datos entre diferentes sistemas de software a través de una red o de internet. Las API web permiten que distintas aplicaciones interactúen entre sí de manera estandarizada y eficiente, lo que les permite aprovechar mutuamente sus funcionalidades y datos.

La adopción de diferentes tecnologías, como la computación en la nube, las arquitecturas de microservicios y las aplicaciones de página única, ha contribuido a la adopción de las API como un movimiento arquitectónico.

Como ocurre con la introducción de cualquier concepto nuevo, puede haber fallos y vulnerabilidades que hagan necesario realizar pruebas. De lo contrario, las API mal protegidas pueden ofrecer un camino directo y sin restricciones hacia datos sensibles.

Este capítulo intenta guiar al investigador de seguridad en los conceptos necesarios para probar API. Esta sección en particular examina las diferentes tecnologías de API y su historia.

¿Qué tecnología de API?

Antes de hacer suposiciones sobre el tipo de API que se está probando, puede ser útil conocer todo el alcance del espacio de problemas que el investigador de seguridad puede encontrar. Estos incluyen:

  1. API Representational State Transfer (REST)
  2. API Simple Object Access Protocol (SOAP)
  3. API GraphQL
  4. gRPC Remote Procedure Calls (gRPC)
  5. API WebSockets

API REST (Representational State Transfer)

¿Qué es REST?

REST es un conjunto de reglas y convenciones para interactuar con recursos web. Los componentes clave de URI, métodos HTTP, cabeceras y códigos de estado respaldan los principios de REST.

Historia

Debido a su simplicidad, escalabilidad y compatibilidad con la infraestructura web existente, las API basadas en REST se han convertido en la arquitectura de API más común en internet al momento de escribir esto. Las API basadas en REST no surgieron de inmediato, sino que tuvieron un largo camino desde la investigación hasta su adopción.

En 1994, Roy Fielding, uno de los autores principales de la especificación HTTP, comenzó su trabajo sobre REST como parte de su tesis doctoral en la Universidad de California, Irvine. En el año 2000 publicó su tesis, Architectural Styles and the Design of Network-based Software Architectures, donde introdujo y definió REST como un estilo arquitectónico. REST fue diseñado para aprovechar las características existentes de HTTP, haciendo énfasis en la escalabilidad, las interacciones sin estado y una interfaz uniforme.

En la década de 2010, REST se convirtió en el estándar de facto para las API web debido a su simplicidad y a su compatibilidad con la arquitectura subyacente de la web. El uso generalizado de las API RESTful fue impulsado por el crecimiento de las aplicaciones móviles, la computación en la nube y la arquitectura de microservicios. El desarrollo de herramientas y frameworks como Swagger/OpenAPI, RAML y API Blueprint facilitó el diseño, la documentación y las pruebas de las API REST.

Para la década de 2020, los desarrollos modernos hicieron evolucionar REST con tecnologías como GraphQL. Además, la especificación OpenAPI/Swagger se convirtió en un estándar ampliamente adoptado para describir API REST, lo que permitió una mejor integración y automatización.

Identificadores uniformes de recursos (URI)

Las API REST utilizan Uniform Resource Identifiers (URI) para acceder a los recursos. Las URI son un elemento crucial de una arquitectura REST. Una URI es una cadena de caracteres que identifica de forma única un recurso en particular. Las URI se utilizan ampliamente en internet para localizar e interactuar con recursos, como páginas web, archivos y servicios.

Una URI consta de varios componentes, cada uno con un propósito específico. La sintaxis genérica de las URI definida en la RFC3986 es la siguiente:

URI = scheme "://" authority "/" path [ "?" query ] [ "#" fragment ]

Para REST, el scheme (esquema) suele ser HTTP o HTTPS, pero de forma genérica indica el protocolo o método utilizado para acceder al recurso. Otros esquemas comunes incluyen ftp, mailto y file.

La authority (autoridad) especifica el nombre de dominio o la dirección IP del servidor donde reside el recurso, y puede incluir un número de puerto. También puede incluir información de usuario (userinfo) como subcomponente.

El path (ruta) especifica la ubicación concreta del recurso en el servidor. Nos interesa la ruta de la URI como la relación entre el usuario y los recursos. Por ejemplo, https://api.example.com/admin/testing/report puede mostrar un informe de pruebas. Existe una relación entre el usuario admin y sus informes.

La ruta de cualquier URI definirá un modelo de recursos de la API REST. Los recursos se separan con una barra diagonal y se basan en un diseño descendente (Top-Down).

Por ejemplo:

  • https://api.example.com/admin/testing/report
  • https://api.example.com/admin/testing/
  • https://api.example.com/admin/

La query (consulta) proporciona parámetros adicionales para el recurso. Comienza con ? y consiste en pares clave-valor separados por &.

El fragment (fragmento) indica una parte específica del recurso, como una sección dentro de una página web. Comienza con #. Vale la pena señalar que los identificadores de fragmento solo se procesan del lado del cliente y no se envían al servidor.

Métodos HTTP

Las API REST utilizan métodos HTTP estándar para realizar operaciones sobre los recursos, siguiendo los HTTP Request Methods definidos en la RFC7231. Estos métodos se corresponden con CRUD, las cuatro funciones básicas del almacenamiento persistente en informática. CRUD significa Create, Read, Update y Delete (crear, leer, actualizar y eliminar), que son las cuatro operaciones que se pueden realizar sobre los datos.

Los métodos de petición HTTP son:

Métodos Descripción
GET Obtener la representación del estado del recurso
POST Crear un nuevo recurso
PUT Actualizar un recurso
DELETE Eliminar un recurso
HEAD Obtener los metadatos asociados al estado del recurso
OPTIONS Listar los métodos disponibles

Cabeceras

REST depende de las cabeceras para soportar la comunicación de información adicional dentro de la petición o la respuesta. Estas incluyen:

  • Content-Type: Indica el tipo de medio del recurso (p. ej., application/json).
  • Authorization: Contiene las credenciales para la autenticación (p. ej., tokens).
  • Accept: Especifica los tipos de medios aceptables para la respuesta.

Códigos de estado

Las API de aplicaciones que se ajustan a los principios REST utilizan el código de estado de un mensaje de respuesta HTTP para notificar al cliente el resultado de su petición.

Código de respuesta Mensaje de respuesta Descripción
200 OK Éxito al procesar la petición del cliente
201 Created Nuevo recurso creado
301 Moved Permanently Redirección permanente
304 Not Modified Respuesta relacionada con la caché que se devuelve cuando el cliente tiene la misma copia del recurso que el servidor
307 Temporary Redirect Redirección temporal del recurso
400 Bad Request Petición mal formada por el cliente
401 Unauthorized El cliente no tiene permitido hacer peticiones o acceder a un recurso en particular
403 Forbidden Al cliente se le prohíbe acceder al recurso
404 Not Found El recurso no existe o es incorrecto según la petición
405 Method Not Allowed Se usó un método inválido o desconocido
500 Internal Server Error El servidor no pudo procesar la petición debido a un error interno
