Exposición excesiva de datos

ID
WSTG-APIT-03

Resumen

La exposición excesiva de datos (excessive data exposure) ocurre cuando una API devuelve en sus respuestas más información de la que el cliente necesita para mostrar o funcionar. Esto sucede comúnmente cuando los desarrolladores implementan endpoints de API serializando objetos completos del backend (como modelos de base de datos o estructuras de datos internas) directamente en las respuestas de la API, confiando en que el código del lado del cliente filtre los campos sensibles antes de presentarlos al usuario.

El problema es que las respuestas de la API son directamente accesibles para cualquiera que pueda hacer peticiones, independientemente de lo que la interfaz de usuario decida mostrar. Un atacante que inspeccione el tráfico sin procesar de la API puede observar todos los campos devueltos, incluidos aquellos que la interfaz oculta intencionalmente. Esto puede exponer contraseñas, tokens de autenticación, identificadores internos, información de identificación personal (PII), datos financieros, detalles de la infraestructura o lógica de negocio interna.

Esta vulnerabilidad se corresponde con OWASP API Security Top 10 API3:2023 Broken Object Property Level Authorization.

Objetivos de la prueba

  • Identificar las respuestas de la API que contienen más datos de los que la aplicación cliente muestra o requiere.
  • Detectar campos sensibles devueltos en las respuestas de la API, como hashes de contraseñas, tokens de autenticación, IDs internos de objetos, PII o detalles de la infraestructura.
  • Determinar si la API depende del filtrado del lado del cliente en lugar de la selección de campos del lado del servidor para controlar la exposición de datos.

Cómo probar

Comparar las respuestas de la API con los datos mostrados

La prueba más directa consiste en comparar lo que muestra la interfaz de usuario con lo que la API realmente devuelve.

  1. Abrir la aplicación en un navegador y navegar a una página que muestre datos de usuario u objetos (p. ej., una página de perfil, un resumen de pedido o un panel).
  2. Abrir las herramientas para desarrolladores del navegador (pestaña Network) o configurar un proxy de interceptación como Burp Suite o ZAP.
  3. Identificar las peticiones a la API que rellenan el contenido de la página.
  4. Comparar los campos mostrados en la interfaz con el conjunto completo de campos de la respuesta de la API.

Por ejemplo, una página de perfil de usuario puede mostrar solo un nombre y un correo electrónico, pero la respuesta subyacente de la API puede devolver:

{
  "id": 12045,
  "name": "Alice Johnson",
  "email": "alice@example.com",
  "password_hash": "$2b$12$LJ3m4ys5qGn...",
  "role": "admin",
  "internal_account_id": "ACC-2024-88421",
  "ssn": "123-45-6789",
  "api_key": "REDACTED_EXAMPLE_KEY_12345",
  "created_by": "system_migration_v2",
  "last_login_ip": "10.0.3.47"
}

En este caso, la API devuelve hashes de contraseñas, números de seguro social, claves de API, identificadores internos y direcciones IP internas que la interfaz nunca muestra.

Inspeccionar las respuestas de distintos endpoints de la API

No hay que limitar las pruebas a un único endpoint. Se deben revisar las respuestas de múltiples tipos de endpoints:

  • Endpoints de usuarios y cuentas: GET /api/users/{id}, GET /api/me, GET /api/account
  • Endpoints de listado y búsqueda: GET /api/users, GET /api/orders?status=completed (los endpoints de listado con frecuencia devuelven el mismo objeto completo para cada elemento de la lista, amplificando la exposición)
  • Endpoints de objetos relacionados: GET /api/orders/{id} puede incrustar objetos de usuario completos, detalles de pago o direcciones de envío dentro de la respuesta del pedido
  • Respuestas de error: Las peticiones fallidas pueden devolver mensajes de error detallados que contienen trazas de pila, rutas internas de archivos, detalles de consultas a la base de datos o valores de configuración
  • Endpoints administrativos o internos: Comprobar si los endpoints destinados al uso interno son accesibles externamente y devuelven datos con privilegios elevados

Probar con distintos niveles de privilegio de usuario

El mismo endpoint puede devolver distintas cantidades de datos según el rol del usuario que realiza la petición. Hay que probar si:

  • Un usuario con pocos privilegios recibe los mismos campos que un administrador al solicitar el mismo recurso.
  • Una petición no autenticada devuelve datos que deberían requerir autenticación.
  • Solicitar los datos de otro usuario (IDOR) devuelve el mismo objeto completo que solicitar los propios.

Por ejemplo, GET /api/users/124 podría devolver el objeto completo, incluidos los campos sensibles, sin importar si quien hace la petición es el usuario 124, otro usuario o un usuario no autenticado.

Analizar objetos anidados e incrustados

Las API modernas con frecuencia incrustan objetos relacionados dentro de las respuestas. Una sola llamada a la API puede devolver estructuras profundamente anidadas que exponen datos de múltiples sistemas del backend.

Ejemplo: Un endpoint de pedidos que devuelve un objeto de cliente, un objeto de pago y un objeto de envío incrustados:

{
  "order_id": "ORD-9923",
  "items": [...],
  "customer": {
    "id": 5001,
    "name": "Bob Smith",
    "email": "bob@example.com",
    "phone": "+1-555-0199",
    "date_of_birth": "1985-03-14",
    "loyalty_tier": "gold"
  },
  "payment": {
    "method": "card",
    "card_last_four": "4242",
    "card_brand": "Visa",
    "card_fingerprint": "fp_abc123xyz",
    "billing_address": {...}
  },
  "internal_notes": "Customer flagged for manual review - suspected fraud"
}

Cada objeto anidado debe revisarse en busca de campos que excedan lo que el cliente consumidor necesita.

Probar la asignación masiva (mass assignment)

Para los endpoints que aceptan un cuerpo JSON o XML, se debe probar la existencia de vulnerabilidades de asignación masiva (mass assignment) añadiendo al cuerpo de la petición campos adicionales a los que se muestran en la interfaz de la aplicación. Campos como identificadores de rol, indicadores de privilegios o atributos de estado de la cuenta son objetivos de alto valor.

Comprobar datos sensibles en las respuestas de GraphQL

Las API GraphQL presentan una forma específica de este problema. Aunque GraphQL permite a los clientes seleccionar los campos que desean, el esquema puede exponer campos sensibles que las consultas predeterminadas de la interfaz no solicitan pero que un atacante puede añadir a una consulta personalizada.

  1. Si la introspección está habilitada, obtener el esquema y revisar los campos disponibles en cada tipo (consulte Testing GraphQL):

    {
  __type(name: "User") {
    fields {
      name
      type { name }
    }
  }
}

  2. Buscar campos como passwordHash, apiKey, ssn, internalId, role o isAdmin que se puedan consultar pero que el frontend no utilice.

  3. Intentar consultar estos campos directamente:

    {
  user(id: "123") {
    name
    email
    passwordHash
    apiKey
    role
  }
}

Examinar los source maps de JavaScript y los bundles del lado del cliente

Los bundles de JavaScript del frontend y los source maps pueden revelar de forma inadvertida la estructura de respuesta esperada de la API, incluidos los campos que la interfaz oculta intencionalmente. Si los source maps son accesibles públicamente (p. ej., en main.js.map), pueden exponer:

  • La lista completa de campos que el frontend espera de las respuestas de la API
  • Rutas internas de endpoints de la API
  • La lógica de los flujos de autenticación y autorización
  • Claves de API, tokens o valores de configuración codificados directamente en el código

Probar la disponibilidad de source maps:

GET /static/js/main.js.map
GET /assets/app.js.map

Si el source map es accesible y contiene sourcesContent, el código fuente original puede reconstruirse y analizarse para obtener las estructuras de respuesta esperadas de la API y los campos ocultos.

Comprobar las respuestas de error y la salida de depuración

Las API pueden filtrar información sensible a través de las respuestas de error, particularmente cuando se ejecutan en modo de desarrollo o depuración:

  • Trazas de pila que revelan rutas internas de archivos, versiones del framework y la estructura del código
  • Mensajes de error de la base de datos que exponen nombres de tablas, nombres de columnas o sintaxis de consultas
  • Errores de validación detallados que enumeran todos los campos esperados, incluidos los no documentados en la API pública
  • Cabeceras de depuración como X-Debug-Token, X-Powered-By o cabeceras personalizadas que contienen información interna

Se pueden provocar respuestas de error enviando entrada mal formada, autenticación inválida o peticiones de recursos inexistentes, e inspeccionando la respuesta completa, incluidas las cabeceras.

Corrección

  • Implementar el filtrado de respuestas del lado del servidor. Nunca devolver objetos sin procesar de la base de datos ni serializaciones completas de modelos en las respuestas de la API. Definir explícitamente esquemas de respuesta que incluyan solo los campos que el cliente necesita para cada endpoint y contexto.
  • Usar Data Transfer Objects (DTOs) o listas de permitidos de serialización. Mapear los objetos internos a objetos de respuesta específicos para cada propósito que contengan solo los campos permitidos. La mayoría de los frameworks web ofrecen mecanismos para ello (p. ej., los serializers en Django REST Framework, JsonView en Spring o ActiveModel::Serializers en Rails).
  • Aplicar control de acceso a nivel de campo. Algunos campos (como las direcciones de correo electrónico o los números de teléfono) pueden ser apropiados para un consumidor pero no para otro. Implementar lógica para incluir o excluir campos según el rol del usuario que realiza la petición y su relación con el recurso solicitado.
  • Evitar exponer identificadores internos. Usar identificadores de cara al exterior (como UUIDs o tokens opacos) en lugar de IDs secuenciales internos de la base de datos, que revelan el número de registros y permiten la enumeración.
  • Restringir los esquemas GraphQL. Eliminar por completo los campos sensibles del esquema GraphQL en lugar de depender de comprobaciones a nivel de resolver. Si un campo debe existir en el esquema para uso interno, aplicar directivas de autorización para impedir el acceso no autorizado.
  • Deshabilitar los source maps en producción. No desplegar source maps de JavaScript en entornos de producción. Configurar el pipeline de compilación para excluir los archivos .map de los artefactos de producción.
  • Sanear las respuestas de error. Devolver mensajes de error genéricos en producción. Registrar la información detallada de los errores en el lado del servidor, pero no incluir trazas de pila, rutas internas ni detalles de consultas en las respuestas dirigidas al cliente.

Herramientas

  • Burp Suite: Usar la herramienta Comparer para comparar el contenido mostrado en la interfaz con las respuestas sin procesar de la API. Las herramientas Repeater e Intruder pueden usarse para probar sistemáticamente los endpoints con diferentes parámetros y contextos de autenticación.
  • ZAP (Zed Attack Proxy): Interceptar e inspeccionar las respuestas de la API, usar reglas de escaneo activo para identificar la divulgación de información y las capacidades de fuzzing para provocar respuestas de error detalladas.
  • Postman: Enviar peticiones a la API con diferentes tokens de autenticación y comparar los cuerpos de las respuestas para identificar diferencias de exposición de datos que dependan del rol.
  • Herramientas para desarrolladores del navegador: La pestaña Network proporciona visibilidad inmediata de las respuestas de la API sin necesidad de configurar un proxy. Es útil para comparar rápidamente los datos renderizados en la interfaz con el contenido sin procesar de la respuesta.
  • jq: Procesador JSON de línea de comandos para extraer y comparar campos entre respuestas de la API: curl -s https://api.example.com/users/me | jq 'keys' lista todos los campos devueltos.
