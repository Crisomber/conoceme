Información sensible enviada por canales sin cifrar

ID
WSTG-CRYP-03

Resumen

Los datos sensibles deben protegerse cuando se transmiten por la red. Si los datos se transmiten por HTTPS o se cifran de otra manera, el mecanismo de protección no debe tener limitaciones ni vulnerabilidades, como se explica en el artículo más amplio Seguridad débil en la capa de transporte y en otra documentación de OWASP:

  • A04:2025 Cryptographic Failures.
  • OWASP ASVS - Verification V9.
  • Transport Layer Protection Cheat Sheet.

Como regla general, si los datos deben protegerse cuando se almacenan, también deben protegerse durante la transmisión. Algunos ejemplos de datos sensibles son:

  • Información utilizada en la autenticación (p. ej. credenciales, PIN, identificadores de sesión, tokens, cookies, etc.)
  • Información protegida por leyes, regulaciones o una política organizacional específica (p. ej. tarjetas de crédito, historiales médicos, datos personales, etc.)

Si la aplicación transmite información sensible por canales sin cifrar como HTTP, se considera un riesgo de seguridad. Los atacantes pueden tomar el control de cuentas mediante sniffing del tráfico de red. Algunos ejemplos son la autenticación Basic, que envía las credenciales de autenticación en texto plano por HTTP, las credenciales de autenticación basada en formularios enviadas por HTTP, o la transmisión en texto plano de cualquier otra información considerada sensible por regulaciones, leyes, política organizacional o la lógica de negocio de la aplicación.

Ejemplos de Información de Identificación Personal (PII) son:

  • Números de seguro social
  • Números de cuentas bancarias
  • Información de pasaporte
  • Información relacionada con la salud
  • Información de seguro médico
  • Información de estudiantes
  • Números de tarjetas de crédito y débito
  • Información de licencia de conducir y de identificación estatal

Objetivos de la prueba

  • Identificar la información sensible transmitida a través de los diversos canales.
  • Evaluar la privacidad y la seguridad de los canales utilizados.

Cómo probar

Diversos tipos de información que debe protegerse podrían ser transmitidos en texto claro por la aplicación. Para comprobar si esta información se transmite por HTTP en lugar de HTTPS, se debe capturar el tráfico entre un cliente y el servidor de la aplicación web que requiere credenciales. Para cualquier mensaje que contenga datos sensibles, se debe verificar que el intercambio se realizó mediante HTTPS. Véase más información sobre la transmisión insegura de credenciales en A04:2025 Cryptographic Failures o en la Transport Layer Protection Cheat Sheet.

Autenticación Basic sobre HTTP

Un ejemplo típico es el uso de la autenticación Basic sobre HTTP. Al usar la autenticación Basic, las credenciales del usuario se codifican en lugar de cifrarse y se envían como cabeceras HTTP. En el siguiente ejemplo el evaluador utiliza curl para probar este problema. Obsérvese cómo la aplicación usa autenticación Basic y HTTP en lugar de HTTPS.

$ curl -kis http://example.com/restricted/
HTTP/1.1 401 Authorization Required
Date: Fri, 01 Aug 2013 00:00:00 GMT
WWW-Authenticate: Basic realm="Restricted Area"
Accept-Ranges: bytes Vary:
Accept-Encoding Content-Length: 162
Content-Type: text/html

<html><head><title>401 Authorization Required</title></head>
<body bgcolor=white> <h1>401 Authorization Required</h1>  Invalid login credentials!  </body></html>

Autenticación basada en formularios realizada sobre HTTP

Otro ejemplo típico son los formularios de autenticación que transmiten las credenciales de autenticación del usuario por HTTP. En el siguiente ejemplo se puede ver que se usa HTTP en el atributo action del formulario. También es posible ver este problema examinando el tráfico HTTP con un proxy interceptor.

<form action="http://example.com/login">
    <label for="username">User:</label> <input type="text" id="username" name="username" value=""/><br />
    <label for="password">Password:</label> <input type="password" id="password" name="password" value=""/>
    <input type="submit" value="Login"/>
</form>

Si no es posible forzar la navegación a un endpoint HTTP en un navegador (por ejemplo, debido a HSTS o al comportamiento de la caché), se debe solicitar el mismo endpoint con curl e inspeccionar la respuesta directamente. Un endpoint correctamente protegido debería devolver de inmediato una respuesta 3XX que redirija a una URL HTTPS.

$ curl -kis -o /dev/null -D - http://example.com/login
HTTP/1.1 301 Moved Permanently
Location: https://example.com/login

Si el servidor responde con 200, sirve contenido por HTTP o redirige a otro endpoint HTTP, entonces la información sensible aún puede estar expuesta en un transporte sin cifrar.

Cookie con ID de sesión enviada por HTTP

La cookie del ID de sesión debe transmitirse por canales protegidos. Si la cookie no tiene establecido el atributo Secure, se permite que la aplicación la transmita sin cifrar. Obsérvese a continuación que la cookie se establece sin el atributo Secure y que todo el proceso de inicio de sesión se realiza en HTTP y no en HTTPS.

https://secure.example.com/login

POST /login HTTP/1.1
Host: secure.example.com
[...]
Referer: https://secure.example.com/
Content-Type: application/x-www-form-urlencoded
Content-Length: 188

HTTP/1.1 302 Found
Server: Apache
Set-Cookie: JSESSIONID=BD99F321233AF69593EDF52B123B5BDA; expires=Fri, 01-Jan-2014 00:00:00 GMT; path=/; domain=example.com; httponly
[...]

http://example.com/private

GET /private HTTP/1.1
Host: example.com
[...]
Referer: https://secure.example.com/login
Cookie: JSESSIONID=BD99F321233AF69593EDF52B123B5BDA;

HTTP/1.1 200 OK
[...]

Restablecimiento de contraseña, cambio de contraseña u otra manipulación de la cuenta sobre HTTP

Si la aplicación web tiene funciones que permiten a un usuario cambiar una cuenta o llamar a un servicio diferente con credenciales, se debe verificar que todas esas interacciones usen HTTPS. Las interacciones a probar incluyen formularios que:

  • Permiten a los usuarios gestionar una contraseña olvidada u otras credenciales.
  • Permiten a los usuarios editar credenciales.
  • Requieren que el usuario se autentique con otro proveedor (por ejemplo, el procesamiento de pagos).

Prueba de información sensible de contraseñas en el código fuente o en los logs

Se puede usar una de las siguientes técnicas para buscar información sensible.

Comprobar si la contraseña o la clave de cifrado está codificada de forma fija (hardcoded) en el código fuente o en los archivos de configuración.

grep -r -E "Pass | password | pwd |user | guest| admin | encry | key | decrypt | sharekey " ./PathToSearch/

Comprobar si los logs o el código fuente pueden contener número de teléfono, dirección de correo electrónico, ID o cualquier otra PII. Se debe cambiar la expresión regular según el formato de la PII.

grep -r " {2\}[0-9]\{6\} " ./PathToSearch/

Corrección

Utilizar HTTPS en todo el sitio web y redirigir cualquier petición HTTP a HTTPS.
