Seguridad débil en la capa de transporte

ID
WSTG-CRYP-01

Resumen

Cuando la información se envía entre el cliente y el servidor, debe estar cifrada y protegida para impedir que un atacante pueda leerla o modificarla. Esto se hace con mayor frecuencia mediante HTTPS, que utiliza el protocolo Transport Layer Security (TLS), un reemplazo del antiguo protocolo Secure Socket Layer (SSL). TLS también ofrece una forma para que el servidor demuestre al cliente que se ha conectado al servidor correcto, presentando un certificado digital de confianza.

A lo largo de los años se han identificado un gran número de debilidades criptográficas en los protocolos SSL y TLS, así como en los cifrados que utilizan. Además, muchas de las implementaciones de estos protocolos también han tenido vulnerabilidades graves. Por ello, es importante comprobar que los sitios no solo implementan TLS, sino que lo hacen de forma segura.

Objetivos de la prueba

  • Validar la configuración del servicio.
  • Revisar la fortaleza criptográfica y la validez del certificado digital.
  • Asegurar que la seguridad TLS no se pueda evadir y que esté correctamente implementada en toda la aplicación.

Cómo probar

Los problemas relacionados con la seguridad de la capa de transporte pueden dividirse en términos generales en las siguientes áreas:

Configuración del servidor

TLS admite una gran cantidad de versiones de protocolo, cifrados y extensiones. Muchos de ellos se consideran heredados (legacy) y tienen debilidades criptográficas, como las que se enumeran a continuación. Es probable que con el tiempo se identifiquen nuevas debilidades, por lo que esta lista puede estar incompleta.

  • SSLv2 (DROWN)
  • SSLv3 (POODLE)
  • TLSv1.0 (BEAST)
  • TLSv1.1 (Obsoleto según RFC 8996)
  • Suites de cifrado EXPORT (FREAK)
  • Cifrados NULL (solo proporcionan autenticación).
  • Cifrados anónimos (pueden estar admitidos en servidores SMTP, como se explica en RFC 7672)
  • Cifrados RC4 (NOMORE)
  • Cifrados en modo CBC (BEAST, Lucky 13)
  • Compresión TLS (CRIME)
  • Claves DHE débiles (LOGJAM)

El proyecto TLSRef (anteriormente administrado por Mozilla) ofrece recomendaciones sobre los protocolos y cifrados que se deben utilizar.

Por su compatibilidad con cifrados poscuánticos, se debe preferir TLS 1.3 sobre TLS 1.2.

Explotabilidad

Debe enfatizarse que, aunque muchos de estos ataques se han demostrado en un entorno de laboratorio, en general no se consideran prácticos de explotar en el mundo real, ya que requieren un ataque MitM (normalmente activo) y recursos significativos. Por ello, es poco probable que sean explotados por alguien que no sea un Estado-nación.

Certificados digitales

Debilidades criptográficas

Desde una perspectiva criptográfica, hay dos áreas principales que deben revisarse en un certificado digital: la firma del propio certificado y el algoritmo de intercambio de claves utilizado durante el handshake de TLS. Al usar criptografía clásica, se deben considerar los siguientes puntos:

  • La fortaleza del cifrado utilizado debe ser de al menos 128 bits de seguridad o superior.
  • Para firmas clásicas se debe usar al menos RSA-3072 o ECDSA con P-256 en combinación con SHA-256 o superior.
  • Para un intercambio de claves clásico se debe usar ECDHE con las curvas elípticas P-256 o X25519 como mínimo.

Además, tanto la firma como el algoritmo de intercambio de claves deben ser compatibles con la criptografía poscuántica. Se deben considerar los siguientes puntos:

  • Para firmas poscuánticas se debe usar al menos ML-DSA-44 (según FIPS-204) o superior.
  • Para intercambios de claves poscuánticos se debe usar al menos ML-KEM-512 (según FIPS-203) o superior.
  • Se pueden usar cifrados híbridos como X25519+ML-KEM-768 durante la transición a los algoritmos poscuánticos.

Validez

Además de ser criptográficamente seguro, el certificado también debe considerarse válido (o de confianza). Esto significa que debe:

  • Estar dentro del período de validez definido.
    • Los certificados emitidos después del 1 de septiembre de 2020 no deben tener una vigencia máxima superior a 398 días.
    • El período de validez de los certificados se reducirá gradualmente hasta una vigencia máxima de 47 días en marzo de 2029.
  • Estar firmado por una autoridad de certificación (CA) de confianza.
    • Esta debe ser una CA pública de confianza para aplicaciones expuestas externamente, o una CA interna para aplicaciones internas.
    • No se debe señalar que las aplicaciones internas tienen certificados no confiables solo porque tu sistema no confía en la CA.
  • Tener un Subject Alternate Name (SAN) que coincida con el nombre de host del sistema.
    • Los navegadores modernos ignoran el campo Common Name (CN) y solo examinan el SAN.
    • Hay que asegurarse de acceder al sistema con el nombre correcto (por ejemplo, si se accede al host por IP, cualquier certificado aparecerá como no confiable).

Algunos certificados pueden emitirse para dominios comodín (wildcard) (como *.example.org), lo que significa que pueden ser válidos para múltiples subdominios. Aunque es conveniente, esto plantea varias preocupaciones de seguridad que deben considerarse. Se analizan en la OWASP Transport Layer Security Cheat Sheet.

Los certificados también pueden filtrar información sobre sistemas internos o nombres de dominio en los campos Issuer y SAN, lo que puede ser útil al intentar construir una imagen de la red interna o realizar actividades de ingeniería social.

Vulnerabilidades de implementación

A lo largo de los años ha habido vulnerabilidades en las diversas implementaciones de TLS. Hay demasiadas para enumerarlas aquí, pero algunos ejemplos clave son:

  • Debian OpenSSL Predictable Random Number Generator (CVE-2008-0166)
  • OpenSSL Insecure Renegotiation (CVE-2009-3555)
  • OpenSSL Heartbleed (CVE-2014-0160)
  • F5 TLS POODLE (CVE-2014-8730)
  • Microsoft Schannel Denial of Service (MS14-066 / CVE-2014-6321)

Vulnerabilidades de la aplicación

Además de que la configuración subyacente de TLS esté configurada de forma segura, la aplicación también debe usarla de manera segura. Algunos de estos puntos se tratan en otras partes de esta guía:

  • No enviar datos sensibles por canales sin cifrar (WSTG-CRYP-03)
  • Configurar la cabecera HTTP Strict-Transport-Security (WSTG-CONF-07)
  • Configurar el atributo Secure en las cookies (WSTG-SESS-02)

Contenido activo mixto

El contenido activo mixto se produce cuando recursos activos (como scripts o CSS) se cargan por HTTP sin cifrar y se incluyen en una página segura (HTTPS). Esto es peligroso porque permitiría a un atacante modificar esos archivos (ya que se envían sin cifrar), lo que podría permitirle ejecutar código arbitrario (JavaScript o CSS) en la página. El contenido pasivo (como las imágenes) cargado a través de una conexión insegura también puede filtrar información o permitir a un atacante desfigurar la página, aunque es menos probable que conduzca a un compromiso total.

Nota: los navegadores modernos bloquean la carga de contenido activo desde fuentes inseguras en páginas seguras.

Redirección de HTTP a HTTPS

Muchos sitios aceptan conexiones por HTTP sin cifrar y luego redirigen inmediatamente al usuario a la versión segura (HTTPS) del sitio con una redirección 301 Moved Permanently. La versión HTTPS del sitio establece entonces la cabecera Strict-Transport-Security para indicar al navegador que utilice siempre HTTPS en el futuro.

Sin embargo, si un atacante puede interceptar esta petición inicial, podría redirigir al usuario a un sitio malicioso o usar una herramienta como sslstrip para interceptar las peticiones posteriores.

Para defenderse de este tipo de ataque, el sitio debe agregarse a la lista de precarga (preload list).

Pruebas automatizadas

Existe un gran número de herramientas de escaneo que pueden utilizarse para identificar debilidades en la configuración SSL/TLS de un servicio, incluidas tanto herramientas dedicadas como escáneres de vulnerabilidades de propósito general. Algunas de las más populares son:

  • Nmap (varios scripts)
  • OWASP O-Saft
  • sslscan
  • sslyze
  • SSL Labs
  • testssl.sh

Pruebas manuales

También es posible realizar la mayoría de las comprobaciones manualmente, usando herramientas de línea de comandos como openssl s_client o gnutls-cli para conectarse con protocolos, cifrados u opciones específicos.

Al realizar pruebas de este modo, hay que tener en cuenta que la versión de OpenSSL o GnuTLS incluida en la mayoría de los sistemas modernos puede no admitir algunos protocolos obsoletos e inseguros como SSLv2 o los cifrados EXPORT. Hay que asegurarse de que la versión utilizada admita las versiones obsoletas antes de usarla para las pruebas, o se obtendrán falsos negativos.

También es posible realizar pruebas limitadas con un navegador web, ya que los navegadores modernos proporcionan en sus herramientas de desarrollo detalles de los protocolos y cifrados que se están utilizando. También ofrecen una forma sencilla de comprobar si un certificado se considera de confianza, navegando al servicio y viendo si se presenta una advertencia de certificado.
