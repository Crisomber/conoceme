Primitivas criptográficas débiles

ID
WSTG-CRYP-04

Resumen

El uso incorrecto de algoritmos de cifrado puede resultar en exposición de datos sensibles, filtración de claves, autenticación rota, sesiones inseguras y ataques de suplantación (spoofing). Hay algunos algoritmos de cifrado o hash que se sabe que son débiles y cuyo uso no se recomienda, como MD5 y RC4.

Además de elegir correctamente algoritmos de cifrado o hash seguros, el uso correcto de los parámetros también importa para el nivel de seguridad. Por ejemplo, el modo ECB (Electronic Code Book) en general no debe utilizarse.

Objetivos de la prueba

  • Proporcionar una guía para la identificación de usos e implementaciones débiles de cifrado o hash.

Cómo probar

Lista de verificación básica de seguridad

  • Al usar AES128 o AES256, el IV (vector de inicialización) debe ser aleatorio e impredecible. Consulte FIPS 140-3, Security Requirements for Cryptographic Modules, sección de pruebas de generación de números aleatorios. Por ejemplo, en Java, java.util.Random se considera un generador de números aleatorios débil. Se debe usar java.security.SecureRandom en lugar de java.util.Random.
  • Para el cifrado asimétrico, se debe usar criptografía de curva elíptica (ECC), con preferencia por una curva segura como Curve25519.
    • Si no se puede usar ECC, se debe usar cifrado RSA con una clave de al menos 2048 bits.
  • Cuando se use RSA en firmas, se recomienda el relleno PSS.
  • No se deben usar algoritmos de hash/cifrado débiles como MD5, RC4, DES, Blowfish, SHA1, RSA o DSA de 1024 bits, ECDSA (curvas elípticas) de 160 bits, ni 2TDEA (triple DES de dos claves) de 80/112 bits.
  • Requisitos mínimos de longitud de clave:
Key exchange: Diffie-Hellman key exchange with minimum 2048 bits
Message Integrity: HMAC-SHA2
Message Hash: SHA2 256 bits
Asymmetric encryption: RSA 2048 bits
Symmetric-key algorithm: AES 128 bits
Password Hashing: PBKDF2, Scrypt, Bcrypt
ECDH, ECDSA: 256 bits
  • En los usos de SSH, no se debe utilizar el modo CBC.
  • Cuando se utilice un algoritmo de cifrado simétrico, no se debe utilizar el modo ECB (Electronic Code Book).
  • Cuando se use PBKDF2 para hacer hash de contraseñas, se recomienda que el parámetro de iteraciones sea superior a 10000. NIST también sugiere al menos 10,000 iteraciones de la función hash. Además, está prohibido usar la función hash MD5 con PBKDF2, como en PBKDF2WithHmacMD5.

Revisión de código fuente

  • Buscar las siguientes palabras clave para identificar el uso de algoritmos débiles: MD4, MD5, RC4, RC2, DES, Blowfish, SHA-1, ECB

  • Para implementaciones en Java, la siguiente API está relacionada con el cifrado. Se deben revisar los parámetros de la implementación del cifrado. Por ejemplo,

SecretKeyFactory(SecretKeyFactorySpi keyFacSpi, Provider provider, String algorithm)
SecretKeySpec(byte[] key, int offset, int len, String algorithm)
Cipher c = Cipher.getInstance("DES/CBC/PKCS5Padding");
  • Para el cifrado RSA, se sugieren los siguientes modos de relleno.
RSA/ECB/OAEPWithSHA-1AndMGF1Padding (2048)
RSA/ECB/OAEPWithSHA-256AndMGF1Padding (2048)
  • Buscar ECB; no se permite su uso en el relleno.
  • Revisar si se utiliza un IV (vector inicial) diferente.
// Use a different IV value for every encryption
byte[] newIv = ...;
s = new GCMParameterSpec(s.getTLen(), newIv);
cipher.init(..., s);
...
  • Buscar IvParameterSpec y comprobar si el valor del IV se genera de forma diferente y aleatoria.
 IvParameterSpec iv = new IvParameterSpec(randBytes);
 SecretKeySpec skey = new SecretKeySpec(key.getBytes(), "AES");
 Cipher cipher = Cipher.getInstance("AES/CBC/PKCS5Padding");
 cipher.init(Cipher.ENCRYPT_MODE, skey, iv);
  • En Java, buscar MessageDigest para comprobar si se usa un algoritmo de hash débil (MD5 o CRC). Por ejemplo:

MessageDigest md5 = MessageDigest.getInstance("MD5");

  • Para las firmas, no se deben usar SHA1 ni MD5. Por ejemplo:

Signature sig = Signature.getInstance("SHA1withRSA");

  • Buscar PBKDF2. Para generar el valor hash de la contraseña, se sugiere usar PBKDF2. Se deben revisar los parámetros para generar el valor hash de PBKDF2.

Las iteraciones deben ser superiores a 10000, y el valor de salt debe generarse como valor aleatorio.

private static byte[] pbkdf2(char[] password, byte[] salt, int iterations, int bytes)
    throws NoSuchAlgorithmException, InvalidKeySpecException
  {
       PBEKeySpec spec = new PBEKeySpec(password, salt, iterations, bytes * 8);
       SecretKeyFactory skf = SecretKeyFactory.getInstance(PBKDF2_ALGORITHM);
       return skf.generateSecret(spec).getEncoded();
   }
  • Información sensible codificada de forma fija (hard-coded):
User related keywords: name, root, su, sudo, admin, superuser, login, username, uid
Key related keywords: public key, AK, SK, secret key, private key, passwd, password, pwd, share key, shared key, crypto, base64
Other common sensitive keywords: sysadmin, root, privilege, pass, key, code, master, admin, uname, session, token, Oauth, privatekey, shared secret

Herramientas

  • Los escáneres de vulnerabilidades como Nessus, Nmap (scripts) u OpenVAS pueden escanear el uso o la aceptación de cifrado débil en protocolos como SNMP, TLS, SSH, SMTP, etc.
  • Se pueden usar herramientas de análisis estático de código para realizar la revisión de código fuente, como klocwork, Fortify, Coverity o CheckMark, para los siguientes casos.
CWE-261: Weak Cryptography for Passwords
CWE-323: Reusing a Nonce, Key Pair in Encryption
CWE-326: Inadequate Encryption Strength
CWE-327: Use of a Broken or Risky Cryptographic Algorithm
CWE-328: Reversible One-Way Hash
CWE-329: Not Using a Random IV with CBC Mode
CWE-330: Use of Insufficiently Random Values
CWE-347: Improper Verification of Cryptographic Signature
CWE-354: Improper Validation of Integrity Check Value
CWE-547: Use of Hard-coded, Security-relevant Constants
CWE-780: Use of RSA Algorithm without OAEP
