Padding Oracle

ID
WSTG-CRYP-02

Resumen

Un padding oracle es una función de una aplicación que descifra datos cifrados proporcionados por el cliente, p. ej. el estado interno de la sesión almacenado en el cliente, y que filtra el estado de validez del relleno (padding) después del descifrado. La existencia de un padding oracle permite a un atacante descifrar datos cifrados y cifrar datos arbitrarios sin conocer la clave utilizada para estas operaciones criptográficas. Esto puede conducir a la filtración de datos sensibles o a vulnerabilidades de escalada de privilegios, si la aplicación asume la integridad de los datos cifrados.

Los cifrados por bloques cifran los datos solo en bloques de ciertos tamaños. Los tamaños de bloque utilizados por los cifrados comunes son de 8 y 16 bytes. Los datos cuyo tamaño no coincide con un múltiplo del tamaño de bloque del cifrado utilizado deben rellenarse de una manera específica para que quien descifra pueda eliminar el relleno. Un esquema de relleno de uso común es PKCS#7. Este llena los bytes restantes con el valor de la longitud del relleno.

Ejemplo 1

Si el relleno tiene una longitud de 5 bytes, el valor de byte 0x05 se repite cinco veces después del texto plano.

Existe una condición de error si el relleno no coincide con la sintaxis del esquema de relleno utilizado. Hay un padding oracle si una aplicación filtra esta condición de error específica del relleno para datos cifrados proporcionados por el cliente. Esto puede ocurrir al exponer directamente excepciones (p. ej. BadPaddingException en Java), por diferencias sutiles en las respuestas enviadas al cliente o por otro canal lateral como el comportamiento temporal (timing).

Ciertos modos de operación de la criptografía permiten ataques de volteo de bits (bit-flipping), en los que voltear un bit en el texto cifrado provoca que el bit también se voltee en el texto plano. Voltear un bit en el n-ésimo bloque de datos cifrados con CBC provoca que el mismo bit en el bloque (n+1) se voltee en los datos descifrados. El n-ésimo bloque del texto cifrado descifrado queda corrompido por esta manipulación.

El ataque de padding oracle permite a un atacante descifrar datos cifrados sin conocer la clave de cifrado ni el cifrado utilizado, enviando al padding oracle textos cifrados manipulados hábilmente y observando los resultados que este devuelve. Esto provoca la pérdida de confidencialidad de los datos cifrados. P. ej., en el caso de datos de sesión almacenados del lado del cliente, el atacante puede obtener información sobre el estado interno y la estructura de la aplicación.

Un ataque de padding oracle también permite a un atacante cifrar textos planos arbitrarios sin conocer la clave ni el cifrado utilizados. Si la aplicación asume que la integridad y la autenticidad de los datos descifrados están garantizadas, un atacante podría manipular el estado interno de la sesión y posiblemente obtener mayores privilegios.

Objetivos de la prueba

  • Identificar mensajes cifrados que dependen de relleno (padding).
  • Intentar romper el relleno de los mensajes cifrados y analizar los mensajes de error devueltos para un análisis posterior.

Cómo probar

Pruebas de caja negra

Primero se deben identificar los posibles puntos de entrada para padding oracles. Por lo general, deben cumplirse las siguientes condiciones:

  1. Los datos están cifrados. Buenos candidatos son los valores que parecen aleatorios.
  2. Se utiliza un cifrado por bloques. La longitud del texto cifrado decodificado (a menudo se usa Base64) es un múltiplo de tamaños de bloque de cifrado comunes como 8 o 16 bytes. Distintos textos cifrados (p. ej. obtenidos en diferentes sesiones o mediante la manipulación del estado de la sesión) comparten un divisor común en su longitud.

Ejemplo 2

Dg6W8OiWMIdVokIDH15T/A== resulta, tras decodificar base64, en 0e 0e 96 f0 e8 96 30 87 55 a2 42 03 1f 5e 53 fc. Esto parece aleatorio y tiene 16 bytes de longitud.

Si se identifica un valor de entrada candidato de este tipo, se debe verificar el comportamiento de la aplicación ante la manipulación bit a bit del valor cifrado. Normalmente este valor codificado en base64 incluirá el vector de inicialización (IV) antepuesto al texto cifrado. Dado un texto plano p y un cifrado con un tamaño de bloque n, el número de bloques será b = ceil( length(p) / n). La longitud de la cadena cifrada será y=(b+1)*n debido al vector de inicialización. Para verificar la presencia del oracle, se decodifica la cadena, se voltea el último bit del penúltimo bloque b-1 (el bit menos significativo del byte en y-n-1), se vuelve a codificar y se envía. A continuación, se decodifica la cadena original, se voltea el último bit del bloque b-2 (el bit menos significativo del byte en y-2*n-1), se vuelve a codificar y se envía.

Si se sabe que la cadena cifrada es de un solo bloque (el IV se almacena en el servidor o la aplicación usa un IV codificado de forma fija, una mala práctica), se deben realizar varios volteos de bits sucesivamente. Un enfoque alternativo podría ser anteponer un bloque aleatorio y voltear bits para que el último byte del bloque añadido tome todos los valores posibles (0 a 255).

Las pruebas y el valor base deben provocar al menos tres estados diferentes durante y después del descifrado:

  • El texto cifrado se descifra y los datos resultantes son correctos.
  • El texto cifrado se descifra, los datos resultantes están corrompidos y provocan alguna excepción o manejo de errores en la lógica de la aplicación.
  • El descifrado del texto cifrado falla debido a errores de relleno.

Se deben comparar cuidadosamente las respuestas. Se deben buscar especialmente excepciones y mensajes que indiquen que algo anda mal con el relleno. Si aparecen tales mensajes, la aplicación contiene un padding oracle. Si los tres estados descritos anteriormente son observables de forma implícita (mensajes de error diferentes, canales laterales de tiempo), hay una alta probabilidad de que exista un padding oracle en este punto. Se debe intentar realizar el ataque de padding oracle para confirmarlo.

Ejemplo 3
  • ASP.NET lanza System.Security.Cryptography.CryptographicException: Padding is invalid and cannot be removed. si el relleno de un texto cifrado descifrado está roto.
  • En Java se lanza en este caso una javax.crypto.BadPaddingException.
  • Los errores de descifrado o similares pueden ser posibles padding oracles.

Una implementación segura verificará la integridad y provocará solo dos respuestas: ok y failed. No hay canales laterales que puedan usarse para determinar estados de error internos.

Pruebas de caja gris

Se debe verificar todos los lugares donde se descifran datos cifrados provenientes del cliente que solo debería conocer el servidor. Dicho código debe cumplir las siguientes condiciones:

  1. La integridad del texto cifrado debe verificarse mediante un mecanismo seguro, como HMAC o modos de operación de cifrado autenticado como GCM o CCM.
  2. Todos los estados de error durante el descifrado y el procesamiento posterior se manejan de manera uniforme.
