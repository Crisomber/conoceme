Revisión del contenido de las páginas web para detectar fuga de información

ID
WSTG-INFO-05

Resumen

Es muy común, e incluso recomendable, que los programadores incluyan comentarios y metadatos detallados en su código fuente. Sin embargo, los comentarios y metadatos incluidos en el código HTML podrían revelar información interna que no debería estar disponible para posibles atacantes. Se debe realizar una revisión de comentarios y metadatos para determinar si se está filtrando información. Además, algunas aplicaciones pueden filtrar información en el cuerpo de las respuestas de redirección.

En las aplicaciones web modernas, el uso de JavaScript del lado del cliente para el frontend es cada vez más popular. Las tecnologías populares de construcción de frontend utilizan JavaScript del lado del cliente, como React, Angular o Vue. De manera similar a los comentarios y metadatos en el código HTML, muchos programadores también incluyen información sensible directamente en variables de JavaScript en el frontend. La información sensible puede incluir (entre otros): claves de API privadas (por ejemplo, una clave de API de Google Maps sin restricciones), direcciones IP internas, rutas sensibles (por ejemplo, rutas a páginas o funcionalidades de administración ocultas) o incluso credenciales. Esta información sensible puede filtrarse desde dicho código JavaScript del frontend. Se debe realizar una revisión para determinar si se ha filtrado información sensible que los atacantes pudieran utilizar con fines de abuso.

En las aplicaciones web grandes, los problemas de rendimiento son una gran preocupación para los programadores. Los programadores han utilizado diferentes métodos para optimizar el rendimiento del frontend, entre ellos Syntactically Awesome Style Sheets (Sass), Sassy CSS (SCSS), webpack, etc. Con estas tecnologías, el código del frontend a veces se vuelve más difícil de entender y de depurar y, por ello, los programadores suelen desplegar archivos de mapas de código fuente (source maps) con fines de depuración. Un "source map" es un archivo especial que conecta una versión minificada/ofuscada de un recurso (CSS o JavaScript) con la versión original escrita por el autor. Los programadores todavía debaten si se deben llevar o no los archivos source map al entorno de producción. Sin embargo, es innegable que los archivos source map o los archivos de depuración, si se publican en el entorno de producción, harán que su código fuente sea más legible para las personas. Esto puede facilitar a los atacantes encontrar vulnerabilidades en el frontend o recopilar información sensible de él. Se debe realizar una revisión del código JavaScript para determinar si se exponen archivos de depuración desde el frontend. Dependiendo del contexto y la sensibilidad del proyecto, un experto en seguridad debe decidir si los archivos deben existir o no en el entorno de producción.

Objetivos de la prueba

  • Revisar los comentarios, metadatos y cuerpos de redirección de las páginas web para encontrar fugas de información.
  • Reunir los archivos JavaScript y revisar el código JS para comprender mejor la aplicación y encontrar fugas de información.
  • Identificar si existen archivos source map u otros archivos de depuración del frontend.

Cómo probar

Revisión de comentarios y metadatos de las páginas web

Los desarrolladores suelen usar comentarios HTML para incluir información de depuración sobre la aplicación. A veces se olvidan de los comentarios y los dejan en los entornos de producción. Los evaluadores deben buscar comentarios HTML que comiencen con <!--.

Hay que revisar el código fuente HTML en busca de comentarios que contengan información sensible que pueda ayudar al atacante a obtener más información sobre la aplicación. Puede tratarse de código SQL, nombres de usuario y contraseñas, direcciones IP internas o información de depuración.

...
<div class="table2">
  <div class="col1">1</div><div class="col2">Mary</div>
  <div class="col1">2</div><div class="col2">Peter</div>
  <div class="col1">3</div><div class="col2">Joe</div>

<!-- Query: SELECT id, name FROM app.users WHERE active='1' -->

</div>
...

El evaluador puede incluso encontrar algo como esto:

<!-- Use the DB administrator password for testing:  f@keP@a$$w0rD -->

Hay que comprobar la información de versión de HTML para verificar números de versión válidos y las URL de las definiciones de tipo de datos (DTD).

<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "https://www.w3.org/TR/html4/strict.dtd">
  • strict.dtd: DTD estricta predeterminada
  • loose.dtd: DTD flexible
  • frameset.dtd: DTD para documentos con conjuntos de marcos (frameset)

Algunas etiquetas META no proporcionan vectores de ataque activos, pero permiten a un atacante perfilar una aplicación:

<META name="Author" content="Andrew Muller">

Una etiqueta META común (pero que no cumple con WCAG) es Refresh.

<META http-equiv="Refresh" content="15;URL=https://www.owasp.org/index.html">

Un uso común de la etiqueta META es especificar palabras clave que un motor de búsqueda puede utilizar para mejorar la calidad de los resultados de búsqueda.

<META name="keywords" lang="en-us" content="OWASP, security, sunshine, lollipops">

Aunque la mayoría de los servidores web gestionan la indexación de los motores de búsqueda mediante el archivo robots.txt, también puede gestionarse con etiquetas META. La etiqueta siguiente indicará a los robots que no indexen ni sigan los enlaces de la página HTML que contiene la etiqueta.

<META name="robots" content="none">

Platform for Internet Content Selection (PICS) y Protocol for Web Description Resources (POWDER) proporcionan infraestructura para asociar metadatos con el contenido de internet.

Identificación del código JavaScript y recopilación de archivos JavaScript

Los programadores suelen incluir información sensible directamente en variables de JavaScript en el frontend. Los evaluadores deben revisar el código fuente HTML y buscar código JavaScript entre las etiquetas <script> y </script>. También deben identificar los archivos JavaScript externos para revisar su código (los archivos JavaScript tienen la extensión .js y el nombre del archivo JavaScript normalmente se coloca en el atributo src (fuente) de una etiqueta <script>).

Hay que revisar el código JavaScript en busca de cualquier fuga de información sensible que los atacantes pudieran usar para abusar del sistema o manipularlo. Se deben buscar valores como: claves de API, direcciones IP internas, rutas sensibles o credenciales. Por ejemplo:

const myS3Credentials = {
  accessKeyId: config('AWSS3AccessKeyID'),
  secretAccessKey: config('AWSS3SecretAccessKey'),
};

El evaluador puede incluso encontrar algo como esto:

var conString = "tcp://postgres:1234@localhost/postgres";

Cuando se encuentra una clave de API, los evaluadores pueden comprobar si las restricciones de la clave de API están definidas por servicio o por IP, referente HTTP (HTTP referrer), aplicación, SDK, etc.

Por ejemplo, si los evaluadores encuentran una clave de API de Google Maps, pueden comprobar si esta clave de API está restringida por IP o restringida únicamente a las API de Google Maps. Si la clave de API de Google está restringida únicamente a las API de Google Maps, los atacantes aún pueden usar esa clave de API para consultar API de Google Maps sin restricciones, y el propietario de la aplicación tendrá que pagar por ello.

<script type="application/json">
...
{"GOOGLE_MAP_API_KEY":"AIzaSyDUEBnKgwiqMNpDplT6ozE4Z0XxuAbqDi4", "RECAPTCHA_KEY":"6LcPscEUiAAAAHOwwM3fGvIx9rsPYUq62uRhGjJ0"}
...
</script>

En algunos casos, los evaluadores pueden encontrar rutas sensibles en el código JavaScript, como enlaces a páginas de administración internas u ocultas.

<script type="application/json">
...
"runtimeConfig":{"BASE_URL_VOUCHER_API":"https://staging-voucher.victim.net/api", "BASE_BACKOFFICE_API":"https://10.10.10.2/api", "ADMIN_PAGE":"/hidden_administrator"}
...
</script>

Análisis de JavaScript y del código fuente del lado del cliente

Las aplicaciones modernas de una sola página y el código del lado del cliente extenso con frecuencia incrustan endpoints de API, indicadores de funcionalidades (feature flags) y, ocasionalmente, secretos. Después de reunir los archivos JavaScript (manualmente, mediante un proxy o con herramientas como Uproot), los evaluadores pueden extraer datos interesantes con:

# Example with jsluice
jsluice urls bundle.js
jsluice secrets bundle.js

# Example with LinkFinder
python linkfinder.py -i bundle.js -o cli

Hay que contrastar los endpoints y parámetros extraídos con los resultados de la recopilación de URL de archivos históricos (gau / waybackurls / waymore) y con las técnicas descritas en Identify Application Entry Points, así como con el capítulo API Reconnaissance.

Identificación de archivos source map

Los archivos source map normalmente se cargan cuando se abren las DevTools. Los evaluadores también pueden encontrar archivos source map agregando la extensión ".map" después de la extensión de cada archivo JavaScript externo. Por ejemplo, si un evaluador ve un archivo /static/js/main.chunk.js, puede comprobar su archivo source map visitando /static/js/main.chunk.js.map.

Hay que revisar los archivos source map en busca de información sensible que pueda ayudar al atacante a obtener más información sobre la aplicación. Por ejemplo:

{
  "version": 3,
  "file": "static/js/main.chunk.js",
  "sources": [
    "/home/sysadmin/cashsystem/src/actions/index.js",
    "/home/sysadmin/cashsystem/src/actions/reportAction.js",
    "/home/sysadmin/cashsystem/src/actions/cashoutAction.js",
    "/home/sysadmin/cashsystem/src/actions/userAction.js",
    "..."
  ],
  "..."
}

Cuando los sitios cargan archivos source map, el código fuente del frontend se vuelve legible y más fácil de depurar.

Identificación de respuestas de redirección que filtran información

Aunque en general no se espera que las respuestas de redirección contengan contenido web significativo, no hay garantía de que no puedan contenerlo. Así, aunque las respuestas de la serie 300 (redirección) suelen contener contenido del tipo "redirecting to https://example.com/", también pueden filtrar contenido.

Considérese una situación en la que una respuesta de redirección es el resultado de una comprobación de autenticación o autorización: si esa comprobación falla, el servidor puede responder redirigiendo al usuario de vuelta a una página "segura" o "predeterminada", pero la propia respuesta de redirección aún puede contener contenido que no se muestra en el navegador y que, sin embargo, se transmite al cliente. Esto puede verse con las herramientas de desarrollo del navegador o mediante un proxy personal (como ZAP, Burp, Fiddler o Charles).

Revisión de los archivos generados en busca de fuga de metadatos

Las aplicaciones web pueden generar archivos descargables como PDF, hojas de cálculo, facturas o informes. Estos archivos pueden contener metadatos incrustados que describen el software o las bibliotecas utilizados para crearlos.

Campos de metadatos como Producer, Creator, Application o Library Version pueden revelar tecnologías del backend y números de versión específicos. Esta información puede ayudar a los atacantes a identificar la aplicación (fingerprinting) y a encontrar vulnerabilidades públicamente conocidas (CVE).

Por ejemplo, un PDF generado puede exponer la biblioteca utilizada para crearlo:

Producer: iText 2.1.7

Un atacante podría entonces buscar vulnerabilidades conocidas que afecten a esa versión.

Cómo probar

Hay que descargar los archivos generados desde la aplicación e inspeccionar sus metadatos.

Para archivos PDF:

exiftool file.pdf
pdfinfo file.pdf
strings file.pdf | grep -i producer

Ejemplo de salida:

Producer: iText 2.1.7

Para documentos de Office (DOCX, XLSX):

exiftool file.docx

Hay que revisar campos de metadatos como:

  • Producer
  • Creator
  • Application
  • Creation Tool
  • Library Version
