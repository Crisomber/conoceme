Revisión de los metaarchivos del servidor web para detectar fuga de información

ID
WSTG-INFO-03

Resumen

Esta sección describe cómo probar diversos archivos de metadatos en busca de fuga de información sobre las rutas o la funcionalidad de la aplicación web. Además, la lista de directorios que deben evitar los spiders, robots o crawlers también puede crearse como dependencia de Map execution paths through application. También puede recopilarse otra información para identificar la superficie de ataque, detalles de tecnología o para su uso en trabajos de ingeniería social.

Objetivos de la prueba

  • Identificar rutas y funcionalidad ocultas u ofuscadas mediante el análisis de archivos de metadatos.
  • Extraer y mapear otra información que pueda llevar a una mejor comprensión de los sistemas en cuestión.

Cómo probar

Cualquiera de las acciones realizadas a continuación con wget también podría hacerse con curl. Muchas herramientas de pruebas dinámicas de seguridad de aplicaciones (DAST), como ZAP y Burp Suite, incluyen comprobaciones o análisis de estos recursos como parte de su funcionalidad de spider/crawler. También pueden identificarse mediante diversos Google Dorks o aprovechando funciones de búsqueda avanzada como inurl:.

Robots

Los Web Spiders, Robots o Crawlers obtienen una página web y luego recorren recursivamente los hipervínculos para obtener más contenido web. Su comportamiento aceptado se especifica mediante el Robots Exclusion Protocol (RFC 9309) a través de un archivo robots.txt en el directorio raíz web.

Como ejemplo, a continuación se cita una muestra del archivo robots.txt de Google tomada el 13 de septiembre de 2026:

User-agent: *
User-agent: Yandex
Disallow: /search
Allow: /search/about
Allow: /search/howsearchworks
Disallow: /sdch
Disallow: /groups
...
# Crawlers of certain social media sites are allowed to access page markup when
# google.com/imgres* links are shared. To learn more, please contact
# images-robots-allowlist@google.com.
User-agent: facebookexternalhit
User-agent: Twitterbot
Allow: /imgres
Allow: /search
Disallow: /groups
Disallow: /hosted/images/
Disallow: /m/

Sitemap: https://www.google.com/sitemap.xml

La directiva User-Agent se refiere al web spider/robot/crawler específico. Por ejemplo, User-Agent: Googlebot se refiere al spider de Google, mientras que User-Agent: bingbot se refiere a un crawler de Microsoft. User-Agent: * en el ejemplo anterior se aplica a todos los web spiders/robots/crawlers.

La directiva Disallow especifica qué recursos tienen prohibidos los spiders/robots/crawlers. En el ejemplo anterior, están prohibidos los siguientes:

...
Disallow: /search
...
Disallow: /sdch
...

Los web spiders/robots/crawlers pueden ignorar intencionalmente las directivas Disallow especificadas en un archivo robots.txt. Por lo tanto, robots.txt no debe considerarse un mecanismo para imponer restricciones sobre cómo terceros acceden, almacenan o republican el contenido web.

El archivo robots.txt se obtiene del directorio raíz web del servidor web. Por ejemplo, para obtener el robots.txt de www.google.com usando wget o curl:

$ curl -O -Ss https://www.google.com/robots.txt && head -n5 robots.txt
User-agent: *
Disallow: /search
Allow: /search/about
Allow: /search/static
Allow: /search/howsearchworks
...

Crawlers de IA

Se ha observado que muchos crawlers de IA, utilizados por empresas de IA para recopilar datos de entrenamiento, ignoran las directivas de robots.txt. Desarrolladores y propietarios de sitios han explorado contramedidas para proteger su contenido; como se describe en un artículo de TechCrunch de 2025, la comunidad de código abierto ha respondido con tácticas como generar contenido falso interminable para consumir los recursos de los crawlers, o servir datos engañosos para degradar la calidad de los conjuntos de entrenamiento de IA. La Free Software Foundation también ha documentado la carga operativa que los grandes volúmenes de crawlers de IA imponen a los equipos pequeños, destacando cómo incluso las reglas de robots.txt bienintencionadas se ignoran de forma rutinaria.

Desde la perspectiva de las pruebas, las entradas de robots.txt destinadas a bloquear crawlers de IA (por ejemplo, User-Agent: GPTBot, User-Agent: ClaudeBot) pueden ser ineficaces, y las rutas sensibles listadas en robots.txt siguen siendo descubribles por cualquier crawler que ignore el protocolo.

Análisis de robots.txt con Google Webmaster Tools

Los propietarios de sitios pueden usar la función "Analyze robots.txt" de Google para analizar el sitio como parte de Google Webmaster Tools. Esta herramienta puede ayudar en las pruebas y el procedimiento es el siguiente:

  1. Inicia sesión en Google Webmaster Tools con una cuenta de Google.
  2. En el panel, introduce la URL del sitio que se analizará.
  3. Elige entre los métodos disponibles y sigue las instrucciones en pantalla.

Etiquetas META

Las etiquetas <META> se ubican dentro de la sección HEAD de cada documento HTML y deben ser consistentes en todo el sitio, para el caso en que el punto de partida del robot/spider/crawler no comience desde un enlace de documento distinto de la raíz web, es decir, un enlace profundo (deep link). La directiva Robots también puede especificarse mediante una etiqueta META específica.

Etiqueta META Robots

Si no existe una entrada <META NAME="ROBOTS" ... >, el "Robots Exclusion Protocol" asume por defecto INDEX,FOLLOW respectivamente. Por lo tanto, las otras dos entradas válidas definidas por el "Robots Exclusion Protocol" llevan el prefijo NO..., es decir, NOINDEX y NOFOLLOW.

Con base en las directivas Disallow listadas en el archivo robots.txt de la raíz web, se realiza una búsqueda mediante expresión regular de <META NAME="ROBOTS" dentro de cada página web. El resultado se compara luego con el archivo robots.txt de la raíz web.

Etiquetas META de información diversa

Las organizaciones suelen incrustar etiquetas META informativas en el contenido web para dar soporte a diversas tecnologías, como lectores de pantalla, vistas previas en redes sociales, indexación en motores de búsqueda, etc. Esta metainformación puede ser valiosa para los evaluadores a la hora de identificar las tecnologías utilizadas y rutas o funcionalidades adicionales que explorar y probar. Sitemaps

Un sitemap es un archivo donde un desarrollador u organización puede proporcionar información sobre las páginas, los videos y otros archivos que ofrece el sitio o la aplicación, y la relación entre ellos. Los motores de búsqueda pueden usar este archivo para navegar por el sitio de manera más eficiente. Del mismo modo, los evaluadores pueden utilizar los archivos 'sitemap.xml' para obtener una visión más profunda del sitio o la aplicación investigados.

El siguiente fragmento proviene del sitemap principal de Google, obtenido el 5 de mayo de 2020.

$ wget --no-verbose https://www.google.com/sitemap.xml && head -n8 sitemap.xml
2020-05-05 12:23:30 URL:https://www.google.com/sitemap.xml [2049] -> "sitemap.xml" [1]

<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="https://www.google.com/schemas/sitemap/0.84">
  <sitemap>
    <loc>https://www.google.com/gmail/sitemap.xml</loc>
  </sitemap>
  <sitemap>
    <loc>https://www.google.com/forms/sitemaps.xml</loc>
  </sitemap>

Security TXT

security.txt fue ratificado por el IETF como RFC 9116 - A File Format to Aid in Security Vulnerability Disclosure, que permite a los sitios definir políticas de seguridad y datos de contacto. Hay múltiples razones por las que esto puede ser de interés en escenarios de prueba, entre las que se incluyen, sin limitarse a ellas:

  • Identificar rutas o recursos adicionales que incluir en el descubrimiento y análisis.
  • Recopilación de inteligencia de fuentes abiertas.
  • Encontrar información sobre programas de recompensas por errores (Bug Bounties), etc.
  • Ingeniería social.

El archivo puede estar presente en la raíz del servidor web o en el directorio .well-known/, por ejemplo:

  • https://example.com/security.txt
  • https://example.com/.well-known/security.txt

Este es un ejemplo del mundo real obtenido de LinkedIn el 5 de mayo de 2020:

$ wget --no-verbose https://www.linkedin.com/.well-known/security.txt && cat security.txt
2020-05-07 12:56:51 URL:https://www.linkedin.com/.well-known/security.txt [333/333] -> "security.txt" [1]
# Conforms to IETF `draft-foudil-securitytxt-07`
Contact: mailto:security@linkedin.com
Contact: https://www.linkedin.com/help/linkedin/answer/62924
Encryption: https://www.linkedin.com/help/linkedin/answer/79676
Canonical: https://www.linkedin.com/.well-known/security.txt
Policy: https://www.linkedin.com/help/linkedin/answer/62924

Las claves públicas OpenPGP contienen algunos metadatos que pueden proporcionar información sobre la propia clave. Estos son algunos elementos de metadatos comunes que pueden extraerse de una clave pública OpenPGP:

  • Key ID: el Key ID es un identificador corto derivado del material de la clave pública. Ayuda a identificar la clave y suele mostrarse como un valor hexadecimal de ocho caracteres.
  • Key Fingerprint: la huella de la clave (Key Fingerprint) es un identificador más largo y más único derivado del material de la clave. Suele mostrarse como un valor hexadecimal de 40 caracteres. Las huellas de clave se utilizan comúnmente para verificar la integridad y autenticidad de una clave pública.
  • Key Algorithm: el algoritmo de la clave (Key Algorithm) representa el algoritmo criptográfico utilizado por la clave pública. OpenPGP admite varios algoritmos, como RSA, DSA y ECC (criptografía de curva elíptica).
  • Key Size: el tamaño de la clave (Key Size) se refiere a la longitud o tamaño de la clave criptográfica en bits. Indica la fortaleza de la clave y determina el nivel de seguridad que ofrece.
  • Key Creation Date: la fecha de creación de la clave (Key Creation Date) indica cuándo se generó o creó la clave.
  • Key Expiration Date: las claves públicas OpenPGP pueden tener una fecha de expiración, tras la cual se consideran inválidas. La fecha de expiración de la clave (Key Expiration Date) especifica cuándo deja de ser válida.
  • User IDs: las claves públicas pueden tener uno o más User IDs asociados que identifican al propietario o entidad asociada con la clave. Los User IDs suelen incluir información como el nombre, la dirección de correo electrónico y comentarios opcionales del propietario de la clave.

Humans TXT

humans.txt es una iniciativa para conocer a las personas detrás de un sitio. Toma la forma de un archivo de texto que contiene información sobre las diferentes personas que han contribuido a construir el sitio. Este archivo suele (pero no siempre) contener información relacionada con sitios o rutas de carreras profesionales o empleos.

El siguiente ejemplo se obtuvo de Google el 5 de mayo de 2020:

$ wget --no-verbose  https://www.google.com/humans.txt && cat humans.txt
2020-05-07 12:57:52 URL:https://www.google.com/humans.txt [286/286] -> "humans.txt" [1]
Google is built by a large team of engineers, designers, researchers, robots, and others in many different sites across the globe. It is updated continuously, and built with more tools and technologies than we can shake a stick at. If you'd like to help us out, see careers.google.com.

Otras fuentes de información en .well-known

Hay otros RFC y borradores de internet que sugieren usos estandarizados de archivos dentro del directorio .well-known/. Se pueden encontrar listas de estos aquí en Wikipedia o aquí en IANA.

Sería bastante sencillo para un evaluador revisar los RFC y borradores y crear una lista para proporcionársela a un crawler o fuzzer, con el fin de verificar la existencia o el contenido de dichos archivos.
