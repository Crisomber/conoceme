Identificación del framework de la aplicación web (Fingerprint Web Application Framework)

ID
WSTG-INFO-08

Resumen

No sería exagerado decir que casi toda idea concebible para una aplicación web ya se ha puesto en desarrollo. Con la gran cantidad de proyectos de software libre y de código abierto que se desarrollan y despliegan activamente en todo el mundo, es muy probable que una prueba de seguridad de aplicaciones encuentre un objetivo que dependa total o parcialmente de estas aplicaciones o frameworks bien conocidos (por ejemplo, WordPress, phpBB, Mediawiki, etc.). Conocer los componentes de la aplicación web que se están probando ayuda significativamente al proceso de prueba y también reducirá drásticamente el esfuerzo requerido durante la misma. Estas aplicaciones web bien conocidas tienen cabeceras HTML, cookies y estructuras de directorios específicas que pueden enumerarse para identificar la aplicación. La mayoría de los frameworks web tienen varios marcadores en estas ubicaciones, que pueden ayudar a un atacante o a un evaluador a reconocerlos. Esto es básicamente lo que hacen todas las herramientas automáticas: buscan un marcador en una ubicación predefinida y luego lo comparan con la base de datos de firmas conocidas. Para lograr mayor precisión, normalmente se utilizan varios marcadores.

Objetivos de la prueba

  • Identificar (fingerprinting) los componentes utilizados por las aplicaciones web.

Cómo probar

Pruebas de caja negra

Hay varias ubicaciones comunes que se deben considerar para identificar frameworks o componentes:

  • Cabeceras HTTP
  • Cookies
  • Código fuente HTML
  • Archivos y carpetas específicos
  • Extensiones de archivo
  • Mensajes de error

Cabeceras HTTP

La forma más básica de identificar un framework web es observar el campo X-Powered-By en la cabecera de respuesta HTTP. Se pueden usar muchas herramientas para identificar un objetivo; la más sencilla es netcat.

Considérese la siguiente petición-respuesta HTTP:

$ nc 127.0.0.1 80
HEAD / HTTP/1.0

HTTP/1.1 200 OK
Server: nginx/1.0.14
[...]
X-Powered-By: Mono

A partir del campo X-Powered-By, entendemos que el framework de la aplicación web es probablemente Mono. Sin embargo, aunque este enfoque es simple y rápido, esta metodología no funciona en todos los casos. Es posible deshabilitar fácilmente la cabecera X-Powered-By con una configuración adecuada. También hay varias técnicas que permiten a un sitio ofuscar las cabeceras HTTP (consulta un ejemplo en la sección Corrección). En el ejemplo anterior, también podemos observar que se está usando una versión específica de nginx para servir el contenido.

En el mismo ejemplo, el evaluador podría no encontrar la cabecera X-Powered-By u obtener una respuesta como la siguiente:

HTTP/1.1 200 OK
Server: nginx/1.0.14
Date: Sat, 07 Sep 2013 08:19:15 GMT
Content-Type: text/html;charset=ISO-8859-1
Connection: close
Vary: Accept-Encoding
X-Powered-By: Blood, sweat and tears

A veces hay más cabeceras HTTP que apuntan a un determinado framework. En el siguiente ejemplo, según la información de la petición HTTP, se puede ver que la cabecera X-Powered-By contiene la versión de PHP. Sin embargo, la cabecera X-Generator señala que el framework utilizado es en realidad Swiftlet, lo que ayuda a un evaluador de penetración a ampliar sus vectores de ataque. Al realizar la identificación, hay que inspeccionar cuidadosamente cada cabecera HTTP en busca de este tipo de fugas.

HTTP/1.1 200 OK
Server: nginx/1.4.1
Date: Sat, 07 Sep 2013 09:22:52 GMT
Content-Type: text/html
Connection: keep-alive
Vary: Accept-Encoding
X-Powered-By: PHP/5.4.16-1~dotdeb.1
Expires: Thu, 19 Nov 1981 08:52:00 GMT
Cache-Control: no-store, no-cache, must-revalidate, post-check=0, pre-check=0
Pragma: no-cache
X-Generator: Swiftlet

La cookie laravel_session, junto con la cookie XSRF-TOKEN que la acompaña y que se usa para la protección contra CSRF, se ha establecido automáticamente, lo que da información sobre el framework en uso. En la sección Cookies se presenta una lista de nombres de cookies comunes. Aún existen limitaciones al confiar en este mecanismo de identificación: es posible cambiar el nombre de las cookies. Por ejemplo, en Laravel esto podría hacerse mediante el valor cookie en config/session.php:

/*
|--------------------------------------------------------------------------
| Session Cookie Name
|--------------------------------------------------------------------------
|
| Here you may change the name of the cookie used to identify a session
| instance by ID. The name specified here will get used every time a
| new session cookie is created by the framework for every driver.
|
*/

'cookie' => env(
    'SESSION_COOKIE',
    Str::slug(env('APP_NAME', 'laravel'), '_').'_session'
),

Sin embargo, es menos probable que se realicen estos cambios que modificaciones a la cabecera X-Powered-By, lo que hace que este enfoque de identificación sea más confiable.

Código fuente HTML

Esta técnica se basa en encontrar ciertos patrones en el código fuente de la página HTML. A menudo se puede encontrar mucha información que ayuda al evaluador a reconocer un componente específico. Uno de los marcadores comunes son los comentarios HTML que llevan directamente a la revelación del framework. Con más frecuencia se pueden encontrar ciertas rutas específicas del framework, es decir, enlaces a carpetas CSS o JS propias del framework. Finalmente, ciertas variables de script específicas también pueden apuntar a un determinado framework.

En la captura de pantalla siguiente, se puede determinar fácilmente el framework en uso y su versión a partir de los marcadores mencionados. Las aplicaciones Angular, por ejemplo, añaden un atributo ng-version directamente en el elemento raíz de la página, revelando explícitamente la versión exacta del framework en uso.


Figura 4.1.8-1: Ejemplo del código fuente HTML de un framework Angular

Con frecuencia esta información se ubica en la sección <head> de las respuestas HTTP, en etiquetas <meta> o al final de la página. No obstante, se deben analizar las respuestas completas, ya que pueden ser útiles para otros fines, como la inspección de otros comentarios útiles y campos ocultos. A veces, los desarrolladores web pueden no ocultar lo suficiente la información sobre los frameworks o componentes utilizados. Todavía es posible tropezar con algo como esto al final de la página, como un pie de página "Proudly published with Ghost" que revela que el sitio se ejecuta en la plataforma de publicación Ghost:

Archivos y carpetas específicos

Existe otro enfoque que ayuda mucho a un atacante o evaluador a identificar aplicaciones o componentes con gran precisión. Cada componente de una aplicación web tiene su estructura específica de archivos y carpetas en el servidor. Se ha señalado que se puede ver la ruta específica en el código fuente de la página HTML, pero a veces no se presentan allí de forma explícita y aun así pueden residir en el servidor.

Para descubrirlos se utiliza una técnica conocida como navegación forzada (forced browsing) o "dirbusting". El dirbusting consiste en realizar fuerza bruta contra un objetivo con nombres de carpetas y archivos conocidos y monitorear las respuestas HTTP para enumerar el contenido del servidor. Esta información puede utilizarse tanto para encontrar archivos predeterminados y atacarlos, como para identificar la aplicación web (fingerprinting). El dirbusting puede hacerse de varias maneras; el ejemplo siguiente muestra un ataque de dirbusting exitoso contra un objetivo basado en WordPress con la ayuda de una lista definida y de la funcionalidad intruder de Burp Suite.


Figura 4.1.8-3: Dirbusting con Burp

Podemos ver que, para algunas carpetas específicas de WordPress (por ejemplo, /wp-includes/, /wp-admin/ y /wp-content/), las respuestas HTTP son 403 (Forbidden), 302 (Found, redirección a wp-login.php) y 200 (OK) respectivamente. Esto es un buen indicador de que el objetivo funciona con WordPress. De la misma manera es posible aplicar dirbusting a diferentes carpetas de plugins de la aplicación y a sus versiones. En la captura de pantalla siguiente se puede ver un archivo readme.txt típico de un plugin de WordPress, accesible en /wp-content/plugins/<plugin-name>/readme.txt, que proporciona información sobre el plugin en uso y revela su versión exacta, potencialmente vulnerable, mediante el campo Stable tag.


Figura 4.1.8-4: Revelación del readme de un plugin de WordPress

Consejo: antes de comenzar con el dirbusting, revisa primero el archivo robots.txt. A veces también se pueden encontrar allí carpetas específicas de la aplicación y otra información sensible. En la captura de pantalla siguiente se presenta un ejemplo de dicho archivo robots.txt.

User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php

Los archivos y carpetas específicos son diferentes para cada aplicación. Si la aplicación o el componente identificado es de código abierto, puede ser valioso configurar una instalación temporal durante las pruebas de penetración para comprender mejor qué infraestructura o funcionalidad se presenta y qué archivos podrían quedar en el servidor. Sin embargo, ya existen varias listas de archivos útiles; un ejemplo notable son las listas de palabras de archivos/carpetas predecibles de FuzzDB.

Extensiones de archivo

Las URL pueden incluir extensiones de archivo que también ayudan a identificar la plataforma o tecnología web.

Por ejemplo, el antiguo wiki de OWASP utilizaba PHP:

https://example.owasp.org/index.php?title=Fingerprint_Web_Application_Framework&action=edit&section=4

Estas son algunas extensiones de archivos web comunes y las tecnologías asociadas:

  • .php -- PHP
  • .aspx -- Microsoft ASP.NET
  • .jsp -- Java Server Pages

WhatWeb

Sitio: https://github.com/urbanadventurer/WhatWeb

WhatWeb es una de las mejores herramientas de identificación de código abierto disponibles actualmente en el mercado y está incluida en la compilación predeterminada de Kali Linux. Lenguaje: Ruby. Las coincidencias para la identificación se realizan con:

  • Cadenas de texto (distingue mayúsculas y minúsculas)
  • Expresiones regulares
  • Consultas de la Google Hack Database (conjunto limitado de palabras clave)
  • Hashes MD5
  • Reconocimiento de URL
  • Patrones de etiquetas HTML
  • Código Ruby personalizado para operaciones pasivas y agresivas

Corrección

Aunque se pueden hacer esfuerzos por usar diferentes nombres de cookies (cambiando configuraciones), ocultar o cambiar las rutas de archivos y directorios (mediante reescritura o cambios en el código fuente), eliminar cabeceras conocidas, etc., tales esfuerzos se reducen a "seguridad por oscuridad". Los propietarios o administradores de los sistemas deben reconocer que dichos esfuerzos solo ralentizan a los adversarios más rudimentarios. Quizás el tiempo y el esfuerzo se inviertan mejor en aumentar la concienciación de las partes interesadas y en mantener las soluciones.
