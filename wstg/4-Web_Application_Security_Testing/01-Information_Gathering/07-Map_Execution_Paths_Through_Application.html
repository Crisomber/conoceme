Mapeo de las rutas de ejecución de la aplicación

ID
WSTG-INFO-07

Resumen

Antes de comenzar las pruebas de seguridad, es fundamental comprender la estructura de la aplicación. Sin un conocimiento profundo del diseño de la aplicación, es poco probable realizar una prueba exhaustiva.

Objetivos de la prueba

  • Mapear la aplicación objetivo y comprender los flujos de trabajo principales.

Cómo probar

En las pruebas de caja negra es extremadamente difícil probar todo el código base. Esto no solo se debe a que el evaluador no puede ver las rutas de código de la aplicación, sino también a que probar todas las rutas de código consumiría muchísimo tiempo. Una forma de conciliar esto es documentar las rutas de código que se descubrieron y probaron.

Hay varias maneras de abordar la prueba y la medición de la cobertura de código:

  • Rutas (Path): probar cada una de las rutas de una aplicación, incluyendo pruebas de análisis combinatorio y de valores límite para cada ruta de decisión. Aunque este enfoque ofrece exhaustividad, el número de rutas que se pueden probar crece exponencialmente con cada rama de decisión.
  • Flujo de datos (o análisis de contaminación, Taint Analysis): prueba la asignación de variables mediante interacción externa (normalmente de los usuarios). Se centra en mapear el flujo, la transformación y el uso de los datos a lo largo de la aplicación.
  • Condiciones de carrera (Race): prueba múltiples instancias concurrentes de la aplicación que manipulan los mismos datos.

La elección del método y el grado en que se usa cada uno deben negociarse con el propietario de la aplicación. Además, podrían adoptarse enfoques más sencillos. Por ejemplo, el evaluador podría preguntar al propietario de la aplicación por funciones o secciones de código específicas que le preocupen en particular y discutir cómo se puede llegar a esos segmentos de código.

Para demostrar la cobertura de código al propietario de la aplicación, el evaluador puede comenzar documentando en una hoja de cálculo todos los enlaces descubiertos al rastrear la aplicación con un spider (ya sea manual o automáticamente). Luego, el evaluador puede examinar más de cerca los puntos de decisión de la aplicación e investigar cuántas rutas de código significativas se descubren. Estas deben documentarse a continuación en la hoja de cálculo con URL, descripciones en prosa y capturas de pantalla de las rutas descubiertas.

Rastreo automático (Spidering)

Un spider automático es una herramienta que se utiliza para descubrir automáticamente nuevos recursos (URL) en un sitio específico. Comienza con una lista de URL por visitar, llamadas semillas (seeds), que depende de cómo se inicie el spider. Rastreo de aplicaciones modernas con mucho JavaScript

El spidering ingenuo suele cubrir de forma insuficiente las aplicaciones modernas, ya que muchas rutas y caminos de decisión solo son alcanzables mediante el enrutamiento del lado del cliente, el contenido renderizado dinámicamente o llamadas a API desencadenadas por la interacción del usuario, y no por seguir enlaces <a href>. Esto significa que una parte significativa de las rutas de ejecución de la aplicación puede no ser descubierta nunca por un spider que solo analiza HTML estático.

Para mejorar la cobertura de estas aplicaciones, conviene considerar crawlers capaces de ejecutar JavaScript y seguir la navegación del lado del cliente, como katana (que admite un modo headless para este fin), el Client Spider de ZAP o el crawler de Burp Suite. Ejercitar manualmente los flujos de trabajo de la aplicación a través de un proxy de interceptación, como se describe en Identify Application Entry Points, sigue siendo importante para alcanzar rutas protegidas tras flujos de varios pasos, estados de autenticación o lógica condicional que los crawlers automatizados pueden no desencadenar por sí solos.
