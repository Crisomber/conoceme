Identificación de la superficie de ataque

ID
WSTG-INFO-04

Resumen

Identificar la superficie de ataque de una aplicación web implica descubrir todas las aplicaciones, dominios, hosts virtuales y servicios expuestos externamente asociados con la infraestructura objetivo. Este proceso va más allá de identificar las aplicaciones alojadas e incluye la enumeración de DNS, el descubrimiento de subdominios, el análisis de hosts virtuales, los puertos no estándar y la revisión de certificados digitales y de los registros de Certificate Transparency.

Con la proliferación del alojamiento virtual y de la infraestructura compartida, la relación tradicional 1:1 entre una dirección IP y un servidor web ha desaparecido en gran medida. Una sola dirección IP puede alojar múltiples aplicaciones en distintos dominios, entornos o interfaces administrativas. No identificar estos activos puede dar lugar a evaluaciones incompletas y a vulnerabilidades que pasen inadvertidas.

A veces se entrega a los profesionales de seguridad un conjunto de direcciones IP como objetivo de prueba. Se puede argumentar que este escenario se parece más a un trabajo de tipo prueba de penetración, pero en cualquier caso se espera que dicha asignación pruebe todas las aplicaciones web accesibles a través de ese objetivo. El problema es que la dirección IP dada aloja un servicio HTTP en el puerto 80, pero si el evaluador accede especificando la dirección IP (que es todo lo que conoce), se informa "No web server configured at this address" u otro mensaje similar. Sin embargo, ese sistema podría "ocultar" varias aplicaciones web asociadas a nombres simbólicos (DNS) no relacionados. Evidentemente, el alcance del análisis se ve profundamente afectado según el evaluador pruebe todas las aplicaciones o solo las que conoce.

A veces, la especificación del objetivo es más rica. Al evaluador se le puede dar una lista de direcciones IP y sus correspondientes nombres simbólicos. Sin embargo, esta lista podría transmitir información parcial, es decir, podría omitir algunos nombres simbólicos sin que el cliente ni siquiera lo sepa (esto es más probable que ocurra en organizaciones grandes).

Otros problemas que afectan al alcance de la evaluación son las aplicaciones web publicadas en URL poco evidentes (por ejemplo, https://www.example.com/some-strange-URL), que no se referencian en ningún otro lugar. Esto puede ocurrir por error (debido a configuraciones incorrectas) o intencionalmente (por ejemplo, interfaces administrativas no anunciadas).

Para abordar estos problemas, se debe realizar un proceso integral de identificación de la superficie de ataque.

Objetivos de la prueba

  • Enumerar todas las aplicaciones web dentro del alcance.
  • Identificar los nombres DNS, dominios y hosts virtuales asociados con el objetivo.
  • Descubrir dominios y subdominios adicionales mediante técnicas de DNS pasivas y activas.
  • Analizar los certificados digitales y los registros de Certificate Transparency en busca de nombres de host adicionales.

Cómo probar

El descubrimiento de aplicaciones web es un proceso que busca identificar las aplicaciones web en una infraestructura determinada. Esta última suele especificarse como un conjunto de direcciones IP (quizás un bloque de red), pero puede consistir en un conjunto de nombres simbólicos DNS o en una combinación de ambos. Esta información se entrega antes de la ejecución de una evaluación, ya sea una prueba de penetración de estilo clásico o una evaluación centrada en la aplicación. En ambos casos, a menos que las reglas del compromiso especifiquen otra cosa (por ejemplo, probar solo la aplicación ubicada en la URL https://www.example.com/), la evaluación debe procurar tener el alcance más amplio posible, es decir, debe identificar todas las aplicaciones accesibles a través del objetivo dado. Los siguientes ejemplos examinan algunas técnicas que pueden emplearse para lograr este objetivo.

Algunas de las siguientes técnicas se aplican a servidores web expuestos a internet, concretamente los servicios de búsqueda basados en web de DNS y de IP inversa, y el uso de motores de búsqueda. Los ejemplos utilizan direcciones IP privadas (como 192.168.1.100) que, salvo que se indique lo contrario, representan direcciones IP genéricas y se usan solo con fines de anonimato.

Hay tres factores que influyen en cuántas aplicaciones están relacionadas con un nombre DNS (o una dirección IP) determinado:

  1. URL base diferente

    El punto de entrada evidente de una aplicación web es www.example.com, es decir, con esta notación abreviada pensamos en la aplicación web que se origina en https://www.example.com/ (lo mismo se aplica a HTTPS). Sin embargo, aunque esta es la situación más común, nada obliga a que la aplicación comience en /.

    Por ejemplo, el mismo nombre simbólico puede estar asociado a tres aplicaciones web como: https://www.example.com/app1 https://www.example.com/app2 https://www.example.com/app3

    En este caso, la URL https://www.example.com/ no estaría asociada a una página significativa. Las tres aplicaciones permanecerían ocultas a menos que el evaluador sepa explícitamente cómo acceder a ellas, es decir, que conozca app1, app2 o app3. Por lo general no hay necesidad de publicar aplicaciones web de esta manera, a menos que el propietario no quiera que sean accesibles de forma estándar y esté preparado para informar a los usuarios de su ubicación exacta. Esto no significa que estas aplicaciones sean secretas, sino solo que su existencia y ubicación no se anuncian explícitamente.

  2. Puertos no estándar

    Aunque las aplicaciones web suelen residir en el puerto 80 (HTTP) y 443 (HTTPS), no hay nada fijo ni obligatorio en estos números de puerto. De hecho, las aplicaciones web pueden asociarse a puertos TCP arbitrarios y se las puede referenciar especificando el número de puerto de la siguiente manera: http[s]://www.example.com:port/. Por ejemplo, https://www.example.com:20000/.

  3. Hosts virtuales

    DNS permite asociar una sola dirección IP con uno o más nombres simbólicos. Por ejemplo, la dirección IP 192.168.1.100 podría estar asociada a los nombres DNS www.example.com, helpdesk.example.com, webmail.example.com. No es necesario que todos los nombres pertenezcan al mismo dominio DNS. Esta relación de 1 a N puede reflejarse para servir contenido distinto mediante los llamados hosts virtuales. La información que especifica a qué host virtual nos referimos está incrustada en la cabecera Host de HTTP 1.1.

    No se sospecharía de la existencia de otras aplicaciones web además de la evidente www.example.com, a menos que se conozcan helpdesk.example.com y webmail.example.com.

Enfoques para abordar el problema 1: URL no estándar

No hay forma de determinar por completo la existencia de aplicaciones web con nombres no estándar. Al ser no estándar, no existen criterios fijos que rijan la convención de nombres; sin embargo, hay varias técnicas que el evaluador puede usar para obtener información adicional.

Primero, si el servidor web está mal configurado y permite la exploración de directorios, es posible detectar estas aplicaciones. Los escáneres de vulnerabilidades pueden ayudar en este sentido.

Segundo, estas aplicaciones pueden estar referenciadas por otras páginas web y existe la posibilidad de que hayan sido rastreadas e indexadas por los motores de búsqueda web. Si los evaluadores sospechan la existencia de tales aplicaciones ocultas en www.example.com, podrían buscar usando el operador site y examinar el resultado de una consulta para site: www.example.com. Entre las URL devueltas podría haber una que apunte a una aplicación poco evidente.

Otra opción es sondear URL que podrían ser candidatas probables para aplicaciones no publicadas. Por ejemplo, un frontend de correo web podría ser accesible desde URL como https://www.example.com/webmail, https://webmail.example.com/ o https://mail.example.com/. Lo mismo ocurre con las interfaces administrativas, que pueden estar publicadas en URL ocultas (por ejemplo, una interfaz administrativa de Tomcat) y aun así no estar referenciadas en ningún lugar. Por lo tanto, hacer una búsqueda de estilo diccionario (o "adivinación inteligente") podría dar algunos resultados. Los escáneres de vulnerabilidades pueden ayudar en este sentido.

Enfoques para abordar el problema 2: puertos no estándar

Es fácil comprobar la existencia de aplicaciones web en puertos no estándar. Un escáner de puertos como Nmap es capaz de realizar el reconocimiento de servicios mediante la opción -sV e identificará servicios http[s] en puertos arbitrarios. Lo que se requiere es un análisis completo de todo el espacio de direcciones de 64k puertos TCP.

Por ejemplo, el siguiente comando buscará, con un análisis de conexión TCP, todos los puertos abiertos en la IP 192.168.1.100 e intentará determinar qué servicios están asociados a ellos (solo se muestran los modificadores esenciales; Nmap cuenta con un amplio conjunto de opciones cuya discusión queda fuera del alcance):

nmap -Pn -sT -sV -p0-65535 192.168.1.100

Basta con examinar la salida y buscar HTTP o la indicación de servicios envueltos en TLS (que deben sondearse para confirmar que son HTTPS). Por ejemplo, la salida del comando anterior podría verse así:

Interesting ports on 192.168.1.100:
(The 65527 ports scanned but not shown below are in state: closed)
PORT      STATE SERVICE     VERSION
22/tcp    open  ssh         OpenSSH 3.5p1 (protocol 1.99)
80/tcp    open  http        Apache httpd 2.0.40 ((Red Hat Linux))
443/tcp   open  ssl         OpenSSL
901/tcp   open  http        Samba SWAT administration server
1241/tcp  open  ssl         Nessus security scanner
3690/tcp  open  unknown
8000/tcp  open  http-alt?
8080/tcp  open  http        Apache Tomcat/Coyote JSP engine 1.1

De este ejemplo se puede observar que:

  • Hay un servidor HTTP Apache ejecutándose en el puerto 80.
  • Parece que hay un servidor HTTPS en el puerto 443 (pero esto debe confirmarse, por ejemplo, visitando https://192.168.1.100 con un navegador).
  • En el puerto 901 hay una interfaz web Samba SWAT.
  • El servicio en el puerto 1241 no es HTTPS, sino el demonio de Nessus envuelto en TLS.
  • El puerto 3690 presenta un servicio sin especificar (Nmap devuelve su huella (fingerprint), omitida aquí por claridad, junto con instrucciones para enviarla e incorporarla a la base de datos de huellas de Nmap, siempre que se sepa qué servicio representa).
  • Otro servicio sin especificar en el puerto 8000; posiblemente sea HTTP, ya que no es raro encontrar servidores HTTP en este puerto. Examinemos este asunto:
$ ncat 192.168.10.100 8000
GET / HTTP/1.0

HTTP/1.0 200 OK
pragma: no-cache
Content-Type: text/html
Server: MX4J-HTTPD/1.0
expires: now
Cache-Control: no-cache

<html>
...

Esto confirma que, de hecho, es un servidor HTTP. Alternativamente, los evaluadores podrían haber visitado la URL con un navegador web, o haber usado los comandos GET o HEAD de Perl, que imitan interacciones HTTP como la que se muestra arriba (sin embargo, no todos los servidores atienden las peticiones HEAD).

  • Apache Tomcat ejecutándose en el puerto 8080.

La misma tarea puede ser realizada por escáneres de vulnerabilidades, pero primero hay que comprobar que el escáner elegido sea capaz de identificar servicios HTTP[S] que se ejecutan en puertos no estándar. Por ejemplo, Nessus es capaz de identificarlos en puertos arbitrarios (siempre que se le indique que analice todos los puertos) y proporcionará, respecto a Nmap, una serie de pruebas sobre vulnerabilidades conocidas de servidores web, así como sobre la configuración TLS/SSL de los servicios HTTPS. Como se mencionó antes, Nessus también es capaz de detectar aplicaciones o interfaces web populares que de otro modo podrían pasar inadvertidas (por ejemplo, una interfaz administrativa de Tomcat).

Un análisis completo de 65535 puertos con Nmap y detección de servicios puede ser lento en muchos hosts. naabu es un escáner de puertos rápido que puede usarse para identificar rápidamente puertos abiertos en una lista grande de hosts y que puede canalizar sus resultados directamente a Nmap para detectar servicios solo en los puertos abiertos que encontró:

naabu -p - -rate 2000 -c 50 -retries 2 -warm-up-time 1 -silent -host 192.168.1.100 -nmap-cli 'nmap -sV -oX scan.xml'

Esta combinación analiza primero todos los puertos con naabu y luego ejecuta el análisis de detección de servicios, más lento, de Nmap únicamente sobre los puertos que naabu encontró abiertos, lo que reduce considerablemente el tiempo total del análisis.

Enfoques para abordar el problema 3: hosts virtuales

Existen varias técnicas que pueden utilizarse para identificar los nombres DNS asociados a una dirección IP determinada x.y.z.t.

Enumeración de DNS

La enumeración de DNS tiene como objetivo identificar dominios, subdominios y registros DNS relacionados asociados con la organización objetivo para ampliar el alcance de la evaluación. La enumeración de DNS desempeña un papel clave en la identificación de hosts virtuales adicionales asignados a la misma dirección IP. Esto puede revelar sistemas de desarrollo, entornos de preproducción (staging), servicios heredados o interfaces administrativas.

Se pueden utilizar tanto técnicas pasivas como activas.

Enumeración pasiva de DNS

Las técnicas pasivas no interactúan directamente con la infraestructura objetivo y, en su lugar, se basan en fuentes de datos disponibles públicamente. Algunos ejemplos son:

  • Registros DNS públicos (A, AAAA, MX, TXT, NS)
  • Búsquedas DNS inversas (registros PTR)
  • Motores de búsqueda
  • Bases de datos de DNS pasivo
  • Registros de Certificate Transparency

Las técnicas pasivas son preferibles durante las primeras fases de reconocimiento para evitar ser detectado.

Chaos y su chaos-client proporcionan acceso a un conjunto de datos curado de subdominios que ProjectDiscovery ya ha rastreado, obtenidos principalmente de los alcances de programas públicos de recompensas por errores (bug bounty). Puede ser un complemento útil y rápido de la enumeración pasiva de DNS para los dominios que ya ha indexado, pero requiere una clave de API, solo cubre los dominios dentro de su conjunto de datos y no debe considerarse un sustituto de herramientas activas como subfinder o amass frente a objetivos arbitrarios de un trabajo.

Enumeración activa de DNS

Las técnicas activas consultan directamente la infraestructura DNS del objetivo y pueden generar logs en los sistemas objetivo. Estas incluyen:

  • Fuerza bruta de subdominios
  • Intentos de transferencia de zona DNS
  • Enumeración de registros DNS mediante herramientas

Las herramientas comunes utilizadas para la enumeración de DNS incluyen:

  • amass
  • subfinder
  • dnsrecon
  • fierce
  • dig
  • nslookup

Ejemplo usando dig:

dig example.com ANY

; <<>> DiG 9.10.6 <<>> example.com ANY
;; QUESTION SECTION:
;example.com.                  IN      ANY

;; ANSWER SECTION:
example.com.            86400   IN      A       93.184.216.34
example.com.            86400   IN      MX      10 mail.example.com.
example.com.            86400   IN      NS      ns1.secure.net.
example.com.            86400   IN      NS      ns2.secure.net.
example.com.            86400   IN      TXT     "v=spf1 -all"

Ejemplo usando subfinder:

subfinder -d example.com -silent

www.example.com
dev.example.com
staging.example.com
mail.example.com
api.example.com

Permutación de subdominios

Una vez recopilado un conjunto inicial de subdominios, las técnicas de permutación (o alteración) pueden generar candidatos adicionales combinando etiquetas conocidas con prefijos/sufijos comunes o aplicando mutaciones (por ejemplo, dev- → staging-, insertar números, etc.). Herramientas como altdns, dnsgen o gotator se usan comúnmente con este fin. Los candidatos generados deben resolverse luego (dnsx / MassDNS) y sondearse (httpx).

MassDNS es un resolvedor DNS de alta velocidad, útil para resolver rápidamente las grandes listas de candidatos producidas por las herramientas de permutación o por la fuerza bruta basada en listas de palabras.

Transferencias de zona DNS

Esta técnica tiene un uso limitado hoy en día, dado que los servidores DNS en su mayoría no atienden las transferencias de zona. Sin embargo, aún podría valer la pena intentarla. En primer lugar, los evaluadores deben determinar los servidores de nombres que sirven a x.y.z.t. Si se conoce un nombre simbólico para x.y.z.t (sea www.example.com), sus servidores de nombres pueden determinarse mediante herramientas como nslookup, host o dig, solicitando los registros NS de DNS.

Si no se conoce ningún nombre simbólico para x.y.z.t, pero la definición del objetivo contiene al menos un nombre simbólico, los evaluadores pueden intentar aplicar el mismo proceso y consultar el servidor de nombres de ese nombre (con la esperanza de que x.y.z.t también sea servido por ese servidor de nombres). Por ejemplo, si el objetivo consiste en la dirección IP x.y.z.t y el nombre mail.example.com, se determinan los servidores de nombres del dominio example.com.

El siguiente ejemplo muestra cómo identificar los servidores de nombres de www.owasp.org usando el comando host:

$ host -t ns www.owasp.org
www.owasp.org is an alias for owasp.org.
owasp.org name server ns1.secure.net.
owasp.org name server ns2.secure.net.

Ahora se puede solicitar una transferencia de zona a los servidores de nombres del dominio example.com. Si el evaluador tiene suerte, puede recibir como respuesta una lista de las entradas DNS de este dominio. Esta incluirá la evidente www.example.com y las no tan evidentes helpdesk.example.com y webmail.example.com (y posiblemente otras). Hay que revisar todos los nombres devueltos por la transferencia de zona y considerar todos aquellos que estén relacionados con el objetivo que se está evaluando.

Intento de solicitar una transferencia de zona de owasp.org a uno de sus servidores de nombres:

$ host -l www.owasp.org ns1.secure.net
Using domain server:
Name: ns1.secure.net
Address: 192.220.124.10#53
Aliases:

Host www.owasp.org not found: 5(REFUSED)
; Transfer failed.

Consultas DNS inversas

Este proceso es similar al anterior, pero se basa en registros DNS inversos (PTR). En lugar de solicitar una transferencia de zona, se intenta establecer el tipo de registro en PTR y emitir una consulta sobre la dirección IP dada. Si los evaluadores tienen suerte, pueden recibir como respuesta una entrada con un nombre DNS. Esta técnica depende de la existencia de mapas de IP a nombre simbólico, lo cual no está garantizado.

Búsquedas DNS basadas en web

Este tipo de búsqueda es similar a la transferencia de zona DNS, pero se basa en servicios web que permiten búsquedas por nombre en DNS. Uno de estos servicios es Netcraft Search DNS. El evaluador puede consultar una lista de nombres pertenecientes a un dominio de su elección, como example.com. Luego comprobará si los nombres obtenidos son pertinentes al objetivo que está examinando.

Servicios de IP inversa

Los servicios de IP inversa son similares a las consultas DNS inversas, con la diferencia de que los evaluadores consultan una aplicación web en lugar de un servidor de nombres. Hay varios de estos servicios disponibles. Dado que tienden a devolver resultados parciales (y a menudo diferentes), es mejor usar varios servicios para obtener un análisis más completo.

  • MxToolbox Reverse IP
  • DNSstuff (varios servicios disponibles)

Los motores de búsqueda de activos de internet como Shodan, Censys y FOFA indexan hosts y servicios conectados a internet y también pueden consultarse por IP, certificado o contenido de banners para revelar otros nombres de host y servicios alojados en la misma dirección. FOFA, en particular, tiene una amplia cobertura de infraestructura en China y Asia-Pacífico, que puede complementar la cobertura de Shodan y Censys. Por ejemplo, una búsqueda en FOFA basada en IP: ip="192.168.1.100", o una búsqueda por un título o cabecera específicos: title="Example App". Como ocurre con los demás servicios de IP inversa mencionados, hay un nivel gratuito con consultas limitadas y planes de pago para un acceso más completo.

Googling

Tras la recopilación de información con las técnicas anteriores, los evaluadores pueden apoyarse en los motores de búsqueda para refinar y ampliar su análisis. Esto puede aportar evidencia de nombres simbólicos adicionales pertenecientes al objetivo, o de aplicaciones accesibles mediante URL poco evidentes.

Por ejemplo, considerando el ejemplo anterior sobre www.owasp.org, el evaluador podría consultar Google y otros motores de búsqueda buscando información (y, por tanto, nombres DNS) relacionada con los dominios recién descubiertos webgoat.org, webscarab.com y webscarab.net.

Las técnicas de Googling se explican en Testing: Spiders, Robots, and Crawlers.

Certificados digitales

Si el servidor acepta conexiones por HTTPS, el Common Name (CN) y el Subject Alternate Name (SAN) del certificado pueden contener uno o más nombres de host. Sin embargo, si el servidor web no tiene un certificado de confianza, o se usan comodines (wildcards), es posible que esto no devuelva información válida.

El CN y el SAN pueden obtenerse inspeccionando manualmente el certificado o mediante otras herramientas como OpenSSL:

openssl s_client -connect 93.184.216.34:443 </dev/null 2>/dev/null | openssl x509 -noout -text | grep -E 'DNS:|Subject:'

Subject: C = US, ST = California, L = Los Angeles, O = Internet Corporation for Assigned Names and Numbers, CN = www.example.org
DNS:www.example.org, DNS:example.com, DNS:example.edu, DNS:example.net, DNS:example.org, DNS:www.example.com, DNS:www.example.edu, DNS:www.example.net

Registros de Certificate Transparency

Los registros de Certificate Transparency (CT) son registros de acceso público de los certificados TLS emitidos. Estos registros pueden consultarse para identificar nombres de host y subdominios asociados con una organización objetivo, incluidos sistemas de preproducción (staging), interfaces administrativas, sistemas heredados u otros servicios accesibles externamente.

Revisar los registros CT puede revelar nombres de host que no son directamente descubribles mediante transferencias de zona DNS, búsquedas inversas o consultas en motores de búsqueda por sí solas. Los evaluadores deben extraer los nombres de host descubiertos y validarlos mediante resolución DNS para determinar si están activos y dentro del alcance definido de la evaluación.

Al revisar los datos de los registros CT, hay que considerar:

  • Nombres de host que indiquen entornos de desarrollo, preproducción (staging) o pruebas.
  • Interfaces administrativas o de gestión.
  • Sistemas obsoletos o heredados que aún podrían ser accesibles.
  • Certificados comodín (wildcard) que podrían implicar subdominios adicionales no descubiertos.

La información reunida de los registros CT debe validarse para confirmar la titularidad y la relevancia antes de continuar con las pruebas.

Se debe tener cuidado de respetar las limitaciones de alcance definidas en el trabajo.

Los activos descubiertos deben validarse y documentarse antes de realizar más actividades de prueba.

Un enfoque común para consultar los registros CT es usar portales de búsqueda disponibles públicamente que agregan datos de certificados. Por ejemplo, un evaluador puede buscar los certificados emitidos para example.com y revisar los subdominios listados.

Por ejemplo: https://crt.sh/?q=%25.example.com

Nota: crt.sh tiene ocasionalmente periodos de inactividad o alta latencia. Merklemap y Cert Spotter de SSLMate son servicios alternativos de búsqueda de Certificate Transparency que conviene tener como respaldo.

Figura 4.1.4-1: Ejemplo de resultados de una búsqueda en registros de Certificate Transparency.

Los resultados pueden listar subdominios como dev.example.com, staging.example.com u otros nombres de host que no están referenciados directamente desde el sitio principal. Los nombres de host descubiertos deben validarse mediante resolución DNS antes de continuar con las pruebas.

Ejemplo de flujo de trabajo moderno de pasivo a activo

Un flujo ligero común utilizado en las evaluaciones actuales:

# Passive subdomain discovery
subfinder -d example.com -silent | tee subs.txt
amass enum -passive -d example.com -o amass.txt

# Resolve and probe live hosts
cat subs.txt amass.txt | sort -u | dnsx -silent | httpx -silent -title -tech-detect -status-code -o live.txt

# Historical URLs (feed interesting hosts later)
cat live.txt | unfurl domains | sort -u | gau --subs | tee archive-urls.txt

# Screenshot live hosts for visual triage of a large host list
gowitness scan file -f live.txt

Con un gran número de hosts descubiertos, tomar una captura de pantalla de cada uno ofrece una forma rápida de clasificar visualmente los resultados, por ejemplo detectando páginas de inicio de sesión, paneles de administración, páginas de instalación predeterminadas o páginas de error sin tener que visitar manualmente cada host. gowitness es una herramienta actual y con mantenimiento activo para esto; httpx también admite una opción -screenshot integrada con el mismo propósito, sin añadir otra herramienta a la cadena.

Respeta siempre el alcance, los límites de tasa y las reglas del compromiso. Valida la titularidad de los activos recién descubiertos antes de realizar pruebas más profundas.

Herramientas

  • Herramientas de consulta DNS como nslookup, dig y host
  • Herramientas de enumeración de subdominios y mapeo de la superficie de ataque:
    • Amass (proyecto de OWASP: pasivo + activo, salida en grafo)
    • subfinder
    • Chaos / chaos-client (conjunto de datos curado de subdominios, requiere clave de API)
    • dnsx
    • httpx (sondeo de hosts activos, detección de tecnologías, títulos)
    • gowitness (capturas de pantalla para la clasificación visual de hosts activos)
    • dnsrecon, fierce
  • Permutación de subdominios: altdns, dnsgen, gotator
  • MassDNS (resolvedor de alta velocidad para la salida de listas de palabras / permutaciones)
  • Motores de búsqueda (Google, Bing y otros motores de búsqueda importantes)
