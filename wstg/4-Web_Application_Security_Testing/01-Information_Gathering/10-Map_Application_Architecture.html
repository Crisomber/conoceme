Mapeo de la arquitectura de la aplicación

ID
WSTG-INFO-10

Resumen

Para probar una aplicación de manera eficaz, y para poder ofrecer recomendaciones significativas sobre cómo abordar cualquiera de los problemas identificados, es importante entender qué es lo que realmente se está probando. Además, podría ser útil determinar si ciertos componentes específicos deben considerarse fuera del alcance de las pruebas.

Las aplicaciones web modernas pueden variar significativamente en complejidad, desde un script sencillo que se ejecuta en un solo servidor hasta una aplicación sumamente compleja distribuida en decenas de sistemas, lenguajes y componentes diferentes. También puede haber componentes adicionales a nivel de red, como firewalls o sistemas de protección contra intrusiones, que pueden tener un impacto significativo en las pruebas.

Objetivos de la prueba

  • Comprender la arquitectura de la aplicación y las tecnologías en uso.

Cómo probar

Al realizar pruebas desde una perspectiva de caja negra, es importante intentar construir una imagen clara de cómo funciona la aplicación y de qué tecnologías y componentes están presentes. En algunos casos es posible probar la existencia de componentes específicos, como un firewall de aplicaciones web, mientras que otros componentes pueden identificarse inspeccionando el comportamiento de la aplicación.

Las secciones siguientes ofrecen una visión general de alto nivel de los componentes arquitectónicos comunes, junto con detalles sobre cómo identificarlos.

Componentes de la aplicación

Servidor web

Las aplicaciones simples pueden ejecutarse en un solo servidor, que puede identificarse siguiendo los pasos descritos en la sección Fingerprint Web Server de la guía.

Plataforma como servicio (PaaS)

En un modelo de Plataforma como servicio (PaaS), el servidor web y la infraestructura subyacente son administrados por el proveedor del servicio, y el cliente solo es responsable de la aplicación que se despliega en ellos. Desde la perspectiva de las pruebas, hay dos diferencias principales:

  • El propietario de la aplicación no tiene acceso a la infraestructura subyacente, lo que significa que no podrá corregir directamente ninguno de los problemas
  • Es probable que las pruebas de infraestructura estén fuera del alcance de cualquier trabajo

En algunos casos es posible identificar el uso de PaaS, ya que la aplicación puede utilizar un nombre de dominio específico (por ejemplo, las aplicaciones desplegadas en Azure App Services tendrán un dominio *.azurewebsites.net, aunque también pueden usar dominios personalizados). En otros casos, es difícil determinar si se está utilizando PaaS.

Serverless

En un modelo Serverless, los desarrolladores proporcionan código que se ejecuta directamente en una plataforma de alojamiento como funciones individuales, en lugar de ejecutar una aplicación web tradicional más grande desplegada en una raíz web (webroot). Esto lo hace muy adecuado para arquitecturas basadas en microservicios. Al igual que en un entorno PaaS, es probable que las pruebas de infraestructura estén fuera del alcance.

En algunos casos, el uso de código Serverless puede quedar indicado por la presencia de cabeceras HTTP específicas. Por ejemplo, las funciones de AWS Lambda normalmente devolverán las siguientes cabeceras:

X-Amz-Invocation-Type
X-Amz-Log-Type
X-Amz-Client-Context

Las Azure Functions son menos evidentes. Normalmente devuelven la cabecera Server: Kestrel, pero esto por sí solo no basta para determinar que se trata de una función de Azure App, ya que podría ser algún otro código ejecutándose en Kestrel.

Microservicios

En una arquitectura basada en microservicios, la API de la aplicación se compone de múltiples servicios discretos, en lugar de ejecutarse como una aplicación monolítica. Los servicios en sí suelen ejecutarse dentro de contenedores (normalmente con Kubernetes) y pueden usar una variedad de sistemas operativos y lenguajes diferentes. Aunque normalmente están detrás de una única puerta de enlace de API (API gateway) y de un único dominio, el uso de múltiples lenguajes (a menudo indicado por mensajes de error detallados) puede sugerir que se están utilizando microservicios.

Almacenamiento estático

Muchas aplicaciones almacenan contenido estático en plataformas de almacenamiento dedicadas, en lugar de alojarlo directamente en el servidor web principal. Las dos plataformas más comunes son los S3 Buckets de Amazon y las Storage Accounts de Azure, y pueden identificarse fácilmente por los nombres de dominio:

  • BUCKET.s3.amazonaws.com o s3.REGION.amazonaws.com/BUCKET para los S3 Buckets de Amazon
  • ACCOUNT.blob.core.windows.net para las Storage Accounts de Azure

Estas cuentas de almacenamiento a menudo pueden exponer archivos sensibles, como se explica en la sección Testing Cloud Storage Guide.

Base de datos

La mayoría de las aplicaciones web no triviales utilizan algún tipo de base de datos para almacenar contenido dinámico. En algunos casos es posible determinar la base de datos. Esto a menudo puede hacerse mediante:

  • El escaneo de puertos del servidor, buscando puertos abiertos asociados con bases de datos específicas
  • La provocación de mensajes de error relacionados con SQL (o NoSQL), o la búsqueda de errores existentes en un motor de búsqueda

Cuando no es posible determinar de forma concluyente la base de datos, el evaluador a menudo puede hacer una suposición fundamentada basándose en otros aspectos de la aplicación:

  • Windows, IIS y ASP.NET suelen usar Microsoft SQL Server
  • Los sistemas embebidos suelen usar SQLite
  • PHP suele usar MySQL o PostgreSQL
  • APEX suele usar Oracle

Estas no son reglas estrictas, pero ciertamente pueden ofrecer un punto de partida razonable si no se dispone de mejor información.

Autenticación

La mayoría de las aplicaciones tienen autenticación de usuarios. Hay múltiples backends de autenticación que pueden utilizarse, como:

  • Configuración del servidor web (incluidos los archivos .htaccess) o contraseñas escritas directamente en scripts
    • Normalmente se manifiesta como autenticación HTTP Basic, indicada por una ventana emergente en el navegador y una cabecera HTTP WWW-Authenticate: Basic
  • Cuentas de usuario locales en una base de datos
    • Normalmente integradas en un formulario o endpoint de API de la aplicación
  • Una fuente central de autenticación existente, como Active Directory o un servidor LDAP
    • Puede usar autenticación NTLM, indicada por una cabecera HTTP WWW-Authenticate: NTLM
    • Puede estar integrada en la aplicación web mediante un formulario
    • Puede requerir que el nombre de usuario se introduzca en el formato "DOMINIO\usuario", o puede ofrecer una lista desplegable de dominios disponibles
  • Inicio de sesión único (Single Sign-On, SSO) con un proveedor interno o externo
    • Normalmente usa OAuth, OpenID Connect o SAML

Las aplicaciones pueden ofrecer múltiples opciones para que el usuario se autentique (como registrar una cuenta local o usar su cuenta existente de Facebook) y pueden usar diferentes mecanismos para los usuarios normales y los administradores.

Servicios y API de terceros

Casi todas las aplicaciones web incluyen recursos de terceros que se cargan o con los que el cliente interactúa. Estos pueden incluir:

  • Contenido activo (como scripts, hojas de estilo, fuentes e iframes)
  • Contenido pasivo (como imágenes y videos)
  • API externas
  • Botones de redes sociales
  • Redes publicitarias
  • Pasarelas de pago

Estos recursos son solicitados directamente por el navegador del usuario, lo que facilita identificarlos con las herramientas de desarrollo o un proxy de interceptación. Aunque es importante identificarlos (ya que pueden afectar la seguridad de la aplicación), hay que recordar que normalmente están fuera del alcance de las pruebas, ya que pertenecen a terceros.

Componentes de red

Proxy inverso

Un proxy inverso se sitúa delante de uno o más servidores backend y redirige las peticiones al destino apropiado. Se pueden usar para implementar diversas funcionalidades, como:

  • Actuar como balanceador de carga o firewall de aplicaciones web
  • Permitir que múltiples aplicaciones se alojen en una sola dirección IP o dominio (en subcarpetas)
  • Implementar filtrado de IP u otras restricciones
  • Almacenar en caché contenido del backend para mejorar el rendimiento

No siempre es posible detectar un proxy inverso (especialmente si solo hay una aplicación detrás), pero a veces se puede identificar por:

  • Una discrepancia entre el servidor frontend y la aplicación backend (como una cabecera Server: nginx con una aplicación ASP.NET)
    • Esto a veces puede dar lugar a vulnerabilidades de request smuggling
  • Cabeceras duplicadas (especialmente la cabecera Server)
  • Múltiples aplicaciones alojadas en la misma dirección IP o dominio (especialmente si usan lenguajes diferentes)

Balanceador de carga

Un balanceador de carga se sitúa delante de múltiples servidores backend y reparte las peticiones entre ellos para proporcionar mayor redundancia y capacidad de procesamiento a la aplicación.

Los balanceadores de carga pueden ser difíciles de detectar, pero a veces se pueden identificar realizando múltiples peticiones y examinando las respuestas en busca de diferencias, como:

  • Horas de sistema inconsistentes
  • Distintas direcciones IP internas o nombres de host en mensajes de error detallados
  • Distintas direcciones devueltas por Server-Side Request Forgery (SSRF)

También pueden quedar indicados por la presencia de cookies específicas (por ejemplo, los balanceadores de carga F5 BIG-IP crean una cookie llamada BIGipServer).

Red de distribución de contenido (CDN)

Una red de distribución de contenido (Content Delivery Network, CDN) es un conjunto de servidores proxy de caché distribuidos geográficamente, diseñado para mejorar el rendimiento del sitio.

Normalmente se configura apuntando el dominio de cara al público a los servidores de la CDN y luego configurando la CDN para que se conecte a los servidores backend correctos (a veces conocidos como el "origen").

La forma más sencilla de detectar una CDN es realizar una consulta WHOIS de las direcciones IP a las que se resuelve el dominio. Si pertenecen a una empresa de CDN (como Akamai, Cloudflare o Fastly; consulta Wikipedia para una lista más completa), es probable que se esté utilizando una CDN.

Al probar un sitio detrás de una CDN, hay que tener en cuenta los siguientes puntos:

  • Las direcciones IP y los servidores pertenecen al proveedor de la CDN y es probable que estén fuera del alcance de las pruebas de infraestructura
  • Muchas CDN también incluyen funciones como detección de bots, limitación de tasa (rate limiting) y firewalls de aplicaciones web
  • Las CDN suelen almacenar contenido en caché. Por lo tanto, los cambios realizados en el backend pueden no aparecer de inmediato en el sitio.

Si el sitio está detrás de una CDN, podría ser útil identificar los servidores backend. Si no se aplica un control de acceso adecuado, el evaluador podría eludir la CDN (y cualquier protección que ofrezca) accediendo directamente a los servidores backend. Hay una variedad de métodos que pueden permitir identificar el sistema backend:

  • Los correos electrónicos enviados por la aplicación pueden provenir directamente del servidor backend, lo que podría revelar su dirección IP
  • El DNS grinding, las transferencias de zona o las listas de Certificate Transparency de un dominio pueden revelarlo en un subdominio
  • Escanear los rangos de IP que se sabe que utiliza la empresa puede ayudar a identificar el servidor backend
  • Explotar Server-Side Request Forgery (SSRF) puede revelar la dirección IP
  • Los mensajes de error detallados de la aplicación pueden exponer direcciones IP o nombres de host

Componentes de seguridad

Firewall de red

La mayoría de los servidores web estarán protegidos por un firewall de filtrado de paquetes o de inspección con estado, que bloquea cualquier tráfico de red que no sea necesario. Para detectarlo, hay que realizar un escaneo de puertos del servidor y examinar los resultados.

Si la mayoría de los puertos aparecen como "closed" (es decir, devuelven un paquete RST en respuesta al paquete SYN inicial), esto sugiere que el servidor puede no estar protegido por un firewall. Si los puertos aparecen como "filtered" (es decir, no se recibe respuesta al enviar un paquete SYN a un puerto no utilizado), lo más probable es que haya un firewall.

Además, si se exponen al mundo servicios inapropiados (como SMTP, IMAP, MySQL, etc.), esto sugiere que no hay un firewall o que el firewall está mal configurado.

Sistema de detección y prevención de intrusiones de red

Un sistema de detección de intrusiones (IDS) de red está diseñado para detectar actividad sospechosa o maliciosa a nivel de red, como el escaneo de puertos o de vulnerabilidades, y generar alertas. Un sistema de prevención de intrusiones (IPS) funciona de manera similar, pero además toma medidas para evitar la actividad, normalmente bloqueando la dirección IP de origen.

Un IPS normalmente puede detectarse ejecutando herramientas de escaneo automatizadas (como un escáner de puertos) contra el objetivo y viendo si se bloquea la IP de origen. Sin embargo, es posible que un IPS no detecte muchas herramientas de nivel de aplicación (especialmente si no descifra TLS).

Firewall de aplicaciones web (WAF)

Un firewall de aplicaciones web (Web Application Firewall, WAF) inspecciona el contenido de las peticiones HTTP y bloquea las que parecen sospechosas o maliciosas. También pueden utilizarse para aplicar dinámicamente otros controles, como CAPTCHA o limitación de tasa. Normalmente utilizan un conjunto de firmas y expresiones regulares de patrones maliciosos conocidos, como el OWASP Core Rule Set, para identificar el tráfico malicioso. Los WAF pueden ser eficaces para proteger contra ciertos tipos de ataques, como la inyección SQL o el cross-site scripting, pero son menos eficaces contra otros tipos, como los problemas relacionados con el control de acceso o la lógica de negocio.

Un WAF puede desplegarse en múltiples ubicaciones, entre ellas:

  • En el propio servidor web
  • En una máquina virtual o dispositivo de hardware independiente
  • En la nube, delante del servidor backend

Dado que un WAF bloquea las peticiones maliciosas, se puede detectar agregando cadenas de ataque comunes a los parámetros y observando si se bloquean o no. Por ejemplo, intenta agregar un parámetro llamado foo con un valor como ' UNION SELECT 1 o ><script>alert(1)</script>. Si estas peticiones se bloquean, es probable que haya un WAF. Además, el contenido de las páginas de bloqueo puede proporcionar información sobre la tecnología específica que se está utilizando. Por último, algunos WAF pueden agregar cookies o cabeceras HTTP a las respuestas que pueden revelar su presencia.

Si se utiliza un WAF basado en la nube, es posible eludirlo accediendo directamente al servidor backend, utilizando los mismos métodos tratados en la sección Red de distribución de contenido (CDN).
