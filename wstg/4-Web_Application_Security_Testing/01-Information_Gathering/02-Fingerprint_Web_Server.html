Identificación del servidor web (Fingerprint Web Server)

ID
WSTG-INFO-02

Resumen

La identificación (fingerprinting) del servidor web consiste en determinar el tipo y la versión del servidor web en el que se ejecuta un objetivo. Aunque esta tarea suele estar incluida en las herramientas de prueba automatizadas, es importante que los investigadores comprendan los fundamentos de cómo estas herramientas intentan identificar el software y por qué resulta útil.

Descubrir con precisión el tipo de servidor web en el que se ejecuta una aplicación puede permitir a los evaluadores de seguridad determinar si la aplicación es vulnerable a un ataque. En particular, los servidores que ejecutan versiones antiguas de software sin los parches de seguridad actualizados pueden ser susceptibles a exploits conocidos específicos de cada versión.

Objetivos de la prueba

  • Determinar la versión y el tipo de un servidor web en ejecución para poder seguir buscando vulnerabilidades conocidas.

Cómo probar

Las técnicas utilizadas para la identificación del servidor web incluyen la captura de banners (banner grabbing), la provocación de respuestas a peticiones malformadas y el uso de herramientas automatizadas para realizar análisis más robustos que combinan varias tácticas. La premisa fundamental en la que se basan todas estas técnicas es la misma: todas buscan provocar alguna respuesta del servidor web que luego pueda compararse con una base de datos de respuestas y comportamientos conocidos y, de ese modo, asociarse con un tipo de servidor conocido.

Captura de banners (Banner Grabbing)

La captura de banners se realiza enviando una petición HTTP al servidor web y examinando su cabecera de respuesta. Esto puede hacerse con curl -I (que envía una petición HEAD y muestra solo las cabeceras de la respuesta), con httpx para sondear listas grandes de hosts a escala, o con openssl s_client para peticiones sobre TLS/SSL.

Como ejemplo, el siguiente comando obtiene solo las cabeceras de respuesta de un servidor:

curl -I https://example.org

Por ejemplo, esta es la respuesta a una petición enviada a un servidor Apache.

HTTP/1.1 200 OK
Date: Thu, 05 Sep 2019 17:42:39 GMT
Server: Apache/2.4.43 (Unix)
Last-Modified: Thu, 05 Sep 2026 17:40:42 GMT
ETag: "75-591d1d21b6167"
Accept-Ranges: bytes
Content-Length: 117
Connection: close
Content-Type: text/html
...

Esta es otra respuesta, en este caso enviada por Nginx.

HTTP/1.1 200 OK
Server: nginx/1.31.5
Date: Thu, 05 Sep 2026 17:50:24 GMT
Content-Type: text/html
Content-Length: 117
Last-Modified: Thu, 05 Sep 2026 17:40:42 GMT
Connection: close
ETag: "5d71489a-75"
Accept-Ranges: bytes
...

Así luce una respuesta enviada por lighttpd.

HTTP/1.1 200 OK
Content-Type: text/html
Accept-Ranges: bytes
ETag: "4192788355"
Last-Modified: Thu, 05 Sep 2026 17:40:42 GMT
Content-Length: 117
Connection: close
Date: Thu, 05 Sep 2026 17:57:57 GMT
Server: lighttpd/1.4.85
...

En estos ejemplos, el tipo y la versión del servidor quedan claramente expuestos. Sin embargo, las aplicaciones que se preocupan por la seguridad pueden ocultar la información de su servidor modificando la cabecera. Por ejemplo, este es un fragmento de la respuesta a una petición a un sitio con una cabecera modificada:

HTTP/1.1 200 OK
Server: Website.com
Date: Thu, 05 Sep 2019 17:57:06 GMT
Content-Type: text/html; charset=utf-8
Status: 200 OK
...

En los casos en que la información del servidor está oculta, los evaluadores pueden deducir el tipo de servidor a partir del orden de los campos de la cabecera. Obsérvese que en el ejemplo de Apache anterior, los campos siguen este orden:

  • Date
  • Server
  • Last-Modified
  • ETag
  • Accept-Ranges
  • Content-Length
  • Connection
  • Content-Type

Sin embargo, tanto en el ejemplo de Nginx como en el del servidor oculto, los campos en común siguen este orden:

  • Server
  • Date
  • Content-Type

Los evaluadores pueden usar esta información para suponer que el servidor oculto es Nginx. No obstante, dado que varios servidores web distintos pueden compartir el mismo orden y los mismos campos, y que los campos pueden modificarse o eliminarse, este método no es definitivo.

Envío de peticiones malformadas

Los servidores web pueden identificarse examinando sus respuestas de error y, en los casos en que no se hayan personalizado, sus páginas de error predeterminadas. Una forma de obligar al servidor a mostrarlas es enviar peticiones intencionalmente incorrectas o malformadas.

Por ejemplo, esta es la respuesta de un servidor Apache a una petición con la versión HTTP inexistente SANTA CLAUS.

GET / SANTA CLAUS/1.1


HTTP/1.1 400 Bad Request
Date: Fri, 06 Sep 2019 19:21:01 GMT
Server: Apache/2.4.41 (Unix)
Content-Length: 226
Connection: close
Content-Type: text/html; charset=iso-8859-1

<!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML 2.0//EN">
<html><head>
<title>400 Bad Request</title>
</head><body>
<h1>Bad Request</h1>
<p>Your browser sent a request that this server could not understand.<br />
</p>
</body></html>

Esta es la respuesta de Nginx a la misma petición.

GET / SANTA CLAUS/1.1


<html>
<head><title>404 Not Found</title></head>
<body>
<center><h1>404 Not Found</h1></center>
<hr><center>nginx/1.17.3</center>
</body>
</html>

Esta es la respuesta de lighttpd a la misma petición.

GET / SANTA CLAUS/1.1


HTTP/1.0 400 Bad Request
Content-Type: text/html
Content-Length: 345
Connection: close
Date: Sun, 08 Sep 2019 21:56:17 GMT
Server: lighttpd/1.4.54

<?xml version="1.0" encoding="iso-8859-1"?>
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN"
         "https://www.w3.org/TR/xhtml1/DTD/xhtml1-transitional.dtd">
<html xmlns="https://www.w3.org/1999/xhtml/" xml:lang="en" lang="en">
 <head>
  <title>400 Bad Request</title>
 </head>
 <body>
  <h1>400 Bad Request</h1>
 </body>
</html>

Dado que las páginas de error predeterminadas ofrecen muchos factores diferenciadores entre los tipos de servidores web, su examen puede ser un método eficaz de identificación incluso cuando los campos de cabecera del servidor están ocultos.
Además, este recurso puede ser útil, especialmente cuando se encuentran páginas de error predeterminadas que no revelan el tipo de servidor web.

Uso de herramientas de análisis automatizadas

Como se indicó antes, la identificación del servidor web suele incluirse como funcionalidad de las herramientas de análisis automatizadas. Estas herramientas pueden realizar peticiones similares a las mostradas arriba, además de enviar otras sondas más específicas de cada servidor. Las herramientas automatizadas pueden comparar las respuestas de los servidores web mucho más rápido que las pruebas manuales y utilizan grandes bases de datos de respuestas conocidas para intentar identificar el servidor. Por estas razones, es más probable que las herramientas automatizadas produzcan resultados precisos.

Estas son algunas herramientas de análisis de uso común que incluyen la funcionalidad de identificación del servidor web.

  • Netcraft Site Report, una herramienta en línea que analiza sitios para obtener información, incluidos detalles del servidor web.
  • Nikto, una herramienta de análisis de línea de comandos de código abierto.
  • Nmap, una herramienta de línea de comandos de código abierto que también cuenta con una interfaz gráfica, Zenmap.
  • WhatWeb y httpx (-tech-detect), que identifican el software del servidor web junto con otras tecnologías (consulta Fingerprint Web Application Framework y Fingerprint Web Application para su uso más amplio en la detección del stack tecnológico).

Corrección

Aunque la información expuesta del servidor no es necesariamente una vulnerabilidad en sí misma, es información que puede ayudar a los atacantes a explotar otras vulnerabilidades que pudieran existir. La información expuesta del servidor también puede llevar a los atacantes a encontrar vulnerabilidades específicas de cada versión que pueden usarse para explotar servidores sin parchear. Por este motivo se recomienda tomar algunas precauciones. Estas acciones incluyen:

  • Ocultar la información del servidor web en las cabeceras, por ejemplo con el módulo mod_headers de Apache.
  • Usar un servidor proxy inverso reforzado para crear una capa adicional de seguridad entre el servidor web e internet.
  • Asegurarse de que los servidores web se mantengan actualizados con el software y los parches de seguridad más recientes.
