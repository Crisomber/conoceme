El marco de pruebas de seguridad web

Descripción general

Este marco pretende ser un conjunto flexible de actividades de prueba que las organizaciones pueden adoptar y adaptar, sin asumir una secuencia fija ni un flujo de trabajo con puertas de control. Las pruebas de seguridad no tienen un único hogar: ocurren en las discusiones de requisitos, en las revisiones de arquitectura, en el IDE, en los pipelines de CI/CD, en los entornos de staging y producción, y mediante escaneo continuo e investigadores externos, a menudo de forma simultánea.

A diferencia de una metodología prescriptiva, este marco reconoce que la cadencia, la secuencia y la responsabilidad de las pruebas varían según el contexto. Una startup puede comenzar con un modelado de amenazas ligero y revisión de código. Una organización regulada puede priorizar el modelado de amenazas, la revisión del diseño y la automatización de CI/CD. Un equipo de producto maduro puede operar todas las actividades de forma continua. El objetivo es ayudar a las organizaciones a elegir y escalar la combinación adecuada de actividades para su modelo de amenazas, sus prácticas de desarrollo y su tolerancia al riesgo. Para la comparación de costos y el contexto de negocio, consulta la Introducción.

Actividades de prueba

Las siguientes seis categorías cubren las principales actividades de prueba que contribuyen a la seguridad de las aplicaciones. Cada una suele repetirse con una cadencia (activada por cambios de requisitos, decisiones de arquitectura, cada commit, según un calendario de lanzamientos o de forma continua) en lugar de ocurrir una sola vez en una secuencia fija. Pueden, y deben, retroalimentarse entre sí. Por ejemplo, una prueba de penetración puede exponer una vulnerabilidad en la lógica de negocio que no se identificó durante el modelado de amenazas, revelando un control faltante que debería añadirse al modelo de amenazas y al diseño. Además, las actividades de prueba forman su propio ciclo de retroalimentación. Durante las pruebas de vulnerabilidades, puede que descubras algo que requiera volver a fases anteriores (el reconocimiento puede necesitar ampliarse, o pueden surgir nuevos objetivos de recopilación de información), tratando las pruebas de seguridad como un ciclo iterativo y continuo en lugar de una secuencia de una sola pasada.

Revisión de requisitos y políticas

Establecer y documentar las políticas de seguridad, los estándares de codificación segura y la línea base de requisitos de seguridad. El OWASP Application Security Verification Standard (ASVS) y la OWASP Cheat Sheet Series proporcionan controles de referencia. Al revisar los requisitos, hay que asegurar la claridad en las siguientes áreas:

  • Gestión de usuarios y federación de identidades
  • Autenticación y autenticación multifactor (MFA)
  • Autorización y control de acceso (RBAC / ABAC)
  • Confidencialidad, integridad y privacidad de los datos (incluido el manejo de información de identificación personal (PII))
  • Gestión de sesiones y manejo de tokens
  • Seguridad del transporte y estándares criptográficos
  • Contratos de API e integraciones de terceros
  • Infraestructura como código (IaC), imágenes de contenedores y configuración de la nube
  • Riesgo de la cadena de suministro y de las dependencias
  • Requisitos de respuesta a incidentes y monitoreo
  • Estándares de cumplimiento aplicables (PCI DSS, HIPAA, GDPR, SOC 2, ISO/IEC 27001, etc.)

Hay que revisar esta línea base cada vez que cambien los requisitos, las regulaciones o las prioridades del negocio.

Diseño, arquitectura y modelado de amenazas

Revisar la documentación de diseño y arquitectura (especificaciones, modelos, plantillas de infraestructura como código) para verificar la alineación con los requisitos de seguridad. Identificar los riesgos de diseño emergentes en estas áreas:

  • Microservicios y API: límites entre servicios, autenticación entre servicios, API gateways
  • Nube y contenedores: políticas de gestión de identidad y acceso (IAM), aislamiento de red, procedencia de los contenedores, gestión de secretos
  • Arquitecturas del lado del cliente: aplicaciones de una sola página (SPA), manejo del estado, política de cross-origin resource sharing (CORS)
  • Dependencias de terceros y servicios gestionados: límites de confianza, responsabilidades de cumplimiento

Emprender el modelado de amenazas para identificar escenarios de ataque realistas y asegurar que cada amenaza haya sido mitigada, aceptada como riesgo residual o transferida a un tercero. Esto ocurre en múltiples niveles: modelado de amenazas de todo el sistema cuando cambia la arquitectura, y modelado de amenazas a nivel de elemento de trabajo (por ejemplo, para historias de usuario individuales) para identificar las amenazas específicas de nuevas funcionalidades o cambios. Herramientas como OWASP Threat Dragon y Pythonic Threat Modeling pueden ayudar a estructurar este ejercicio.

Revisión y análisis a nivel de código

Revisar manualmente el código en busca de defectos de seguridad, en particular en la lógica compleja, las implementaciones criptográficas, el control de acceso y el código de las API. Combinar la revisión manual con el análisis estático automatizado:

  • Las herramientas de Static Application Security Testing (SAST) escanean el código fuente en busca de patrones de vulnerabilidades conocidos.
  • Las herramientas de escaneo de secretos detectan credenciales incluidas accidentalmente en commits antes de que lleguen al control de versiones.
  • Las herramientas de Software Composition Analysis (SCA) escanean las dependencias en busca de vulnerabilidades conocidas.

Usa herramientas como SonarQube, Semgrep, TruffleHog, OWASP Dependency-Check o Snyk, y establece políticas para corregir las dependencias vulnerables. Idealmente, estas actividades se integran en el entorno de desarrollo (plugins del IDE, hooks de pre-commit) y en el pipeline de compilación, ejecutándose en cada commit o pull request.

Pruebas dinámicas y de penetración

Probar la aplicación en ejecución en busca de vulnerabilidades que el análisis estático o la revisión manual del código pudieron haber pasado por alto. Esta actividad incluye:

  • Las herramientas de Dynamic Application Security Testing (DAST) como ZAP o Burp Suite rastrean y aplican fuzzing a la aplicación
  • Las pruebas de penetración manuales validan la explotabilidad, prueban los puntos de integración y sondean la lógica de negocio
  • La revisión de la configuración asegura que no haya servicios innecesarios habilitados, que se hayan cambiado las credenciales por defecto, que las cabeceras de seguridad estén presentes y que las versiones y los cifrados de TLS/SSL sean los adecuados Estas actividades pueden dirigirse a entornos de staging o producción, ejecutarse bajo demanda o con una cadencia programada, y ser realizadas por un equipo interno, un consultor externo o mediante un programa de bug bounty. Para metodologías y marcos de trabajo de pruebas de penetración, consulta el Apéndice G.

Pruebas en el pipeline de integración continua

Integrar las pruebas de seguridad en los pipelines de integración continua (CI) y entrega continua (CD) para que la seguridad no sea una ocurrencia tardía. Definir las comprobaciones de seguridad por etapa del pipeline:

  • En tiempo de compilación, ejecutar SAST, SCA y escaneo de secretos
  • En staging, ejecutar DAST y escaneo de IaC y de imágenes de contenedores
  • Antes del lanzamiento, exigir la aprobación de seguridad y definir umbrales para bloquear el despliegue Este es el tejido conectivo que permite que la revisión de código, el escaneo automatizado y las pruebas dinámicas se ejecuten de forma continua sin convertirse en un cuello de botella. Consulta OWASP SAMM y NIST SSDF para orientación sobre cómo escalar estas prácticas.

Pruebas continuas y colaborativas (crowdsourcing)

Operar las pruebas de seguridad como una actividad permanente más allá del pipeline de desarrollo. Esto incluye el monitoreo de seguridad operativa y la reevaluación periódica (volver a ejecutar las herramientas SAST/DAST/SCA, pruebas de penetración manuales o revisiones del modelado de amenazas) para detectar nuevas vulnerabilidades introducidas por cambios de código, actualizaciones de dependencias o la deriva de la infraestructura. También incluye los programas de bug bounty, que operan de forma continua y aprovechan a investigadores de seguridad externos para identificar ataques novedosos y casos límite que las pruebas internas pueden pasar por alto. Como las demás actividades de prueba, esto no es un evento único sino una práctica sostenida y paralela.

Asociar la actividad con la cadencia

La siguiente tabla muestra cómo suelen encajar las actividades de prueba en el flujo de trabajo de una organización, sin asumir una secuencia fija:

Actividad de prueba Cadencia típica Responsable típico Ejemplos y referencias
Revisión de requisitos y políticas Por evento (nueva funcionalidad, cambio regulatorio) Gerente de producto + seguridad OWASP ASVS, Cheat Sheet Series, documentos de cumplimiento
Diseño, arquitectura y modelado de amenazas Por evento (cambio de arquitectura, nueva historia de usuario/elemento de trabajo) Arquitectos + seguridad + desarrolladores Threat Dragon, pytm, STRIDE, evaluación de riesgos del NIST
Revisión de código, SAST, SCA, escaneo de secretos Continua (cada commit / PR) Desarrolladores + herramientas automatizadas SonarQube, Semgrep, TruffleHog, Dependency-Check, Snyk
DAST y pruebas de penetración Programada + por evento (calendario de lanzamientos, bajo demanda) Equipo interno de seguridad o un tercero ZAP, Burp Suite, pruebas manuales
Programas de bug bounty Continua, siempre activa Investigadores externos HackerOne, Bugcrowd o autoalojado

Por dónde empezar

Si tu organización está construyendo un programa de pruebas desde cero, no te sientas obligado a implementar todas las actividades a la vez ni en un orden fijo. En su lugar, comienza con la actividad que ofrezca el valor más inmediato según tu perfil de riesgo y tus prácticas de desarrollo:

  • Los equipos con una gran velocidad de desarrollo pueden comenzar con la revisión de código y la integración de SAST en CI/CD, detectando de forma temprana los errores comunes.
  • Los equipos que construyen sistemas complejos e interconectados pueden priorizar el modelado de amenazas y la revisión de la arquitectura.
  • Los equipos que despliegan en infraestructura de nube o de microservicios pueden enfocarse en el escaneo de IaC y la revisión de la configuración de la nube.
  • Los equipos de producto con una API publicada pueden priorizar las pruebas de API y las pruebas de penetración centradas en la seguridad.
  • Las organizaciones que manejan datos sensibles pueden comenzar con la clasificación de datos, los estándares de cifrado y la revisión de requisitos orientada al cumplimiento.

A medida que se alcance la madurez, hay que ampliar la cobertura para incluir las demás actividades, refinando el enfoque según lo que revelen las pruebas. El marco no es una lista de verificación que deba completarse en orden, sino una referencia del rango de actividades que, con el tiempo, construyen un programa de pruebas integral.
