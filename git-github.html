🔧 Git y GitHub desde cero

1 · Control de versiones

Qué es Git, qué es un repositorio y por qué importa el historial de cambios.

1. ¿Qué es un sistema de control de versiones?

Antes de Git, mucha gente "versionaba" sus proyectos a mano, duplicando carpetas o archivos:

proyecto_final.zip, proyecto_final_v2.zip, proyecto_final_v2_DEFINITIVO.zip

Un sistema de control de versiones hace eso automáticamente y mucho mejor: guarda todo el historial de cambios de tus archivos, con fecha, autor y mensaje, dentro del propio proyecto:

un solo proyecto, con historial completo guardado por Git

💡 Git no borra el pasado: siempre puedes volver a ver (o recuperar) cómo estaba tu código en cualquier punto anterior.

2. Las tres piezas clave

TérminoQué es
Repositorio ("repo")Una carpeta cuyo historial de cambios vigila Git
CommitUna "foto" guardada del proyecto en un momento dado, con un mensaje
Historial (log)La lista ordenada de todos los commits de ese repositorio

3. ¿Por qué hacer commits pequeños?

  • Es más fácil entender qué cambió y por qué.
  • Si algo se rompe, es más fácil encontrar en qué commit pasó.
  • Puedes deshacer un cambio concreto sin perder los demás.

4. Dónde vive todo esto

Dentro de cada repositorio, Git guarda todo el historial en una carpeta oculta llamada .git. Esa copia vive en tu computadora (local); más adelante veremos cómo compartirla con otros a través de GitHub (remoto).

    2 · Comandos esenciales

    Los comandos que más vas a usar, día a día, trabajando con Git.

    1. Crear y preparar cambios

    ComandoQué hace
    git initConvierte la carpeta actual en un repositorio Git
    git add archivo.txtPrepara (staging) ese archivo para el próximo commit
    git add .Prepara TODOS los archivos modificados

    editar archivo → git add archivo → git commit editar archivo → git commit (sin add)

    2. Guardar cambios: commit

    Un commit siempre lleva un mensaje corto que explica el cambio, con la bandera -m:

    git commit -m "Arregla el botón de enviar" git commit -m "cambios"

    💡 Un buen mensaje de commit explica el porqué, no solo repite "cambios" o "fix".

    3. Revisar: status y log

    ComandoQué muestra
    git statusQué archivos cambiaron, cuáles están en staging y cuáles no
    git logEl historial de commits: autor, fecha y mensaje
    git log --onelineEl mismo historial, una línea por commit
    git diffQué cambió línea por línea, antes de hacer add

    4. Ramas: branch, checkout y switch

    ComandoQué hace
    git branchLista las ramas del repositorio
    git branch loginCrea una rama nueva llamada "login"
    git switch loginTe mueve a la rama "login" (forma moderna)
    git checkout -b loginCrea la rama "login" y te mueve a ella, en un solo paso
    💡 Una rama es una línea de desarrollo independiente: puedes probar cosas ahí sin afectar el código principal (main).

      3 · GitHub y colaborar

      Git funciona en tu computadora; GitHub es donde lo compartes con otros.

      1. Local vs remoto (origin)

      Tu copia del repositorio en tu computadora es la copia local. La copia alojada en un servidor (como GitHub) es el remoto. Por convención, Git le llama origin al remoto principal.

      2. Subir y bajar cambios: push y pull

      ComandoQué hace
      git push origin mainSube tus commits locales a la rama "main" del remoto
      git pullDescarga y combina (merge) los cambios del remoto en tu copia local
      git fetchDescarga la información del remoto, pero sin combinarla todavía
      💡 Antes de empezar a trabajar en un repo compartido, haz git pull para traer los últimos cambios de tus compañeros.

      3. Clonar y hacer fork

      git clone https://github.com/usuario/repo.git descarga una copia completa de un repositorio remoto a tu computadora, lista para trabajar.

      Si no tienes permiso de escritura sobre un repositorio ajeno, puedes hacer un fork: una copia personal de ese repositorio en tu propia cuenta de GitHub.

      4. Pull request: proponer un cambio

      PasoQué haces
      1Creas una rama nueva y haces tus commits ahí
      2git push esa rama a GitHub
      3Abres un Pull Request (PR): una propuesta de cambios para que alguien la revise
      4Si todo está bien, se hace merge (fusión) a la rama principal

      rama nueva → commits → push → Pull Request → review → merge push directo a main, sin revisión
